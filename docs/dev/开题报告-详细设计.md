来源：`开题报告-242332-毛忠昊.doc` 第 5 章“技术路线”。

## 5. 技术路线

### 5.1. 面向 ARM 平台 GPU 的多虚机共享机制研究

#### 5.1.1. 设计概述

本文拟提出一种面向 ARM 集成 GPU 的共享虚拟化方案，设计影子页表弥补其缺乏硬件虚拟化支持的问题，实现对单个虚拟机的高效直通访问；在此基础上，引入直通 GPU 的代理虚拟机，通过驱动级协同与集中式地址翻译控制机制，对 GPU 内存资源与地址映射进行统一管理，实现多虚拟机间高效安全的 GPU 直通共享能力。整体方案主要包括两个部分：1）面向单虚拟机的 GPU 直通访问机制，使代理虚拟机能够直接控制 GPU；2）面向多虚拟机的共享扩展机制，引入代理虚拟机作为核心中介，对 GPU 资源进行统一管理与复用。

#### 5.1.2. 面向单虚拟机的 GPU 直通访问机制

针对单个虚拟机的 GPU 直通访问机制，如图 8 所示，本文为虚拟机对 GPU 的访问构建完整的数据与控制通路：在内存管理方面，引入软件影子页表机制，将 GPU 虚拟地址直接映射至宿主机物理地址，弥补 Mali GPU 缺乏 Stage-2 地址转换的缺陷；在设备访问方面，对 GPU 寄存器空间采用 MMIO 恒等映射的方式，使代理虚拟机能够直接配置 GPU 硬件；在中断通知方面，通过中断直通机制将 GPU 中断直接注入代理虚拟机，确保任务完成与异常处理的低延迟响应。通过上述机制，代理虚拟机获得接近原生的 GPU 访问能力。

> 图 8 单虚拟机的 GPU 直通

在内存管理方面，由于 GPU 内嵌 IOMMU 仅支持单级地址转换，在缺乏影子页表机制时，虚拟机只能建立从 GPU 虚拟地址到虚拟机物理地址（Guest Physical Address, GPA）的映射，而 GPU 实际只能访问宿主机物理地址（Host Physical Address, HPA），从而导致虚拟机内存无法被 GPU 正确访问。为此，如图 9 所示，系统对虚拟机中 GPU 驱动的内存管理路径进行了改造：在涉及页表构建与更新时，通过调用 KVM 提供的 HVC（Hypervisor Call）接口，将对应的虚拟机物理地址预先转换为宿主机物理地址，并在代理虚拟机侧据此构建从 GPU 虚拟地址到宿主机物理地址的影子页表映射。同时，考虑到虚拟机自身仍运行在二阶段地址转换环境下，无法直接以宿主机物理地址形式访问内存，系统在虚拟机侧维护一套辅助映射机制：通过构建宿主机物理地址到虚拟机虚拟地址的哈希映射关系，将影子页表所使用的物理页重新映射回虚拟机可访问的地址空间。在页表填充与更新过程中，驱动可通过该映射快速定位对应的虚拟地址，从而完成页表项的读写与维护操作。

基于以上设计，GPU 可以使用虚拟机构建的影子页表正确高效的访问内存。另外，GPU 驱动对于内存区域的构建与更新主要集中在缓冲区生命周期与任务提交两个关键阶段。在缓冲区分配与释放过程中，驱动需要为 GPU 可访问的数据结构（如命令缓冲区、数据缓冲区等）建立或销毁对应的地址映射；在任务提交阶段，驱动根据任务所引用的内存对象，批量构建或更新相关页表项，以确保 GPU 能够正确访问所需数据。而在上下文切换过程中，仅涉及通过 MMIO 寄存器切换页表基址，并不引发页表内容的实际修改。基于上述特性，影子页表的维护开销主要集中在相对低频的内存分配与任务提交路径上，而不会随着 GPU 调度或上下文切换频繁触发。因此，在合理设计下，该机制对性能的影响是可控的。通过对页表更新操作进行批量处理、缓存虚拟机物理地址到宿主机物理地址的转换结果以及减少不必要的映射重建，可以进一步降低影子页表同步带来的额外开销，从而在保证地址隔离与访问安全的前提下，实现高性能的 GPU 内存访问。

> 图 9 GPU 内存的不同寻址路径

对于设备访问路径，GPU 寄存器空间通常以内存映射 I/O（MMIO）的形式暴露给系统。为使代理虚拟机能够直接参与 GPU 的控制与管理，系统采用对 GPU 的 MMIO 地址空间进行直通映射的方式，使其具备接近原生环境的设备访问能力。具体而言，通过 ARM 平台的设备树声明 GPU 的 MMIO 区域，并且对相关地址区域实施恒等映射（Identity Mapping），代理虚拟机可以直接访问 GPU 控制寄存器，从而完成任务提交、执行队列配置以及上下文管理等关键操作，避免传统虚拟化路径中频繁陷入带来的额外开销。在具体实现中，如图 10 所示，系统依据寄存器访问在性能敏感性与安全敏感性方面的差异，对 GPU 的 MMIO 空间进行细粒度的分类与差异化处理。对于位于性能关键路径上的寄存器访问（如任务提交相关寄存器、队列指针更新等），系统通过直接修改虚拟机的 Stage-2 页表，将对应 MMIO 地址区域以恒等映射方式直通至代理虚拟机，使其能够在无陷入（Trap-free）的情况下完成寄存器读写操作，从而有效避免频繁 VM Exit 所带来的性能损耗，提升 GPU 任务调度与执行效率。与此同时，对于涉及全局资源管理、执行上下文切换控制以及可能影响系统隔离性与稳定性的安全敏感寄存器，系统则采取访问拦截机制。具体而言，该类寄存器对应的 MMIO 访问不会被直接映射，而是在访问发生时触发陷入，由 Hypervisor 接管处理。在 Hypervisor 中对访问请求进行合法性校验，并结合系统策略执行必要的访问控制或语义检查，从而防止恶意或异常操作对 GPU 全局状态及其他虚拟机造成干扰。

> 图 10 GPU 设备访问控制

另外，对于 Host Kernel 侧的访问控制，系统采用最小权限原则，对 GPU 相关 MMIO 空间进行严格限制。具体而言，仅允许 Host Kernel 访问电源管理单元（Power Management Unit, PMU）以及时钟与复位单元（Clock and Reset Unit, CRU）对应的 MMIO 地址区域，用于维持设备基本的上电、时钟配置与复位控制功能；而对于 GPU 核心控制路径相关的其他 MMIO 寄存器空间，则统一禁止 Host Kernel 直接访问，由直通的虚拟机独占管理。

> 图 11 GPU 物理中断对虚拟机的注入

对于中断通知方面，GPU 主要通过中断机制向 CPU 报告任务完成、异常状态及调度事件。为降低虚拟化引入的中断处理延迟，系统采用中断直通机制，将 GPU 产生的物理中断直接注入代理虚拟机，使其能够及时响应任务完成与异常事件。在具体实现上，系统基于 IRQFD 机制，对 VMM 预先注册的 Trigger FD 与 Resample FD 进行绑定与配置：如图 11 所示，当 GPU 产生物理中断时，内核侧触发对应的 Trigger FD，并通过 KVM 将中断直接注入虚拟机的虚拟中断控制器；虚拟机内核随后感知该虚拟中断，并进入 GPU 驱动的中断处理流程。在中断处理完成后，虚拟机在返回 KVM 的 VM-exit 路径中检测中断状态变化，并通过 Resample FD 通知宿主机内核完成中断应答，从而保证中断状态的一致性与可重入性。在此过程中，中断路径无需频繁经过用户态 VMM 或 Hypervisor 显式转发，大部分任务完成中断可在内核态快速完成注入与响应，有效降低 VM Exit 与上下文切换带来的开销。

通过上述对内存管理、MMIO 访问及中断通知的直通支持，系统为代理虚拟机构建了完整且高效的 GPU 访问通路，使其具备接近原生的设备控制与执行能力。在此基础上，系统进一步在驱动层引入统一的资源管理与调度机制，由代理虚拟机对 GPU 任务与内存资源进行集中管理与分配，从而在单虚拟机直通能力之上，实现多虚拟机之间对 GPU 资源的隔离与共享。

#### 5.1.3. 面向多虚拟机的 GPU 共享机制

在已实现单个代理虚拟机对 GPU 直通访问机制的基础上，本文进一步提出一种基于驱动级中介的多虚拟机 GPU 共享机制，以解决 ARM 平台集成 GPU 缺乏硬件虚拟化支持、难以高效共享的问题。该方案将代理虚拟机扩展为 GPU 资源的统一仲裁与调度中心，多个客户虚拟机运行轻量级前端驱动，通过高效的驱动级通信协议与代理虚拟机交互，从而在软件层面实现 GPU 任务的隔离执行与动态调度。

在上下文管理方面，系统对不同类型的 GPU 上下文状态采用差异化设计。对于 GPU 的 VM Context（Virtual Memory Context），其本质是对 GPU 可访问内存空间的统一管理，核心在于影子页表的构建与地址空间的高效切换。系统无需为不同客户虚拟机重复构建完整的页表层级结构，仅需将目标虚拟机对应的页表根 PGD 即 L0 PTE 的地址发送至代理虚拟机，并写入 GPU 相关 AS（Address Space）寄存器，即可完成地址空间切换。每个客户虚拟机维护一套独立的影子页表实例，该页表由客户虚拟机在任务提交过程中动态构建，并由代理虚拟机通过 KVM 机制对其进行约束与校验，确保所有页表项仅指向经过验证的合法宿主机物理地址。在 GPU 执行阶段，所有内存访问均基于当前激活的影子页表完成地址翻译，从而在硬件层面实现不同虚拟机之间的内存访问隔离。而 Command Buffer 本质上承载 GPU 的执行语义，其内容直接决定了 GPU 的操作类型、执行顺序以及内存访问行为。因此，相较于仅作为数据载体的普通缓冲区，Command Buffer 属于安全敏感的控制信息流。若缺乏有效约束，恶意构造的命令流可能导致越界内存访问、非法资源操作甚至设备拒绝服务等问题。因此系统在设计上要求代理虚拟机对 Command Buffer 保持可见性，并将其纳入受控的任务提交路径之中：客户虚拟机构建命令缓冲区后，通过共享内存方式提供给代理虚拟机；代理虚拟机在执行任务下发前，对其进行必要的合法性校验，包括命令结构完整性验证、间接访问路径解析以及地址访问范围检查等。在校验通过后，代理虚拟机基于该 Command Buffer 构建受控的提交描述，并统一完成 Queue 写入与 Doorbell 触发操作，从而确保 GPU 执行行为始终处于可验证与可约束的范围内。

在中断通知方面，系统延续单虚拟机场景中的中断直通机制，并结合代理虚拟机的集中管理能力，实现 GPU 中断的统一接收与按需分发。具体而言，GPU 产生的物理中断首先通过 IRQFD 机制注入至代理虚拟机，由其作为唯一中断接收方进入内核态中断处理流程。代理虚拟机结合当前 GPU 执行上下文（VM Context/Job Context），识别中断对应的客户虚拟机，并完成中断归属判定与状态更新。在中断分发阶段，对于任务完成等常规中断，代理虚拟机通过调用 KVM 将虚拟中断注入到对应客户虚拟机，实现执行结果的同步与反馈；而对于异常或错误中断，则由代理虚拟机优先处理或进行隔离控制，以防止错误在不同虚拟机之间传播。该设计避免了多个客户虚拟机直接竞争物理中断资源的问题，实现了中断路径的集中化与可控化。

> 图 12 基于代理虚拟机实现的 GPU 多虚拟机共享机制

综合以上设计，系统利用代理虚拟机作为唯一的硬件交互主体，统一负责 GPU 作业的下发与执行控制。具体而言，如图 12 所示，各客户虚拟机仅在本地构建标准化的任务描述符（如命令缓冲区、数据缓冲区等）及对应的影子页表，并通过共享内存与 Doorbell 机制将任务请求及页表根（PGD）提交至代理虚拟机；代理虚拟机在接收到请求后，结合当前资源分配状态与调度策略，对任务进行合法性校验、地址验证及依赖关系解析，并在完成影子页表配置后，将作业提交至 GPU 固件的命令队列，由 GPU 硬件执行。在任务执行过程中，系统结合硬件多地址空间能力与软件调度机制实现 GPU 资源的高效复用。代理虚拟机可将不同客户虚拟机的 GPU 上下文映射至不同 AS，使多个任务在硬件层面实现并行执行；同时，针对 AS 数量受限及底层计算资源共享的问题，引入基于时间片的调度机制，由代理虚拟机统一管理 GPU 执行权。代理虚拟机根据预设的公平性策略（如轮转或基于权重的调度），对 AS 资源进行分配与复用；在需要进行上下文切换时，通过更新页表基址（PGD）及相关上下文寄存器，实现不同客户虚拟机 GPU 地址空间与执行环境的快速切换。当时间片到期或当前任务执行完成时，代理虚拟机根据调度策略选择下一客户虚拟机继续执行，从而在并行执行与时间复用之间取得平衡。任务完成后，GPU 通过中断机制通知代理虚拟机；代理虚拟机在中断处理路径中更新任务状态，并依据维护的上下文信息确定任务归属的客户虚拟机。随后，代理虚拟机通过虚拟中断注入的机制将完成事件与相关结果信息回传至对应客户虚拟机，触发其前端驱动执行资源回收、同步对象更新及后续任务提交等操作，从而完成一次完整的任务执行闭环。

### 5.2. 基于 ARM 机密计算架构的 GPU 安全隔离机制研究

#### 5.2.1. 设计概述

> 图 13 多机密虚拟机共享 GPU 的威胁模型

本文针对多虚拟机场景下的 GPU 共享系统，构建如下威胁模型。如图 13 所示，在该模型中，Host OS 及 Non-secure 世界被视为完全不可信的攻击者，假设其具备对系统软件的完全控制能力，包括但不限于 Stage-2 页表的管理与篡改、设备驱动的操控以及 I/O 路径的干预等。此外，考虑到多租户环境中的对抗行为，本文同时假设恶意用户可能通过其所控制的机密虚拟机，对其他用户的机密虚拟机发起攻击，从而形成跨虚拟机的内部威胁。在信任基础方面，本文将 ARM 机密计算架构所提供的硬件机制纳入可信计算基（Trusted Computing Base, TCB），包括基于 Granule 的内存隔离机制及相关状态管理逻辑；同时，安全固件层（如 TF-RMM 与 TF-A Monitor）亦被视为可信执行基础，负责关键安全策略的实施与隔离边界的维护。与面向云数据中心的相关工作不同，本文的研究场景聚焦于智能车载设备与边缘物联网设备。在此类场景中，底层硬件通常处于设备拥有者的物理控制范围内，因此本文不考虑硬件被恶意篡改或存在后门的攻击模型，也不涉及设备主动绕过体系结构约束的情形。具体而言，默认 GPU 等外设遵循既定的地址转换流程与访问控制语义，不存在规避内存保护机制的行为。在此假设下，本文的安全分析重点转向防御来自不可信软件栈（尤其是 Host 侧）的攻击。基于上述威胁模型，本文将系统的安全目标归纳为以下三个方面：（1）机密性（Confidentiality），即保证 Host 及其他未授权实体无法通过 GPU 访问或推断机密虚拟机中的敏感数据；（2）完整性（Integrity），即确保 GPU 任务的执行过程及其依赖的内存映射不被 Host 篡改或干扰；（3）跨 Realm 隔离性（Isolation），即在多机密虚拟机共享 GPU 资源的情况下，防止不同 Realm 之间产生信息泄露或越权访问，从而实现强隔离保障。

针对以上威胁模型，本文设计了一种面向 ARM 机密计算环境的 GPU 安全共享机制，通过软件控制和硬件隔离的协同方式，在不依赖传统 IOMMU 虚拟化能力的前提下，实现多机密虚拟机间 GPU 资源的安全复用。整体方案主要分为两个部分：1）基于端到端加密与共享内存的机密虚拟机通信机制；2）基于 GPT 的多机密虚拟机 GPU 内存隔离机制。

#### 5.2.2. 基于端到端加密与共享内存的机密虚拟机通信机制

在多机密虚拟机共享 GPU 的场景中，机密虚拟机之间需要建立通信实现 GPU 上下文以及任务信息的传递，比如影子页表的根页表项、GPU 任务信息等等。而安全通信不仅需要保证数据在传输过程中的机密性与完整性，更需要解决通信双方身份可信性的问题。在本文所定义的威胁模型下，Host OS 及 Non-secure 世界均不可信，攻击者可能伪造通信实体或劫持通信路径，从而对 GPU 任务进行篡改、窃取或重放。

> 图 14 多机密虚拟机安全通信机制

为此，本文基于 ARM CCA 提供的远程度量（Remote Attestation）机制构建机密虚拟机之间的信任基础，并在此之上设计支持多虚拟机场景的安全通信机制。具体而言，每个机密虚拟机在创建时由受信执行环境对其初始状态（包括内核镜像、初始页表及运行平台）进行度量，生成唯一度量值并形成证明报告。该报告由安全固件签名，并提交至远程可信服务进行验证，从而确认虚拟机运行于受保护的 Realm 环境且其软件状态未被篡改。如图 14 所示，在验证通过后，机密虚拟机生成独立的公私密钥对，并将公钥与度量结果进行绑定。远程可信服务为每个机密虚拟机分配唯一标识（VM_ID），并建立 VM_ID 与会话密钥之间的映射关系。同时，根据度量结果实施差异化策略控制：仅允许经过验证的代理虚拟机从密钥存储服务 Key Broker 获取密钥分发能力，而普通机密虚拟机仅能获取自身对应的通信密钥，从而避免密钥在不可信环境中的扩散。通过该设计，实现了基于度量的身份认证、密钥隔离以及细粒度访问控制。在此基础上，GPU 任务在发送端机密虚拟机中被封装为包含虚拟机标识的结构化数据，并使用对应会话密钥进行加密与完整性保护。虚拟机标识与任务内容共同参与认证计算，从而防止攻击者篡改任务归属关系。封装后的任务通过共享内存传递至接收端，尽管该路径暴露于不可信 Host 环境，但由于数据始终处于加密状态，Host 无法获取其语义信息或实施有效篡改。在接收端，受信组件首先解析任务中的虚拟机标识，并根据预先建立的 VM_ID 与会话密钥映射关系选择对应密钥；随后对任务进行完整性验证，仅当验证通过时才执行解密并提交至 GPU 执行。通过将虚拟机标识与密钥选择过程纳入统一的安全保护范围，系统能够在多租户环境下正确区分不同机密虚拟机的任务来源，防止密钥误用与身份混淆，从而保证 GPU 执行语义的正确性与跨虚拟机隔离性。

#### 5.2.3. 基于 GPT 的多机密虚拟机 GPU 内存隔离机制

> 图 15 基于 GPT 实现的多机密虚拟机内存隔离

在多机密虚拟机共享 GPU 的场景中，尽管 GPU 设备及其固件被假设为可信执行实体，但其执行过程中依赖的关键内存数据（如命令缓冲区、数据缓冲区以及 GPU 影子页表等）仍可能暴露于不可信的 Host OS 及其他虚拟机的潜在攻击之下。因此，如何在不可信软件栈环境中保障 GPU 相关内存的机密性与完整性，成为实现安全共享的核心问题。

为此，本文基于 ARM 机密计算架构中的 GPT 内存颗粒保护机制，从物理内存隔离的角度对 GPU 相关数据进行细粒度保护。如图 15 所示，GPT 以固定粒度对物理内存进行划分，并为每个内存区域标记其所属安全域（如 Realm 或 Root）及访问权限，从而在硬件层面强制执行跨安全域访问控制。在本文设计中，每个客户虚拟机对应一个独立的 Realm 内存域，其 GPU 相关数据根据安全语义被划分为不同类别并映射至不同的 GPT 属性中。具体而言：

- 命令缓冲区：对代理虚拟机和客户虚拟机均标记为 Realm 属性，并通过受控共享机制映射至代理虚拟机，使代理虚拟机能够对其进行解析与校验；对 Host 标记为 Root 属性，拒绝访问。
- 数据缓冲区：对代理虚拟机标记为 Root 属性，防止其直接读取或篡改客户虚拟机的数据内容。对客户虚拟机标记为 Realm 属性，可以正常访问；对 Host 标记为 Root 属性，拒绝访问。
- GPU 影子页表：属于关键安全数据，在代理虚拟机的 GPT 视图中被标记为 Root 属性，从而对代理虚拟机不可见，仅允许代理虚拟机通过加密传输获得 Client GPU 影子页表的根表项地址；对 Host 标记为 Root 属性，拒绝访问。

通过上述设计，代理虚拟机仅对执行语义相关的控制信息（命令缓冲区）保持可见性，而对数据内容及地址空间结构（影子页表与数据缓冲区）均不可见，使代理虚拟机能够在不接触敏感数据的前提下完成任务合法性验证与 GPU 调度控制。此外，不同客户虚拟机之间通过各自独立的 GPT 视图实现严格隔离，每个虚拟机仅能访问其所属 Realm 内的内存资源。为了在多虚拟机场景下维持这一隔离性，系统在虚拟机切换过程中同步完成 GPT 视图的切换。具体而言，GPT 的访问控制依赖于处理器在 EL3 态维护的安全上下文，不同 Realm 对应独立的 GPT 配置或视图。当系统发生虚拟机切换（World Switch）时，由 TF-RMM 协同 TF-A Monitor 完成安全上下文的切换，包括目标 Realm 的标识信息以及与之绑定的 GPT 视图。该过程通常通过更新 EL3 中的相关控制寄存器或上下文描述符实现，使后续内存访问在硬件层面自动遵循新的 GPT 权限配置。在这一机制下，GPT 视图的切换与 CPU 执行上下文保持一致：当处理器切换至某一客户虚拟机所属的 Realm 执行时，仅能访问该 Realm 对应 GPT 所允许的物理内存区域；而当切换至代理虚拟机或 Host 侧执行环境时，则加载其对应的 GPT 视图，从而获得不同的访问权限集合。由于整个切换过程由 EL3 固件主导并在硬件层面生效，低特权级软件（如 Host OS 或 Hypervisor）无法干预或伪造 GPT 视图的切换行为。

基于上述机制，即使 Host OS 或 Hypervisor 具备对页表与内存管理的控制能力，也无法绕过 GPT 机制直接访问或修改受保护内存，从而有效防止来自宿主环境及跨虚拟机的攻击。同时，在多虚拟机交替执行 GPU 任务的过程中，各虚拟机所对应的 GPT 视图始终与其执行上下文严格绑定，确保内存访问均被限制在当前安全域内，从而在动态执行环境下依然维持强隔离属性。

### 5.3. 面向 ARM 平台 GPU 的多虚拟机共享与安全隔离原型系统

本文拟基于前述面向 ARM 平台集成 GPU 的多虚拟机共享机制以及结合机密计算架构的安全隔离机制，设计并实现一套面向 ARM 平台 GPU 的安全隔离与共享原型系统，如图 16 所示。该系统以支持多虚拟机（包括机密虚拟机）安全、高效地共享集成 GPU 为目标，构建从 GPU 访问控制、任务提交到执行隔离的完整运行框架。在系统架构设计上，原型系统基于 OpenCCA [29] 平台构建，结合 KVM 虚拟化框架与 ARM CCA 扩展，实现普通虚拟机与 Realm 虚拟机的协同运行。系统采用代理虚拟机（Proxy VM）和客户虚拟机（Client VM）的分层架构，由代理虚拟机作为唯一的 GPU 硬件交互主体，统一负责 GPU 资源管理与任务调度；各客户虚拟机则通过受控接口发起 GPU 计算请求。在执行环境层面，系统基于 Debian/Ubuntu Linux 构建虚拟机运行环境，并集成开源 Mali GPU 驱动（Panthor）及其用户态运行时库，支持基于 OpenCL 的 GPU 计算任务执行。同时，结合 TF-A 与 TF-RMM 开源固件构建 CCA 安全运行时，实现不同安全域之间的隔离与切换。

在原型系统实现完成后，本文通过典型 GPU 计算负载（如图形渲染与通用计算任务）对系统进行系统性测试与评估。测试过程中，在多虚拟机及机密虚拟机混合运行环境下，验证 GPU 任务提交、执行与结果回传的正确性，并通过构造跨虚拟机访问与非法命令流等攻击场景，评估系统的隔离性与安全性。同时，通过对比单虚拟机直通执行与多虚拟机共享执行的性能差异，分析代理虚拟机引入的调度与校验开销。最终，通过实验结果验证本文提出的 GPU 共享与安全隔离机制在实际 ARM 平台上的可行性与有效性，表明该方案能够在保证机密性与隔离性的前提下，实现集成 GPU 资源的高效复用。
