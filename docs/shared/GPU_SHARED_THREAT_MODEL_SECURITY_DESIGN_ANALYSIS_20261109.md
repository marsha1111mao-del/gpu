# GPU 安全共享：威胁模型、安全设计与攻击验证

Notion 文档：[GPU 安全共享｜威胁模型、安全设计与攻击验证（含 CVE）](https://app.notion.com/p/413659a3b8cc8135b0dddc71449cb2fa)。

日期：2026-11-09。用途：功能性研究的理论依据与后续测试设计。依据当前基线和已有安全设计文档整理；未修改运行代码，未执行新增攻击用例，无新增性能测量。下文将目标安全模型、已有机制与待实现扩展分别说明。

2026-11-10 澄清范围。系统使用一个 Proxy 和多个 Client，保护方向包括 Proxy→Client、Client B→Client A、Host→Client、Client→Proxy 和 Host→Proxy。此修订只更新威胁模型，历史证据仍限相应验证范围。[发布版边界](../design/03-security.md)

**核心主张：将功能服务权与安全决定权分开。Client 持有私有数据并表达任务意图；Proxy 提供驱动功能与调度服务；RMM 和最小可信设备后端约束真实访问、执行、完成和撤权。保护 Client 时，其余 Client、Proxy 与 Host 可恶意串通；保护诚实 Proxy 时，各 Client 与 Host 均可恶意。双方都不应因此被越权访问或被迫破坏资源生命周期。能否继续运行属于另一个问题。**

## 1. 威胁模型

**1.1 研究对象与安全边界**

研究唯一 Proxy 为多个 Client Realm 提供 GPU 服务的场景。对任一诚实 Client A，保护其输入、输出、shader、命令及任务授权；其他 Client 可以是攻击者，不能因为同属 Realm、使用同一 Proxy 就被信任。还要保护诚实 Proxy 的代码、私有内存与会话状态免受恶意 Client 和 Host 侵犯。默认不存在 Client 之间的显式数据共享；若以后支持共享 BO，需要另行定义授予、撤销和共享者责任。

| 主体 | 信任与职责 | 可被攻击者控制的行为 |
| --- | --- | --- |
| Client A | 信任其应用、Guest 内核和本地 GPU 提交路径；代表所保护用户 | 不要求保护 A 免受自身已被攻陷的内核或应用破坏 |
| 唯一 Proxy VM | 对 Client 隔离不可信；提供元数据对象、驱动服务、编排与通知；诚实运行时自身也是保护对象 | 恶意时可修改请求、替换句柄、提前发布、重复提交、谎报完成、拒绝服务；诚实时仍须抵御恶意 RPC 与 Host 越权访问 |
| 其他 Client | 不可信；允许攻击者控制其整个 VM | 构造任意请求和 GPU 命令，尝试跨地址空间访问、状态伪造和资源耗尽 |
| Host / Hypervisor | 不可信；掌握非可信调度与虚拟化设施 | 延迟、重排或伪造通知，尝试重映射、DMA、MMIO、设备配置和恢复操作 |
| RMM、Monitor、可信平台后端 | 系统可信软件；维护授权和硬件边界 | 其实现被攻陷不属于本模型保证范围；其接口必须按恶意输入设计 |
| GPU/FW 与平台隔离机制 | 依赖其规定的翻译、权限、执行和一致性语义 | 硬件隔离缺陷、可信 FW 被利用属于前提失效，不能靠 Proxy 请求检查补救 |

**允许 Host、Proxy 和恶意 Client 串通。** 同样“不可信”不代表权限相同：Proxy 掌握驱动服务接口，Host 掌握调度和平台管理入口，其他 Client 可以提交攻击性 GPU 工作。因此必须分别封闭其越权路径。

**1.2 TCB 包括什么**

系统级可信软件包括启动信任链、相关 Monitor/Root 服务、RMM 的内存与授权管理、GPU 专用页表/控制/完成/撤权后端，以及实际批准并加载的 GPU FW。Client A 的内核和运行时属于 A 自己的可信计算环境；Proxy 的完整驱动、Host 内核和其他 Client 不属于 A 的可信软件。保护诚实 Proxy 时，P 自身的内核、RPC 解析与对象生命周期实现也必须接受恶意输入审查；将其列入自身 TCB 不代表这些入口已安全。RMM 的跨域隔离无法自动修复 P 内部的越界解析或 UAF，而 P 被攻陷也不能使其他诚实 Client 丧失隔离。

CPU/GPU、SMMU、GIC、互连和物理访问控制提供硬件前提。TCB 缩小的合理表述是“移出了完整 Proxy 驱动和 Host 服务逻辑”；不能据此说 RMM 仅增加几个检查，也不能忽略可信 FW 和设备协议的复杂度。

**1.3 必须成立的五个前提**

1. **CPU 与其他 DMA 路径受完整隔离。** Host/Proxy/其他 Client 无法越权读取或写入私有页、页表及权威控制状态。GPT 的 Realm PAS 分类不能单独隔离不同 Realm，还需要可信 RTT、真实页面归属和设备访问控制。
2. **GPU 的全部相关访存受正确 Stage-1 约束。** RMM 在软件中解析 Client IPA→HPA，建立 GPUVA→HPA 的真实页表；这里没有 GPU 硬件 Stage-2。CCA SMMU 是平台访问边界的前提，不会自动区分同一 GPU 内的各个 Client。普通 GPU 命令不能绕过翻译、改变 root，或借用 MCU 权限访问其他安全域。
3. **所有影响隔离的控制路径都经过可信约束。** 覆盖敏感 MMIO、页表根、FW 输入、ring、SMMU/设备身份配置，以及会破坏隔离的 reset、电源和时钟操作。私有页面交给 GPU 前，必须完成可信接管并处理原有执行和在途访问。
4. **设备观察具有明确且可信的语义。** FW/硬件能提供普通恶意 GPU 工作无法共同伪造的执行、错误和完成依据；缓存、屏障、请求应答及在途访问退出协议符合规格。软件加锁不会冻结 GPU。
5. **身份、版本与恢复边界可靠。** 实际 Realm 身份、设备归属、固件版本和可信状态由启动与运行时机制建立。会话内 token/epoch 防重放不自动解决跨重启、整 VM 快照和持久数据回滚；这些需要额外的新鲜性与持久化协议。

若目标平台不能满足某个前提，应降低安全声明或补充机制，不能以正常应用跑通代替验证。特别是存在绕过页表的特权 GPU 命令时，需要限制命令能力、增加必要的验证或更强硬件隔离。

**1.4 要保证什么，不保证什么**

| 性质 | 本研究目标 | 边界 |
| --- | --- | --- |
| 私有数据保密与完整性 | 保护诚实 Client 或 Proxy，阻止未授权 CPU/DMA/GPU 读写、替换映射及跨域残留数据访问 | Proxy 可见必要大小、句柄、提交时序等服务元数据；不提供访问模式隐藏 |
| 接收端与会话安全 | 双方抵御恶意 RPC 的越界解析、跨会话对象访问、并发销毁、返回泄露和无界资源占用 | 需要接收端自身校验、引用管理与预算；仅有 Realm 私有内存或 RMM 设备授权不足以证明 |
| 授权执行 | 只有合法 Client 授权的对象、队列与提交范围才能被发布 | 不等于验证整个 shader 或应用算法；依赖关系须由可信 Client 表达 |
| 完成真实性 | 只有对应执行实例满足完成与可见性条件，才交付成功 | 不等于重新计算并证明神经网络或图形结果数学正确 |
| 生命周期安全 | 旧访问仍可能生效时，不允许 backing 被危险复用 | 故障时可以隔离并保留资源；内存及时回收不是无条件保证 |
| 有条件进展 | Host/Proxy 合作、资源充足且设备正常时，合法任务可推进 | 恶意调度、断供、丢通知、拒绝恢复造成的 DoS、饥饿和截止时间违约不在保证内 |

物理侵入、可信硬件/FW 漏洞、微架构侧信道和流量分析不由这四类机制完整解决。资源配额可以限制影响范围，但不能把恶意 Host 变成可用服务。

## 2. 安全设计

**2.1 用最少权威状态约束实际效果**

```text
私有数据：Client 私有 BO  ←→  获授权的 GPU 执行
功能服务：Client  ←→  Proxy（对象管理、规划、调度建议、通知）
安全提交：Client 授权 / Proxy 有限代办 → RMM → 可信设备后端 → GPU/FW
结果交付：新鲜设备证据 → RMM 判定 → Client fence / 应用
拟议扩展：按协议补充可信 IRQ 来源与必要事件历史
```

共享 RPC 页仅用于请求和提示，不是权威状态；FW ring、queue I/O、真实 producer 和完成记录则属于设备执行协议，两类“控制内存”必须分开。RMM 不需要理解模型网络或复制完整驱动对象，但必须维护影响访问和执行的权威关系。

**2.2 私有内存、GPU 地址空间与回收**

Client 分配并持有真实 BO，Proxy 只维护 GEM 等功能表示。RMM 从真实调用身份出发解析页面来源，校验私有属性、范围、权限、别名和冲突；不接受 Proxy 提供的 HPA 作为归属证明。请求先取可信快照，再核验并使用，避免共享描述在检查期间被替换。

RMM 独占构造和修改真实 GPU PTE、root 与映射版本。普通 VM_BIND 通过事务提交，检查 GPUVA、BO offset、长度、权限和保留控制区；同时处理页表可见性及旧翻译。GPUVM 不变的地址数值不能证明 backing 未变，因此任务还要绑定映射状态并持有引用。

执行期间，映射、对象和 backing 的安全引用阻止不安全的注销与改绑。普通活动地址空间不得套用离线改表协议；运行中 heap 扩展需有独立的受限协议。GPUVM 隔离不自动形成逐 JOB 的 BO 白名单：同一 GPUVM 中可访问哪些页，仍由其实际映射决定。

释放按“禁止新发布→停止或排空旧访问→撤销相关映射与翻译→处理在途访问和引用→必要清理→允许复用”推进。具体设备顺序由协议规定；GPU reset、本地引用归零、Proxy GEM 关闭或任务成功都不能单独替代这一过程。跨安全域再分配还要履行 CCA 页生命周期与清理要求。

**2.3 对象关系与有限任务授权**

| 权威关系 | 最少安全含义 |
| --- | --- |
| Client / service / session | 真实调用者、指定 Proxy 服务和允许代办范围 |
| BO / GPUVM | owner、合法 backing、范围/权限、真实 root、映射版本 |
| GROUP / QUEUE | 所属 GPUVM、队列配置、硬件槽与绑定代次 |
| JOB / batch | 获准成员、命令入口及范围、依赖就绪条件、执行实例与发布权限 |
| 生命周期 | 当前阶段、未决控制操作、故障范围和安全引用 |

句柄和 token 用于定位记录，不能仅凭“知道 token”获得权限。每次敏感操作仍核验实际调用身份或有限委托、对象关联、代次和允许状态。Client 的应用依赖由可信 Client 控制，Proxy 不能自行宣称依赖满足。

提交描述快照固定入口与范围，并不意味着整个命令 BO 已冻结。对于诚实 Client，命令内容与数据交接遵循提交后的稳定性和同步契约；对于恶意 Client，其任意内容也必须被设备权限限制在授权域内。如果要进一步保证提交内容逐字不变，需要另外设计内容冻结或完整性机制。

**一次性授权限制发布次数；不确定结果禁止盲目重发。** 在第一笔可能被设备看到的控制写入之前，就记录“可能已生效”并持有引用。回复丢失后只能查询或恢复，不能把超时当成未执行，再消耗同一授权发布一次。多线程接纳、关闭和发布必须共享明确的原子提交边界。

**2.4 敏感 MMIO、固件与执行控制资源**

Proxy 提供配置建议及 FW 来源；可信路径决定哪些字节被加载、哪些控制写入生效。认证应针对受保护的完整镜像快照，运行镜像和 MCU 页表由该快照形成，再可信安装与启动。批准摘要限制版本，不证明 FW 没有漏洞；FW 仍属于 TCB。

敏感 MMIO 不直接授权给 Proxy。Realm VM 的 RTT 撤映射只是其中一层，Host/普通 VM 还要受到物理平台边界约束；Root PAS 的 MMIO 需要合适的可信 Root 服务访问，不能假定 RMM 自然拥有权限。优先提供有限的语义接口，如安装已验证 root、发布已授权队列、受控停止，而不是接纳任意寄存器地址和值。

| 区域 | 合法写入来源与约束 | 不允许的行为 |
| --- | --- | --- |
| 真实 GPU/MCU 页表、FW 代码 | 可信加载与映射路径；按用途设置设备权限 | Proxy 或普通 GPU 工作修改翻译、替换取指目标 |
| ring、可信 wrapper、FW 输入、producer | 可信路径按任务授权和设备协议发布 | 换入口、增加成员、越过依赖、重复发布 |
| FW 输出、consumer、错误状态 | GPU/FW 按相应协议更新；RMM 取得新鲜观察 | Proxy 直接写入，或普通命令冒充权威 FW 更新 |
| 完成记录 | 根据具体机制限定 GPU/FW 写入来源，并关联执行实例 | 仅因完成字达到目标值就确认成功 |
| doorbell、AS 配置、停止/reset MMIO | 可信后端依据当前授权与状态执行 | 用任意 MMIO 脚本绕过对象或生命周期检查 |

“RMM 保护”不等于“只有 RMM 访问”：GPU/FW 必须访问自己的协议区域。关键是 CPU 映射、GPU/MCU 地址空间和命令权限共同限定合法写者。若普通恶意 GPU 命令能改写所有完成依据，多个计数交叉检查也不能恢复可信性。

**2.5 完成判定：物理事件记录与语义检查组合**

拟议扩展让 Monitor/可信前端记录物理 IRQ 的来源和交付状态；可信设备后端按协议提取子事件并保存相关故障影响；Proxy 继续处理功能通知。Client 收到提示后查询 RMM，只有可信终态才能驱动成功 fence。

这里检查的是允许的状态转换，不是预测唯一的下一次 IRQ：

```text
Allow(S, A, E, D) = 调用身份或委托合法
                 ∧ 对象及执行实例匹配
                 ∧ 当前状态允许操作 A
                 ∧ 操作所需的事件 E / 新鲜设备证据 D 充分
                 ∧ 设备协议和参数约束成立

SUCCESS = 已授权且实际发布
        ∧ 绑定和映射仍对应本次执行
        ∧ 全部必要成员满足执行完成条件
        ∧ 无阻止成功的相关故障或证据缺口
        ∧ 输出可见性成立
```

上述条件由可信路径在明确提交点确认。任务的调度进展、队列消费、shader 完成和输出可见不是同一个状态。STATUS/ACK、新鲜读取、错误检查、cache 维护及必要后检查必须组成一致协议，不能拼接不同执行代次的观察。

| 协议层 | 跟踪什么 | 不可混同的结论 |
| --- | --- | --- |
| IRQ 来源与交付 | 物理来源、捕获记录、GIC pending/active、交付与应答 | 有真实 IRQ 不等于任务完成 |
| 设备控制操作 | 对应请求、目标、REQ/ACK、未决或不确定状态 | 一个旧 ACK 不等于本次操作已完成 |
| 任务结果 | 已授权、可能发布、执行中、成功/错误/取消 | ERROR 或 SUCCESS 不等于资源已经撤权 |
| 资源生命周期 | 固定引用、撤权中、可安全复用 | 超时或功能对象关闭不等于可释放 |

**事件关联依赖可信绑定边界。** IRQ 通常不携带 JOB ID；软件事后添加 generation 不能证明迟到事件来自当前任务。槽位复用前，需要处理旧执行、FW 未决请求、设备事件及 GIC pending/active，并保证旧访问不再作用于新绑定。IRQ 捕获后的状态读取只是后续观察，不是原子捕获快照。

**真实事件与查询触发分开。** 一个 IRQ 可以包含多个事件或涉及多个任务；多个 IRQ 也可能只表示同一任务的进展。普通虚假提示最多触发查询，若查询时任务确实完成，可以成功；轮询完成也不必强求一条 IRQ 记录。需要物理记录约束的是受保护的中断交付及相关历史，不能用它替代设备语义。

**错误历史不能被清除后遗忘。** 故障影响必须在必要硬件状态被清除前保存。不能确定具体任务时，按可信硬件/FW 能确定的保守范围隔离，不能采信 Proxy 猜测而缩小范围。日志溢出标记为历史不完整；若只是丢唤醒，可用可信轮询恢复；若丢失会改变结果判断的故障，则不能因为当前寄存器正常就交付成功。Monitor 保持最小捕获工作，复杂检查在可控上下文执行，避免 IRQ 重入 RMM 锁。

与 Devlore 的区别是驱动信任边界：Devlore 保护不可信 Host 向可信目标 CVM 的中断交付，目标驱动仍解释设备语义。本方案的 Proxy 驱动也不可信，所以还要约束其请求的状态转换；这两层可以组合，不能概括成“Devlore 只要 IRQ 正确就证明结果正确”。

## 3. 安全性分析与攻击验证

**3.1 条件式安全论证**

证明思路是：从经过可信接管的合法初态出发，所有安全敏感效果都经过可信路径；每次状态转换维持下列不变量；异步设备行为按第 1 节的硬件/FW 前提解释；证据不足时不提交成功或释放。它是设计论证框架，尚不是完成的形式化证明。

| 不变量 | 必须始终成立的性质 | 四类防御如何协作 |
| --- | --- | --- |
| I1 授权不扩大 | CPU/GPU 只能访问授权页面与控制范围 | 页面归属、对象关系、受保护 PTE/root、设备访问边界共同约束 |
| I2 执行目标不被替换 | 实际发布对象与 Client 接纳的执行实例对应 | 描述快照、映射/绑定版本、安全引用、可信 wrapper 和 MMIO 提交 |
| I3 旧授权不产生新效果 | 旧 token、ACK、IRQ 不能授权新的发布或新绑定 | 代次、一次性发布权、未决操作状态与干净切换边界 |
| I4 不产生假成功 | 部分进度、错误、陈旧或可伪造证据不能成为成功 | 权威完成依据、完整成员检查、错误历史与可见性协议 |
| I5 不提前复用 | 旧执行仍能访问时，资源不转交给新使用者 | 引用、停止、撤权、翻译/在途访问处理和必要清理 |
| I6 失败不升级权限 | 部分失败和不确定状态不能开启绕过路径 | 失败阶段记录、幂等查询、有限恢复、隔离保留 |

单独某一项不够：页表内容正确但 root 可替换，I1 仍失败；IRQ 来源真实但完成字可伪造，I4 仍失败；成功 fence 正确但旧映射未失效，I5 仍失败。**安全分析必须覆盖真实效果的所有写入路径和失败路径。**

**3.2 攻击场景与后续功能测试**

以下保留首轮 **40 类负面/攻击场景和 6 类正常对照**。本次已扩展为 **80 类负例＋12 类正常对照，共 92 项**；新增场景、CVE 与测试步骤见 [扩展攻击测试计划](GPU_SHARED_ATTACK_TEST_PLAN_20261109.md)。它们是测试设计，不是已发现漏洞清单；新增用例全部为 NOT_RUN。先在受控模型和测试后端注入，再选择目标平台验证，不以运行公开利用程序作为完成条件。

验证层次：**L1** 为有限状态模型与接口边界测试；**L2** 为实际可信代码配合可控制的设备后端、故障与并发注入；**L3** 为具备目标隔离条件的实体平台测试。L1/L2 通过不能替代 L3；OpenCCA 功能原型不能直接提供其不具备的物理隔离证据。

| --- | --- | --- | --- |
| R01 | 执行中关闭 BO/GEM/GPUVM，或谎报本地引用归零 | 功能对象可关闭，真实 backing 仍被安全引用固定；不能提前交给新 owner | L1/L2/L3 |

**正常对照不可省略。** 否则“全部请求都拒绝”也可能让攻击测试看起来通过。

| ID | 合法场景 | 应有行为 |
| --- | --- | --- |
| P01 | 两个 Client 使用相同数值的 IPA/GPUVA，但分别解析和映射各自 BO | 各自正确执行且输出互不污染 |
| P02 | 一个 IRQ 合并多个进度事件，或一个任务产生多个 IRQ | 根据真实状态推进，不要求 IRQ 与 JOB 一一对应 |
| P03 | Proxy 提示到达很早或很晚 | 早到返回 PENDING；检查时已完成可以成功，不强求消息时间的因果证明 |
| P04 | 没有可用 IRQ 提示，但可信轮询具有充分完成证据 | 允许按轮询协议完成；不能仅因缺 IRQ 记录永久拒绝 |
| P05 | 图形 tiler OOM 后，合法页面扩展并继续执行 | 本次请求只生效一次，最终按正常完成协议交付 |
| P06 | 正常停止/UNMAP 后复用 BO，或多个已就绪任务合法交错 | 新授权可用、旧授权不可用；合法调度不触发无依据的全设备 reset |

**优先级与测试判据。** P0 首先验证 M04–M08、H01–H08、C01/C04/C08/C10、R01–R04 中决定基础边界的部分；其余在完整矩阵中补齐。IRQ 扩展尚未实现的项标记 NOT_IMPLEMENTED，不能以现有 FINISH 测试替代；平台不能表达的隔离项标记 NOT_VERIFIED。

每项至少记录：调用者和目标 owner、对象/映射/绑定代次、注入阶段、可信前后状态、真实 PTE/控制写入是否发生、终态/fence、backing 引用及受害者哨兵。以可信插桩和独立结果为依据，不只查看 Proxy 日志或一个错误码。拒绝后系统不应出现半提交、授权残留或无法解释的引用；故障隔离期间合理保留的资源需要单独记账，不能简单算作泄漏。

并发测试建议先用“两 Client、两槽位、每组两队列”的有限模型，在复制后、授权接纳后、首次设备可见写入后、ACK 前后、观察后和撤权各阶段枚举交错。测试覆盖整数/计数边界、失败返回、丢响应、槽位复用与 reset；随后用实际后端验证模型依赖的硬件语义。结果统一使用 PASS、FAIL、NOT_RUN、NOT_IMPLEMENTED、NOT_VERIFIED，并附版本、命令、run-id、退出码与证据位置。

官方机器可读记录可按 `https://cveawg.mitre.org/api/cve/<CVE-ID>` 获取。原始技术披露：[GHSL-2022-054](https://securitylab.github.com/advisories/GHSL-2022-054_Arm_Mali/)。这些资料支持的是漏洞类型与既有受影响范围；表中映射到本项目的用例是新的研究设计，不能反向说 CVE 原因就是本项目某个缺陷。

**如何利用 CVE 验证本项目。** 先确认受影响代码是否实际存在于某个组件、是否可达及版本是否匹配；若是 Proxy 驱动缺陷，模型已经允许 Proxy 被完全攻陷，应进一步检查攻击者获得 Proxy 权限后能否跨越 RMM 边界。若类似缺陷进入 RMM/可信后端，或影响可信 FW，则会扩大到系统 TCB，需要直接修复。若缺陷只让攻击者破坏其自身 Client，不构成跨 Client 隔离失败，但仍是该 Client 的本地安全问题。

因此，优先复现“权限放大、陈旧引用、并发回收、元数据泄露”等根因条件。厂商 JIT/shrinker 实现若未被采用，不必机械移植原 PoC；对 IRQ 伪造和语义错配也不强行附会一个内存类 CVE。真正的研究贡献是说明完整 Proxy 失陷后，哪些安全效果仍受到可信不变量约束。

**3.4 TCB 与性能的取舍**

| 可以优化的工作 | 可以采用的方式 | 必须保留的条件 |
| --- | --- | --- |
| 重复页面登记和对象准备 | Client 复用已确认空闲的 backing；按用途重新授权 | 零活动引用、必要清零、不能复用旧任务授权 |
| 重复静态检查 | 在 owner、映射和绑定版本不变的有效期内复用验证结果 | 明确失效条件；reset、重绑定、权限变化使旧结论失效 |
| 高频进度通知 | 合并提示、批量观察共享上下文、采用事件驱动查询 | 保留故障历史；不把 IRQ 当作成功，也不静默丢安全事件 |
| 反复冷启动和域切换 | 在隔离与生命周期受控时保留执行域 | 安全引用持续存在；关闭和竞争处理不能提前释放 |
| 可信侧复杂功能 | 将布局规划、对象缓存、调度策略留给 Client/Proxy | RMM 仍核验计划并独占提交敏感效果 |

不能为提速删除实际归属、动态错误、新鲜性、可见性或安全撤权的唯一检查。可以消除重复证据获取，但必须说明哪个可信条件保证复用仍有效。IRQ 记录会增加捕获、日志、切换和验证成本，只有减少的轮询与通知成本更大时才会提速；当前不能预设性能结论。

**3.5 当前项目证据边界**

| 项目状态 | 可以据此说明什么 | 尚不能说明什么 |
| --- | --- | --- |
| 私有 BO、真实 GPU 页表、对象授权、可信 FW/控制后端已有实现记录 | 已形成可运行的职责拆分与有限安全协议 | 所有物理 CPU/DMA/MMIO 绕过已在实体平台被拒绝 |
| FINISH 使用新鲜 STATUS/ACK、队列/成员/错误检查与结果交接 | 存在可信完成语义检查路径 | 任意恶意 GPU 命令均无法伪造全部完成依据 |
| 当前私有后端屏蔽 GPU/MMU/JOB 三类 IRQ | 当前完成主要依靠可信设备观察 | Monitor 物理 IRQ 记录及完整语义关联已经实现 |
