## 2. 问题与研究贡献

论文研究跨进程 GPU 数据残留：GPU 驱动可以把新分配缓冲映射给正确进程，但如果实际存储未初始化，新进程仍可能读到前任内容。被释放的纹理、常量、代码、参数以及片上工作状态因此可能跨安全域流动。

作者将残留读取用于恢复浏览器渲染纹理，再根据像素序列和颜色直方图推断访问页面。贡献包括系统梳理不同存储类型、区分 context 结束和 kernel 结束两种读取窗口，以及在真实浏览器和多种旧代 GPU 上验证影响。

它不是 GPU TEE 设计，也没有证明机密计算系统被攻破；对本项目的价值是提供资源复用必须满足内容安全的具体证据。地址空间隔离与初始化是两个互补条件。

## 3. 威胁模型

攻击者是本地普通用户，可通过 CUDA/OpenCL 使用同一 GPU；无法在 OS 层读取受害者内存，没有 root 或恶意 hypervisor 前提。受害者使用图形或计算 API，论文还考虑受害者经 VirtualGL 访问、攻击者无 VirtualGL 权限的场景。

这不是仅靠恶意网页即可执行的远程攻击：本地原生 GPU 计算接口权限是关键。论文不需要破坏 CPU 进程隔离；数据通过 GPU 存储的再次分配流出。对项目，类似攻击者可对应合法接入但不可信的另一 Client，前提仍要按项目接口与硬件实际行为验证。

## 4. 存储类型与术语

论文沿用 OpenCL：global/constant 是设备可见存储，local 是工作组/CU 共享的片上区域，private 是单线程/PE 使用的状态。CUDA 的 local memory 术语含义不同，不能把论文所有 local/private 直接翻译成当前 Mali 的某个缓存或寄存器。

被测 NVIDIA 的 shared/local 与 L1 存储可配置分配比例，论文利用不同配置间的重叠观察到前任 cache 内容。这是特定代际结构，不等于任意 GPU 的 L1 都可直接枚举。

## 5. 基础现象：释放句柄不等于擦除内容

作者使用写入已知值的程序，再读取新分配空间，发现 context 结束后仍可观察残留。还有驱动管理的 kernel 代码、常量和按值参数，应用缺少直接擦除接口。

当没有其他活动 GPU 程序时，某些测试只观察到 dummy 数据；作者推测与休眠有关。应将实测“有/无活动程序时内容不同”与未独立证明的电源因果解释分开，不能依靠偶发休眠宣称安全清除。

本项目因此不能将句柄释放、进程退出、fence 完成、设备可能降功耗等事件自动等同于数据不可恢复。

## 6. End-of-Context：回收后的全局存储残留

EoC 针对受害者 context 销毁释放的空间。论文利用可见的 GPU 空闲容量变化判断受害者分配/退出，再取得新分配区域并读取其中内容。攻击者读的是自己当前被分配的空间，核心失效发生在所有权转换时的初始化。

作者还使用预先写入的固定标记区分背景与新增内容；这是分析过滤手段，不提供真实性或密码学意义的归属证明。多受害者版本针对释放事件和代码特征筛选，但不能保证每次都准确识别目标进程。

对于已受保护的映射，实际页重新合法授予 Client B 之前，仍须满足对 Client A 数据的保密条件；仅确认 B 不再能使用 A 的旧页表是不够的。

## 7. End-of-Kernel：context 尚存时的片上残留

EoK 观察前一个 kernel 遗留在 local/private 的内容，受害者 context 不必退出。论文中的调度模型通常在不同进程 kernel 之间顺序共享设备；作者还讨论受害者运行期间释放的 global 区域。

多受害者竞争时，攻击 kernel 主要观察紧邻前任的状态，无法保证读取任意受害者的所有片上数据。论文对密码密钥等敏感状态的威胁讨论，不应全部记成已在每个真实密码库完成端到端密钥恢复。

对共享 GPU 的启发是应列出主存页之外需要隔离或清除的状态，并说明硬件、可信固件或调度器分别承担哪些职责；它不能单独证明当前 Mali 存在相同片上残留路径。

## 8. NVIDIA 与 AMD 路径的不同

被测 NVIDIA 环境通过容量 API 观察活动；被测 AMD/OpenCL 环境缺少等价容量查询，作者使用 kernel 时延变化。AMD 旧驱动的显存置换路径还可能将 inactive context 数据搬回 CPU，却未为新分配者清除重新使用的显存，从而扩大读取窗口。

因此“用户未显式 free 对象”不一定意味着底层物理页未被回收，所有权证明应跟踪实际物理存储和迁移状态。项目使用共享主存时仍需按实际分配/导出/映射生命周期分析，不能照搬独立显存置换细节。

容量与时延是定位窗口的观察通道；直接读到残留才是数据通道。隐藏容量统计可增加定位难度，但不能修复未清理重分配的根因。

## 9. 从纹理残留到页面推断

GPU 纹理存在布局重排，作者没有完整还原硬件格式，而是提取非黑白像素序列，用 Jaccard 相似度比较；另以规范化 RGB 直方图、随机投影和欧氏距离衡量颜色分布。

组合方法先按像素序列选 top-k 候选，再用直方图选最近页面。像素序列依赖 GPU/浏览器布局，直方图对部分跨 GPU 情形更稳健，但仍受浏览器及非纹理内容影响。

这些是根据候选集分类，不是无先验完整重建任意网页、输入文本或浏览历史数据库。多个页面的相似配色、动态内容和布局差异都会影响结果。

## 12. 作者缓解建议及局限

建议在交付新 global 页前初始化，并在 context 切换时处理 local/private；应用也可尽量在释放前清除敏感区域。但应用无法可靠覆盖驱动拥有、编译生成或异常退出时的全部状态，图形 API 也未必暴露对应清理接口。

论文给出清理开销示例与设计动机，没有实现一个完整且已验证的低开销防护系统。不能把作者关于性能代价的推测写成现代 GPU 无法提供安全复用的结论。

对异步回收，正确顺序是先阻止旧任务继续写、确保相关事务停止或被有效隔离，再完成所需清理，最后把资源交付另一安全域。若先清零后仍有旧 DMA 写入，零化本身不能证明安全。

## 13. 公开 PoC 实际包含什么

固定仓库仅有少量文件，已读取 `README.md`、`attack.cu`、`draw_img.py` 及 tree。README 明说代码旧且演讲后未更新，测试环境为 Ubuntu Server 12.04、NVIDIA 驱动和 CUDA SDK。

`attack.cu` 是 NVIDIA 全局存储/EoC 风格样例：固定设备容量、预填标记、观察空闲容量、分配后复制回 CPU，并过滤未变化标记。存在声明但未实际用于完成片上读取的 kernel，因此不能把它当作完整 EoK、AMD、浏览器数据集或多候选识别 artifact。

`draw_img.py` 使用 Python 2 与旧 PIL，忽略零值，把 dump 解释为 RGB；它不实现论文的 Jaccard/直方图分类实验。仓库中的 `google.bmp` 与样例 dump 只是示例产物，不能据此重现论文全部定量结果。

代码硬编码容量、分配回退和输出格式，部分 API 未统一检查返回值，调试格式也有旧式类型问题。本轮只做静态范围核验，没有以今天的工具链构建，也未替作者修复或运行该攻击。

## 14. 与 GPU TEE 和当前项目的关系

与 PhantomMap 的关系是实际物理页及生命周期，而非仅 VA/句柄标签；与 gGuard 的关系是清理责任和执行位置；与 sNPU 的关系是主存之外的片上状态；与 Hopper 的关系是跨租户交接前必须使旧状态不可被新租户恢复。

本项目已假定可信 ProxyRealm 控制映射，平台保护 PTE/root/MMIO，固件可信且撤销后安全回收。论文不推翻这些假设，而是要求将“安全回收”展开为可检查的状态与覆盖范围，明确实际页、上下文、固件状态及未完成事务各由谁保证。

当前已有独立 GPUVM、请求私有快照、真实 fence、cookie/epoch 和 RMM 持久通知，不能把它们当作尚未实现。更适合补充的条件是：旧完成凭据不能确认新分配对象；清理完成之前新 Client 不能读取该资源；取消/reset/error 路径不能跳过同样的隔离要求。

## 15. 可继续验证的设计问题

用可信测试数据验证跨 Client 的时间隔离：Client A 写入标记并结束或异常退出，Client B 在合法新分配页、对象池及允许读取的上下文状态中不应观察到 A 的标记。分别覆盖正常释放、取消、reset、映射失败回滚和页池复用；这些是建议测试，本轮未执行。

对于异步清理，保持清理中的资源与可分配池隔离，记录真实完成依据；清理失败进入隔离/报错路径，不能因超时把页面重新交付。该原则可以在既定软件与硬件假设下实现，不要求每个 job 全设备 reset。

若系统暴露容量、任务和完成统计，应说明其观察粒度与范围。减少跨 Client 统计有助于限制活动推断，但不能替代页初始化和上下文隔离。论文支持这些研究方向，尚不证明本项目存在残留泄漏或已经完成相关安全验收。
