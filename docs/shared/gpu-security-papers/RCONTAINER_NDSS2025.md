## 2. 问题及贡献的位置

普通容器共享内核；即使把用户页隔离，内核中共享的对象、计数和控制流仍可能形成跨容器影响。将所有检查放进最高权限 EL3，又会扩大最敏感层的代码量。论文试图同时实现容器用户态隔离、内核数据隔离和较少的新增 EL3 代码。

其方法是把可信 mini-OS 和不可信 Linux 同放在 **Normal EL1**，通过不同 GPT 视图隔离，mini-OS 接管关键内存管理与跨域控制；每个容器还有一个隔离的 con-shim。这里的 CCA 是 RME/GPT 原语的复用，不能将容器称为标准 Realm VM，也不能把 mini-OS 称为 RMM。

## 3. 威胁模型与可信基

攻击者可以控制 Normal、Secure、Realm 中的系统软件和恶意容器，尝试重映射、DMA、寄存器窃取、Iago 及多应用攻击。可信部分为 mini-OS、EL3 原有固件与所需硬件。con-shim **不可信**，其隔离是限制影响范围，而非使其中的 Linux 服务成为可信服务。

假设启动阶段良性，密钥和签名可以安全保存，镜像加密与既有证明机制可以应用。应用自身漏洞、主动泄密、密码攻击、物理攻击、侧信道及一般 DoS 不在目标内；部分内存消耗和抽象资源滥用被单独考虑。不要把这项有限资源防御写成整体抗 DoS。

将普通内核与 mini-OS 链成一个镜像，再依赖早期良性启动完成分离，是明确的启动信任条件。网络和串口尚未初始化的论述不能单独取代完整的启动链与镜像来源验证。

## 4. Mixed-pagetable：相同 EL 的不同权限

Priv-GPT 供 mini-OS 使用，可访问正常运行所需内存；OS-GPT 禁止普通 Linux 访问 mini-OS 和容器私有区域。两者共享部分页表层级，关键页表页由 GPC 保护，低层页表页不混装两个域的条目；各自的顶层视图避免普通 Linux 为 mini-OS 构造任意可执行映射。

页表结构共享是减少重复管理的方法，其安全性仍取决于根选择、可写页表页归属和所有更新入口。单有“数据页不可访问”不足以证明可信域总会执行正确的代码。论文的控制流和元数据检查是隔离论证的一部分，不能从图示省略。

EL3 新增切换 GPT、批量修改 GPI、查询 GPI 的三类接口。完整论证需要说明哪些当前状态可以调用哪项接口，避免不可信内核直接申请 Priv-GPT。正文描述 mini-OS 介入与控制流约束；本次没有实现源码，未独立核实所有 SMC 调用者检查或将其当作形式化证明。

## 5. Con-shim 隔离什么

每个容器的 Shim-GPT 只允许自身用户内存与 con-shim，禁止其他容器、mini-OS、普通 Linux 和固件的私有页。con-shim 保存与该容器有关的任务结构、内核栈、部分全局状态、配额及共享缓冲区；mini-OS 监控调用和返回。

这是将共享内核数据面分离的尝试，不能据此认为任意 Linux 隐含共享状态都已穷尽。可信对象归属、分配记录和调度身份仍需放在受保护的位置；不可信 con-shim 提交的字段应作为待验证输入。

对应本项目，独立 GPUVM 已经隔离页表，但驱动内部全局状态、GPU context、恢复资源和 fence 所属关系还要具有同等明确的归属约束。这里是设计比较，不是声称当前代码缺少 GPUVM 或认证队列。

## 6. 生命周期、映射与返回值

mini-OS 检查新映射的虚拟范围、物理页是否已归属于其他容器、来源页归属和映射计数，清理新页，再更新隔离视图。共享和解除共享必须通过受控路径；调度切换要验证目标上下文所属域。

系统调用将必要参数复制到 con-shim 共享区，清除不需外传的寄存器，移交普通 Linux；返回时检查结果，再复制到私有内存。它和本项目已有的私有请求快照具有可比较的目的，但两者都不能只凭“复制过”推导所有嵌套指针、对象长度和返回状态都正确。

销毁需要清理 con-shim/容器关联内存并撤回访问。CPU 视图失效与设备事务停止是不同条件；本文没有实现 GPU 提交到撤销再复用的完整协议，不能代替项目针对 GPU DMA 和真实 fence 的论证。

## 7. 中断、信号和 IPC 的证据边界

异常和中断先经 monitor/mini-OS 再交给不可信 OS，mini-OS 执行时关闭中断。信号讨论主要依赖受保护用户栈和 GPT 阻止非法写入。它说明上下文写入受到限制，**不自动证明信号原因、发送者和所请求副作用得到认证**。与 Sigy 对照时，应补充事件语义证据，而不是宣布已经重现同类漏洞。

原型的可选 IPC 加密使用 Linux 原生 AES-ECB、每容器密钥和文件描述符跟踪。ECB 加密本身没有消息完整性、新鲜性或语义发送者认证；相同明文分组的模式也可暴露。论文没有给出足以将这条路径称为具备认证与抗重放的安全消息协议的证据。本次未执行攻击，不声称已发现具体可利用链。

若迁移到 GPU 完成事件，应检查受保护记录中的 Client、会话、context、job、事件类型和允许状态转换；不能将“共享内存受 GPT 保护”或“通知经过可信入口”当成特定任务成功的充分条件。

## 8. 多核与 DMA

EL3 用锁序列化 GPT 更新，更新和切换时失效相关 GPC/TLB 缓存；TTBR 的 CnP 设置为 0，避免跨核共享不合适的缓存视图。其安全论证涉及每核当前视图和所有核的观察，不只是单个页表条目。

设备方向使用 SMMU 的 IOGPT，默认禁止访问，只有显式允许的 DMA 页可被设备访问，例如需要传输的加密数据。这是 DMA 隔离策略，**不包含 GPU 固件、并发 GPU context、任务完成来源与 reset 的协议**。

本项目按既定假设由可信 ProxyRealm 控制 SMMU，以 RMM 认证的原始 Client 校验并软件合成 GPU Stage-1 HPA 映射。两者值得比较的是物理页归属和更新原子性，而非要求改回另一种硬件翻译层级。

## 9. 镜像和证明

镜像预处理的 scan-encrypt 保留供加载器读取的 ELF 信息，可信路径核对哈希后解密到私有区域。它需要可信的预期哈希、密钥和版本来源；对持久状态和跨重启回滚没有因为“使用哈希”就自然闭合。

正文假设既有 attestation 可用，并未提供项目所需的 Proxy 实例、Client 会话和当前设备所有权的一体证明。镜像身份相同也不等于服务实例相同。本项目可以复用已有可信身份机制，再明确运行期会话绑定与失效条件。

## 10. 两个原型及 TCB 口径

功能验证：Armv9.4 RME FVP、Linux 6.2-rc2、TF-A 2.8.0；正文 Docker 版本写作 1.5。性能：Firefly RK3399、2×A72/4×A53、4GB、Linux-firefly 4.4.149、TF-A 1.3、Docker 25 beta，通过替代寄存器和 TLB 操作模拟 GPT 成本。系统调用覆盖处又写 4.4.194，与此前版本不一致。

模拟是合理实验方法，但数字不是原生 RME 板上的完整 GPC/加密成本。本文不因模拟平台缺少硬件能力否定其架构。

新增可信代码 2647 行：ATF 130 行、Linux C 2272 行与汇编 112 行、镜像预处理 Python 133 行；可选 AES 再加 2308 行，总计 4955 行。约 200 行 con-shim 补丁不计入 TCB。**130 行只是新增 EL3 部分，不是完整 TCB**；既有固件、库和部署链不能从信任基础中消失。

## 11. 功能与安全评估

LTP 1409 项：970 通过、280 跳过、159 失败，原生容器与 RContainer 的这三类数量相同。作者解释部分失败与旧内核和不支持的功能有关。这是相对兼容性证据，不能写成 1409 项全部通过。

30 个 CVE 采用分析及深层攻击模拟，附录常先假定攻击者已有 root，再尝试跨域访问页表/内存，观察 GPT fault 或密文。列表还包含 Windows Docker、PowerPC 热插拔等不同环境的案例，不能说 30 个原始漏洞已在同一 Arm 原型完整复现并被修补。论文明确允许某些提权仍发生，只限制其对受保护区域的后续影响。

这些结果支持指定内存访问被隔离，未穷尽并发调用、中断伪造、恢复竞争和所有 Iago 语义。正文“均可防御”的概括应按附录实际实验方式理解。

## 15. 独立评价与可验证后续设计

有价值的增量是把用户态隔离推进到内核数据归属，并明确最高权限代码预算。较弱的证据主要在安全信道语义、完整调用入口核验、深层攻击模拟与完整 exploit 的区别，以及特殊原型基线的比较条件。

对项目建议优先形成三项验证目标：第一，检查者只能使用受保护的原始 Client/对象归属，不能在检查后重新读取不可信嵌套字段；第二，为完成、错误、取消、ACK 和 reset 各列允许的前置状态、写入副作用和重复处理规则；第三，撤销完成须同时说明映射失效、队列退出、旧 DMA 停止及页清理，再授予新 Client。

可在协议模型和故障注入中构造跨 Client 句柄、伪造长度、重放旧信号、Host 延迟返回、与销毁交错的完成及恢复。验收指标应包含未授权状态转换次数、重复释放/重复完成、旧事务触达新页，以及合法并发路径的额外成本；普通 benchmark 通过不替代这些性质。
