## 2. 研究问题与贡献

DNN 加速器通常由 Host 上复杂的软件栈决定执行顺序、数据位置与算子参数。如果沿用 CPU TEE 加设备 TEE 的方案，CPU 软件、两侧证明与通信也进入可信边界。GuardNN 尝试让 Host 继续做复杂调度，但不能因它恶意而直接导出机密明文。

其主要方法是限制设备接口：任何计算指令产生的敏感数据都只能在加速器内以明文存在，片外内存、输入导入和输出导出始终受到密码保护。执行哪些指令可以由 Host 决定，而是否让秘密离开保护边界由设备 ISA 决定。

论文进一步把目标拆成两档：只保护机密性，以及同时保护机密性和完整性。后一档增加片外 MAC 验证、输入/权重/输出和指令操作数哈希，以及结果签名。不能用机密性原型的低开销代表完整计算证明已经在同一原型中全部实现。

## 3. 威胁模型、可信基与排除项

信任加速器制造商、设备内部逻辑、唯一私钥、片上状态和运行在内部控制器上的固件；不信任 Host 处理器及其软件、片外内存和外部通信。用户通过厂商证书识别设备，并与设备建立安全会话。

论文将模型结构视为公开信息，只保护输入、权重、训练数据、中间结果及输出。其内存/时间侧信道主张依赖固定模型执行时的访问模式和指令延迟不随秘密变化；动态 pruning 被排除在该主张的典型条件外。功耗与 EM 等物理侧信道不在保护范围内。

“TCB 只有 accelerator”不表示可信软件不存在：原型仍有约 4.5K LoC 的 MicroBlaze 指令固件，以及保护逻辑和基础加速器。厂商证书、密钥供应和正确硬件也是信任条件，不因 Host 被移出 TCB 而消失。

论文没有提供多租户 GPU 的并发命令隔离、按 Client 的页授权或共享 reset 协议。单用户拥有输入、模型和输出的信任关系，也不能直接替代模型方与数据方互不信任的多方授权。

## 4. ISA、会话与数据路径

GetPK 返回设备公钥和证书。InitSession 与远程用户交换会话密钥，清除已有密钥、数据及哈希，产生新的内存加密密钥，重置内部计数器，并按用户选择启用完整性功能。重置计数器与换内存密钥必须组合，不能在相同密钥下任意重用旧写版本。

SetWeight/SetInput 从用户会话导入加密权重和输入，在设备内解密后按片外内存保护重新存储；分别更新权重或输入计数。完整性模式同时记录相应输入哈希。ExportOutput 将片外受保护结果转换成会话密文，用户持有解密权。

SignOutput 对输入、权重、输出及已执行指令/操作数的哈希生成设备签名。这里的证明对象是一次具体执行轨迹，用户需要知道预期模型、输入和允许的指令语义，才能判断签名对应的执行是否符合请求；验证签名本身不能替代这些比较。

SetReadCTR 允许 Host 为一个地址范围设置读取 feature 的版本依据，配合编译优化和复杂调度。论文认为 Host 给错读取版本不会破坏只加密输出模型下的机密性，因为它只影响解密内容；这与“读取的是当前正确数据”不是同一主张。

论文没有给出完整的会话标识、输出序号、证明挑战与消息重放窗口编码，也没有完整展开中断、取消和重新连接时如何绑定 SignOutput。这里只能说材料未细化这些部署条件，不能据此直接宣布已验证的重放漏洞。

## 5. 内存保护与版本依据

片外数据采用 AES-CTR，counter 包含 PA 和 64-bit VN；同一密钥下，同地址的每次写入都必须使用不同 counter。MAC 在完整性模式绑定数据、PA 和 VN，检测片外篡改。DNN 的规则搬运允许共享版本状态及更粗的验证块，例如原型每次搬运的 512 bytes。

feature 写版本由片上 CTR_IN 与 CTR_F,W 组合：导入新输入时递增前者并重置后者，每个写输出的计算指令递增后者。读取端的 CTR_F,R 则来自 Host；weights 使用片上权重更新计数。训练梯度的版本共享还依赖它们与 feature 不占相同物理位置。

与 MGX 的重要区别是控制权分配：MGX 依赖可信控制 kernel 重建读写 VN，GuardNN 为缩小 TCB 允许不可信 Host 提供部分读版本，并通过受限输出接口保护机密性，在完整性模式额外验证执行。两篇不能只归纳成同一个“无树内存保护”。

MAC 证明某组数据与被选定 VN 相符，不独立证明该 VN 就是本任务当前应读的最新值。对完整性，需要结合指令/操作数记录和预期程序检查；若希望设备本地直接拒绝错误任务，还需明确本地授权规则。这个区别对异步 GPU 完成语义很重要。

## 6. 为什么机密性模式不等于通用 GPU 保护

GuardNN 的“无论执行什么指令都不泄漏明文”依赖 ISA 不提供任意明文导出、输出只能使用用户会话密钥、指令的可观察时间和地址不随秘密变化，以及内部密钥和版本不能被 Host 改写。这是整个受限接口的性质，不是仅在 buffer 上加密即可获得的性质。

通用 GPU 的任意 shader、原子操作、间接寻址、设备控制和共享队列拥有更丰富的可观察效果。若想借鉴 GuardNN，必须明确可执行命令和外部副作用边界；不能直接宣布“GPU 输入输出已加密，所以恶意调度和任意命令都安全”。

结果签名与真实完成也不同：签名可以关联实际数据和执行记录，但通知仍需要识别属于哪个请求、是否当前代次、结果是否可见，以及是否允许进入成功终态。论文没有建立多 Client 的 IRQ 路由、native fence 或页回收协议。

## 7. 原型与评估方法

FPGA 原型在 CHaiDNN 上加入 VN generator、AES-128 和 MicroBlaze，只实现以机密性为主的 GuardNN_C。论文明确说明所用 FPGA 不支持其所需 bitstream 安全远程证明，所以原型主要用于功能展示；不能把 GetPK/密钥交换演示当作完整可信加载链已部署。

FPGA 使用 128/256/512/1024 DSP、6/8-bit 定点精度的八种组合，200 MHz，流水 AES 延迟 12 cycles。完整性性能另由 SCALE-Sim 与 Ramulator 模拟 TPU-v1 风格设计：64K MAC 单元、24 MB 片上内存、16 GB DDR4。两组平台和保证不能混合。

| 指标 | 作者结果 | 条件与边界 |
| --- | --- | --- |
| FPGA 运行性能 | 表 II 中机密性开销约 0.2%–3.1% | AlexNet/GoogleNet/ResNet/VGG，八种配置，三个 AES 引擎 |
| 增加 AES 引擎 | 最高开销可降至 1.9% | 改为四个 AES 引擎，资源成本也变化 |
| 会话建立 | GetPK/InitSession 约 23.1 ms | MicroBlaze 上 ECDHE–ECDSA，一次性成本 |
| 导入权重 | 四模型约 19.5/2.2/8.0/43.3 ms | 重新加解密及加载，不是计算 runtime |
| 每输入操作 | SetInput 约 0.1 ms；ExportOutput 约 0.01 ms；SignOutput 约 4.8 ms | 1000 类输出；签名不是免费操作 |
| 完整性模式流量 | inference/training 平均多 2.4%/2.3% | 模拟，与运行时间比例不同 |

正文 §III-C 将 GuardNN_CI 的平均开销写成 inference 1.05%、training 1.07%，GuardNN_C 写成 1.04%/1.05%；但 Fig.3 纵轴及 Table III 使用归一化时间，Table III 对 VGG 的 GuardNN_CI 为 1.05×，附近文字也称 5% 开销。这里存在百分比与倍率口径不一致，不能自行将所有数字改成确定的 1% 或 5%。

面积讨论引用其他论文的 28 nm AES 核和 TPU-v1，估算增加 344 个 AES 引擎约 0.3% 面积、1.8% 功耗；这不是将 GuardNN 全部可信控制器和证明逻辑一起完成 ASIC 综合的实测结果。Table III 的功耗也为估计。

FPGA 单 AES 核为约 9K LUT/3K FF，给出的 8.2%/2.6% 是一个 AES 核的比例；系统使用多个 AES 核。MicroBlaze 另有 LUT/FF/BRAM/DSP 成本，不能把单核比例当作完整系统面积开销。

## 9. 与当前 ProxyRealm GPU 设计的关系

项目保持 RMM 认证原始 Client、可信 ProxyRealm 控制 SMMU、建图时对象/实际页/权限/生命周期授权，并软件 IPA→HPA 合成受保护的 GPU Stage-1；其他设备保留硬件 Stage-2。GuardNN 不以本地实验板能力否定这组假设。

GuardNN 直接支持把任务隔离再拆清：访问隔离回答能读写哪个对象；执行绑定回答实际处理的输入/命令是否对应预期；可信完成回答什么实际状态足以触发哪个 Client 的终态。三者互相关联，但认证队列、加密或签名不能各自替代全部证明。

当前已有 GPUVM、私有快照、native fence、cookie/epoch 和 persistent IRQ127，适合继续建立提交快照到实际执行、结果可见再到完成发布的关联，而不是新增一套与现有字段重复的协议框架。

若需要远程证明，可以借鉴将输入/命令/输出及策略代次纳入可验证记录，但应先明确用户是否真的需要密码学远程证明，以及证明检查者掌握哪些预期值。平台内受保护队列已有的真实性不必为了引用论文强制改成每任务签名。

## 10. 建议形成的验证义务

第一，明确可信 Proxy 可以接受哪些命令和参数，以及每种命令允许的 MMIO、映射和输出副作用；不能只验证请求来自有效 Client 就执行任意共享设备操作。

第二，沿现有私有快照验证检查后被执行的对象与内容一致，避免合法输入检查后被不可信方改成另一任务。完成记录继续关联原 Client、job、对象实例和当前 epoch。

第三，把实际完成、结果可读、发布通知、消费 ACK 与安全回收分开定义。设备已经产出加密或签名数据，不意味着旧 DMA 已终止；反过来真实 fence 完成也不自动证明任意高层 DNN 模型语义正确。

第四，reset、重试、Client 重连和页转交须维持执行实例连续性。设备身份相同或程序镜像相同不能代替新任务身份；旧结果和旧完成不能因复用数值地址而被新任务接受。

第五，在性能比较中同时记录 runtime 与会话建立、权重导入、签名及回收成本，按应用是否摊销分别说明。没有项目实测，不以 GuardNN 的约 3% 推断当前 GPU 保护层也具有同样开销。
