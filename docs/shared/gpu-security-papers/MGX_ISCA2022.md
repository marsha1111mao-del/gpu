## 2. 问题与主要增量

可信加速器若要保护不可信 DRAM 中的数据，通常需要加密、MAC 和防重放版本号。通用 CPU 必须支持任意读写顺序，因此逐 cache line 记录版本号，并用以片上根为锚的完整性树防止攻击者同时重放数据、MAC 和旧版本号。

这会引入大量元数据访问，尤其不利于流式处理大量数据的 DNN 和图计算。MGX 的观察是：专用加速器往往由可信控制程序管理数据搬运，可以从执行调度和片上状态重建版本号，不必把全部版本号存到不可信 DRAM。

论文组合两个优化：在片上可信状态中生成版本号，以及根据实际数据搬运粒度合并 MAC。去掉版本号的片外存储后，也可以去掉为这些片外版本号而设置的完整性树；MAC 本身仍要存储、读取和验证，不是取消完整性保护。

## 3. 威胁模型与可信基

威胁包括恶意 Host 特权软件、共享不可信片外内存以及数据篡改、重放、替换和搬移。信任 CPU TEE、加速器内部硬件和片上状态，以及运行在可信控制处理器上的 application kernel。kernel 负责发起计算和提供正确版本号，必须被证明并纳入 TCB。

远程用户与 CPU TEE/加速器之间的可信接入、设备私钥基础设施、证明和密钥交换为系统假设。新会话清除内部状态并建立新的对称保护密钥。MGX 主要贡献是内存保护优化，不是独立实现上述全部证明与供应链机制。

物理对手不能直接读取或修改加速器内部状态；不考虑地址、时间、功耗等侧信道。内存加密不会自然隐藏访问模式、模型拓扑或中断时序；论文明确这些需要其他防护。

模型信任本任务的控制 kernel，没有研究恶意 kernel 如何被约束为只访问所属 Client 对象，也没有给出多租户 GPU 命令级沙箱。不能把 MGX 的“可信 kernel 可提供 VN”推广为任意不可信 GPU 程序可自行声明授权。

## 4. 机制与关键安全条件

加密使用 AES-CTR，输入 counter 由物理地址 PA 和版本号 VN 构成。相同密钥下，对同一个 PA 的每次写入必须使用新的 VN；不同 PA 可以共享 VN，因为完整 counter 仍不同。

MAC 绑定密文、PA 和 VN。读取时可信侧依据片上状态提供该地址最新写入所用 VN，再检验 MAC，阻止旧值、其他地址数据或未经授权替换通过。关键不是“数据带签名”，而是可信侧知道本次应该接受哪个版本。

论文安全分析将加密与完整性分别归约到 AES-CTR 和所选 keyed hash 的安全性，但前提包括 VN 不复用、读取端使用正确当前 VN。没有给出对所有控制 kernel、所有写入调度的自动证明或机器检查的完整协议证明。

读取可以任意不规则，因为读不消耗新 VN；写也不必严格顺序，但同一 VN 下某个地址最多写一次，且后续读取能确定对应版本。如果调度更复杂，需要额外片上状态，而不是宣称任意通用 GPU 工作负载都只需一个计数器。

数据搬运以较大块为单位时，可使用每 512 bytes 一个 MAC 等粗粒度保护；若访问只取很小的不规则片段，仍需要细粒度标签或额外读入完整验证块。保护粒度取决于实际访问语义，不能仅根据页大小决定。

## 5. DNN、图算法与其他应用

DNN kernel 维护 features、weights、gradients 等版本状态，以数据类型标记区分相关 counter 空间。只读 weights 可保持同一 VN，更新时递增；中间输出若因 tiling 多次回写，每次都要更新 VN，不能只按 layer 编号计一次。

矩阵乘法示例对不同输出 tile 使用相同一轮 VN，但每次重新写同一个输出地址时递增。残差网络和训练路径则依据执行图保留仍会被后续使用的中间结果版本。作者举例 127 层网络可用约 1 KB 片上 VN 状态，并讨论进一步压缩。

GraphBLAS 的 PageRank/BFS 中，静态图结构只读，属性向量按迭代更新，可从可信迭代计数器生成版本。稀疏图地址不规则不自动破坏方案，但细粒度随机读取的向量可能仍需小粒度 MAC。

Darwin 基因组加速器案例将 genome/query 会话计数器组合，因为参考序列和表只读、输出按 query 产生；其 GACT 部分使用细粒度 MAC，仅评估片上 VN 优化。H.264 案例以 bitstream 标识和显示帧编号生成版本，允许 B-frame 的非顺序解码，并检查每帧对输出地址的写入次数。

动态 pruning 可以跳过部分 VN，只要不重用且读取仍匹配实际写入。论文用 PyTorch 软件模拟若干稀疏/通道裁剪策略；这不等于验证所有动态控制流或任意稀疏 GPU kernel。

## 6. 实验方法与结果边界

DNN 使用 SCALE-Sim 生成计算/访存事件；图计算用 GraphLily HLS/RTL 仿真生成事件，再由内存保护模拟器与 Ramulator 评估。不是在量产安全 GPU 上测得的端到端应用结果。

Cloud/Edge DNN 配置分别为约 64K/1K MAC 单元、24 MB/4.5 MB 片上内存、700/900 MHz；内存采用 DDR4-2400，分别四/一条 64-bit 通道，保护内存 16 GB。图计算模拟四通道和 800 MHz 设计。实际匹配计算与带宽的配置影响观察到的开销。

基线 BP 使用通用内存加密/完整性机制、64-byte 粒度和 32 KB VN/MAC cache。MGX 去掉片外 VN，并对大部分数据使用 512-byte MAC；DLRM embedding table 仍用 64-byte。因此总体结果是两个优化的组合效果。

训练包含 forward/backward，但 SCALE-Sim 没有对应操作，论文明确没有模拟 weight update。评估列表中训练图也未列 DLRM；不能把 DNN 训练结果扩大成含所有优化器、权重更新及任意模型的完整端到端训练成本。

H.264 是 RTL 功能正确性与读写规律验证，没有给出与上述 DNN 同口径的通用平均性能。CHaiDNN 微控制器/AES-GCM 部署讨论使用“预期开销适中”，不应写成已综合测得完整原型面积。

## 8. 安全评价：省下元数据，不能省下版本权威

MGX 没有让 freshness 消失，而是把防重放依据从片外版本树转移到可信控制状态与正确调度。若复位、恢复快照或迁移后保留旧加密密钥却回退 VN，可能重用 AES-CTR counter 或接受旧状态；安全部署必须保证这些状态连续，或使用新密钥并按策略重新初始化。

物理地址复用尤其需要注意：旧对象与新对象若使用同一密钥、PA 和 VN，会发生保护域重叠。仅仅 object ID 或 job ID 变化而密码学输入未变化，不足以保证新鲜性。本段是由论文 counter 条件推导的部署要求，不是本轮复现了公开实现漏洞。

将多个 Client 的 VN 状态放在同一服务中，还需要处理并发更新、地址别名、映射代次与取消恢复，不能让某个 Client 通过重置公共计数器影响其他 Client。论文没有实现或证明这种多租户 GPU 生命周期。

还应分别分析认证失败前数据是否已被执行使用，以及是否能影响外部输出或设备控制。MGX 说明需要验证，但没有像专门延迟验证工作那样给出完整结果发布/外部副作用状态机；不能直接据此推出当前项目的异步完成可提前宣布成功。

## 9. 与当前 ProxyRealm 内存模型的关系

本项目假设由 RMM 认证 Client、ProxyRealm 可信建图、检查实际页授权与权限，并以受保护的直接-HPA Stage-1 限制执行期访问。该模型解决谁可访问哪些页；MGX 主要解决不可信片外存储中的内容保密、完整性与新鲜性，属于不同层次。

若平台假设已经提供所需的内存内容保护，就不必为采用这篇论文而新增软件加密层。若未来把恶意片外内存、设备外存或跨节点传输纳入模型，MGX 才可作为专用数据路径的候选，并需重新论证可信 VN 生成和密钥生命周期。

对当前设计更实际的借鉴，是把已有 cookie/epoch 与对象、页、GPUVM 生命周期统一论证：重启和 reset 后旧状态不能取得新对象授权；版本更新不能只存在于通知字段而未落实到实际页表、设备 context 和回收行为。

MGX 的 VN 是加密/认证使用的写版本，本项目的 epoch 是协议代次，两者职责不同。不能因为都叫版本就直接共用字段，或认为 epoch 自增已经提供了内容完整性与 DMA 停止证明。

## 10. 对两部分研究结构的用途

在直通/共享实现与性能部分，MGX 展示按工作负载语义优化保护开销的方法，但其专用 ASIC 的规则访存不能不加分析迁移到通用 GPU。若要优化，应先找出可信路径已有冗余工作，并保留等价授权、真实 fence 与生命周期要求。

在任务隔离部分，适合将 MGX 与 ACAI/PhantomMap、TensorTEE、PSSM、SeDA 分别比较：页归属、映射生命期、内容认证、版本新鲜性和验证后发布各解决什么问题。不要把这些工作统称“有内存保护”而忽略目标差异。

建议后续形成一张项目状态转换表，列明 Client 重启、job 重试、取消、GPU reset、unmap 和页转交时哪些状态可保留、哪些必须失效、谁有权更新以及何时允许资源复用。这可复用已有机制，不需要另建一套与 GPUVM/epoch 平行的版本框架。
