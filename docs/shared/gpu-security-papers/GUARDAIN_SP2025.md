## 2. 背景、问题与设计位置

许多 GPU/加速器 TEE 将 CPU enclave 或机密 VM 纳入可信基，保护主机驱动与设备之间的通信。GuardAIn 选择另一条路线：只信任 NPU 及其受保护固件，Host 的 CPU、OS、Hypervisor、驱动和 AI 运行时都不可信。

场景包含模型提供者、数据提供者、云基础设施提供者。模型和数据双方互不信任，也不信任云；分别与 NPU 建立密钥，避免云看到模型权重、算子二进制和用户输入输出明文。

只加密传输不足：NPU 解密后 Host 原有 DMA 映射仍可能访问明文；Host 还能重排任务、替换算子，或把输出区指向权重。因此设计同时处理端到端认证加密、内存归属状态和任务完整性。

这与项目的共同点是把授权和设备控制收敛到可信实体。区别在于它把实体放在离散 NPU 内，且整设备单租户；项目采用 RMM 认证 Client 与可信 ProxyRealm，并研究多 Client 共享，不需要因采用不同信任边界而改为设备唯一信任根。

## 3. 威胁模型、可信基与排除项

攻击者可控制 Host 软硬件和网络转发，构造任务、修改输入、发送控制命令、尝试 DMA、调试及加载旧固件。可信依赖包括 NPU 硬件、HSM/e-fuse 根密钥、控制 CPU、内存管理器、task scheduler、加密算子和所执行的可信固件。

“只信任 NPU”并非仅信任几个加密函数；设备内 Linux/固件及其可达管理路径都影响隔离。新增约 2 KLoC 是实现增量，不是完整可信计算基大小，也没有取代对原固件复杂度的评估。

DoS、侧信道、model stealing、membership inference 明确排除。论文还排除算子漏洞把模型二进制或参数复制到用户输出的情况；不提供对任意恶意算子的信息流无泄漏证明。恶意模型可以覆盖模型状态，作者认为其不符合模型方利益，这不是内存安全的技术阻断。

模型结构仍向 Host 暴露；改层名只能减少语义直观暴露，不能隐藏图形状、大小、交互模式。论文宣称保护模型和数据时应保留这一结构泄漏边界。

## 4. 实际平台与执行模型

原型是 Huawei Ascend 910A：32 个 AI Core、4 个带 Arm 加密扩展的 AI CPU、控制 CPU、task scheduler 和 HBM，Host 经 PCIe/SVM 访问。图 1 描述多个 MMU/SMMU，不能将其简化成任何一个 CPU 页表即可阻断所有设备访问。

Host 运行时根据模型生成任务和流，每个任务包含 PC_START、参数地址、workspace 等。任务写入 NPU task buffer，executeModel 触发调度，执行完成进入 CQ。静态图和 eager 模式属于背景，本文的认证和训练处理依赖可确定、可收集的执行图及任务序列。

所有对 Host 的 PCIe 访问受 NPU 可信内存管理器控制，这是保护成立的重要平台假设。本文按该假设分析协议，不以其他实验板能力否定它；同时不把特定 NPU API 名称当成所有设备通用的隔离证明。

## 5. 加密、密钥与证明链

模型方和数据方分别与 NPU 进行认证 Diffie–Hellman，得到 KM、KD。NPU 使用 HSM 中根密钥和固件测量派生会话材料；启动验证厂商签署固件，证明中携带固件版本/测量。两方应验证自己认可的设备身份和版本策略。

模型权重和算子二进制使用 KM 加密认证，输入输出使用 KD。AES-GCM-128 作为受测量的内部 AI CPU operator，在原地处理数据；多 AI CPU 并行与 AI Core 的模型计算重叠。

论文描述云提供 PKI，但没有完整展开证书授权、根信任配置和密钥释放策略。应把这些视为需要独立可信锚的协议条件，不能仅因转发来自云就认定某个设备或版本已经获准。

同样，正文没有完整列出每条 AEAD 消息的 nonce、重放窗口、方向区分、session/request ID 和输出关联字段。认证加密防篡改不自动证明跨轮次的新鲜度；该处是材料未充分展开，不是本次已确认的重放漏洞。

## 6. 内存状态机：先完成撤销，再允许解密

基本路径是：装载密文 → 撤销 Host 映射并确认 → 任务认证 → 解密 → 执行 → 加密输出并确认 → 重新映射密文输出 → 清理输入；结束会话时还需清理模型再开放对应区域。

可信 TS 经 Host 不可访问的共享内存向控制 CPU 内存管理器发送同步请求。内存管理器使用 dma_unmap_page 等撤销映射，完成后确认；失败则终止执行。没有这份确认，TS 不应调度解密算子。Host 中断可阻断流程，但不能使后续阶段越过前置条件。

输出只在加密算子成功后重新映射。TS 通过可信 CQ 确认算子成功/失败，再请求内存管理器开放区域。真正的安全条件是“正确算子对正确区域处理成功”，不能缩成“收到过一个中断”。

内存管理器记录已分配地址及 DMA_TO_DEVICE、DMA_FROM_DEVICE、DMA_BIDIRECTIONAL 方向，禁止输出与已分配模型/输入等区域重叠；能改变 SMMU 的关键接口只由 TS 控制，Host 不能直接任意 remap。

正文对“撤销完成”的叙述主要是 API 与同步 ACK，没有逐项展开缓存失效完成、别名映射覆盖、旧 DMA 排空和 reset 中断路径。安全迁移需要把这些纳入完成条件；不能仅依据 API 返回就将其普遍等同于所有在途访问已经停止。

## 7. 持久模型与逐轮输入的生命周期

模型参数、二进制和 workspace 首次锁定解密后，跨推理轮次保留私有状态，直到卸载或 reset；输入输出按轮次锁定、解密/加密和重映射。输入覆盖清零后才能再次对 Host 开放，不能开放仍含明文的区域。

图 8 用 S0–S8 表达状态转换，包含模型一次性准备和输入循环。它支持将初始化成本摊销到后续轮次，但也说明状态、密钥和跨轮次残留是长期安全对象。

本篇没有给出任意 reset、异常终止、迁移或多客户端交错下的完整状态机与证据集。尤其不允许用“正常轮次清零”代替所有异常退出已经安全回收的结论。

## 8. 模型与任务认证：实际认证了什么

模型方为每个算子二进制生成 MAC，再对按预期顺序连接的二进制 MAC 形成摘要 B。Host 选择二进制放置地址 PC，并把地址序列交给数据方；数据方生成 P1=MAC_KD(PC) 和 P2=MAC_KD(B)。

executeModel 后锁定任务队列和内存。TS 收集已提交任务的 PC_START 序列，以 KD 验证 P1。可信 AI CPU operator 逐个解密认证二进制，根据实际二进制 MAC 重建 B′，再验证 P2；成功后处理模型权重并执行。

关键价值是把“不可信 Host 提交的地址序列”与“模型方授权的二进制顺序”连接，既检查执行入口，也检查入口实际指向的代码；锁定队列避免认证之后再被 Host 修改。

但协议明确展开的绑定主要是 PC_START 和二进制/MAC 顺序。任务还有参数、workspace、长度、DMA 源目的地址、stream 和依赖等安全语义，正文没有完整列出它们如何纳入认证及授权。相同代码指针本身不能证明所有参数和数据流均获准。

同理，数据方对 Host 提供的 PC 做 MAC，不意味着数据方理解地址所有权；安全性仍依赖设备内实际映射、布局和不重叠检查。B 也不等于完整图语义承诺：常量、图拓扑、动态分支和可变 shape 需要按具体编译模型定义。

上述是协议覆盖范围的分析，没有公开实现可用于验证额外检查是否存在，不能据正文省略断言已经构成可利用攻击。对项目最适合借鉴的是建立完整执行契约，而不是把每个 job 都改成远程在线认证。

## 9. 多方互不信任与单租户限制

输出始终使用数据方 KD 加密，模型方即使在输出中编码用户数据，也不能直接通过 Host 解密取走。分离 KM/KD 与受控输出通路是该模型的主要防护。

然而论文明确不允许同一 NPU 多模型租户，也不允许一个模型同时服务多个互不信任推理用户；模型方可能与用户 A 串通，把用户 B 的数据复制进 A 的输出。作者提出页归属标记、动态 taint tracking 和将页表管理移入可信 NPU 作为未来方向，没有实现成本文多租户保证。

这不说明任何多 Client 共享都必须做动态污点跟踪：若各 Client 的状态、GPUVM 和任务相互隔离，不共享恶意模型可同时读写的状态，威胁不同。若项目未来提供跨 Client 模型服务，则须额外定义模型方、用户与服务方的信任关系。

## 10. 固件、调试与中断的边界

控制 CPU 截获 Host 命令，关闭内存检查、调试、profiling 等绕过路径。固件版本参与远程证明，使数据/模型方可以拒绝旧版本；设备不能伪造不可导出的根私钥身份。

版本签名仍需要依赖方策略，不能自动替代防回滚状态。reset、session 结束、授权变更后如何绑定新实例及废弃旧密钥/确认，正文未完整展开。

本文中断分析聚焦 Host 打断锁定/解密或加密/解锁时，可信 TS 不应越过内存管理和算子完成门槛。它没有解决多 VM 间 IRQ 路由、目标身份、重复/迟到通知、ACK/ARM、per-job cookie 或 reset epoch 协议。

因此它支持项目“通知不能授予状态转换权力”的论证，但不能作为多 Realm 中断隔离已经完成的引用。可信 CQ 的来源、归属和当前执行代次仍是迁移时必须说明的条件。

## 11. 实现、公开代码与复现限制

作者修改驱动、固件、CANN runtime、Ascend PyTorch adapter，增加约 2 KLoC。AES-GCM-128 基于 AArch64cryptolib，使用 AI CPU SDK 开发内部 operator；模型方以 TCP server 模拟，提供认证加密模型。

论文的“无需改变 AI 软件栈”应按应用接口理解：既有 PyTorch 用户工作流基本保持，但底层 runtime、adapter、driver 和 firmware 均有修改。不能写成现有任意 AI 软件栈零修改即可部署。

附录 meta-review 明确指出源码和实现不会公开，作者对此项未回应。因此缺少匹配公开 artifact 是论文明确披露的复现限制，不需要把 GitHub 中同名无关项目当作代码。通用 Ascend adapter、SDK 和加密库也不能替代新增 TS/锁定/认证逻辑。

本轮完成全文和元数据核验，没有可固定的 GuardAIn 实现提交，未审计 nonce、DMA 排空、task 参数检查、CQ 身份和异常恢复源码，也没有执行攻击或复现实验。

## 12. 评估设置与作者结果

平台为真实 Ascend 910A。对比普通执行与 GuardAIn；推理包括 GPT-Neo-125M、Llama2 7B/13B、Llama3 8B、CodeLlama 等变体，batch=1；数据为 SQuAD v2，temperature=0，比对普通与保护输出。训练用 ResNet50/152 和 nanoGPT-162M，分别为 CIFAR-10、Tiny Shakespeare。

| 指标 | 作者报告 | 解释和限制 |
| --- | --- | --- |
| 并行 AES-GCM 峰值 | 约 6.1 GB/s，1KB chunk | 大块数据约收敛到 1.6 GB/s；不能把小块峰值套用整模型 |
| 4KB map/unmap | 每次约 2.47 μs | 大模型页数会放大一次性成本 |
| Llama2-7B fp16 映射准备 | 4KB 页约 7s；1GB huge page 约 15 μs/页 | 作者说明优化潜力；不将两种页配置混为同一测量 |
| GPT-Neo setup | 约 50–71%，额外约 0.17s | 相对基线加载时间；短模型 setup 显著 |
| GPT-Neo 推理 | 输入 50/100 token：16.03%/13.74%；2000 token：0.91% | 不能只摘长上下文最低开销 |
| Llama 推理 | 作者总体称各变体低于 0.1% | 长计算摊薄加密成本，非所有加速器/工作负载保证 |
| Llama3-ChatQA 2048 token | 图中约 0.02821% | 是特定配置的推理增量，不是冷启动端到端 |
| 训练 | ResNet152 batch256：3.39×10^-4%；nanoGPT batch4：0.16% | 未训练 Llama 7B/13B，不外推大型 LLM 训练结果 |

Llama2 13B 的更长上下文因 OOM 未测，最多到 2K；其他图存在标为 6114 的横轴，保留作者标注，不擅自改成 6144。Llama3 Base 的 bfloat16→float16 转换抬高加载时间，不能归为新增安全机制的成本。

正文将 1KB 性能拐点解释为 shared L2 cache size，未提供独立硬件配置证据；本报告只保留原文实验/解释，不将此数作为 Ascend 真实物理 L2 容量的结论。动机部分把 KV cache 随序列增长概括为平方也不宜直接引用：固定层数和维度时，常规 KV 存储随 token 数线性增长，注意与 attention 计算/其他中间数据区分。

论文没有完整原始重复数据、置信区间及公开实现可重算极小开销；小到 10^-4% 的训练数字应按作者报告保留，不视作已独立证明的稳定差异。output 一致性和 training loss 不变是功能证据，不等于恶意任务、重放或异常退出的安全验证。

## 13. 扩展能力与证据边界

data-parallel 可在不同 NPU 上独立运行；pipeline 和 tensor parallel 需要加密设备间中间数据。作者指出 HCCS 高带宽下加密量大，需进一步设计，明确将完整 scale-out 排除本篇。

训练通过 ahead-of-time 编译合并 forward/backward/update 子图后认证，并非证明任意动态 Python 控制流都可原样保护。向其他 GPU/NPU/FPGA 推广属于原则与讨论，附录承认某些设备可能需硬件变化，未提供跨平台实现。

正文安全论证是非形式化分析；没有公开完整恶意测试集和逐项实验记录。论文对 PCIe/TDISP、MIG 等其他系统的概括应回到对应规范核验，不能反过来作为这些系统的权威支持矩阵。

## 14. 与项目和相关工作的关系

PORTAL 说明可信服务 Realm 与设备控制，CAGE/ACAI 说明执行保护与身份/映射归属，PhantomMap 强调实际物理页和生命周期；GuardAIn 补充“被授权的任务语义”与“内存对谁开放”的联动，不取代这些既有保证。

MOLE 提醒内部 MCU/固件也影响隔离；GuardAIn 把可信固件、TS、内存管理器和内部 crypto operator 明确纳入路径。其 signed firmware/测量策略不能据此自动覆盖所有设备内部组件和更新链。

Devlore、SHELTER 扩展、Heckler/WeSee/Sigy 侧重事件可信边界；GuardAIn 的 ACK/CQ 门槛说明来源可信只是第一步，还要核对该事件能授权哪项状态转换。没有把不同架构的攻击直接移植成 CCA 已知漏洞。

项目已有 RMM 认证队列、私有描述符快照、独立 GPUVM、真实 native fence、cookie/epoch 和 persistent IRQ127。本文建议在这些基础上明确定义组合性质，没有重新把已有机制写成缺失功能。

## 15. 建议研究的具体设计

第一，给现有执行计划定义完整契约：原始 Client/会话、plan 代次、GPUVM、每个对象及代次、范围和读写权限、依赖、允许的命令类别、终态发布位置。可复用计划和可信元数据缓存都必须在对象或授权变化后失效；不必引入每次远程交互。

第二，把安全边界建成显式状态机：授权建立、实际映射可用、任务在途、真实完成/错误/取消、撤销确认、旧访问停止、清理完成、重新授权。来自 IRQ、CQ 或共享队列的消息只能触发其有权推动的边，不能单凭类型或 sender 可信就跳过前置条件。

第三，把完成链和回收链分别定义：native fence 成功、DMA/缓存输出可见、可信 completion 发布、Client 验证属于当前 job；页面复用还需要旧访问停止及清理。cookie/epoch 约束事件归属，不能自动代替 quiescence。

第四，区分 Client GPUVM 隔离与共享模型内部用户隔离。前者可由项目现有页归属和执行授权支撑；后者如要允许互不信任用户共享可变模型/KV 状态，需要额外服务契约与信息流边界，不能只增加页表条目就宣称解决。

独立评价：最有用的是锁定/解锁的确认门槛、实际算子序列绑定及模型/输入不同生命周期。最明显的迁移限制是单租户、闭源和任务完整认证字段未充分展开。可作为项目任务隔离的强相关对照，但不应以其低推理开销或单设备安全结论代替多 Realm 共享的证据。
