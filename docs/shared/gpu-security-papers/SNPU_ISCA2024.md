## 2. 研究问题及与项目的联系

传统外部 IOMMU 保护主存访问，但无法自动覆盖加速器内部 scratchpad 和核间 NoC。sNPU 讨论正常与敏感 ML 任务共享集成 NPU 时，如何阻断错误的片上数据读取、路由访问和主存 DMA，同时避免整机串行与频繁清空。

对本项目，价值不是直接替换 SMMU，而是扩大安全对象清单：最终 HPA 映射合法之后，还应说明 GPU 内部 SRAM、寄存器、队列、固件状态及切换时的残留由谁隔离和初始化。不同设备的内部结构不同，不能把 NPU scratchpad 攻击直接认定为当前 Mali GPU 的已证实漏洞。

## 3. 威胁模型、信任与排除项

论文不信任正常域 NPU 驱动、调度器、ML 框架和编译器；攻击者可以构造错误分配、指令、地址或路由。可信基包括 CPU TEE 基础、NPU 安全扩展、可信 monitor，以及安全执行所依赖的设备和加载机制。排除物理与侧信道攻击。

“不信任框架”并不意味着任意恶意 kernel 能在同一安全硬件域中无条件共享全部状态。§VII 明确：本文硬件集中在 secure / normal 两个域；多个安全域需要增加 ID 位并承担额外硬件开销。软件层可以进一步管理安全任务资源，但不能把一个 secure bit 等同于任意数量 Client 的硬件身份隔离。

## 4. 总体结构

**NPU Guarder** 负责主存地址翻译与权限；**NPU Isolator** 负责 scratchpad 和 NoC；**NPU Monitor** 负责可信资源管理、上下文设置、代码验证及安全加载。三者分别处理外部访问、内部状态、执行前配置，构成相互补充的边界。

原型使用 RISC-V Penglai、Chipyard、Gemmini 和 AuRORA 启发的互连，利用 FireSim 做 FPGA 加速的周期精确 RTL 系统评估。不能把模拟平台的选择当作要求本项目更换 GPU 的理由。

## 5. NPU Guarder：翻译与授权在 DMA 打包前完成

检查寄存器记录连续物理区域及权限；按计算 tile 配置的翻译寄存器建立 VA→PA 映射。翻译寄存器可在计算前更新，粗粒度授权区域则较少变化。Guarder 位于 NPU 核内、DMA engine 之前，先得到实际 PA 并检查权限，再将合法 DMA 请求拆成固定大小的内存包。

这一位置让一个 DMA 请求只需检查一次，而外部 IOMMU 可能对多个包分别检查。这里的 tile 是 NPU 计算分块，不能误作 CPU/GPU 的普通页大小。原文个别翻译方向措辞存在不一致，本记录按其流程图和微架构的 VA→PA 过程解释。

与 ProxyRealm 的联系是“在可信边界验证最终实际地址和权限”。你的方案把软件 IPA→HPA 检查放在建立映射时，再由硬件 Stage-1 持续约束访问；sNPU 则在设备内用专用寄存器执行每个 DMA 请求的检查。两者的检查位置与生命周期不同，不能由相似思想推导出等价安全性或相同开销。

## 6. Scratchpad：局部与共享资源需要不同规则

对于局部 scratchpad，写入会覆盖数据和 ID 状态，读取要求行标签与当前核的安全状态匹配。对于可由其他核访问的全局 scratchpad，正常域不能读取或覆盖安全行；安全访问会标记安全属性，并由安全机制控制降级。

规则的关键在于“覆盖了什么”：整行重写并初始化可替代旧内容的部分清理需求，但部分字节写入、异常中断和标签更新顺序仍必须满足安全要求。本次没有独立 RTL 审计，不能从摘要推导出所有粒度和异常路径都已验证。

对多 Client，secure / normal 标签只是类别标签。要保护两个互不信任的 Client，仍需 Client 或上下文身份、资源独占/分区、可信切换清理等明确机制；一个共同的 secure 标签不表达对象所有者及其代次。

## 7. NoC：源身份、目的校验和整包生命周期

peephole 机制将发送核的安全身份放入包头，目的核先检查身份；通过后锁定路由，直到整包接收并写入 scratchpad 才释放。可信 loader 还检查任务所需核分配、代码及预期路由，防止不可信软件直接构造跨安全边界的数据流。

这里的 authentication 是可信硬件生成和检查的域 ID，并非抵御物理攻击者的密码学报文认证。锁定到整包完成，也不等同于任务已经成功执行或结果已经可以回收。

对应本项目，可借鉴“提交方身份由可信来源生成、接收端检查归属、通信状态持续到一次操作结束”的原则；不应机械地在共享队列消息里增加一个 Client 自填的 ID，然后称其可信通信。

## 8. Monitor、可信加载与不可信调度

Monitor 包含 context setter、trusted allocator、code verifier、secure loader。分配器管理安全主存与不重叠的 scratchpad；代码验证器检查任务代码测量，安全 loader 建立设备上下文并验证路由。通过安全队列与 trampoline 接受正常域的调度协助。

调度者可以决定何时请求执行，但资源和安全配置由可信侧检查；调度自由不是改变其他任务地址、路由或安全域的授权。项目可以保留 Host 的调度协助，同时确保 RMM 认证的会话身份到 Proxy 对象、GPUVM、真实 fence 的关联不由 Host 或 Client 字段决定。

## 9. 原型与评估条件

评估 NPU 包含 10 个 tile，每个 tile 有 16×16 systolic array 和 256KB scratchpad；系统有 2MB L2、8 个 bank、16GB/s DRAM 带宽，以 1GHz 模型评估。工作负载包括 GoogleNet、AlexNet、YOLO-lite、MobileNet、ResNet 和 BERT。

评估不计入离线任务复制和模型解密，输入设想可来自直接安全传感器。因此作者的接近零运行检查开销不能扩写成启动、模型装载、证明、解密、撤销的全生命周期零开销。

## 12. 对本项目应补充什么

首先，列清“主存映射之外”的资源归属：固件队列、内部存储、寄存器、共享输出缓冲、上下文与 reset 状态。分别注明依赖可信固件、硬件上下文隔离、初始化还是可信清理，不笼统宣称 SMMU 覆盖设备全部状态。

其次，持续维护 Client 会话、上下文和对象的身份关联。RMM 认证原始 Client，Proxy 检查对象及最终 HPA，GPU 使用受保护的 Stage-1；由可信提交记录关联真实 fence。设备内部安全状态如何继承该上下文也应写明。

再次，将完成通知和撤销分开：通知只促使接收端读取可信任务状态；成功、失败、取消和 reset 后的状态各有终态，旧事件不能重新赋予新任务权限。释放资源前必须证明无在途访问、旧映射及旧完成记录不能误命中新对象。

这些是从论文提取的设计要求，不是本轮已实现的新功能。当前基线已记载独立 GPUVM、会话对象校验、真实 fence、epoch 与 RMM 持久通知，后续应针对具体剩余边界补证据，避免重复包装已有机制。

## 13. 可以开展的针对性验证

验证跨 Client 上下文切换前后的可读内部状态、部分初始化缓冲的残留、错误/reset 后资源复用，以及旧队列通知在新会话中能否被接受。每项明确可观察资源和判据；无法访问设备内部状态时记录证据限制，不由主存负例通过代替内部状态证明。

性能方面分别记录映射建立、正常运行、切换、清理和故障恢复，避免仅用长 kernel 吞吐掩盖短任务或高频回收成本。本文没有提供可直接套用的 GPU 中断认证协议，仍须结合 Devlore 等中断安全文献分析。
