## 2. 与本项目的关系和保护目标

PKUS有知识提供方、服务运营方和客户端三个角色。提供方把专业知识编码为LoRA增量，在各自CPU TEE中计算；运营方控制公开冻结骨干和GPU，论文明确视GPU及运营方为不可信。目标是提供方不交出适配器权重，仍允许多个提供方参与推理、更新访问策略并撤销知识。

这一目标与PORTAL/CAGE/ACAI不同：后者直接处理设备访问或可信执行边界，PKUS主动让骨干留在不可信侧。它不提供GPUVM之间的通用内存隔离、可信物理IRQ路由或原生GPU任务完成证明；更适合作为本项目“服务授权、跨Realm数据交换、在途撤销和输出发布”的应用案例。

“专业知识可信利用”需拆成权重存储保密、函数泄露、请求身份/权限、执行结果完整性、撤销后停止新利用、已输出信息不可追回等性质。TEE中保存权重可以支持第一项，不能自动推出其余性质。本文没有独立完整的形式化威胁模型/安全证明，安全对比RQ5主要为定性论述。

## 3. EdgePrune：减少私有计算与边界交互

每个提供方在本地冻结骨干、训练rank8、alpha16的attention/FFN LoRA。按注入站点的权重幅度评估重要性，逐步剪除低重要性站点；每次增加剪枝率，若held-out任务指标仍不低于稠密适配器指标减容忍量epsilon，则保留，直到最大剪枝率或质量约束触发。正文举epsilon约0.5–1个百分点，并非所有任务都采用相同可核验超参数。

设计中的剪枝率定义偏向被移除站点比例，评估文字又称适配器参数比例；每站点参数量不等时二者不同。保留“稀疏注入站点减少CPU计算及GPU/TEE往返”的机制，不把站点百分比直接视为精确的字节/参数缩减证明。

剪枝主要提高效率，并不构成新的安全边界。被保留的私有线性层仍接收外部激活并返回增量；减少站点不能自动防止运营方通过合法接口学习其等效函数。SST-2/MNLI/SQuAD是实用性代理，不是专业私有知识保密性的攻击测试。

## 4. AegisProto：证明、策略和密钥

论文描述最小开源、固定依赖、可复现构建的签名镜像，提供方验证预期measurement；双方协商骨干ID、owner、允许client、到期或最大请求等策略plan，把其hash绑定quote用户数据。随后使用绑定运行时/plan的认证ECDH通道，以AES-GCM上传适配器，owner签名更新策略，并用更新quote反映plan。

这个方向值得借鉴，但measurement证明运行某段程序与证明特定请求被正确授权是两步。需要把quote中的公钥、验证者nonce、实例和策略版本与实际会话逐一核验；只检查quote有效或把planhash放入quote，不足以抵抗旧quote、新公钥替换、实例复制或回滚。最大请求数/expiry还需要受保护计数与可信时间/外部租约，不能交给恶意Host独立决定。

运行期间论文说消息用入驻密钥做MAC并具备端到端机密性/完整性。MAC本身不提供机密性，必须说明额外加密路径、密钥持有者与明文接收方。即便使用AEAD，也应绑定provider、client、骨干hash、注入站点、request/token/batch、序列、session和policy epoch，防止合法消息被用于错误任务或旧实例。

## 5. AlignAgg：聚合公式和实际信任位置

对每个站点s、提供方k，TEE计算 `delta_y = DeltaW * x`，其中DeltaW由两层低秩矩阵乘积构成；聚合把当前有权参与且保留该站点的提供方增量平均，无参与者时为零。论文符号的矩阵命名与PEFT惯例可不同，不影响其线性性质。提供方退出时从参与集合移除，无须重训其他适配器。

论文称骨干只能看到聚合结果，但描述又是runtime向各enclave发激活并收集增量；没有精确定义可信聚合器位置或实现保密聚合协议。如果不可信runtime先收到每份明文delta，再平均，隐藏单个提供方贡献的性质并不成立。需要可信聚合端或发给可信接收者的加密份额，而不只是为每份delta加MAC。

即使仅输出平均值，只有一个提供方时就是原始增量；可选择不同参与子集时还可能通过差分分离贡献。因此参与集合、授权策略和聚合输出泄露模型必须一起分析。移除一个提供方后平均分母变小，其他提供方参数虽然未变，其数值贡献权重会变化，不能宣称其他贡献完全不受影响。

## 6. 条件性线性查询反例：参数留在TEE不等于函数不可恢复

若不可信调用者可向某私有站点提交足够多线性独立输入x，并观察对应单提供方增量y，就能恢复等效矩阵DeltaW：选择输入基向量即可逐列获得；一般观测可写成 `Y = DeltaW * X`，当X满行秩且数值精度足够时可求右逆得到DeltaW。恢复低秩因子的原始唯一分解并非必要，等效更新函数已足以复用知识。

这是带前提的代数反例，没有执行模型提取攻击，也不宣称正常文本请求一定产生所需满秩输入。关键是论文显式允许不可信GPU生成激活，却没有展示激活与合法骨干执行/客户端请求来源的可信绑定；所以“权重不出TEE”不能直接支持无条件的模型知识保密结论。仅验证client ID也不等于授权其对所有激活任意查询。

可行方向包括缩小允许接口、绑定真实任务与激活来源、可信聚合、限额和输出泄露评估，或将敏感计算及聚合放入可信GPU执行域。限额只能降低采样机会，不是一般性的函数保密证明；即使合法客户端也可能从允许输出中学习模型，需要明确安全目标允许的泄露。

## 7. 不可信骨干与端到端结果完整性

TEE正确返回对某输入的delta，只能证明这一段局部计算。运营方控制GPU时仍可替换骨干权重、构造激活、遗漏某提供方、重排层次、忽略合法delta或修改最终输出；论文没有展示类似可验证线性外包/完整模型验证的闭环。因此不能把通道认证写成最终推理正确性保证。

同理，prompt和中间激活在不可信GPU侧可见，不应把提供方适配器保护扩写成客户端prompt或整条LLM推理的机密性。基座公开不意味着其执行结果自动可信；MAC验证成功也不能验证消息内容与正确骨干执行的语义关系。

本项目若GPU及执行链在声明的可信边界内，受保护的Stage-1映射、页表根、固件和MMIO能支持不同目标。应清楚声明哪些调度/解析/驱动属于TCB、哪些Client可恶意，以及任务间信息流和输出归属，不能照搬PKUS不可信GPU的安全结论，也不以其x86载体否定CCA目标假设。

## 8. 撤销、清理和“provably erased”的限制

论文称收到撤销立即拒绝后续请求、使用编译器barrier清零适配器/策略/中间缓冲，最后quote包含撤销标记，并称知识可被“provably erased”。测量清理程序不等于证明所有实例的新鲜清理状态：需要验证者nonce、实例身份、策略epoch、回滚/复制约束、外部密钥释放或租约，以及旧密封载荷重启后的准入规则。

新鲜quote可以支持“可信代码报告这个实例完成了所定义的清理”，不能追回Host/GPU已得到的delta、复制缓冲或已导出的知识，也不能仅凭一个实例的报告证明所有副本消失。未收到quote时应标记无法确认，而不是推断具体清理状态或成功。

异步调度使撤销还涉及在途任务：明确禁止新准入的时刻、已准入任务可否继续、delta和最终结果可否发布、何时释放引用并复用缓冲。仅清TEE私有页不能取消Host/GPU已获得的输入输出或未完成DMA。对本项目，epoch失效与设备真正静默是两个条件，必须经过native fence真实终态、缓存/映射撤销与安全回收。

## 9. SwiftSched：异步、批处理及依赖约束

论文并行执行GPU的 `W*x` 与TEE的 `DeltaW*x`，用通信线程和每层队列调度，消费输出前同步；把连续attention/FFN片段的多个注入站点打包，预取下一层激活，按提供方延迟调节粒度并工作窃取，复用二进制缓冲降低序列化成本。

同一站点的基座线性计算与LoRA增量可以并行；不同站点却不一定独立，例如FFN后续投影和下一层激活依赖前面的delta。只能批处理已就绪的独立工作，不能由“连续站点”推出可同时预取全部真实输入。论文未给出所有模型依赖的形式化调度证明，性能结果也不证明任意改排均保持语义。

工作窃取应只迁移有权执行的任务，不能跨provider私有状态。延迟响应必须绑定站点、token、provider、request及generation，固定可重用buffer需防旧响应写入新任务。Host队列ACK、发送成功与GPU真实完成分别定义；这与本项目中断仅作唤醒、完成记录决定状态的方向直接相关。

## 13. 候选原型：安全传输模块尚未接入推理

根README给Python3.12/CUDA12/PyTorch2.7 cu128/QEMU8.2.2/libvirt10，并要求手工配置Host/Guest模型路径和ivshmem；clone命令却指向SEC-bench/SEC-bench再cd pkus，来源对应仍有限。protocol README标题为“SMCP – TDX Edition”，明确当前集中数据传输，而会话初始化、能力协商、协议完成、动态修改、优雅退出、撤销仍开发中；AMD SEV/TrustZone/Kunpeng适配列未来工作，与论文SEV完整AegisProto叙述需分开。

`client.py` 的Host路径先从模型读取LoRA权重/配置，经明文ivshmem发Guest；Guest接收后建立私有线性层。它没有调用protocol模块的ECDH/quote/AEAD。因此这条具体路径不能作为“提供方私有权重从不被不可信Host掌握”的实现证据。未剪枝Host路径部分权重载入被注释，默认TEST_OUR_METHOD为False、模型为8B instruct，也与论文主测774M/1B不同，不能直接用默认运行复现论文表格。

`model_def.py` 先完成base_layer，再发送激活并阻塞等delta，加到结果；所读路径没有并行 `W*x` 和delta的调度。请求和响应msg_id固定0，响应站点标识没有与发起站点核对；未看到将provider/client/policy epoch/session/token绑定的认证记录。不能从此证明完整SwiftSched已公开实现，也不能把它的存在等同论文方法无效。

多线程分支创建32个worker，共享同一guest_lora_model，每个接收同一请求；收集全部32个结果后仅返回 `results[0]`。这是同一模型重复计算，既不是32个隔离enclave/独立provider的实现，也没有把多个知识增量正确平均。它不能验证表4多CVM扩展性、AlignAgg隔离或安全工作窃取。

`ivshmem_comm.py` 是直接序列化tensor与模块名的共享内存分块协议，锁调用被注释，未接MAC/AEAD或消息epoch。header包含msg/seq/length并不等于可信绑定，重组主要排序后拼接；没有完整检查同一请求、连续唯一seq、长度上限和站点授权。角色flag/零header分支在原offset继续循环，恶意或故障对端可使等待无界；clear_shm仅清16字节，不是清空16MiB，更不等于安全销毁全部权重。以上为静态观察，无攻击复现。

## 14. 候选原型：quote、AEAD与运行缺口

ECDH辅助函数采用P-256及HKDF-SHA256，info固定，salt=None；这种KDF选择本身不能直接定性为漏洞。生成quote确实hash所给公钥/数据并交外部TDX工具，但所读验证函数主要解析外部pipeline的JSON；调用方只检查success，未比较quote reportdata与实际peer公钥hash、期望measurement、challenge或策略。外部工具源码未取得，不能声称它永远不做任何验证；但当前调用接口没有传入这些预期绑定值，不能据此证明完整认证ECDH。

代码还存在明确的未完成接口：query_app在定义Flask app前使用app.config/SocketIO；导入verify_quote却调用quote_verify；stream server使用os.mkstemp而非tempfile.mkstemp；quote生成返回字段没有success，调用者却索引该字段；验证辅助文件string路径缺base64导入。这些足以说明所读版本不应被当成开箱即用生产协议，本轮未执行来触发异常。

AESGCM.encrypt返回ciphertext与tag拼接的bytes，server却写 `ct, tag = aesgcm.encrypt(...)`，不能按预期拆分；START/EOF和普通chunk帧格式也不一致，TCP recv没有完整定长读取。AEAD没有AAD绑定chunk序列、请求或协议阶段，成功解密本身不保证流的顺序/完整性。修正语法/分帧之后仍须补协议，不能认为“换AES-GCM”即可完成可信通信。

HTTP data-request路径返回base64明文和quote，base64不加密；data-query未显示将返回data hash与quote claims匹配。data_name直接拼路径、quote验证shell拼接文件名且pipeline未显式pipefail等扩大了输入审查面；不把这些静态输入条件写成已执行利用。create_vm只是常规virt-install命令，所读片段未显式启用SEV launch security；start_vm未读，因此不据此断言整个仓库没有任何SEV配置。

11个文件与完整21项树未展示EdgePrune训练脚本、所有CVM隔离编排、完整撤销和实验原始数据。把缺失明确记录，比以不完整候选代码替论文补全安全证明更可靠；同时不把后续候选缺口倒推为作者2025评估必然使用同一版本。

## 15. 对当前CCA GPU项目的设计建议

继续采用RMM认证原始Client、可信ProxyRealm统一管理SMMU，映射建立时核对对象归属、真实HPA授权、权限和生命周期，软件IPA→HPA合成受保护的GPU Stage-1，其他设备维持硬件Stage-2。平台保护页表、根配置、关键MMIO和固件，硬件作为模拟测试载体；这里不新增另一套身份或地址授权体系。

第一部分直通/共享及性能：复用GPUVM、认证队列、私有plan/snapshot，批处理仅合并已授权且依赖满足的工作；记录实际提交、GPU执行和通知成本。驻留/共享buffer不能把另一Client的权重、激活、KV或旧输出带入新任务；公平预算和尾延迟也纳入设计，PKUS的x86秒数和加速比不作为本项目预期成绩。

第二部分内存/中断通信隔离：把原始Client、GPU上下文、任务cookie、对象/策略epoch和native fence终态关联起来，真实完成记录决定输出发布与引用释放；持久IRQ127只作唤醒核验。共享内存flag、Host ACK或收到中断不单独决定任务成功，旧通知不能匹配新任务，丢失通知可通过受保护完成状态恢复。

撤销按“停止准入—处理在途任务及发布规则—确认native fence或可信reset完成—撤销映射/缓存—安全清理及释放”定义状态转换。epoch拒绝旧消息不等于阻止旧DMA，清某个Realm私有内存不等于清所有设备及共享副本。设备/队列重置后的generation和旧cookie也要失效，保持与当前已有身份及队列机制一致。

区分任务间隔离与应用合法输出泄露。受保护HPA不能防可信服务主动把A的结果写给B；对类似PKUS的服务，可在既有授权入口绑定客户端权限、输入/输出对象、模型/策略版本与允许聚合集合。若应用仍主动向不可信方输出敏感线性响应，则须另立泄露模型，不能把通用设备内存隔离当作模型防提取证明。
