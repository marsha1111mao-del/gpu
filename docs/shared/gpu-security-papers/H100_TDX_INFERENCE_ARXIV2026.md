# H100／TDX 机密推理基准：吞吐分母、饱和拐点与安全配置证据

## 2. 研究问题与两个负载模型

作者研究开启机密计算后服务容量和用户时延怎样变化。固定请求率实验使用Mistral-7B v0.1的10req/s和Qwen3-30B-A3B的5req/s；闭环实验维持N个在途请求，完成一个立即补一个。前者能暴露给定到达率的排队，后者观测在途压力下吞吐随并发的变化；二者不等价。

Mistral为较小dense模型，Qwen为总参数30B、激活约3B的MoE。两者还可能在精度、上下文、输出长度、kernel、KV占用和批处理上不同。因此只能说所测Qwen配置表现不同，不能把差距单因归给“模型更大”，也不能用激活3B直接预测完整驻留权重或安全开销。

闭环每个并发点三个trial，吞吐取trial均值，TTFT/端到端时延取各trial p50的均值。这不是合并所有请求后的p50，更不是p95/p99。固定率表含平均和p50，但未充分说明相同的三trial规则是否也适用于固定率实验。

## 3. 平台与安全状态的证据强度

作者列GCP us-central1-a、a3-highgpu-1g、26vCPU、234GB RAM、单H100 80GB、250GB balanced disk；镜像为`ubuntu-accelerator-2404-amd64-with-nvidia-580-v20251021`，CC实例类型Intel TDX，Secure Boot关闭。

论文主动声明不证明完整生产安全配置，这是必须保留的边界。Secure Boot关闭不等于已经证明所有TDX或GPU保护关闭，但不能将这组性能数据描述为经过完整启动链、设备证明及密钥策略核验的端到端安全部署。镜像名称里的580也不是独立读取的实际驱动/CUDA/固件版本证据。

文中没有附GPU CC模式查询、GPU/CPU证明报告及验证策略、nonce新鲜性、固件度量、证书状态、SPDM会话或实际密钥释放日志；也未给Non-CC实例完整等价配置、是否同一物理卡、VM重建顺序、功耗/频率、测量时段与租户干扰。可以报告“作者标注CC/Non-CC的系统级对照”，不能把每一个安全机制都当已独立核验。

本次请求论文引用的Google Cloud配置页失败，错误为`Network is unreachable`，完整请求记录保留于`acquisition-batch88.json`。因此上述平台要求来自论文，未把未取得的现行官方正文当作独立交叉验证，也不据失败猜测当前云平台支持范围。

## 4. 指标定义：吞吐差距不等于下降百分比

论文对时延用`(CC−NonCC)/NonCC`，对吞吐则用`(NonCC−CC)/CC`。后者回答Non-CC比CC高多少，计算自身明确，但摘要/结论用“throughput drops”容易被读成通常以Non-CC为分母的损失。

| 指标 | Non-CC → CC | 作者以CC为分母的gap | 以Non-CC为分母的下降 |
| --- | --- | --- | --- |
| Mistral全局tok/s | 1458.65 → 1239.26 | 17.70% | 15.04% |
| Qwen全局tok/s | 993.80 → 820.31 | 21.15% | 17.46% |
| Mistral单请求tok/s | 28.50 → 25.18 | 13.19% | 11.65% |
| Qwen单请求tok/s | 50.20 → 43.85 | 14.48% | 12.65% |
| Mistral并发100 req/s | 1.54 → 1.32 | 16.67% | 14.29% |
| Qwen并发40 req/s | 1.01 → 0.84 | 20.24% | 16.83% |

换算来自印出的表格，记录于`h100-arithmetic88.json`，不是新增实验。若gap为g，传统下降为g/(1+g)。闭环11.5–20.2%的作者gap大致对应10.3–16.8%的基线下降，不应原样当成相同定义的项目损失。

## 5. 固定率时延与单位问题

Mistral平均TTFT 279.56→340.64，增加约21.85%；端到端314.72→381.04，增加21.07%。Qwen平均TTFT 394.61→504.35，增加27.81%；端到端414.51→527.18，增加27.18%。Table2和Fig1的数值对应，正文约21–30%的定性比较成立于所测配置。

§3.3明确写固定率输出单位是秒，闭环是毫秒；Table2本身没有附时延单位，Fig1两个时延面板也没写单位。报告按作者文字保留秒，不能因为数值看起来较大就替作者改成毫秒。需要匹配输出字段和计时实现才能排除单位标注问题。

固定率10/5req/s显著高于闭环所列最高约1.54/1.01req/s，但未给足输入输出分布、持续时间、并发限制及拒绝/超时策略来确认负载等价。可能是工作负载不同、过载排队或其他报告差异，本次不能选一种当事实；更不能将两组点直接拼为同一条服务曲线。

全局tok/s与单请求tok/s的比值也不能简单当活跃请求数，除非明确统计时间窗、输出token口径和平均权重。TTFT是否包含客户端排队、网络、tokenization、prefill及服务等待，需要计时边界，而非仅指标名称。

## 6. 闭环吞吐与饱和拐点

Table3的Mistral并发32/48/64/80/100：CC吞吐1.12/1.18/1.26/1.28/1.32，Non-CC为1.27/1.37/1.42/1.52/1.54req/s。最高两点仍有增长，支持边际收益变小，不能证明已找到全局最大容量；也没有并发更高点或误差条确认80–100为唯一精确拐点。

Qwen并发24/32/40/50：CC为0.78/0.84/0.84/0.84，Non-CC为0.87/0.97/1.01/1.01req/s。按两位小数，CC从32起持平、Non-CC到40才持平，支持所测采样范围内CC更早出现平台。并发采样稀疏、无方差和低层计数，不能定位为严格32或归因到PCIe、HBM、加密引擎或某一队列。

对本项目可迁移的是同时测吞吐和排队，而不是照搬单H100的并发阈值。多个Client共享GPU时总在途、每Client在途、任务长度、公平调度和可信通知延迟共同决定曲线；总吞吐稳定也可能掩盖某个Client饥饿。

## 7. TTFT异常及表内算术核查

Mistral并发32/48时，CC p50 TTFT分别1186.7/1218.9ms，Non-CC为1472.0/1586.4ms，约低19.4%/23.2%；但其吞吐仍较低、端到端时延仍较高。这不支持“开启CC使推理整体更快”，可以是调度/排队等因素，作者没有剖析来确认原因。

Qwen并发32时，CC TTFT为20823.1ms，Non-CC为2874.1ms。Table4写“725.0% higher”；同表比值为724.51%，实际相对增加为624.51%，约7.245倍。正文将其保留为饱和异常合理，但百分比文字不能照抄。相同点端到端41187.0/22114.2ms，增加约86.24%，与表列86.2%相符，两项问题不可混为一谈。

并发40/50的Qwen TTFT差约9.7%，不应为了得到平稳均值删除并发32结果。可以分运行区间报告并解释待查，但异常仍是容量与尾延迟相关的重要证据。没有p99或原始trace，不能判定其是否只有单点抖动、持续长尾或trial聚合效应。

## 8. 端到端时延、统计与容量规划

Mistral所有所列闭环点CC端到端p50增加约12.3–15.6%；Qwen除并发32外约8.9–9.1%。这些是trial p50平均值的相对变化，不代表每请求上界、最坏调度等待或所有流量分位。

作者建议类似部署初始预留15–25%吞吐容量，再用自身流量验证。这个启发可以解释为弥补现有CC容量与Non-CC差值的资源增量，不能无条件等同于损失比例；还应考虑SLO、成本线性、批处理和GPU份额是否可连续扩展。没有本项目测量，不能据此为Arm共享GPU承诺固定预留率。

Little定律若用于检查闭环，应使用同一稳态窗口的平均在途数、完成吞吐和平均响应时间。附录只有p50的trial均值，不能用`N/X`与该p50不相等判实验错误。应要求补齐真实平均值和时间窗再做一致性审计。

## 9. 缺失的复现实验条件与因果归因

没有足够推理引擎/工具固定版本、模型revision、dtype/量化、输入输出token分布、stop条件、batch上限、KV配置、预热、运行长度、超时/错误率、trial顺序/随机化、置信区间及原始请求日志。模型名称和机器类型不足以重现表中精确值。

本文明确未剖析PCIe传输、利用率、HBM带宽、kernel、CPU-GPU复制和scheduler内部。相关工作观察CPU-GPU传输开销不等于本文已证明同一瓶颈；测得系统差距可能包含多个组件。也不能通过一组CC/Non-CC对照把TDX成本与GPU保护成本相加拆分，需分层控制实验或路径测量。

对照还应记录完整启动、GPU ready/证明、模型加载、warmup、稳态、排空和销毁时间。本文主要稳态服务，不支持模型切换、跨Client清理、reset恢复或证明会话建立成本已接近零。

## 10. 与PORTAL／CAGE／项目安全设计的关系

本文评估厂商TDX/H100机密实例的服务成本，不引入Realm管理、软件Stage-2授权或跨VM共享协议。因此它适合项目第一部分“直通/共享实现和性能评估”的方法学，不能作为第二部分“内存/中断隔离”的安全证明。

本项目假设继续接受：可信RMM认证原始Client；ProxyRealm统一控制SMMU，按对象归属、实际HPA、权限和生命周期完成软件IPA→HPA并建立受保护GPU Stage-1；其他设备保持硬件Stage-2，实际页表/root/MMIO及可信固件由平台保护。不以H100与实验Arm GPU的不同否定这套架构。

已有GPUVM、认证队列、private plan/snapshot、native fence、cookie/epoch与IRQ127应继续作为任务身份和通知链的基础。本论文没有证明GPU中断真实归属，也未验证多Client、旧映射重用、迟到IRQ、reset后DMA静默或恶意Host干扰。这些缺项不因CC吞吐可用而消失。

## 11. 建议吸收的项目设计与评估

第一项是带可信任务身份的阶段计时：区分Client提交、Proxy授权/快照、可信接受、原生排队、GPU执行、native fence终态、输出可见、通知发布与Client消费。跨时钟域的差值必须校准或使用同域跨度；不把不可信时间戳作为安全裁决依据。计时是诊断，权威状态仍由可信组件维护。

第二项是按Client的有界在途与公平性评估。报告1–N Client总吞吐、每Client份额、等待分布、拒绝/超时和异常恢复，覆盖短长任务混合及一个Client持续施压。调优窗口不能省略实际HPA/权限/generation核验，也不能以未认证提交量强迫可信Proxy无限分配资源。这里是研究建议，不声明当前基线缺失或已经实现。

第三项是把通知与终态分开验证。可以测重复/合并/延迟通知对性能影响，但必须保持可信终态可查询，cookie/epoch绑定原任务，迟到IRQ不能推进新任务。IRQ到达不等于job成功、输出可见、计算正确、DMA静默或安全复用；时延曲线不能替代这些负例检查。

第四项是有条件的矩阵对照：性能主线先遵循现有完整720p门槛和正确性/资源恢复流程，再开展获准的计算/LLM实验。本文研究没有启动任何硬件测试，不用文献百分比替代本项目glmark或ML记录。若以后做消融，应一次定位一个阶段并保留失败/未执行项，避免把调度变化误归为安全检查成本。

## 12. 证据结论与后续研究

本文支持一个有限但实用的结论：作者所测单H100/TDX服务配置存在系统级CC差距，且所测Qwen更早出现吞吐平台。它没有证明统一GPU安全税、完整安全部署、底层瓶颈或跨VM隔离；吞吐分母和Qwen异常百分比应明确纠正，单位问题等待匹配artifact确认。

继续追踪匹配`cc_benchmarks`、请求级数据和安全状态记录；不因暂未找到仓库阻断对全文论证的分析，也不把有界检索写成无实现定论。下一轮直接CCA/GPU隔离全文仍优先于无限扩充一般LLM性能文献，FlexClave、XpuTEE、GR-T正式版等缺全文项继续保留。
