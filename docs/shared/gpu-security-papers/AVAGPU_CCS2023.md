## 2. 它解决的是哪一类隔离

内存机密性与完整性成立，仍不保证 GPU 任务能够开始、持续执行和按时交付结果。恶意 OS 可以降低频率、延迟命令提交、操纵页表和 DMA，或者不断提交任务挤占计算资源。AvaGPU 将这些路径一起纳入安全关键 CPS 任务的计算可用性问题。

核心设计由三部分组成：可信 CPU/GPU 协同调度；对 GPU 代码插桩，实现保存上下文后的自暂停和恢复；可信精简驱动、资源管理及 MMIO 请求审核。它把调度与进度条件提升为安全机制，而非只作为性能优化。

这与项目“直通与共享实现/优化”和“GPU 任务内存及中断通信隔离”的划分兼容。它尤其支持在第二部分增加可用性边界的讨论，但不要求项目立即承诺硬实时、移植整个插桩编译器或放弃已有 native fence 路径。

## 3. 威胁模型、假设与排除项

攻击者完全控制 REE 的软件与内存，可利用非安全 GPU 任务的漏洞，在该任务地址空间内读写和劫持控制流。可信基包括安全世界软件、Stage-2 管理、定制 GPU 编译器、硬件、可信定时器及固件；设备初始化纳入 secure boot。设计者拥有 GPU 任务源码，任务在可信机器上编译，安全任务 WCET 应可获得。

物理、密码、算法复杂度及侧信道攻击排除。安全任务计算可用性也不等于完整 CPS 的传感器、网络、电源和物理环境均可用；论文明确将其与 CPU 系统可用性支撑工作组合。

基本模型把安全 GPU 任务视为可信，REE GPU 任务不可信。第 9 节另讨论并实现互不信任安全任务的扩展；不可把基本设计自动概括为任意多租户任务都已在相同开销下隔离。

## 4. CPU/GPU 协同调度

CPU 使用 world scheduler 与各 world 内部调度的层次结构，GPU 使用扁平调度。CPU 进入安全世界执行时，优先对应安全 GPU 工作；在一个安全域内，GPU 任务继承关联 CPU 任务优先级。原型 world scheduler 与安全世界 scheduler 使用 RM，可信物理定时器触发调度。

优先级耦合避免 CPU 任务已获资源、其 GPU 子任务却被低优先级工作长期压住。作者也承认这种紧耦合不一定性能最优，算法优化留待后续。论文的 RM/利用率设置不能直接成为项目任意多 Client 场景下的可调度性定理。

项目中的 Client/vCPU、Proxy 请求处理线程、GPU 调度和完成通知是不同资源层。即使 GPU 调度公平，Proxy 工作线程或目标 Client 没有 CPU 时间，端到端延迟仍无界；分析应写清每层的可信性及资源前提。

## 5. 软件抢占：任务必须主动到达检查点

编译转换先将超量逻辑线程工作放入软件队列，用可并发驻留的线程反复取工作，减少硬件排队线程引入的抢占延迟。再插入抢占信号检查：任务保存寄存器到安全内存，退出执行；恢复时重建上下文，保留原有内存状态。

原型按任务释放周期的最大公因数安排检查，用 LLVM 插桩和 clock64 对基本块/语句做时间定位，循环中保证存在检查点；长数据传输也分割以支持抢占。它不是无需修改任务的任意指令级硬件抢占，能否维持原程序同步语义仍依赖正确编译转换。

论文使用资源表记录寄存器、共享内存和线程需求，附录 Algorithm 1 用四维 DP 尽量减少同优先级被抢占任务数。公开伪码未完整展开不可达状态、初始剩余资源和“至少释放所需资源”的边界处理；不能未经核实直接当作可部署资源分配器，也不能由表的维数推导出实际调度时间上界。

## 6. 代码签名不能阻止所有运行时绕过

非安全 GPU 任务必须携带可信开发流程生成的签名。验证前先使 REE 中代码页只读，避免验证后再修改；后续重复加载可比较已验证摘要，减少公钥操作。抢占信号对 REE 也只读。

签名约束的是被加载的代码，无法单独阻止任务内存安全漏洞劫持控制流并绕开抢占检查。因此论文监测可信任务的计算进度：安全任务到达检查点时更新安全内存变量，可信定时器检查它是否按预期变化；超时后暂停响应正常的非安全任务，并通过指定硬件 channel reset 停止不响应任务。

这是基于后果的检测与处置，不是对所有非安全任务内存安全的预防证明。进度延迟在真实系统也可能来自错误 WCET、缓存/带宽变化或设备故障；检测点未通过不自动证明某个 Client 就是攻击者。论文的保守策略可能影响正常 REE 工作，作者明确讨论此取舍。

## 7. 检查点优化与实时保证的条件

模型为每个任务给定截止时间 d、原执行时间 e、GPU 时间 g，插入 n 个检测点，每次检测开销为 Δc。约束包括总和 (e+nΔc)/d 不超过指定利用率上界，以及 e、相邻检查点间最长潜在延迟和检测成本之和不超过截止时间；目标是最小化全部检测开销。

附录 Algorithm 2 使用遗传算法寻找检查点数和位置，属于启发式求解，不能由此宣称获得全局最优。作者对三个、各含三项任务的集合观察到少于 2000 次迭代收敛，检测成本从 43.98% 降到 3% 以下；不是所有工作负载都享有该结果。

主文公式没有把可信定时器抖动、进度变量可见性、channel reset 完成、在途 DMA 停止和恢复成本逐项独立展开。移植时必须明确哪些已经包含在 WCET/余量中，不能只拿“最大检查间隔”充当完整端到端最坏延迟证明。采样平均耗时和有限轮次零 miss 同样不能替代 WCET 证据。

## 8. 可信资源管理与命令私有副本

REE 不可直接修改 GPU MMIO；配置请求进入 TEE mediator，按 OEM 策略审核。GPU 页表和目录受保护，REE 可读但不可直接写；写请求进入可信管理器，检查物理范围与目录指向，阻止 REE 指向安全内存及安全任务页表。

环形队列管理放入 TEE，REE 命令缓冲区与 TEE 命令缓冲区分开。成组提交后将命令复制到可信缓冲区，GPU 从可信副本取命令；仅在 GPU 忙且 ring 非空时采用批量同步，避免空闲设备等待凑批。

这一思路与项目已有可信私有快照直接呼应。安全依据应是被授权的私有内容及生命周期；“已经复制”本身不覆盖描述符内所有地址、长度、间接命令与权限。论文没有展开任意命令语言的完整验证证明，不应自行补成此保证。

通用设计另有 DMA reference monitor 检查源、目的及长度，防止安全 GPU 上的非安全任务访问安全页。但第 5 节明确：Nvidia 原型 DMA 使用虚拟地址，因此未按 Arm 物理地址 DMA 情况执行源/目的检查；该部分包含 monitor framework，不能称为已在原型完整验证所有 Arm DMA 路径。

## 9. 实现与 TCB 口径

原型为 Jetson AGX Orin，12 个 Cortex-A78AE、2048 CUDA cores、32 GB RAM；LLVM 17、CUDA 11、Linux 5.10.65-tegra、OP-TEE。预留 16 MB 安全区域放 GPU 页表与 Stage-2 表，迁移 nvgpu GPUVM、MMU 及命令/ring 管理，利用预先记录的 MMIO 序列和运行时资源地址完成 replay。

录制阶段还区分普通调用和中断处理 MMIO 序列；中断相关序列只在中断触发后 replay。该事实说明作者注意设备事件驱动顺序，并不等于完成了多 VM 事件身份认证、重复/过期通知检查和逐 job 成功状态绑定。

论文新增运行时可信代码 7,301 LoC，其中精简可信 GPU driver 5,331 LoC，对照 nvgpu 的约 46 KLoC。定制编译器另列 4,212 LoC，且在威胁模型中可信；OP-TEE、固件和安全应用也未被 7,301 全部代表。不能把增量行数当作整个系统 TCB。

## 11. 中断防护究竟覆盖到哪里

第 7 节指出，攻击者可大量触发 REE 中断拖延调度。作者将 REE interrupt handling 放入固定周期预算任务，并在 CPU 调度分析中容纳该预算耗尽的情况。这是预算化处理中断干扰的直接相关证据。

它处理的是不可信中断造成的执行资源消耗，没有给出项目所需的完整多 Client 完成事件协议。设备 IRQ、可信进度检查、job 终态、面向某 Client 的通知是不同对象：进度点只说明到达某处；收到 IRQ 不证明目标 job 成功；超时终止也不意味着旧 DMA 已排空。

项目已有 RMM 身份认证队列、私有快照、GPUVM、native fence、cookie/epoch 与 persistent IRQ127。增量研究应在这些基础上明确：哪些可信状态转换可以发布完成、事件绑定哪个 Client/job/epoch、重复唤醒是否无害、通知抑制或风暴如何受预算限制，以及 reset 后何时允许复用页与任务标识。

## 13. 对当前设计的研究建议

建议优先写成“可信完成与受控干扰”契约：可信提交状态允许进入执行，真实 native fence/设备终态允许进入完成，输出可见性满足后发布 Client 记录，通知只推动 Client 检查记录；超时进入错误/取消和停止访问流程，达成回收条件后才改变 epoch 和复用资源。

可另定义每 Client 的在途任务、请求处理、通知和错误恢复预算，分析一个 Client 占满队列、触发重复通知或长任务时，另一个 Client 还能获得哪些资源保证。预算、通知合并或定向投递不得改变已有 job 语义和真实完成依据。

若未来明确需要有界服务延迟，再增加可信 WCET/预算假设、抢占或终止能力、可信定时器及完整恢复时延模型。仅凭 round-robin、IRQ 定向投递或论文的 69% 数字，不能承诺恶意工作负载下硬实时。

项目仍采用用户给定的可信 ProxyRealm 统一控制 SMMU、RMM 认证原始 Client、建图时授权并软件合成直接 HPA Stage-1 的假设；AvaGPU 的 CPU Stage-2 与 TrustZone 安排是其实现选择，不用于否定项目隔离模型。
