## 2. 要解决的问题：访问合法仍可能留下敏感派生数据

原文以神经网络特征、AES 密钥及明文为例：敏感输入经过 GPU 计算后，会在寄存器、local/shared/global memory 中产生派生值。只擦除最初的输入缓冲区，不一定擦除这些副本。跨任务或跨进程资源复用时，后来的程序可能读取残留。

论文也研究 CPU-only 污点跟踪的缺口：数据经 GPU 计算后返回 CPU，若 GPU 上传播未跟踪，CPU 可能错误认为结果不敏感。它尝试扩展信息流可见性，而不是重新实现 MMU/SMMU 的地址授权。

§2 关于 MPS 进程互读、分配后数据残留的陈述对应当时 NVIDIA 软件与 GPU，不能直接写成当代所有 MPS、MIG 或 Mali 平台都存在相同漏洞。项目应通过明确的目标机制假设及独立验证确认残留边界，不以旧平台个案推翻目标设计。

## 3. 机制：静态改写二进制，动态维护污点

工具先分析 GPU 二进制和控制流图，再插入跟踪指令；原程序运行时，各线程维护实际污点传播。静态分析确定哪些指令可能需要跟踪，动态状态决定本次执行中哪些值真的敏感。这两种状态不能混为一谈。

典型数据传播规则为 `T(v) = T(v1) OR T(v2)`。加载还需考虑被读取位置与地址寄存器的污点；赋常量时可能需要清除旧污点。§3.1 的循环例子明确保留 `R0 = 0` 对应的清标记操作，否则上一轮迭代的污点会错误遗留。

以一个 bit 表示“是否受指定输入影响”不同于记录“属于哪个 Client”。多个 Client 的数据混合时，单一 bit 不能表达来源集合、接收方权限或授权解密分类。项目的 owner/generation/permission 元数据仍不可省略。

## 4. 两遍分析：减少跟踪工作，而非放宽隔离

§3.2 实际先执行 backward pass，再执行 forward pass。后向分析维护 `mightSpread`：值是否可能传播到内存 sink；前向分析维护 `taintTrack`，包括可能带污点以及必须处理的去污点状态变更；间接寻址另记录 `addrTrack`。最终主要对同时满足传播和可达条件的操作数插桩。

Figure 3 将前驱基本块出口的寄存器状态作并集，Figure 4 从后继基本块入口状态反向传播，通过迭代获得保守可达信息。这里是建立在所建 CFG 和已建模指令语义上的数据流分析，不是对任意 GPU 二进制、动态控制流和整个设备固件的形式化安全证明。

原文把线程/block ID、某些 kernel 参数、常量及其地址运算作为不可能由所选污点源污染的值，以过滤大量指令。这是相对于 source 定义的结论。只读并不等于不敏感：如果模型密钥本来就作为只读参数或 constant memory 输入，必须将其纳入 source 模型，不能沿用“只读所以无需跟踪”的简化。

后向 sink 裁剪还需区分两种任务：正常执行中的显式输出，与退出后的寄存器残留。一个不再写回 global memory 的敏感寄存器仍可能是下次任务可见的残留。因此用于数据流优化的 sink 集合，不能未经论证直接成为安全擦除的完整对象集合。原文 §5.3 说明清理使用 forward-filter 结果；本轮未取得匹配源码，不能确认每个该类边界都已覆盖，也不据此声称发现可利用漏洞。

## 5. 污点元数据：寄存器换取低延迟

§3.3 将寄存器污点图本身放进额外的通用寄存器，每个 32-bit 寄存器保存最多 32 个被跟踪寄存器的污点状态。这样避免频繁访问较慢的 shadow memory，但可能增加寄存器压力、降低 occupancy 或引发 spilling。作者样本每线程通常不到 64 个原始寄存器，污点位图最多额外两个寄存器；这不代表插桩全部临时状态只需两个寄存器，也不是任意程序的保证。

对不可信 GPU 程序进行安全强制时，shadow state 与跟踪指令自身必须不可被绕过、覆盖或伪造。论文提出了可信插桩工具的必要性，但没有给出 CCA Realm、远程证明、恶意驱动隔离、设备固件保护及任意 shader 的完整防篡改链。一个 GPUVM 内可写的普通 shadow 缓冲，不会仅因其名为安全元数据就受到保护。

## 6. 用例一：按生命周期清理敏感残留

§4.1/§5.3 对线程私有寄存器和 local memory，在 EXIT 前加入清理；shared memory 需要等同一 thread block 中使用它的线程完成，设置 reconvergence/barrier，再协作清零。global memory 可能跨 kernel 使用，不能每次 kernel 退出就盲目清除，应在相应对象生命周期结束后处理。

§4.1 将 shared memory 描述为同一“basic block”线程可见，结合前后文和 CUDA 模型应理解为 thread block；控制流基本块并不是存储隔离域。early exit、不同退出点和发散控制流需要正确组织同步；向任意 EXIT 前机械插入 barrier 不能自动保证无死锁和语义不变。

这条正常退出路径没有自行解决 GPU fault、超时、强制终止、reset、固件挂起或电源转换。若插入的 EXIT 清理没有执行，不能把 fence 返回或错误 IRQ 当成“所有存储已擦除”的证据。预抢占保存的寄存器镜像、spill/context buffer 及实际设备内部状态也应分别纳入目标平台生命周期；这些是项目设计推导，不是论文已实现的功能。

## 7. 用例二：跟踪 GPU 数据出口

§4.2 在 `cudaMemcpy`、`clEnqueueReadBuffer` 等传输 API 检查地址区间：如果输出包含污点，可以告警，或将 CPU 目的区标为污点以延续全系统跟踪。告警、传播标记与拒绝传输是不同策略，不能统一表述为原型对所有泄漏均强制阻止。

作者以 Keylogger/Jellyfish 说明 CPU-only 监测会遗漏 GPU 处理，但未给出完整全系统部署和所有攻击检测率。原文还明确承认，检测恶意程序扫描前一用户留下的未初始化敏感内存这一扩展尚未实现。

“所有通信都经过显式拷贝 API”的条件不应原样迁移到项目：统一内存、CPU/GPU 共享页、host-mapped memory、peer DMA、命令元数据与其他设备均可能形成出口。项目已有 vmshm 共享数据面，必须按真实映射和可观察路径定义 sink；拦截某几个用户态 API 不等于完整中介。

## 8. 信息流保证的边界

数据依赖跟踪不自动提供完整非干扰。例子 `if(secret) out=1; else out=0;` 可由控制依赖编码秘密，即使两条赋值都来自常量。原文展示的前后向伪代码没有给出覆盖一般隐式流的完整 PC-label 规则与证明，不能因引言提及 control operations 就认为所有隐式流已安全覆盖。定时、资源竞争、cache 和调度信号也不由普通数据污点自动阻断。

同样，`out = secret XOR secret` 的简单 OR 规则可能保守地保持污点，即使值恒为零；加密输出仍依赖明文，不会因算法是加密就自然被去污点。去分类需要独立策略，不能让任意 Client 自报“已加密”后清除标签。

跨线程共享内存上的数据更新与污点更新需要相容的顺序及同步，否则另一线程可能看到数据却未看到标签。论文给出有价值的 GPU 并行原型和实验，但没有完整描述所有 atomics、竞态、纹理/只读路径、设备侧动态调用与异常的覆盖；没有源码时，本报告不推断这些全部正确或全部错误。

## 9. 实验：5–20 倍是相对朴素跟踪的优化

作者在 NVIDIA GTX 745（Maxwell、compute capability 5.0）上修改二进制，工具受 asfermi/MaxAs 启发。七个 kernel 来自 Caffe 的 im2col/ReLUForward/MaxPoolForward、CUDA SDK 的 FDTD3d/BlackScholes、SSLShader AES 和 Rodinia Needleman–Wunsch。结果是 kernel 级评估，不是完整模型、端到端服务或多 VM 共享安全系统评估。

Figure 5 比较 naive、reg-in-reg、forward-filter、backward-filter、two-pass-filter、fully optimized；图中 code size 是静态指令数归一化，不是动态指令数或内存容量。Table 1 各过滤原因可重叠，百分比不能相加得到总过滤率。

正文报告综合优化后平均归一化运行时间为原生的 3.0 倍；FDTD3d 5.7 倍、Needleman–Wunsch 3.6 倍、SSLShader 2.5 倍。摘要“快 5–20 倍”是相对未优化污点跟踪，不能写成相对无保护原生 GPU 加速 5–20 倍。平均 3 倍时间意味着约 +200% 时间，而非 +3% 或 +300%。

正文分别报告 reg-in-reg 相对 naive 降低 slowdown 78%、forward pass 降低 53%，组合平均降低 87%；这些比例的比较基线不同，不相加，也不直接由平均比例反推单个 kernel 原始用时。图形柱高未给全部精确数字，本报告不伪造原始测量表。

作者为评估 local memory 清理，把 SSLShader 从使用 40 个寄存器重新编译为 20 个以制造 spilling；这项条件必须保留。正文还报告该例定向清理 47 mSecs、连同不敏感 shared memory 全清约 407 mSecs，但未在该段给出完整归一化上下文，不外推到 Mali 或项目清理时延。

## 11. 与 CCA/GPU TEE 主线的对应关系

| 研究 | 主要边界 | 与本篇的互补关系 |
| --- | --- | --- |
| CAGE / StrongBox | GPU 任务执行与可信管理边界 | 隔离任务仍需定义片上残留和异常回收 |
| ACAI / PhantomMap | 身份、真实物理页、映射一致性与生命周期 | 地址授权不能独自追踪合法计算产生的敏感副本 |
| PORTAL | 可信服务 Realm 与设备映射、交接 | 交接状态机可接入清理完成条件，但本篇没有实现 Realm 交接 |
| MOLE | GPU 内部 MCU 与固件信任边界 | 若可信固件被攻陷，单纯应用插桩不能独自约束设备内部行为 |
| Devlore 及可信中断研究 | 事件来源与虚拟注入的可信边界 | 真实 IRQ 不代表残留擦除、DMA 静默或计算正确 |

这些是本报告按保护对象作的比较，并非作者声称的一条继承链。GPU Taint Tracking 对当前项目的价值在于补充“授权访问之后的传播与释放”，而不是替换现有映射期授权方案。

## 12. 对项目的建议：先完成可验证的安全回收

接受项目假设：RMM 认证原始 Client，可信 ProxyRealm 统一管理 SMMU，核验对象/真实 HPA/权限/生命周期，软件完成 IPA→HPA 并合成受保护 GPU Stage-1；其他设备维持硬件 Stage-2。该假设已解决重要访问授权问题，本篇不要求机械增加另一层设备页表。

建议把任务与资源回收的状态拆清：停止接受新启动、确认相关队列和在途访问终止、撤销旧访问权限并完成必要失效、清理可复用数据与上下文、最后发布资源可复用状态。具体擦除/撤映顺序取决于可信清理者需要的访问能力；关键是未完成清理的资源不能被新 Client 获得。可信清理者可使用受控专用映射，不能为方便清理继续保留旧 Client 的启动和访问权限。

异常时如果无法证明清理成功，资源进入隔离/待恢复状态，不能因超时就重新分配。若目标平台能提供可信固件或硬件完成的跨上下文存储清理，优先建立并验证该契约；只在确有收益、完整覆盖和不可绕过时考虑选择性污点清理。目标能力可在实验平台模拟，但应明确模拟了什么保证以及哪些未验证。

短期不建议把完整指令级污点跟踪变成必需主线：它增加 ISA、二进制验证和 shadow state 的可信复杂度，论文的平均 3 倍运行时间也不是低成本证据。可以先用 Client/对象标签和实际 backing generation 跟踪受保护服务内的显式数据流；这属于粗粒度授权与审计，不能宣称等价于指令级信息流安全。

## 13. 中断通信：完成、清理与可复用通知分别绑定

项目可以在 Proxy 内维护作业终态与清理终态的权威记录，通知携带并核验 Client 实例、session、job、device epoch 与相关资源 generation，防止 reset 后旧通知让新任务被错误标记完成或使旧资源被错误释放。字段与状态必须受可信路径保护，不能只依赖共享内存自报身份。

物理 IRQ 只触发检查；Proxy 读取权威设备/驱动终态后才能更新对应 job。job 失败、job 正常完成、DMA 静默、片上残留清理及对象可复用是不同条件。对 Client 的逻辑完成通知可以早于资源可复用，但必须保证 API 契约、所有权和缓冲可见性正确，不能让一次通用 ACK 承担全部语义。这里是项目研究建议，不声称论文提出了该协议或本项目已经实现。

## 14. 可验证负例与剩余证据

建议验证正常完成与 fault/timeout/reset 后的 A→B→A 复用，覆盖寄存器、片上共享存储、spill/context 页及共享缓冲。负例还包括清理前提前交接、旧 epoch 完成通知、未知/漏标污点源、只读敏感参数、不同 EXIT 分支、清理过程被中止，以及并发数据/标签更新；评价是否阻断新授权或泄漏，而不只观察是否崩溃。

匹配的 2017 原型代码本轮仍未取得，不能声称静态审计了它的解析器、完整 ISA、并发 shadow map 或异常清理。当前完成的是正式全文精读及来源范围核验；论文缺失的安全强制条件保留为未证明边界，不当作已复现漏洞。GR-T 正式版、XpuTEE、AccShield 等其他直接候选继续待全文，不以重复前作或无关仓库凑数。
