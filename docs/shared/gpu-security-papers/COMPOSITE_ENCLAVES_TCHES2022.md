## 2. 为什么与本项目直接相关

论文把一个可信应用拆成多个 unit enclave：CPU application enclave、CPU driver enclave，以及设备上的 unit enclave。一个设备由一个可信 driver enclave 管理，多个 application enclave 可以通过它共享设备；驱动负责区分每个应用的状态及授权。这与可信 ProxyRealm 承接 Client 请求、统一管理设备的方向接近。

其贡献重点是将 CPU enclave 的保护和证明扩展到异构组件及组件间连接。它基于 RISC-V/Keystone，既不是 Arm CCA 实现，也不是现代商用 Arm GPU 的多租户 TEE 原型。文中 GPU 风格加速器案例具有参考价值，但不能替代 PORTAL、CAGE、ACAI 对 CCA 设备路径的直接论证。

对项目最有用的新增问题是：即使每个参与者代码都可信、共享页也受到保护，Client 当前连接的是否仍是先前授权的那个服务实例？设备或 Proxy 重启后，原有页、密钥、请求和完成记录应如何失效？

## 3. 威胁模型与可信基

攻击者控制 OS/Hypervisor，能调度 CPU、安排映射、控制设备连接和 reset，并可能借其他设备 DMA 越界。安全目标包括 unit enclave 代码和数据的机密性、完整性，以及组合关系的可信证明。

可信基包括 CPU 的硬件保护及安全启动、Security Monitor、参与组合的 enclave 软件、可信设备固件和设备侧隔离机制。经过 driver enclave 的明文和状态对该驱动可见；将其放进 enclave 不意味着驱动不可信或不必审核。

CPU PMP 只约束相关 CPU 访问，不能单独阻挡任意外设 DMA。论文另外依赖 IOMMU/IOPMP 等访问控制；当时 RISC-V IOPMP 仍是讨论中的机制。不能把 CPU PMP 原型验证等同于完整的恶意 DMA 隔离实验。

平台设备发现也需要可信来源：静态配置可以由可信 DT/ROM 提供，动态设备则需要受保护的总线控制器驱动或相应发现路径。普通 OS 任意提供的设备树不能自然成为安全身份依据。

物理攻击、DoS 和侧信道不属于本文保证；侧信道缓解主要是讨论。论文不承诺恶意 OS 一定及时调度服务，也不提供可用性或实时截止期保证。

## 4. 体系结构与共享模型

SM 管理私有区和共享区，检查范围及重叠关系，建立受保护的组件连接。共享内存原则上只在恰好两个实体间使用，而不是建立任何 enclave 都能访问的公共池；复杂组合通过多个成对连接构成。

应用不直接信任 OS 转发的设备身份，而是验证相关 unit enclave 的测量和连接关系。driver enclave 管理设备 MMIO、提交与状态；设备具备自有可信执行能力时，设备 unit enclave 也进入组合证明。

不同设备可采用不同共享方式：有的时间复用并在交接时 reset，有的依赖设备内空间隔离。论文认可驱动必须维护每个应用状态，但没有给出任意现代 GPU 固件、队列、缓存和共享调度器的完整多租户隔离实现。

共享页受保护仍不代表页内消息可信。消息的来源、长度、对象归属、当前状态和是否被对端并发修改，需要上层协议承担。项目已有 RMM 身份、认证队列和私有快照，是此处可继续使用的基础。

## 5. 核心生命周期：异步断开、同步断开和重连

论文区分两种断开。异步断开处理一端突然消失或被撤下：共享区应保留给存活端，避免 OS 立即回收仍含其秘密的页。同步断开则显式通知相关端点，使它处理断开、释放或失效连接，之后才能完成相应资源回收。

新连接必须经过前置同步断开，阻止 OS 静默换入另一台设备或另一个 enclave。否则新端点即使运行相同代码，也可能获得旧端点会话中的敏感状态，或被误当成原授权参与者。

这里有两个不同义务：一是存活端仍依赖的共享区不能泄漏；二是旧 CPU/DMA/设备事务不能继续作用于已转授资源。保留共享区解决前者的一部分，但不会自动证明旧 DMA 已停止。论文没有完整展开所有总线在途事务、热拔插、reset、缓存和撤销确认的具体握手。

因而不能把“SM 收到断开请求”直接当作可安全重新分配物理页的证明。对 GPU 需明确停止新提交、确定在途 job 终态、排空或取消旧访问、撤销和失效映射、清理内部状态及最终转授之间的顺序。

## 6. 证明必须覆盖连接和实例连续性

单独比较组件代码哈希不够：同代码的组件可以连接到不同设备，也可以是新启动的另一实例。论文的证明包含 SM/组件测量和所连接 ID 等信息；同平台签名及设备厂商身份支持证明 CPU、驱动与设备组成的关系。

设备证明还涉及其共享物理区域，意图将远端验证看到的设备身份与实际通信关系关联。若应用只验证设备证书，却把数据写入 OS 指定的另一个缓冲区，信任链仍未闭合。

§6.3 专门讨论 ID 回收和 chained attestation：旧实例销毁后，相同 ID 和相同代码可能再次出现，即 ABA 问题。论文依赖强制断开通知，以及新实例不知道旧连接已建立的秘密，阻止静默替换后继续冒充旧参与者。

这不等于所有 freshness、challenge、密钥协商和恢复策略均被完整形式化。迁移到项目时应说明连接实例、密钥连续性、重启代次、授权策略与证明挑战如何绑定，不能仅引用代码哈希或数值 Client ID。

## 7. 中断：设计提出，原型未实现同步

论文讨论由 SM 将设备中断交给相关 unit enclave；其中中断控制器驱动也需要可信。它明确说明原型没有实现中断同步，实际评估使用 polling。

因此本篇可用于论证“连接及断开通知属于安全状态机”，不能用于声称可信多 VM IRQ 路由已由其原型解决。目标身份、pending/ACK、重连后迟到 IRQ、重复通知和每任务完成归属，仍需另外定义。

项目已有 persistent IRQ127 和 RMM 保存的 pending/ack/armed 状态，也已有 native fence、cookie/epoch。这里适合补充的是：通知只使接收端重新检查当前实例的可信状态；不能凭通知本身完成 job、转移页归属或开放输出。

## 8. 原型平台和加速器案例

CPU 原型为 Genesys2 FPGA 上的 Ariane；Arduino Due 模拟外设，约 8 MHz 连接、约 1 MB/s。密码处理使用 AES-128-CTR、HMAC-SHA256、Curve25519 和 SHA3 等；Arduino flash 中的密钥保存是原型安排，不代表商用抗物理攻击硬件信任根。

PMP 增加约 160 行 SystemVerilog，检查点覆盖 CPU 相关访问及 page-table walker。使用 Yosys 的有界检查针对 PMP 等局部硬件属性，不能称为组合协议、连接证明或所有设备访问的端到端形式化证明。

Keystone SM 增改约 390 LoC，runtime 约 213 LoC，摘要约 600 的表述主要是二者合并；这不是完整 TCB。SM 约 2 KLoC 另有 SHA3/ed25519 约 4 KLoC，runtime 约 3.6 KLoC，外设固件和驱动约 2.5 KLoC；简单 display 驱动约 50 LoC 不能代表完整现代 GPU 驱动大小。

加速器案例为 Manticore GPU 风格的 4096 核 RISC-V 系统，每 cluster 8 核、4 个 PMP 表项，一个核心更新规则、各核心执行规则。固件约 143 行汇编和 73 行 C，交接时刷新上一任务 scratchpad 并更改 PMP。

这展示了设备内部保护和时间交接的可能性，不是商品 GPU 原生驱动的等价替代。scratchpad 刷新不能直接推广为所有缓存、寄存器、队列、MCU 和并发状态都已清理的证明。

## 10. 固定公开代码核验：论文协议不能直接当作实现完成

仓库固定提交的递归树共 5 项且未截断，实际公开源码主要是 `patches/keystone.patch` 和 `patches/eyrie.patch`。README 指明 Keystone 基线 `8175c673745e94eeb35da860bc5c7fe7c60adca0` 和 Ariane/CVA6 基线 `5536dfe0180080d12074edd2d0b705738239a146`。

README 明确说补丁难以直接构建，平台适配破坏 QEMU 支持，未完成迁移新 Keystone；补丁应用和 CVA6 镜像构建说明仍是 TODO。部分 FPGA 外设接线/IP 修改因许可未公开。因此不能说下载该仓库就取得全部论文硬件、外设和加速器实现。

定向静态核验发现以下事实，均限定于上述固定补丁，没有执行或证明可利用性：

- SM 增加 `REGION_SEM`、`REGION_CON` 和单一 connector；`ENCLAVE_SHARED_MAX=1`，连接逻辑明确标注仅适合静态配置，并限制同一个 SEM 再次共享。
- `connect_enclaves` 把一端 SEM 放入另一端 region，检查 enclave 存在、类型和共享计数；通知和 disable interrupts 仍是 TODO。同步断开处理器通知、异步断开的 ownership move 也仍是 TODO，不能视为论文完整生命周期的实现证据。
- 连接与断开函数在持有 `encl_lock` 后存在直接错误返回、未见对应 unlock；这是补丁可见的错误路径问题，未运行触发。断开可见代码清除 connector 字段，但未在同一路径展示完整撤销、缓存失效及 DMA 排空。
- `validate_and_hash_enclave` 增加 connector 结构入哈希；连接函数可见字段赋值不包含 connector 的 `eid`，也未见连接变更后完整重测量/新证明流程。因而只能确认增加了相关代码，不能据此宣称动态连接证明链全部闭合。
- Eyrie `map_pt` 中一个 VPN 计算使用逻辑 `&&` 而非位与 `&`；共享映射带 RWX/U 权限且启动路径使用固定 VA。这说明公开实验路径有特化/待完善之处，不代表本项目应复制该映射实现。

上述核验没有应用补丁、恢复所有依赖、审计整份上游 Keystone 或验证每种设备。它支持将“论文设计”“公开补丁完成度”“实际测试结果”分开，而不是仅按作者提出的协议推定公开实现可靠。

## 11. 与 PORTAL、ACAI、CAGE 及当前项目的关系

PORTAL 更直接对应可信服务 Realm 和设备服务化；ACAI 直接涉及 CCA 下设备身份、映射归属与受保护设备访问；CAGE 讨论 GPU 执行路径及保护。Composite Enclaves 补充的是更一般的异构组件组合：证明中要覆盖连接，实例变更不能只靠代码哈希识别，共享资源须有断开及重连语义。

本项目接受既定假设：可信 ProxyRealm 控制 SMMU；RMM 认证原始 Client；映射阶段检查对象归属、实际物理页、权限和生命周期，软件 IPA→HPA 后建立受保护的直接 HPA Stage-1；其余设备硬件 Stage-2 同样受可信准入控制；页表、根配置和关键 MMIO 受到保护。

在这些假设下，本篇不会推出“必须更换实验硬件才可能安全”。进一步研究应聚焦授权关系在时间上的连续性，以及连接、任务、完成和撤销是否对同一个实例成立。

现有认证队列、私有快照、GPUVM、native fence、cookie/epoch、persistent IRQ127 均是已实现基础，不能重新包装成待补的空白功能。本轮没有重新审计项目全部源码，不将论文中的公开补丁缺口映射成当前项目已存在的漏洞。

## 12. 建议补充的可验证设计

第一，建立统一连接标识，明确绑定 RMM 认证的原始 Client、Proxy 实例、设备授权代次及会话。对象、计划、完成和回收引用必须在该绑定内解释；沿用现有 cookie/epoch，检查其是否覆盖 Proxy/device reset 和连接重建，而非另建一套重复机制。

第二，写出断开状态机：禁止新提交 → 处理在途任务 → 撤销并完成失效 → 保留仍被存活端引用的页 → 清理敏感设备状态 → 显式完成断开 → 允许新授权。区分异常断开后的保留条件和最终可复用条件，不能仅按页表项已删除就进入复用态。

第三，将连接证明与运行期授权分开：证明可信软件及设备实例，运行期由受保护状态机约束实际对象和任务。旧实例的迟到 IRQ/完成只能成为无效提示，不能解除新实例的 fence 或放行旧对象释放。

第四，针对同 ID/同测量新实例、Client 退出同时设备完成、Proxy reset 后迟到通知、断开 ACK 丢失及半完成回收等交错，编写模型或后续负例。当前仅提出验证义务，没有执行这些实验或宣称新的 PASS。
