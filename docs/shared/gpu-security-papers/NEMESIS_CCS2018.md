## 2. 核心问题与论文增量

TEE 可以在中断时安全保存并清除寄存器，也可以禁止 Host 直接读私有内存，但中断响应要等当前指令到达可中断边界。若指令剩余时间与秘密、分支、缓存或操作数有关，攻击者仍可通过 IRQ 到处理程序开始之间的时间推断机密执行状态。

Nemesis 将中断本身识别为可观察通道，超出“借中断暂停受害者，再观察缓存/页表”的传统用法。即使保护程序没有向不可信 handler 交出真实寄存器，时间仍可能带出信息；即使两个秘密分支总耗时相同，逐指令中断也能拆开总时间。

这与恶意注入中断导致错误 handler 副作用不同，也与 GPU 伪造完成不同。它研究机密性中的时序观测；本项目完成记录真实性、状态转换授权与撤销回收仍是独立目标。

## 3. 威胁模型与必要条件

攻击者知道受害程序的编译代码，控制 OS 及非保护应用，可配置 timer、加载驱动、选择调度和部分 BIOS 配置；硬件及安全中断保存逻辑仍按设计工作。模型允许同一运行中反复中断；SGX 宏基准还假设能多次处理相同秘密输入。

基础攻击需要多周期且不能在任意周期中断的指令、可控中断到达时机、足够精度的时间观测和能区分秘密相关行为的路径。并不要求一定有 cache、MMU、分支预测或乱序执行；现代复杂 CPU 只是让计时更有噪声。

“远程可利用”指在远程托管平台上控制软件即可实施，不代表无 OS 权限的网络对手能直接产生周期精确中断。没有把该攻击模型套到所有 Realm、所有 ARM CPU 或当前 GPU。

## 4. 机制：架构状态安全与时序安全分开

简化地记观测时间 L 为“当前指令剩余执行时间+安全保存/清理时间+进入 ISR 的其他时间”。攻击者需要控制或统计消除后两者的噪声，以得到前者的秘密相关差异。该分解是解释机制，不是对真实 CPU 所有流水线行为的精确模型。

论文 Fig.2 以两周期与三周期指令为例：在指令首周期触发相同 IRQ，进入 handler 时会相差一周期。此时受保护内存和寄存器没有被直接读出；泄漏来自何时允许控制权返回攻击者。

普通整段恒时可能用一条多周期指令与多条 NOP 补齐总耗时。中断对手既能测每个指令边界的延迟，也可能统计完成前可中断多少次。因此“总时间相同”“每次进入 handler 的延迟固定”和“可观察中断轨迹相同”不是同一安全性质。

## 5. Sancus 原型与实际结果

Sancus 是基于 MSP430 的公开研究处理器，原始系统不可中断。作者为此工作实现类似 TrustLite 的硬件安全中断扩展，保存/清理私有状态，并修改进入 stub 支持恢复。对只包含 MMIO、没有普通私有数据区的 driver enclave，论文脚注明确说明寄存器清除而不保存；不能泛化为所有 driver 具有同样上下文语义。

Sancus 的无缓存、无流水线简化使执行周期可预测，作者利用 Timer_A 的周期精确能力测出单周期差异。这是作者实验平台与假设的匹配，不应因平台简化而否定研究问题。

BSL 案例将已公开的旧版 MSP430 密码比较片段放进隔离模块，并用 NOP 平衡分支。论文明确当时分发的较新 BSL 已使用 XOR 消除相应分支；作者以 BSL v9 骨架替换为实验代码，不是宣称最新商用 BSL 仍具有该旧比较漏洞。

平衡后的例子仍可借 IRQ 延迟判断单字节猜测，作者报告每个候选字节一次恰当中断即可判断，完整搜索从指数穷举降为按字节线性工作。该说法描述论文的机制，不等于本轮已运行密码恢复。

安全 keypad 案例中 MMIO driver 与处理 PIN 的 enclave 都受保护。作者报告一次 poll 的最多 16 个 IRQ 即可识别全部键状态，不需要重复同一次物理按键；附录 B 包含实现及 LLVM/Clang 3.7.0 汇编。其说明表明可信 I/O 数据路径仍需考虑 handler 可观察时序。

## 6. SGX 机制、测量口径与结果

SGX AEX 把真实执行状态保存在 enclave 内部 SSA，交给不可信 ISR 的寄存器是替代状态。作者扩展 SGX-Step，使 IRQ 直接进入用户空间 ISR，减少内核代码、特权切换及缓存污染的噪声；这种能力由攻击者控制内核/IDT 的模型支持，不是普通用户默认权限。

测量链含 ERESUME、受测指令、AEX 和少量外部指令，因此图中的数千 cycles 不是单条指令原始时延，更不能拿去估算 Arm GPU 中断开销。运行环境关闭部分频率/超线程干扰、绑核并隔离 CPU；噪声、重复输入和平台校准是结果条件。

原 SGX-Step 文献报告大于 97% IRQ 在首次 enclave 指令内到达、少于 3% 可能发生于 ERESUME 形成 zero-step。Nemesis 在其平台上实验利用代码页 accessed bit 过滤 zero-step，再按指令序号聚合。这里的“noiseless single-stepping”不代表时间样本没有噪声，也不是所有 SGX 实现的规范保证。

| 实验 | 作者设置与观察 | 证据边界 |
| --- | --- | --- |
| 微基准 | 10,000 个相同指令的 slide，区分 NOP/ADD 与 RDRAND/FSCALE；DIV 操作数、数据 cache 和页表 cache miss 影响延迟 | 部分相近指令仍难区分；有些缓存分布解释为作者假说 |
| Zigzagger | 从原论文复制示例汇编并放在同一 64-byte cache line；图示 100 次，作者称约 10 次已可识别分支 | 未取得完整 Zigzagger compiler pass，不能扩大为全部加固应用结果 |
| bsearch | 调用 SGX SDK 的真实库函数，选择先左、再右、后相等的查找值；100 次取中位数观察模式 | 属于选定演示输入，不是任意数据库应用的攻击成功率 |

SGX 实验机器为 Dell Inspiron 13 7359，Skylake i7-6500U 双核 2.5 GHz，Linux 4.13.0；附录 C 指明 Intel SGX Linux SDK 2.1.2 的 bsearch 源码和 GCC 5.4.0 汇编。不得推广为当前 SGX、TDX、CCA、Mali 或 GPU job 的已验证泄漏。

论文没有给出可直接用于本项目的 bit/s 带宽、端到端 GPU 性能或整体防护开销，§6 也明确 SGX 实际泄漏带宽仍需后续研究。宏基准的中位数可见分离不等于统计独立的普遍成功概率。

## 7. 缓解手段及未闭合问题

作者讨论将中断响应补到最坏周期，但指出可中断指令数仍可能暴露不同分支；中断到来时取消/重启多周期指令也不自然消除所有观测。固定 IRQ 延迟不是完整防御。

消除秘密分支和数据相关变时指令可减少泄漏，但复杂非密码工作负载难以识别全部秘密依赖，编译器转换也有成本。论文没有提供经形式化证明、覆盖一般程序的完整防御实现。

基于异常频率的检测可能漏过少数精准中断；Sancus 案例单次中断已经可能泄露。TSX 中断感知的兼容、性能与误报/漏报限制也在原文讨论。不能把“发现高频”解释为“阻止所有泄漏”。

与后续 AEX-Notify 的关系是问题与部分防御链：Nemesis 展示 IRQ 观测能力，AEX-Notify 增加可信恢复感知并提高精确单步难度。两者都不提供 GPU job 完成的原始 Client 归属、唯一终态或 DMA 停止证明。

## 9. 对当前 ProxyRealm GPU 设计的关系

RMM 认证原始 Client、ProxyRealm 统一控制 SMMU、建图时完成对象/实际页/权限/生命周期检查并合成合法 HPA Stage-1，这些假设保持成立。Nemesis 不证明该内存模型失效，也没有测试 Arm GPU。

已有 GPUVM、私有快照、认证队列、native fence、cookie/epoch 与 persistent IRQ127 可支撑事件真实性和生命周期，但时序泄漏取决于对手还能观测什么。是否能暂停 Proxy/Client CPU、控制物理 timer、读取 GPU 状态/频率、看到 IRQ 次数和目标、反复提交同一输入，需在目标模型逐项列明。

| 项目性质 | 应主张的安全条件 | 本篇能支持什么 |
| --- | --- | --- |
| 完成真实性 | 记录绑定原 Client/job/epoch，来自可信的实际状态观察 | 提醒 IRQ 出现本身不是业务证明，不能替代现有 native fence |
| 跨 Client 完整性 | 伪造、重复、错序或迟到事件不能引发越权状态转换 | 与时序机密性独立，需要原协议自身论证 |
| 时序机密性 | 对手可见的 IRQ 时机、次数、处理路径只泄露明确允许信息 | 本篇直接说明为何内存隔离不能自然保证它 |
| 可用性 | 持续通知/中断不能无界挤占其他 Client，公平性前提明确 | 本篇无 GPU 配额或有界延迟保证 |
| 安全回收 | 资源不再被旧任务访问后方可复用 | 中断次数、ACK 或 epoch 都不自动证明 quiescence |

## 10. 建议的研究增量与验证问题

第一，为现有通知路径定义允许泄漏，而不是直接承诺完全恒时。可把任务总完成时间视为允许输出，同时研究是否必须隐藏细粒度调度、队列深度、其他 Client 身份、错误原因或中间阶段。不同目标需要不同机制与性能预算。

第二，把现有 IRQ127 保持为唤醒线索，可信记录继续承担身份和终态证据；减少发送给非目标 Client 的元数据和全局状态可见性。减少无关通知是降低观测面的候选，不自动构成侧信道关闭证明。

第三，围绕已有可信队列评估批量/固定窗口发布策略。若 Host 仍能观测物理 GPU IRQ、Proxy handler 或在途队列，单独延迟 Client 虚拟 IRQ 不能消除那些上游轨迹；任何“隐藏”主张都须指明对手可见层。

第四，考虑可信侧的中断预算与过载处理，但预算只限制采样/骚扰能力，不是秘密无关性的充分证明。应分析单次事件、跨会话累计和低频定点观测，避免只验证高频风暴。

第五，明确暂停恢复时的不可重放操作。Nemesis 及相关单步防御处理 CPU 指令与恢复过程；不能据此重复 GPU doorbell、job submit 或带副作用 MMIO。仍须使用既有 job 身份和终态状态机控制一次性效果。

候选验证分两组：完整性检查错 Client/旧 epoch/重复/迟到/伪造原因；机密性检查同允许输出而秘密不同的两次执行，在固定对手权限下比较可见事件轨迹。两组结论不可互相顶替；本轮未执行这类实验，也未给出当前系统的新漏洞结论。

## 11. 独立评价与后续引用

Nemesis 对本项目最有用的贡献是把“中断可信”拆清：保存正确状态、送达正确 Client、引发合法转换和不泄露过多内部行为，各自需要证据。当前主线仍可集中于跨 Realm GPU 任务隔离；时序机密性可作为明确限定范围的扩展目标。

后续值得追踪的是中断可观察模型与恢复等价性的形式化工作，以及限制不可信调度权的机制；例如论文后续链中的 Provably Secure Isolation for Interruptible Enclaved Execution on Small Microprocessors（CSF 2020）和 Aion（CCS 2021）尚须独立取得全文、研读，不能在本篇顺带计为完成。
