## 2. 为什么它与 CCA GPU 设计相关

PORTAL、CAGE、ACAI一类方案建立可信设备控制和内存访问边界；LeftoverLocals补充的是GPU计算单元内部状态的复用边界。两者保护对象不同：受保护页表不允许越权访问另一Client的外部物理页，仍需另外保证计算单元不会把旧Client的片上状态分配给新Client读取。

这篇不是CCA架构论文，也没有证明本项目或Arm Realm存在对应漏洞。纳入文献库的目的是补全威胁模型与安全回收条件，不能把跨进程结果直接升级为跨VM/Realm攻击事实。

## 3. 攻击者权限与真正泄漏位置

攻击者能在同一GPU提交普通计算任务，使用OpenCL、Vulkan或Metal等接口，不需要读受害进程地址空间。攻击kernel读取尚未初始化的OpenCL local memory；对应CUDA shared memory和Metal threadgroup memory，是工作组共享的片上存储，不是CUDA所谓每线程local memory。

前一kernel留下的数据未在不同所有者之间清除，后一个kernel便可能把残留复制到自己合法的global buffer，再由CPU读回。攻击没有必要构造非法HPA，也不以绕过SMMU页表为前提。

读取未初始化变量涉及源语言未定义行为，作者使用volatile和特定访存模式避免编译器消除相关代码。这说明PoC受编译器及代码生成影响；语言层不保证程序行为，不等于操作系统可以允许跨进程秘密泄漏。本文没有另行反汇编确认所有框架的实际指令。

## 4. 标记实验及阴性结果的边界

writer写入标记123，listener另进程读取残留。可信的跨进程证据是观察到另一个进程的已知标记，不是“读出了非零值”。作者在Arm设备看到非零但未看到标记，厂商调查也没有确认跨进程泄漏，不能将这些行算作Arm GPU已受影响。

## 6. LLM 演示实际窃取了什么

演示使用RX7900XT、llama.cpp/OpenCL/CLBlast及WizardLM-7B量化模型。关键路径是读取最终输出投影层的输入隐藏向量，结合已知模型的输出权重重算logits和token；没有展示恢复完整KV cache或所有层、所有token的连续内存镜像。

这与KV-Shield引用该工作时强调KV泄漏的叙述需要区分。LeftoverLocals证明片上残留可以暴露敏感推理数据，不能单凭该演示就认定完整KV提取和任意对话重建均已验证。

受害端GEMV被修改为将完整输入向量缓存在local memory。作者明确披露这是一种惯用优化变体；不能隐去修改条件，写成对未经修改的任意llama.cpp版本直接成功。模型识别在原文有指纹讨论，实际artifact则预先假定WizardLM模型，不是全自动识别任意模型的实现。

原文称输入向量约“4KB”，固定源码和README则明确4096个FP32元素，即16KiB。输出矩阵为32001×4096；这一尺寸差异应保留，并以实际dtype解释字节量，而不是把4096个float写成4096字节。

`ggml-opencl.cpp`仅定向阅读kernel定义、注册及选择/调用位置，未全文件审计：`ToB_optimized_matvecmult`把4096元素写入tmp并barrier，随后复用tmp计算32001输出；Host在输出维度32001时切换该kernel，分配4098个float的local参数。该条件与README披露相符。

LLM listener两个源码文件已完整读取：kernel复制未初始化的local float到自身global buffer，并将读过的位置写零；Host等待queue完成并读回，用“4096非零为主元素、两侧零”等启发式寻找候选，再用已加载输出权重计算。没有实现完整KV解析器。

token输出采用最大logit，且连续相同token不重复打印；最大值初始设0，另有阈值/候选启发式。因此示例输出并非逐token完整转录器。即使正确重算logits，也不能在未获得受害端采样随机状态时保证复现随机采样的同一token。

## 8. 基础测试代码的保证范围

完整读取根README、OpenCL/Vulkan说明及所选writer/listener源码。OpenCL listener初始化自身global buffer为零并等待kernel完成，但这不等于清理GPU local memory；它通过读回直方图输出最高频十个值，需要实验者判断跨进程canary，并非现成自动PASS分类器。

Vulkan使用clspv产生SPIR-V，依赖easyVK；测试大小、工作组数和编译配置影响物理覆盖。`common.h`虽然注释称8位元素，实际kernel用uint，4096元素对应16KiB，不能按注释误算。此次未构建或验证随附SPIR-V与源码的一致性。

完整仓库树不等于全仓审计。13个文件完整读完，72KB的 `ggml-opencl.cpp`只定向读取，其他平台应用及依赖未审计；文件清单和哈希见 `leftover-source-acquisition-batch60.json`、`leftover-listener-acquisition-batch60.json`。

## 9. 泄漏容量不等于有效秘密吞吐量

RX7900XT按84CU、每CU64KiB推算总local为5376KiB，即5.25MiB、约5.505MB，解释了原文5MB/5.5MB的近似表述。这是硬件容量和覆盖动机，不等于每次攻击都恢复这么多唯一受害者字节。

33层乘约5.5MB得到约181.5MB的原始读取机会，与原文约181MB叙述相近；其含重复状态、无用值和覆盖假设，不是181MB/s，不是已验证的唯一秘密量，也不是完整模型/KV恢复量。指纹权重约80MB的估计同样不是全权重恢复率实验。

## 10. 清理为什么必须与资源移交配合

原文直接指出：在计算kernel之后另排清理kernel，攻击者可能插入两者之间。只要求应用“用完再清零”不能建立多租户系统级保证。需要由可信调度控制从秘密计算结束到状态清理、再到其他所有者获得执行资源的整个顺序。

把清理嵌入kernel也需要覆盖所有使用位置、线程退出路径和屏障，并确认写入未被编译器移除。恶意Client不能被当作替其他Client清理状态的可信主体；取消、抢占、异常和reset时也不能沿用正常结束才执行的清理路径。

可考虑按安全所有者切换进行可信清理，减少每kernel成本，但必须证明覆盖全部可复用状态及抢占保存区；这是本项目建议，不是本文实现或已测优化。单个清理kernel能覆盖所有CU/所有资源也需证据，不能仅按逻辑buffer长度推断。

## 11. 与本项目现有内存和中断机制衔接

维持用户目标模型：RMM认证原始Client，可信ProxyRealm控制SMMU，在映射建立时校验对象归属、实际物理页、权限与生命周期，软件IPA→HPA合成受保护GPU Stage-1；其他设备使用硬件Stage-2，并保护实际页表、根配置、MMIO及可信固件。片上状态清理是对此模型的补充，不以实验硬件能力否定架构。

建议写入不变量：旧Client秘密仍可能留在可复用设备状态时，新Client不得获得对应计算资源；资源释放条件须包含必要静止、清理及清理完成证据。复用现有GPUVM、认证队列、private plan/snapshot和cookie/epoch，不新增平行身份体系。

native fence仍表示既有计算完成语义，不应悄悄改成“全设备已清零”。分别规定结果可发布条件和跨Client资源可移交条件；若对外某个完成承诺包含安全回收，则其发布必须等待相应清理，否则计算完成记录与清理完成事实应明确区分。

IRQ127只唤醒接收方检查受保护状态，不证明清理完成。通知重放、合并或乱序不得让资源提前移交；必须核对实际任务终态、所属Client/epoch、取消/reset结果和可信清理状态。这样把中断可信性落实到它能够授权的状态变化，而不是仅保护中断号。

## 12. 验证计划与评价

后续应在受控实验中验证：A写唯一片上标记后B是否可读；正常完成、异常退出、取消、抢占及reset是否都触发必要清理；攻击任务能否插入计算与清理之间；旧完成/清理通知能否在epoch复用后错误释放资源。阴性结果要附采样覆盖和编译配置，不能以一次全零证明普遍隔离。

性能单独计量计算完成延迟、跨所有者切换清理成本、吞吐、公平性及故障恢复；不能用本文容量数字代替实际性能。按工作区要求，本轮没有运行硬件回归，也不宣称glmark提分或新PASS。

本文最直接的研究启示是“可信资源移交”：页授权、真实完成通知、静止与片上状态回收需要形成一个可论证的协议。它为项目第二部分的内存/中断隔离提供具体负例，但没有证明任意CCA GPU方案已经失效。
