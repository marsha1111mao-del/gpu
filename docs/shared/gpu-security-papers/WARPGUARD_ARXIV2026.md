## 2. 研究问题

即使 CPU 代码和 GPU kernel 分别属于合法程序，也可能在错误的 CPU 调用点启动了错误 kernel，或使用被修改的 grid/block 配置。只验证 CPU 控制流，无法知道实际启动的 GPU 内容；仅验证 GPU kernel 身份，也无法判断它是否符合当前调用的意图。

WarpGuard 提议联合验证 CPU 控制流、GPU 运行控制流和二者之间的 launch 事件。它与本项目的交集是可信任务关联，而不是 CCA 页归属或 SMMU 隔离。不能把它作为完整 GPU TEE 或恶意 Host 下的跨 VM 隔离方案。

## 3. 威胁模型与可信基

论文信任硬件、OS、GPU 驱动、CUDA runtime、prover 和 verifier，也假定相关本地通信可信。攻击者位于应用层，可以利用 CPU/GPU 程序内存缺陷，修改返回地址、kernel 镜像或启动配置。

这比本项目“Host 与其他 Client 可恶意、可信完整驱动在 ProxyRealm 内”模型不同。其 OS 级 monotonic counter 和信道身份保证，迁移时必须由 RMM/Proxy 的可信状态承担，不能直接交给不可信 Host。

论文排除部分数据攻击、CFG 内合法路径的控制流弯曲、GPU 数据攻击、侧信道、动态生成或自修改代码，以及 GPU 可写可执行内存带来的代码注入。因此遵守 CFG 不等于计算结果正确，也不等于程序不越权访问其他对象。

## 4. 五类攻击与检查对象

| 类别 | 目标 | 设计检查 |
| --- | --- | --- |
| A | CPU 控制流劫持 | CPU 轨迹是否符合 CPU CFG |
| B | GPU 控制流劫持 | GPU 轨迹节点及相邻边是否合法 |
| C | GPU kernel 镜像修改 | 实际 kernel 内容身份与参考内容一致 |
| D | 合法 kernel 被放在错误调用点 | 当前 CPU callsite 的允许 kernel 集合 |
| E | grid/block 等启动配置被修改 | 启动配置符合该 callsite 的策略 |

C、D、E 的区分很有价值：内容未改、内容合法、当前调用有权启动此内容是三个不同命题。对项目还需增加“当前 Client 有权让它访问这些对象”的授权条件；程序身份白名单无法替代内存授权。

## 5. Composite CFG 与启动记录

离线在可信环境提取 CPU CFG、各 GPU kernel CFG 和每个 CPU GPU-callsite 的允许 kernel/配置策略。在线记录 CPU 线程与调用点，以及 launch counter、kernel 内容标识、grid/block。GPU 日志批次再绑定对应 launch counter。

论文设计采用 per-session challenge 保证证明报告的新鲜性，传输和计数器由所信任的 OS 提供。这描述了需要维持的关联，并不是已证明适用于任意异步多流、多个进程及 reset 后 counter 复用的完整协议。

## 6. Warp 粒度日志

GPU 每个基本块入口插入 hook，由当前 active mask 中最低编号的 lane 代表该组记录，从而在未分歧的 warp 中避免 32 份重复。发生 divergence 时，各 active 子组分别留下记录。16 字节记录编码函数索引、基本块偏移、SM、warp 和 active mask。

CPU verifier 结合 kernel 实例及 warp 上下文重建控制流；原型使用分 SM ring buffer、批量 flush 和接收线程降低竞争。该 NVIDIA SIMT 方案不能直接照搬到 Arm Mali，只能迁移“保留合法并行语义，同时压缩事件”的方法。

## 7. 原型与设计目标有明显距离

原型使用 Jetson Orin Nano、DynamoRIO 和 NVBit；CPU 基本块轨迹被采集并发送，**没有实际执行 CPU CFG 验证**。作者将其交给既有 CPU CFA 系统作为后续集成。

**GPU callsite 策略没有预置并自动执行。** 当前原型记录 launch 事件、打印汇总，需人工检查；论文将自动化留给未来工作。因此不能说实验系统已完整自动检测 A–E 五类攻击。

设计描述使用密码学 kernel 内容标识，但 §6.2 原型实际采用对 `(offset, opcode)` 的 **FNV-1a-64** 摘要，并按 `CUfunction` 缓存。FNV 不是抗恶意碰撞的密码学哈希。完整指令编码、操作数覆盖以及加载后内容变更如何重新测量，也需从对应实现继续确认，不能将正文“覆盖全部指令字节”的论述直接当作已审计事实。

## 8. CFG 验证精度和漏检边界

原型对部分间接跳转、调用使用 wildcard source，接受任意观察到的后继；返回边是适用返回点的并集。重汇聚时会抑制部分相邻边检查，以免把硬件序列化的 divergence 误报为非法跳转。这些选择降低误报或简化实现，也扩大被接受的轨迹集合。

作者说明测试集未遇部分间接跳转，但这不证明其他程序没有该路径。函数级 tracing 的覆盖也弱于基本块 tracing；不能将低开销函数级结果与基本块级检测能力合并成同一个保证。

## 9. 日志完整性仍是限制

论文 §5.2、§8 明确承认 GPU 可访问的日志缓冲可能被同一上下文中的恶意 kernel 修改，在 CPU 取走之前隐藏事件。随机位置及缩小 flush 窗口是降低机会的措施，不能替代硬件强制隔离或密码学真实性。

设计叙述采用 GPU-local 缓冲并批量传到 CPU，§6.2 又说明评估平台使用 CUDA pinned mapped host memory 以消除显式拷贝。物理上在 host memory 不意味着 GPU 无权写该缓冲。安全判断应看实际访问权限；本次没有源码来统一这些实现细节。

未来硬件日志、可信缓冲或专用摘要引擎属于讨论方向，没有作为已完成机制计入本篇评价。

## 10. 性能结果应按实际倍率理解

| 工作负载 | 作者报告 | 范围限制 |
| --- | --- | --- |
| 微基准 | 每种配置五次取均值；部分单独框架开销约至 5 倍 | hook 频率、计算量、首次 JIT 均显著影响 |
| SPECaccel 2023 基本块级 | 2.4–128 倍，均值 39.3 倍 | 使用 test 规模；另三项因显存不足无法执行 |
| SPECaccel 函数级 | 1.2–113 倍，均值 26.7 倍 | 覆盖粒度降低；不能当成相同安全强度 |
| 八个 TensorRT 模型基本块级 | 15.5–120 倍 | 不是百分之十几的额外开销 |
| 八个 TensorRT 模型函数级 | 1.9–6.9 倍 | 部分仍保有可用吞吐，不等于开销很小 |
| 函数级吞吐例子 | MobileNet 104.9、VGG-19 101.5、ResNet-50 82.1 QPS | 应同时考虑无保护吞吐及应用实际时限 |

作者用 “moderate overhead” 概括全文，但表述不足以反映部分工作负载的数十至百倍开销。较低绝对时延或仍满足某个应用吞吐需求，和较低相对开销是不同指标。没有把这些数据用于推算本项目 glmark 成绩。

## 11. 安全实验的实际覆盖

作者改写已发表 GPU stack overflow PoC，使 `sum1` 返回进入非预期 `sum2`；还加入 dead call，让目标函数进入分析和插桩范围。节点检查接受该合法代码节点，但边检查发现非法转移，说明仅检查节点集合弱于检查边。

这是一条特定 PoC 的检测示例。C/D/E 主要由设计推理和人工可检查 launch 记录支撑，不能称为所有跨设备攻击均已自动端到端验证；CPU A 类也未在当前 verifier 完成。

## 13. 与本项目最值得迁移的部分

最有价值的是启动记录的结构：可信 Client 会话、job/queue 实例、设备 epoch、实际提交快照以及所授权对象应相互关联。Proxy 必须让最终被执行的内容与已验证的快照一致，防止检查后被 Client 改写。

对于通用 GPU 共享服务，Client 本来可以提交自定义 kernel，未必存在固定“允许算法”清单。应优先检查资源访问权限、设备状态和提交结构；只有保护固定推理服务时，才适合增加模型/kernel 内容与启动策略约束。不能以不必要的算法白名单取代通用接口。

完整基本块轨迹验证会引入新的可信日志和性能成本，当前项目没有证据表明必须引入。可先落实较小的可信提交与完成记录，验证它是否解决具体威胁，再考虑运行 CFA。

## 14. 与中断完成协议的关系

Launch 关联证明“启动了哪个实例”，不证明“该实例已成功完成”；合法控制流也不保证输出正确或 DMA 已停止。物理 IRQ、job/fence 终态、输出可见性、映射撤销和页回收应分别检查。

建议为当前设计加入恶意事件测试：旧 launch 的完成晚到、多个 stream 乱序完成、设备 reset 后编号复用、Client close/reopen 及重复通知。可信端不能因收到一个形式正确的旧记录而推进新 job。这些是结合项目提出的验证方向，不是 WarpGuard 已实现的中断防护。

## 15. 研究结论

WarpGuard 提供了 CPU–GPU 语义关联的设计思路，但其信任模型、原型覆盖、日志完整性和开销使它不能直接承担本项目的主要隔离边界。它适合作为 PORTAL/ACAI/Devlore 主线之外的补充，帮助区分“身份和内存隔离”“启动授权”“运行证明”“可信完成”各自需要的证据。
