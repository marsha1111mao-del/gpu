# LightGuard：TEE抽查GPU训练、异步验证与结果提交边界

研读日期：2026-10-28。完整阅读正式17页PDF、§1–7、30条参考文献、3幅图、4张表与Algorithm1；10页渲染视觉核对，特别核对公式、算法和表格，避免字体提取丢失ε及取整符号导致误读。未取得匹配论文的实现和原始数据，不宣称源码安全审计、训练或攻击复现。未改运行代码，无新增性能测量。

## 2. 问题与主要贡献

云训练者可能省略迭代/数据、返回随机权重、重放旧结果或替换数据。全程CPU TEE训练慢，密码学可验证计算昂贵，训练结束后才抽查又发现过晚。作者提出在每epoch提交检查点摘要，下个epoch训练期间由TEE随机重放部分区间，争取尽早发现不诚实行为。

SmartFetch把检查点分成细粒度FGC和粗粒度CGC：保留细粒度承诺，较稀疏地持久化完整状态；查询时从附近CGC重建所需FGC。重建可分给GPU或TEE，TEE负责最终核验，用检查点间隔、抽样数和CPU/GPU分配比平衡训练与验证延迟。这是性能与发现时机的设计，不是每条GPU指令都经可信执行。

## 3. 威胁模型、可信基与排除条件

用户诚实，云训练者不可信；云上TEE完整性和机密性被假定成立，用户与TEE经TLS通信。训练代码、数据、初始权重和超参数发给云，数据集摘要另送TEE。论文未以GPU机密性为目标，GPU和云端可看到训练资料；因此不应把本方法描述为保护模型/输入不被云读取的完整GPU机密计算方案。

可信基至少包括TEE中的验证程序、训练重放库、状态解析/比较、随机抽样、密钥与签名逻辑，以及保证其正确运行的CPU TEE。作者用Gramine运行未修改应用；没有给出完整TCB清单、LoC或实际manifest。§6说抽样逻辑在helper进程并经共享内存与TEE通信，需要明确helper是否在可信边界内；Host可修改的helper不能决定可信挑战。

远程证明可以认证验证器代码身份，不能单凭平台quote证明不可信GPU的性能探测结果真实。TLS也须绑定已证明的端点及受信代码、会话和策略。正文没有完整给出证书/quote验证、共享内存安全复制、挑战随机源及重放防护报文，本报告不补写成已实现。

原文将SGXv2与512GB EPC近似等同。SGX2指令能力、服务器型号、平台配置和可用EPC容量应分别确认，不能从版本名推出任意机器都具备512GB；这也不影响以实验平台模拟目标协议的合理性。

## 4. 端到端工作流与检查点含义

初始化传入诚实迭代比例h_A、期望检出延迟约束T_max、训练任务及数据摘要；TEE给nonce N确定数据打乱顺序。GPU每epoch按间隔记录FGC摘要与CGC状态，结束时提交P_e。TEE先接收承诺，再随机选择L个FGC，取回被检查的前驱与目标状态，从前驱按相同数据顺序重放，比较结果摘要。

GPU可从最近CGC重建状态，但取回的前驱和目标都需与先前P_e核对。hash只证明“与已承诺的内容相同”，不证明承诺内容本来正确；训练转移检查、初始状态、跨epoch链和随机抽样缺一不可。可信前驱不是天然由不可信GPU返回的内容赋予的。

论文称训练具有Markov性质，实际可重放状态不能只有权重：还需optimizer动量/方差、学习率与步号、RNG、dropout、数据顺序/增强、BatchNorm统计、混合精度loss scale和相关缓冲。必须记录完整且被授权的状态；只重放权重而遗漏隐藏状态，会改变正确性或攻击面。原文没有完整状态序列化格式。

只发送h(D)不能自动拒绝旧任务结果：还需把模型/代码、数据、初始状态、超参数、会话、epoch/step、checkpoint索引和策略版本绑定到承诺与结果签名。nonce确定数据顺序也不等于证明所有旧承诺不可重放。文中Theorem1提及TEE签名，但未列完整签名载荷和终止协议。

## 5. 非确定性与摘要比较

§3将GPU/CPU浮点非确定性处理交给已有容差及rounding-aware logging技术，细节排除在本文范围；§4却直接比较重算状态hash。密码hash对数值近似没有容差，除非规定一致的日志、舍入/规范化或改为明确的数值比较，否则“诚实运行必然通过”不能由摘要相等直接推出。

容差本身也要分析可被恶意训练者利用的累计偏差、数据依赖变化与错误接纳；硬件非确定性不能成为允许任意修改检查点的理由。本文引用的Optimistic Verifiable Training和PoL攻击研究值得继续精读，但不能把引用存在当成LightGuard已经完整集成了这些保证。

## 6. SmartFetch成本模型

f_f/f_c名为frequency，但式子用ceil(p/f)，实际表达每隔多少迭代取点；L为每epoch样本数，r为TEE承担的重建比例。GPU成本包含训练pG、FGC/CGC写入及L·SR_gpu·(1−r)；TEE成本为L·f_c·T加L·SR_tee·r，epoch时间取两者最大。式2用平均f_c/2次迭代估计从CGC重建，另加load/store。

该模型假设两条执行路径可重叠，并用均匀采样估计平均重建距离；实际磁盘/PCIe/主存带宽争用、SGX分页、同步拷贝、GPU重建占用、整数任务分配和队列尾部均可能改变关键路径。连续r只描述平均预算，还需要可实施的离散调度、队列上限与最差耗时分析，不能从max成本直接推出实时系统保证。

模型验证项用f_c，实际重放描述从前驱FGC到目标FGC，通常跨度由f_f决定；需要说明两者关系与是否采用保守上界。L候选枚举到p，但可用FGC约ceil(p/f_f)，未写明样本有无放回及不足时如何处理；重复取点不能按完全独立新证据重复计入样本数。

## 7. Algorithm1的可复现性缺口

视觉核对确认，算法把T_epoch初始化为无穷，第10行可行性判断却使用当前最优T_epoch而非第9行的候选T_current。对有限T_max、0<h_A<1及正常非空epoch，乘数为正，首次判断不会通过；随后无法更新最佳值，最终总是“无可行解”。这是公开伪代码按字面执行的问题，不能据此认定未取得的实际实现也有相同行为。

第5行r公式的验证项是L·f_f·T，第8行及式1却用L·f_c·T。如果令A为GPU训练与checkpoint固定成本，按式1平衡两端应得到r=(A+L·SR_gpu−L·f_c·T)/(L·(SR_gpu+SR_tee))再截断至[0,1]。两式在f_f≠f_c时通常不同，原文没有解释是在优化不同模型还是符号错误。

以纯代数例A=100、L=10、f_f=1、f_c=4、T=2、SR_gpu=5、SR_tee=8，印刷公式r=1，代入式1最大成本160；平衡式r≈0.53846，最大成本≈123.0769。此例仅核查公开公式内部一致性，不是作者程序运行结果或本项目性能测量。式1把最优时间写成argmin也存在“参数与目标值”记号混用。

这些问题要求公开实现/勘误解释；在修正之前，不能把Algorithm1视为可以直接复现作者实验或严格满足其约束的算法证明。正文所称凸优化也主要是在固定离散参数后平衡两条线性成本，不证明整个离散问题或实际系统具有全局最优性。

## 8. 1% soundness保证成立的条件

作者采用每次挑战命中不诚实转移概率1−h_A，独立挑战l次未检出的概率h_A^l，要求l≥ceil(log ε/log h_A)。ε=1%时h_A=90%需44次、98%需228次，算术正确。但h_A是“不诚实工作中诚实迭代的比例假设”，不是用户主观设置的置信度就能约束任意攻击者；更稀疏或集中攻击需要另外计算。

该结论需要挑战随机且攻击者不能预知，承诺在挑战前不可变，坏状态与抽样单位定义一致，每次命中都可靠检出，完整状态可确定重放，且样本独立或使用相应无放回公式。TEE受保护本身不能证明这些前提，也不保证被污染区间一定出现在所抽样的全部转移中。

式1用L·N_e约束整个训练的总样本，而Theorem2写成任意不诚实epoch的通过概率小于ε，范围并不相同。例N_e=100、h_A=.9、L=1，总样本100≥44，但对单个被攻击epoch一次抽样仍可能以.9概率漏检；h_A=.98、L=3时单epoch漏检约.941192。不能把训练全过程持续攻击模型下的总漏检界直接搬成每epoch或任意瞬时攻击的1%保证。

局部重放验证的是遵守指定训练转移，不等于任意模型质量或数据语义正确。用户批准的数据本身若带毒，忠实训练仍可能通过；论文的label-flip检测应理解为云端偏离已承诺干净数据，而非通用识别任何后门/投毒。对不可信GPU返回的两个相互一致但缺少可信起点的检查点，还须论证跨区间链及承诺机制。

## 9. “实时”是期望检测，不是硬期限

Theorem3借助几何分布的首次命中索引X，把每epoch检查L次转换成约ceil(E[X]/L)个epoch。对无限独立Bernoulli试验，E[X]=1/(1−h_A)；正文却给出截断和，未补充未命中尾部，也将L同时描述为每epoch样本数和每L个epoch抽样一次，两种频率方向相反。

有限m截断的sum(k·h_A^(k−1)·(1−h_A), k=1..m)不等于无界E[X]，也不等于完整的截断等待E[min(X,m)]，后者还需尾项。ceil(E[X]/L)通常也不是E[ceil(X/L)]；从近似期望满足T_max不能推出每次攻击都在期限内检出或以某个指定概率按时检出。

若要高概率期限，应在明确调度和攻击分布后约束期限前实际完成的有效挑战数s，使漏检概率满足相应上界，并计入当前epoch提交、验证排队及Host延迟；若云可任意停机/不提交，则还须定义超时即中止或拒绝发布，而非保证恶意平台必然按时完成。本文没有完整证明这种最坏期限与对抗调度性质。

## 11. 性能与检出结果的适用范围

Table3报告的是平均检出时间，单位分钟，不能称为最大延迟。V3在90%/5%预算下，ResNet18/VGG16/ViT/BERT为0.7/12.0/50.7/29.6分钟；98%/5%为2.9/49.3/195.0/119.8分钟。不同任务差异很大，“实时”可以长达数小时，并非立即发现。破折号是预算不可行，不是零耗时或没有攻击。

90%/10%预算的BERT，V2GPU73.8、V2TEE53.4、V3 16.7分钟，分别约4.42/3.20倍加速，支持部分“4–5倍更快”实例；不能推广全部模型/预算。h_A从90%变98%意味着假定攻击更稀疏，所需挑战更多，不是任意提高一个主观置信度就自动提高实际安全。

Table4的LightGuard额外开销标12.4/16.8/8.6/14.2%，四项算术平均13%，并非每项不超过12%；正文平均12%应视其Fig2特定聚合，而非全表上限。各方案std.基线不同：TEE用CPU分钟级基线，TrustFL/LightGuard用GPU；不能直接用附加百分比比较端到端速度。ViT的TEE341.23→437.48分钟实际约+28.21%，表标19.0%，明显不符，已视觉核对；其他小差异可能与显示舍入有关，缺原始数据不能擅自修订作者测量。

安全实验称从epoch10开始攻击、98%参数、LightGuard5%预算，label flipping约20%标签、unlearnable examples约90%图像及l∞8/255；作者报告2–4epochs后检出。Fig3横轴延伸到150，100后标为TrustFL验证阶段，点约在末段；“少浪费40–50epochs”包含训练后验证窗口的计时表达，不能无条件解释成省掉40–50个实际GPU训练epoch。没有重复试验分布、漏检矩阵、伪造承诺、适应性攻击或验证器延迟注入证据。

## 13. 对本项目的设计建议

保留RMM认证原始Client、可信ProxyRealm统一控制SMMU，映射建立时校验对象归属、实际HPA授权、权限与生命周期，软件IPA→HPA合成受保护GPU Stage-1；其他设备保留硬件Stage-2及可信检查，平台保护实际页表、根配置、MMIO及固件。LightGuard的抽查不应替代这些持续隔离，也不应把跨Client越权改成“有一定概率检出即可”。

若项目增加训练完整性服务，可在现有GPUVM、认证队列、private plan/snapshot上绑定应用策略、完整状态和检查点链，作为可选上层验证；明示“设备执行完成”与“应用计算已验证”两个状态，按应用威胁模型选择是否抽查。不要为此另建一套与现有session/cookie/epoch平行的归属体系。

异步验证期间的结果先保持未提交，必要检查完成后才由可信路径发布；数据到达、native fence成功、验证成功、用户可见与资源可回收分别记录。IRQ127只提示读取权威状态，Host通知或一次抽查通过不能直接授权整批SUCCESS。复用cookie/epoch拒绝旧验证结果和迟到完成，设备在途访问排空及实际撤权仍是回收前提。

两epoch检查点保留只在验证确已完成、相关引用释放且没有待处理争议时才安全。Host停调度、验证超时、hash/状态不匹配、取消或reset时，需要明确失败终态、输出抑制、回滚/终止及清理规则。正常路径的“验证后删除”不构成所有异常路径可安全回收的证明。

后续定向验证应覆盖挑战前后篡改承诺、替换前驱/optimizer/RNG、跨任务重放、稀疏与集中攻击、非确定性下误报/漏报、验证 backlog及reset后旧结果；分别记录跨Client隔离和应用完整性的成功标准。SmartFetch可启发重建调度，但不直接采用其未解释的公式或把12%当本项目预算。

## 14. 研究判断与后续阅读
