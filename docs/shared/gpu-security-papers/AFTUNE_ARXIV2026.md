## 2. 与 CAGE、ACAI、PORTAL 的关系

AFTUNE 研究不可信云服务商是否按合同训练、是否用约定模型返回推理结果；TEE 位于 CPU 验证侧，GPU 计算和记录过程不可信。它没有设计 Arm CCA 的 Realm 设备分配、SMMU 授权、GPUVM 或可信中断。应归入应用层可审计计算支撑文献，不能与 CAGE/ACAI/PORTAL 作为同类设备隔离架构比较。

本项目接受既定假设：RMM 认证原始 Client，可信 ProxyRealm 控制 SMMU，在建立映射时验证实际 HPA、权限、归属和生命周期，GPU 使用合成后的受保护 Stage-1，其他设备沿用授权后的硬件 Stage-2；页表、根配置、关键 MMIO 和固件受保护。本报告不以测试硬件缺少某项能力否定该架构。AFTUNE 可补充任务语义审计，却不替代这些强制隔离条件。

## 3. 安全目标、参与方与排除项

Client 提供数据和超参数，但不能读取专有模型权重；服务商拥有模型、训练数据和 GPU 软件栈。CPU TEE 内重算选中块，只向 Client 返回审计结果，避免在审计时公开权重。这里不保护 Client 数据免遭服务商查看，也不要求 GPU 本身具备 TEE。

根假设包括可靠哈希、TEE 隔离、远程证明和安全信道，单个参数张量不超过 TEE 容量。最后一项不足以单独保证一个块可执行：参数、优化器状态、激活、反向图、框架和工作区的峰值总和也必须受限。TEE/哈希被攻破不在论文范围；Gramine、Python、PyTorch 和被加载的模型结构仍影响验证可信计算基。

## 4. 工作流与二维执行块

训练前公开基础模型哈希，Client 确认数据及超参数。训练时按层数 B_L 和步骤数 B_S 划分二维网格，N = ceil(L/B_L) × ceil(T/B_S)。记录层边界激活、梯度，以及步骤块边界参数和优化器状态；相邻块共享边界以去重。服务商先提交摘要，Client 隐藏抽样选择，再让 CPU TEE 重算选中块。

重算一个块时，内部逐步执行前向、反向和更新，外部输入来自已承诺的边界状态。这种分解减少单次 TEE 工作集，并允许并行审计；但它首先验证的是局部转换关系。若要支持任意计算图，边界必须覆盖所有跨块依赖：残差、共享参数、全局梯度裁剪、归一化状态、RNG/dropout、loss scaler、scheduler、mask、位置编码及 KV 状态，不能只记录线性层序列。

## 5. 哈希承诺的实际作用

论文将张量切块，在 GPU 并行计算分块哈希，再由 CPU 对有序分块摘要拼接求最终哈希。它是复合哈希编码，不是直接对平坦张量字节执行一次标准 SHA-256/BLAKE3。基础模型、Client 数据与验证器必须采用完全一致的编码和分块约定。

承诺可以约束已提交字节不能在抽样后替换，但不能证明这些字节当时由诚实训练产生。不可信 GPU/Host 可以诚实地哈希虚构记录；这不构成哈希碰撞攻击。必须把“承诺绑定”和“重算检测错误”分别论证，服务商签名也只认证声明者身份。

推荐摘要覆盖类型化 manifest：Client/session、run、模型和合同版本、层/步骤/方向、shape/dtype/字节序、长度、分块配置、输入输出和最终模型摘要。检查对象还须是不可变快照，不能校验共享区中的一份字节后，又使用被并发 GPU/CPU 改写的另一份字节。

## 6. 信任锚与组合性：需要收紧的核心论断

公开基础模型哈希把版本固定下来，不证明模型本身没有预置后门；在具体合同之前发布也不排除面向多客户的通用恶意行为。必须另有基础模型身份、授权目录和可接受来源策略。Client 输入/标签锚与最终模型、实际服务输出之间也要有完整绑定。

附录 C 称未查出的错误块承诺成为邻块的“new trust anchors”，不影响后续验证。这只表示后续可以相对于固定边界检查，不能把错误边界升级为正确边界。概念上，一次错误状态转换后，服务商可从错误状态继续诚实计算；许多后续状态会偏离原诚实轨迹，但对应局部转换可能仍通过检查。该论证不等同于已验证全部历史计算。

因此抽样公式中的 k 必须是“抽到后会被验证器拒绝的局部约束数”，不能未经证明地替换为“不同于诚实轨迹的状态数”“少执行的 API 次数”或“受影响的后续检查点数”。本轮给出的是逻辑边界分析，没有执行作者系统构造攻击。

## 7. 抽样保证与成立条件

均匀不放回抽样 m 个块，预先固定的 k 个坏块全部可被检查拒绝时，逃逸率为 C(N−k,m)/C(N,m)，检测率为其补数；1−(1−π)^k 和 1−exp(−πk) 是近似式。N=1000、k=100、m=10 时精确检测率约 65.31%，而 k=1 时只有 m/N。

成立条件包括：全部有关记录先承诺，选择不可预测，所有需要的状态都被认证，选中坏块确实拒绝，不能通过选择性中止、重启或分叉记录逃避失败。论文使用 floor(πN)，预算小于一个块时实际抽样为零；不能无条件声称始终有正检测概率。

多次审计只有在保留同一不可变证据、明确新抽样的独立性并防回滚/拒答时才能累计保证。在线审计会暴露时序和偏好，频繁切换策略是缓解建议，不是完整自适应安全证明。偏置抽样需要按实际分布推导，不能直接沿用均匀公式。

## 8. Table 2 与公开采样脚本的复核

公开 `sampling_vs_detection.py` 帮助解释了输入定向抽样的分母：其预算是 round(π × 全体块数)，再集中用于输入块，不是抽取输入块本身的 π 比例。脚本取 N=136、输入块17、坏输入块2、预算14，检测率为97.794%；另一配置输入块34、坏输入块4、预算27，检测率99.9245%，分别解释表中的97.8%和99.9%。应明确公布预算分母，不能把它与输入块总体抽样10%混用。

同时脚本写 L=34、T=136，并把 T 注释为2048样本/batch16，但该除法实际是128；网格数量用 `(L//BL)*(T//BS)`，与正文 ceil 网格不同。在34层、136步、BL4/BS8时分别得到136和153个块。脚本采用 round 抽样，正文公式采用 floor。跳过50%/25%时，用脚本的136块、k68/34、抽7块，算得99.336%/87.347%，对应表格数值，说明它们依赖该脚本参数而非严格按正文默认条件得出。

本次算术由独立标准库脚本复核，没有运行作者采样程序或模型。不能据此断言表格使用了何种未公开训练配置；应要求明确层定义、实际步骤数、尾块和预算舍入策略。参数比例也不能直接等于层比例：一个很大的 embedding/head 张量可能占据很多参数却只影响一个块，坏块下界需要参数分布和局部拒绝条件的证明。

## 9. 数值容差与“误报为零”

论文使用相对 L2 差异处理 CPU/GPU 浮点变化。训练图4记录的参数差异较小，推理图5中 BF16 差异则明显更大，部分配置与图7优化找到的攻击扰动量级重叠；正文承认该问题并推荐推理至少FP32。参数误差很小也可能与小学习率及全局归一化有关，不能直接当作激活和分类稳定性的上界。

附录 H 用 PGD/SGD 找到能改变结果的较小扰动，称为经验下界。严格地说，找到一个可行攻击只能给出最小攻击扰动的上界，不能证明不存在更小攻击；单样本实验也不是所有输入的认证鲁棒性界。多块小扰动的组合、决策边界附近样本、NaN/Inf、零范数及不同dtype归约都需要独立规则。没有把这些风险写成已复现漏洞。

§6.3.2 的“误报为零”论述还把不同问题混在一起：伪造轨迹可以具有自洽哈希，替换模型可以保持同一结构和维度，数据污染是否触发哈希不匹配取决于检查的锚是否确为Client原始承诺。经验上的数值间隔不能证明任意攻击必定被拒绝。

## 10. 稀疏检查点：存储换准备时间

I_C 控制参数/优化器检查点保留间隔，缺失边界先在 GPU 重放生成，再交 TEE 审计；推理还可按 I_A 稀疏保留激活。要匹配原已承诺的哈希，准备阶段需要逐字节确定性。论文对此明确提出一致硬软件和确定性要求，不能用密集验证允许浮点容差的表述覆盖它。

README 指出 DINOv2-Giant 在作者平台需要确定性模式；`prepare_block.py` 会生成状态并比较已存哈希。这不是把全部审计都移到 CPU：GPU 准备阶段仍消耗资源，并可能延后任务回收。工作集、准备时间、记录保留时间和验证排队都须单独计量。

## 11. 公开实现：哈希锚与不可信文件输入

选读实现从本地 `metadata.json`、`hashes.json`、`checkpoint_hashes.json`、最终参数哈希读取预期值；本轮选读路径未找到把这些值与远端Client事先保存的承诺及证明会话进行比对的完整协议。因此这些命令首先是实验重放/差异测量工具，不能直接视为已实现论文端到端认证协议；未审计部分不能据此断言绝对不存在其他集成。

manifest 的 `sgx.trusted_files` 包含程序/库，记录和模型目录则列入 `sgx.allowed_files`；`recorder.load_tensor_compressed`、`load_module_structure` 与推理参数加载使用 `torch.load(..., weights_only=False)`，在内容哈希核对之前进行反序列化。若记录或模型结构来自威胁模型中的恶意服务商，必须先解决不可信反序列化和模型代码授权，TEE本身不会把加载的数据变成可信输入。模块目录可由metadata选择，manifest中未见明确的该目录认证绑定；实际Gramine权限结果未运行验证，不声称已证明任意文件可读或已实现代码执行攻击。

建议固定并测量验证代码与允许的模型结构，使用受限tensor格式、严格schema/shape/长度/资源预算，先验证可信来源和承诺，再解析使用；TEE证明报告应覆盖真正执行的验证器，而不只是提供一个SGX启动命令。

## 12. 公开实现：数值判定与状态覆盖

`verify_tensor_diff` 默认返回差异平方和；训练验证汇总参数/优化器相对L2，主程序打印结果，未在选读默认路径中实现论文算法的统一τ拒绝。`verify_inference.py` 同样打印L2；`--strict_hash` 可对部分重算输出作精确哈希拒绝，但这与容差式安全判定是不同模式。

训练验证中，末层已记录激活和输入梯度有磁盘哈希检查，但选读循环未把它们逐项与本次重算结果作数值比较，而主要通过块末权重差异反映；外部输入/上游梯度的完整承诺覆盖还需核实。推理程序明确跳过 `lm_head`/`classifier` 的块末输出比较，非首块输入从上一块输出加载，需审查其与Client承诺的哈希绑定；默认从目录中选择首个run，README也要求只保留目标目录。这些都不能作为项目最终输出认证器直接照搬。

零/无有效比较项时，相对范数代码有返回0.0的分支；非有限值也缺明确拒绝策略。这是选读静态路径观察，不是攻击执行或所有输入必然可绕过的结论。可信审计接口必须返回经过规范判定的终态，并拒绝缺项、空验证、错误run和不完整边界。

## 15. 从推理记录到实际交付输出

验证某次forward记录不自动证明服务端交付文本就是该次结果。应绑定Client、请求nonce、模型版本、tokenizer、prompt、mask/位置、KV状态、解码策略、随机性及最终输出摘要。论文把每个推理请求按单步骤处理，但完整自回归token循环与服务发布协议仍需进一步规范。

相同确定性请求的缓存答案可能在函数正确性意义上有效；承诺/重放不能单独证明服务商每次请求都实际重新计算。应区分功能正确、历史计算/计费和新鲜输出三种目标。离线审计如果发生在错误输出已被使用之后，只能追责；需要预防性保证时，应先标记暂定结果并由可信发布门控制对外可见性。

## 16. 对本项目内存与中断隔离的具体建议

首先复用现有GPUVM、RMM认证队列、private plan/snapshot、native fence、cookie/epoch和IRQ127，不为AFTUNE另建重复GPU提交系统。记录和验证对象继续受实际HPA归属、权限及生命周期检查；输入/激活/梯度/KV/模型/审计日志都属于授权对象，不能因为用于审计就允许跨Client读取。

将同一任务的设备状态、审计状态、发布状态分开：设备完成须由真实原生fence及任务身份认定，IRQ只提示检查；AuditPass须来自可信验证器并绑定不可变记录和规范；Publish须绑定被批准的精确输出。设备成功不代表数学结果正确，审计失败也不必然意味着DMA已停止。

建议记录主键至少为Client/session epoch、device reset epoch、job/cookie、GPUVM、对象generation、输入/输出/规范摘要。迟到IRQ、迟到审计结果、重复发布或reset前旧epoch的成功消息均不得认证新任务。Client身份以RMM认证为准，不能信任请求者在共享消息中自填的身份。

安全回收需要设备不再访问、所有原生引用释放、验证读者退出/快照留存策略完成、映射撤销与必要同步完成，再清零复用。取消、审计超时、记录配额耗尽和Client退出都要终态；Host拒绝调度仍可造成DoS，不能仅靠可信消息承诺时间保证。

## 17. 建议验证的问题与保留结论
