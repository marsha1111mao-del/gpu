## 2. 为什么机密 GPU 系统需要关注这类工作

CPU 允许读某个页、设备也拥有合法映射，并不代表接收方在收到完成信号后一定能看到这次任务的全部结果。请求被接受、数据进入传输通道、写入全局内存、完成记录发布，是不同阶段。

论文的平台使用 Intel CCI-P，把 CPU 与 FPGA 接入共享内存。CPU 遵循 x86-TSO，FPGA 经一个 QPI 和两个 PCIe 通道发送访问。请求池、不同通道和响应返回路径都可能重排；因此，简单顺序执行的 FPGA 状态机也可能读到自身先前写入之前的值。

这不是认定项目的 Mali 硬件有相同语义。可迁移的是分析方法：找出每个接口中“完成”的具体定义，再确认端到端发布链确实连接起来。

## 3. 必须区分的响应与 fence

| CCI-P 事件 | 在本文模型中的保证 | 不能直接推出 |
| --- | --- | --- |
| WrReq | 发出写请求 | 已进入通道或结果可见 |
| WrRsp | 相应写进入指定通道 | 数据已跨全部通道全局可见 |
| RdRsp | 返回此前某次读取得的数据 | 数据一定是响应到达时的最新值 |
| 单通道 fence 响应 | 该通道中 fence 之前的写已经到达共享内存 | 其他通道的全部写完成 |
| 全通道 fence 响应 | fence 之前全部通道的写已到达共享内存 | 已经发出的旧读响应因此被刷新 |

同通道写后读，需要在发出读之前等待写响应；跨通道写后读则需要相应 fence 及响应。仅仅把两个请求放在同一通道还不够，因为进入通道之前存在重排。

论文的 read-response 与 write-response 含 metadata，用于关联请求。在既定匹配模型中它只是关联标签，不提供攻击者模型下的身份认证、新鲜性或不可伪造性。

## 4. 异构 message passing 与方向差异

FPGA 写入数据 x，再通过另一通道发布 ready y，需要跨通道 fence 防止 y 先到达。CPU 读到 y 后再读 x，作者依赖 x86-TSO 的读读顺序；这个依赖不能直接带到 Arm。

反向由 CPU 发布 x/y、FPGA 消费时，CPU 的写写顺序来自 TSO；FPGA 必须先得到 y 的读响应，再发起 x 的读请求。若 x 的读早已发出，即使旧响应晚于 fence 返回，内容也可能来自更早的时刻。

图 4a 标题和代码显示 FPGA 是 producer，但紧随正文有一处误称 consumer。本报告按图中实际操作解释，没有据该句倒置生产者与消费者。

对项目而言，GPU→Proxy、Proxy→Client、Client→Proxy 是不同方向，不能只用一个泛化的“加屏障”描述全部保证；应注明 CPU、GPU、DMA 和缓存维护各自的责任。

## 5. 操作语义：把隐藏阶段显式表示

作者将系统状态分为 FPGA 读/写请求池、各通道 upstream/downstream FIFO、共享内存，以及每 CPU core 的 TSO 写缓冲。

请求池允许一定重排；请求进入通道后按 FIFO 前进。写响应发生在请求进入 upstream FIFO 时，真正更新共享内存则是另一条内部转移。读从共享内存取得值后进入 downstream FIFO，因此不同通道的返回顺序可以与取值顺序相反。

fence 位于写请求池中，限制请求继续进入通道；其响应需要相关 upstream 通道排空。作者不把这个模型当作内部微架构的逐门还原，而是依据公开手册构造可解释的语义。

手册对“其他通道上的单通道 fence 是否也阻止写重排”描述不清。实机未观察到某弱结果，但作者在正文仍选择较保守、允许更多行为的解释，没有仅凭未观察到就增强规范。

## 6. 公理语义与尚未覆盖的程序

公理模型显式区分请求和响应，并通过 pair 关联。普通 CPU 内存模型常用一个事件表示一次访问，但这里省略请求/响应的区分会错误合并“先发出的旧读晚返回”和“真正等待完成后才发新读”。

十项约束涵盖 CPU coherence、传播、读写顺序、fence 响应和 fence 对后续写的阻塞。模型只把 CPU 的相应行为限制为 TSO，不假定 FPGA 具备全部单地址 coherence。

论文要求请求与响应精确一一配对，不分析 dangling request 或复用同一 metadata 引起的歧义。设备侧单个 FPGA 线程也是生成测试的条件。这样的正常执行内存模型不能自动证明恶意 Host 的通知伪造、Client 身份混淆、设备 reset、取消或跨代次响应安全。

本项目已有 cookie/epoch 等机制，恰好用于覆盖这类模型没有处理的生命周期身份；应把它们加入项目的协议模型，而不是因论文已有 pair 关系就省略。

## 7. 双模型交叉验证的实际强度

作者以 C 编写操作模型，由 CBMC 检查指定 trace；Alloy 实现公理模型，自动生成“刚好被禁止”的执行。移除关键事件后应转为允许，再把这些执行转译到 CBMC 交叉检查。

| 参数/结果 | 论文口径 |
| --- | --- |
| 操作模型步数 | 30 |
| CPU 线程 | 最多两个 |
| upstream/downstream 容量 | 各二 |
| 读/写请求池容量 | 各四 |
| CPU 写缓冲容量 | 二 |
| 手册例子 | 17 条 trace |
| 自动禁止测试 | 583 个，四至八事件 |
| 自动允许测试 | 180 个，由删除 fence 等关键同步产生 |
| 交叉检查跳过 | 34 个含超过两个 CPU 线程的测试 |

`--unwinding-assertions` 用于检查 C 循环展开是否足够；它不能扩大数组容量、线程数和 MAX_TIME，更不能证明模型与任意实际硬件等价。论文的可达性 smoke test 也只是辅助排除显然过小的步数。

作者没有给出两个无限状态模型的完整等价证明。操作/公理交叉检查、与手册一致、硬件有限实验是三类互补证据，各自存在边界。

## 8. 实机结果：不能省略 stress 的覆盖范围

作者使用 Broadwell Xeon 与 Arria 10。每项测试运行一百万次；为避免每个 litmus 单独综合一至两小时，作者实现一次综合的软核 litmus processor，由 CPU 上传事件序列，并记录实际响应顺序。

| 运行集合 | 禁止结果 | 允许弱结果 |
| --- | --- | --- |
| 全集，无 stress | 0/583 个测试观察到 | 0/180 个测试观察到 |
| 人工调优 stress 的子集 | 0/10 个测试观察到 | 4/10 个测试观察到 |

这里分母是测试数量，各测试又有一百万次迭代，不是总共仅运行 583 次。引言概述可能让读者以为全部测试都在 stress 下完成，应以 §6 和表 3 的实际集合为准。

未压力运行的 180 个允许结果全部未出现，仍不代表模型过弱或硬件保证更强。调优压力后十个中的四个出现：跨通道重排三项都能触发，请求池重排三项中一项触发，特定响应顺序四项未触发。

自动压力调参遭遇设备无响应，作者改为人工调节、必要时重新刷写，只完成选定子集。本轮没有运行这些操作；这些是论文作者的实验限制，不是当前实验室 Host 的状态。

## 9. 队列实验：正确同步仍可优化

案例是 32 槽、64 位元素的单生产者/单消费者环形队列。producer 写 payload 后更新 tail，consumer 先确认 tail 再读 payload，之后推进 head；既需发布顺序，也需防止旧槽过早被覆盖。

作者给出两种正确实现：固定同一通道并等待响应；允许多通道并使用相应 fence。通过四类关键交互 litmus 验证基本 enqueue/dequeue 顺序，但这不等于任意无限运行队列的完整形式化证明。

重负载下，多通道正确版本耗时约为单通道版本的 60%，即该实验约少 40% 时间。它来自通道分摊，不是取消同步，也不能作为本项目性能收益预测。

去掉 FPGA 写响应等待及 fence 后，无 stress 时 enqueue/dequeue 更快且错误少；stress 下 FPGA enqueue 约有 11% 元素错误，图中个别点为 12%–13%。dequeue 图中显示 0% 错误，也不能把该方向认定为无需同步。

论文允许在近似计算中讨论这种有损队列，但安全控制消息、授权、完成与撤销需要保留精确语义。模型授权及完成的控制面不能因最终图像看起来正确而容忍丢失或错序。

## 12. 对项目完成链的具体启发

本项目的可信 ProxyRealm、RMM Client 身份、映射授权、受保护 Stage-1 与固件前提保持不变。已有 GPUVM、认证队列、私有快照、native fence、cookie/epoch 和 persistent IRQ127 是分析基础。

建议文档对每个阶段给出明确谓词：任务已经被接受；GPU 已真正结束；输出写对所需观察者可见；可信终态已发布；对应 Realm 被唤醒；Client 已验证并消费。可以优化中间调度和通知次数，但成功终态不得跳过必要的可见性阶段。

不是每个阶段都必须单独新增一次 fence。应先利用现有驱动、DMA API、锁和认证队列的保证，标清实际边，再只补缺失条件。CPU 的 release/acquire、设备 cache flush 和 SMMU 失效完成分别服务不同对象，不能互相代替。

## 13. 内存与中断两个方向的共同状态机

| 项目事件 | 需排除的结果 | 已有基础及下一步 |
| --- | --- | --- |
| 合法映射执行 | 页已转属其他 Client，旧任务仍可访问 | 在实际页授权与生命周期中表示在途操作 |
| native fence 完成 | 完成对象正确但输出对 Client 仍不可见 | 明确现有 cache/DMA 同步所在位置 |
| 发布认证完成记录 | 身份正确而 payload/状态跨代次混合 | 将私有快照、cookie/epoch 与发布顺序一起建模 |
| 投递/合并 IRQ127 | 唤醒推进错误任务终态、重复消费 | 保留通知与完成状态验证的分工 |
| 回收/撤销 | ACK 后旧写或旧 completion 影响新对象 | 分开描述停止提交、排空、失效、确认与复用 |

本篇不能证明这些性质已经满足或存在漏洞；它帮助定义应检查什么。未来负例可覆盖旧读已发出但延后返回、先通知后数据可见、两个 Client 同 VA/不同对象、reset 后旧完成、错误响应和重复通知。

## 14. 文献定位与独立评价

PORTAL/CAGE/ACAI 规定谁管理设备、谁可以访问哪些页；PhantomMap 关注实际物理页及映射生命周期；Devlore、SHELTER 及机密 VM 中断论文关心来源和路由。本篇补充异构请求、响应与数据可见性，不能替代上述安全机制。

对项目最有价值的研究组织方式，是在“直通与共享实现/性能”与“任务隔离安全”两个大部分之间，用明确的完成和回收语义连接：第一部分的优化是否保持第二部分所需的状态转换与可观察结果。

独立评价：论文的双模型、软核测试和正确/有损队列对照具有很强方法价值；应同时保留有限线程/容量、stress 子集、精确配对假设和公开 artifact 差异。它支持提出更严谨的可信通信设计，不能包装为新发现的 CCA GPU TEE 架构。
