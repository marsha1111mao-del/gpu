# Securator（HPCA 2023）：自动版本生成、层级聚合完整性与可信完成边界

## 研读结论与材料

Securator 沿 TNPU/GuardNN 的数据流优化继续前进：以少量参数和片上状态自动产生 tile 版本，不再逐项读取软件版本表；同时将逐块认证值在片上 XOR 汇总，减少片外 MAC 存储和流量。它适合研究“为了性能将检查延后、合并之后，究竟还证明了哪些访问与副作用”。

本报告最重要的独立判断是：XOR 聚合的等式首先表达带标签项出现次数的奇偶关系，不自动表达每一次重复读取都正确。对正文的只读重复读取检查，可给出有条件的代数反例；此外，消费层验证前已经产生的输出，以及网络最终输出由谁验证，需要明确的发布屏障和终态协议。以下不把这些分析写成已复现的实现漏洞。

论文：Nivedita Shrivastava、Smruti Ranjan Sarangi，Securator: A Fast and Secure Neural Processing Unit，IEEE HPCA 2023，1127–1139 页，DOI：[10.1109/HPCA56546.2023.10071091](https://doi.org/10.1109/HPCA56546.2023.10071091)。[作者官方出版页](https://www.cse.iitd.ac.in/~srsarangi/publications.html)直接链接[全文](https://www.cse.iitd.ac.in/~srsarangi/files/papers/securator.pdf)。

本篇是专用 NPU TEE/安全内存研究，不是 CCA GPU 多 Client 系统。硬件是论文架构和实验载体；本报告不以 RK3588 能力否定目标设计，也不把作者模拟、FPGA PoC 和本项目测量混在一起。

## 1. 问题、可信基与安全范围

TNPU 为 tensor/tile 保存可信版本，GuardNN 也将数据流引入版本管理，但仍需要逐块 MAC 或相关缓存。Securator 认为规则的 DNN 读写序列可以再压缩成参数化规律，用更少状态覆盖整个层的输出与后续消费。

CPU/NPU 不必在同一封装，可信 CPU 代码、NPU、相关缓存与通信接口属于可信基；OS、hypervisor、恶意进程和片外物理攻击者可控制或观察 DRAM/总线。Host 可以只在开始时初始化，也可以继续调度，但安全关键的命令和参数必须来自可信代码及可信传输。

正文前部称 CPU scheduler 可选运行于 TEE，安全分析又假定可信 Host 代码在安全执行环境中。不能由“调度可选”推出恶意 Host 可以任意替换安全参数而无须认证；实际部署仍要确定哪些输入具有授权效力。

研究限于 inference；数据相关访问导致不可预测的 VN 模式，作者明确不支持。动态剪枝、条件路由、任意 GPU 原子写、一般并发 kernel、动态 LLM KV cache 都不能因“本方案可编程”而视为已覆盖。

作者将机密性、完整性、身份与新鲜性列为目标，也讨论 model extraction；功耗和电磁侧信道不考虑。论文未给出多租户公平性、抗 DoS 或可信完成时限，安全失败后的 reboot 也不构成可用性保证。

## 2. 版本序列如何压缩

论文分析卷积的 input/weight/output reuse、不同 loop order 和 tile 组织。读/写观察者记录的是数据离开或进入 global buffer 时的 VN 序列，不是只根据算子名称判断版本。

例如两输入通道、三输出通道，在部分结果逐次写回时可出现 `1,1,1,2,2,2`；随空间 tile 再重复。不同数据流产生 multi-step、step、linear、sawtooth、line 等模式，Table II/III 分别列出输入/输出复用与权重复用。

它们用统一表达式 `(1^η, 2^η, …, κ^η)^ρ` 表达：η 为每个 VN 的重复数，κ 为 VN 阶段数，ρ 为整个序列重复数。这里指数表示序列重复，不是整数乘方；三元组与片上 FSM 决定运行时 VN。

矩阵乘法另按固定 P/Q/R 的 tiling 方式列出模式；图像预处理分三类，分别是单通道映射、多个输入合并成一个输出、多个输入映射成多个输出，附录给出对应 loop order 和读写模式。

可将某些 GAN/Transformer 基础算子映射到这些规律，不等于任意完整模型都已用同样安全协议验证。作者也受 Timeloop 可模拟的数据流和篇幅限制，没有穷尽所有组合。

三元组要安全传给 NPU，而且必须与真实指令、数据块身份、tile 边界和执行进展一致。省去版本表没有省去可信状态：FSM、参数、层/feature-map ID、块索引、重启边界和合法命令共同承担原先版本管理的一部分责任。

## 3. 加密与密钥的具体描述

Securator 用 AES-CTR 加密每个 64B 数据块，正文称使用四个并行 AES-128 engines。major counter 由 fmap ID 与 layer ID 构成，minor counter 由 VN 与 fmap 内块索引构成，随写入更新 VN。

正文用 accelerator secret ID 与执行前随机数拼接成 128-bit key，意图让密钥随硬件与每次执行变化。这不是完整的 KDF/熵分配/密钥传输规范；不能仅凭“128-bit 宽”推出秘密熵、域分离和安全建立全部满足 128-bit 密钥安全目标。

64B 有四个 16B AES 分组，实现必须使各分组 pad 输入不同，并保证同 key 下任意同位置重写不复用旧 counter。论文概述没有给出完整位域宽度、溢出、四 lane 编码和恢复协议，本报告不据此判定实现必然复用 pad，而是保留实现核对条件。

命令经共享 key 从 Host 交给 accelerator；初始输入、权重加密后放入内存。正文把 session key 或 public-key 加密视为 authenticity 的既有解法，但加密本身不自动认证请求来源、完整内容和新鲜性；需要明确实际采用的认证协议及证明对象。

## 4. 层级 MAC 与跨层核对

逐块中间认证值为 32B：`MAC_B = SHA256(P || L || F || VN || I || B)`，P 为 accelerator secret ID，L/F 为层/fmap ID，I 为块索引，B 为 64B 内容。它是正文的 secret-prefix hash 表达式，不是已给出参数化证明的标准 HMAC。

不能简单把它叫作“公开 SHA256 校验和”，因为 P 被假定秘密；也不能仅凭摘要称“MAC”就自动赋予完整 PRF/消息认证证明。若各字段固定长度、编码规范且 B 固定 64B，常见的任意附加消息长度扩展不直接等于这里存在可用攻击，本报告不提出这种未经证实的断言。

MACW 与 MACR 分别 XOR 汇总写和读的 MAC_B；当前层最后写出的结果留到消费层首次读取，用 MACFR 汇总。核心条件为 `MACW = MACFR XOR MACR`，意图验证生产层的全部写入由自身中间读回或消费层最终读取覆盖。

论文用交替的两组寄存器应对跨层重叠，并称多输出、skip/back connection 也可适用。但任意图中生产层可能被多个较晚消费者分批消费；需要说明每个生产者的期望集合、首次读取归属、状态保留和结束条件，不能由两组寄存器概述直接推出一般图的完整协议。

只读输入和权重另用 MACIR 汇总，VN 固定为生产层最后版本或权重版本 1。同一 ifmap tile 读偶数次时目标为零，读奇数次时为首次读取的 MACFR；正文据此认为输入也完成验证。

论文引用 Bellare、Guérin、Rogaway 的 XOR MAC 研究支持安全性，但没有在本文给出把本构造、重复读取、字段编码、消息结束和对手能力归约到该研究具体定理的证明。本轮未完整研读被引用的原始论文，不将引用本身当成这里构造已满足其全部前提的证据。

## 5. 独立分析：重复读取的 XOR 相消

先只考虑正文描述的只读检查，固定同一块的全部身份字段，令 `h(x)=SHA256(P||L||F||VN||I||x)`。合法三次读取 x 时，MACIR 为 `h(x) XOR h(x) XOR h(x) = h(x)`，MACFR 也为 h(x)。

若首次读取正确，后两次均读成相同错误内容 y，则 `h(x) XOR h(y) XOR h(y) = h(x)`。最终 MACIR 与合法执行完全相同，MACFR 仍然正确；这个结论不需要 hash 碰撞、恢复 P 或伪造单个 h(x)。

它的成立条件是同一块确实重复读取、两次使用相同身份/VN，验证只使用所述奇偶 XOR 关系，而且错误内容在读取后参与计算。对固定 CTR pad 的只读重读，攻击者在两次读取前提供相同的修改后密文，可使两次解密得到同一个 y；不必知道 y 的明文具体值。

这说明仅靠所述聚合等式不能证明“每次读取的内容都正确”。加入地址、fmap ID 或 layer ID 可以防不同身份项的直接交换，但同一个身份的两个相同错误项仍会相消。只验证总次数而不区分每次读取出现，也不能排除此例。

这不是对完整公开实现的利用结论：本轮没有匹配实现，也没有确认是否另有逐读检查、不可变片上副本、每次读取唯一身份或其他限制排除上述条件。它是对正文所述只读验证规则的条件性代数反例，不应被弱化成“SHA256 不够强”，也不能被扩大成已恢复模型或完成 FPGA 攻击。

可选的修正方向包括只在第一次认证通过后从受保护副本复用，或为不同出现建立经证明的认证结构。单纯给读取计数加一、随机等待或把 XOR 换成更宽 XOR 都不足以证明修正成立；具体方案需重新分析读写语义、开销和允许并发，而非补一个无调用者的 token 字段。

## 6. 延后验证、最终输出与可信副作用

消费者开始读取并使用生产者数据，才逐步形成 MACFR；生产者输出的正确性可能在消费层已经执行部分计算之后才被判定。即便最终能检测篡改，也需要把未验证输入引起的影响限制在可丢弃的状态中。

可暂存的内容包括 speculative 输出、错误状态和后续 DMA 请求；不能在验证前触发不可撤回的外部输出、授权变更或其他 Client 的可见状态。本文没有描述覆盖全部这些副作用的 poison/commit 协议，也没有量化完整的错误传播窗口。

网络末层没有下一层消费者，外部 CPU 或远程用户需承担最终认证端点；必须说明如何获得可信期望、确认本次任务和决定输出发布。不能把“中间层有后继校验”当作最终输出自然已认证。

正文说 security breach 后 reboot，PoC 却明确未实现 raising an alarm 的系统。这限制了原型对 fail-closed 反应的证据：演示可接入加密/版本模块，不等于已验证错误阻断、reset、安全回收及重新执行后的连续性。

## 7. 模拟、FPGA PoC 与综合分别做了什么

内部 cycle-accurate CNN simulator 被作者称已与 SCALE-Sim 和 native hardware 对照验证，但没有给出本轮可核验的完整验证数据或实现。Timeloop 用于选择数据流，不应把作者的“optimal”表述理解为穷尽全部数据流并证明全局最优。

主配置为 32×32 PE、240KB global buffer、2.75GHz、双通道 DDR4、100-cycle memory latency、64B 块；secure/TNPU 用 4KB counter cache、8KB MAC cache。文中按 4B pixel 分析一块存 16 pixels；这些配置不与 TNPU 原文 Float16、480KB total SPM 等数值自动等同。

表中列出 MobileNet、ResNet、AlexNet、VGG16、VGG19；后续评估另包括 GAN 和 basic Transformer。不能据此写成现代 LLM、多 Client GPU 任务或动态数据访问验证。

PoC 使用 CHaiDNN v2、Vivado HLS 2018.2、SDSoC、ZCU102。前端将每层三元组放进 dummy layer，后端跳过该层、追踪主存请求并接入安全模块。Host 代码未修改与框架接入工作量有关，不代表 Host 信任链、命令认证和异常处理无需实现。

作者称 triplet generator 实验验证，AES/SHA/VN 模块易于接入；同时明确 PoC 未实现安全异常告警。本轮没有取得对应 PoC，也不把 general CHaiDNN 源码当成已取得安全实现。

VN generator、SHA256 和 AES 用 Verilog 实现，Cadence Genus 在 28nm 下综合/布局布线，再依据引用工作缩放到 8nm。它们的综合估计与 ZCU102 PoC、性能模拟是三类证据，不是同一系统在同一工艺上的实测。

## 8. 数字结果与比较边界

作者明确 performance 是执行时间的倒数。摘要与结论说相对 TNPU 吞吐改善 20.56%，正文性能段又称 performance overhead 减少 20.56%；缺少完整原始数据，保留不同措辞。若按吞吐口径是 1.2056×，固定工作量时间减少约 `1−1/1.2056 = 17.05%`，不能同时说时间减少恰为 20.56%。

动机 Figure 4 讨论 secure/TNPU/GuardNN 比无保护“慢”45%/27%/75%；后文又给 GuardNN 约 64% performance degradation。配置、workload 集合和倒数口径未完全展开，不能把它们当作相同条件的单一数字，也不能用后来数字擅自覆盖前文。

Securator 的比较同时改变 VN 生成和 MAC 聚合，并移除相关片外访问/缓存；20.56% 只能归因于该组合，不能全归因于某一个硬件 FSM。作者模拟的 GuardNN 无 MAC cache、TNPU 有 8KB MAC cache，也不代表对两篇原作者实现做了相同平台的实测。

正文称 TNPU MAC cache 约 35% misses、伴随约 21% DRAM access 增加，Securator 降低这些流量。自身逐块中间 hash 为 32B，竞争方案片外 MAC 为不同粒度/长度；它减少片外标签流量，但仍有每次读取计算 hash 的成本，不能说完整性检查完全没有带宽、延迟或流水压力。

Table VI 给 AES128/SHA256/VN generator 面积分别为 3900/270/40µm²、功耗 640/40/4.4µW，随后汇总为 4210µm² 和 sub-mW，数值对应每类各一个模块。前文却要求四个并行 AES engines；若表中 AES 数字是单 engine，则四个的简单加和为 15910µm²、约 2.6044mW。原文没有解释计数口径，本报告保留这一条件性算术差异，不把推算当作真实完整实现面积。

这些数字不包括完整 NPU、Host TEE、认证链、错误告警、隔离配置和恢复逻辑，不能从小模块面积推出整个安全 TCB 或系统成本同样小。8nm 预测也不等于实际流片功耗。

Securator+ 的 layer widening 将 MobileNet 基础层 111×111×3 扩到原大小的 3–7 倍，相对 TNPU 的收益从原始约 16.6% 到 7× 时约 21%。这是扩展尺寸的性能实验，没有展示实际模型提取攻击的成功率、泄漏界或给定攻击者下的机密性证明。

正文“无 cache 因而无 cache side-channel”也仅能支持受限 scratchpad 数据路径的论述；图示仍有 CPU/L1/LLC/通信等组件，不能据此排除整个异构系统的共享资源、调度与时间通道。Padding 或 dummy network 的性能可承受，不等于 side-channel 已消除。

## 10. 与项目的关系和可研究设计

保持既定设计：RMM 认证原始 Client，可信 ProxyRealm 统一控制 SMMU；建图校验对象、实际 HPA、权限与生命周期，软件 IPA→HPA 合成为受保护 GPU Stage-1；其他设备继续硬件 Stage-2。实际页表、根配置、MMIO、可信固件与撤销后回收仍作为平台保护基础。

Securator 没有否定该内存隔离设计，而是补充“合法页里的内容”和“内容何时被认证”的问题。仅当项目需要将重复读取、结果完整性或片外攻击纳入目标时，才考虑对应认证机制，不因引用一篇 NPU 论文就为全部 GPU 数据再加一套 layer MAC。

已有 GPUVM、认证队列和私有快照可以承担对象与输入固定的基础。重要的是说明同一对象被多次读取时，是反复使用同一受保护快照，还是允许不可信共享内容变化；聚合检查不能把多次使用压成只有奇偶性的统计值。

已有 native fence、cookie/epoch 和 persistent IRQ127 应对应真实任务终态，但 fence 只反映它所定义的执行完成条件。若采用延后校验，还必须让“全部所需校验成功、输出可见、可信完成发布”有明确顺序；校验失败不能借普通成功 IRQ 提交结果或提前释放资源。

对折叠 fence、合并 IRQ、批量唤醒等优化，可借鉴的是验证优化后的观察/状态变化与原协议一致：每个应交付终态被覆盖，重复事件没有额外副作用，跨 Client 不能靠重复计数相消，失败不能被聚合成成功。复用现有身份字段与状态机，不重新堆叠重复 token 框架。

若后续确实需要安全批量认证，应先定义需要证明的是集合、出现次数、顺序还是每次使用的内容，以及允许验证前发生的副作用，再选有对应安全论证的结构。Securator 的性能收益提供研究动机，不能充当这些协议性质的证明。
