## 2. 研究问题与分类方法

综述的问题不是“如何再造一种TEE”，而是：CPU TEE扩展至GPU后，保护哪些组件；GPU原有攻击是否仍成立；CPU TEE攻击会怎样破坏GPU服务。它把CPU侧GPU驱动与运行时、GPU执行和内存、CPU–GPU互连、电源管理，以及共享微架构资源连接起来考察。

结构为：§2介绍GPU、攻击类型和CPU TEE；§3给分类；§4比较GPU TEE；§5总结GPU攻击与防御；§6讨论潜在GPU TEE攻击；附录A补CPU TEE攻击。核心贡献是攻击面组合与研究路线整理，不是对全部系统给出统一安全证明或当代产品支持清单。

§4按x86与Arm分类，表2列11行：Graviton、HIX、HETEE、H100、TNPU、LITE、SAGE、Honeycomb，以及StrongBox、CRONUS、CAGE。TNPU是NPU保护研究，其纳入用于异构可信计算比较；不能把11行全部计为11种严格意义上的GPU架构，更不能计为11种CCA方案。

ISA分类便于定位生态，却不足以决定安全模型。更适合本项目的比较维度是：可信管理者在哪里；不可信驱动能提交什么；谁认证原始请求者；映射与完成状态由谁产生；设备是独占、时间复用还是空间共享；哪些状态需在交接时清除。

## 3. GPU TEE 路线及其可迁移部分

| 路线 | 综述中的代表和机制 | 对本项目的比较价值 |
| --- | --- | --- |
| 设备内可信资源管理 | Graviton：命令处理器管理资源，主机驱动不可信 | 对授权、实际执行和回收建立单一权威 |
| CPU可信组件管理GPU | HIX、Honeycomb：保护必要控制路径或以monitor/静态验证约束代码 | 缩小输入接口，检查可信代码究竟担保什么 |
| 机架级可信管理 | HETEE：独立控制器和设备资源分配 | 设备交接及管理面信任，不等同逐Client并发 |
| 软件证明/加密域 | SAGE、LITE：软件证明或寄存器内解密计算 | 安全条件不同，不能互换为访问控制证明 |
| 厂商支持的CPU CVM＋GPU | Hopper H100 | 启动、证明、会话和重分配生命周期 |
| Arm TrustZone扩展 | StrongBox、CRONUS | 内存权限组合、受保护控制路径及共享粒度 |
| Arm CCA扩展 | CAGE：shadow task与受保护的GPU内存视图 | 与本项目的可信服务Realm路线逐项比较 |

Graviton并不要求CPU侧SGX；综述§4.1明确这一点，但§6.4又将Graviton、HIX、HETEE概括为通常基于SGX。报告采用各系统具体设计，不把章节末概括强行套给全部例子。

Honeycomb的静态验证针对其代码与执行模型，CAGE的shadow task针对不可信大驱动，ProxyRealm路线则信任服务Realm中的后端。三者减少或转移的可信内容不同。建图期授权检查与load-time验证有相似的前移思想，但不能据此认为任意命令、权限和生命周期都已验证。

StrongBox的顺序执行模型不能外推为Arm GPU普遍不支持并行任务；本项目已有多个Client的真实GPUVM和共享调度。共享模式改变后，应重新检查并发可见状态、GPU缓存/TLB、错误恢复和跨Client通知归属。

## 4. “保护”必须分开陈述

综述表2包含attestation、secure resource management、secure I/O、integrity及GPU memory encryption。表中勾号只表示作者的分类，且带附加支持/未来能力的脚注；不是各系统所有版本都交付这些能力的证据。

资源访问控制阻止未授权主体读写页；物理内存加密针对特定物理观察；完整性保护防篡改但还要明确新鲜性；可信I/O需要正确端点与会话；远程证明描述测量和策略接受。任一项都不能独自推出输出确实来自正确Client的正确任务。

GPUVM分离同样不等于消除缓存、TLB、互连、调度或中断时序泄漏。对本项目，应明确哪些时间、任务大小、唤醒次数可被其他Client或Host观察；若侧信道不在安全目标内，应直说，避免把功能隔离命名为全面非干扰。

本项目硬件作为模拟实验载体，按用户给定平台保护假设分析：实际页表、根配置、关键MMIO及固件加载受可信控制。不因某现有板卡缺少CCA硬件功能否定协议；也不因实验能运行就把目标平台全部安全属性判为已测。

## 5. 需要修正或保留时效的综述描述

Hopper部分在§6.2推测GPU采用类似SGX的MEE，表2也将H100列为具备显存加密。此前保留的[NVIDIA CVM威胁模型](https://docs.nvidia.com/confidential-computing/virtual-machines/dev/threat-model)明确：GPU内存中的明文由硬件访问控制保护，GPU memory encryption不是其机制。因此不能把该推测当作HBM普遍片外加密的产品事实。

同一官方快照说明其配置为整GPU分配给单CVM，所述CC配置不支持MIG、MPS、GPUDirect RDMA。综述关于H100上多tenant MIG的分析适合作为潜在研究场景，不能证明这些CC共享模式已部署。未来支持变化需查具体版本；该限制也不否定本项目研究可信共享的价值。

§2.1对NVIDIA/Arm驱动闭源、MPS缺少地址空间隔离的概括不能无版本适用。当前项目直接使用开源Panthor源码；开源驱动不意味着设备MCU和固件全部开放，驱动开放也不自动提供恶意多租户安全。应按实际软件代际和共享模式描述。

§6.2将CacheWarp称为最新SEV-SNP仍未缓解，附录又列microcode更新为防御。它没有提供当前每一CPU/固件版本的公告核验，不能据此宣称2026所有SNP或Hopper部署都可被同样利用。本报告不补造补丁结论，仅保留攻击成立所需版本和配置条件未逐一复核。

所读§5.3–5.3.3文本多次把物理电磁信号及“隔墙数米”描述为MMIO信号。工程上必须区分EM电磁泄漏与MMIO寄存器访问；保护MMIO映射不会自动屏蔽物理电磁信号。本轮未逐像素核对PDF排版，因此将其记录为所读文本的术语混用，不据此重构原实验细节。

表3和正文§5.2.2对隐蔽信道的单位也不一致：2017工作4MB/s对4Mbps，NoC工作24MB/s对24Mbps，TLB工作81KB/s对81Kbps。三组均可能相差8倍；未重读相应原文前不选择其中一组作为定量比较依据。不同信道、错误率和测量条件也不能按单一带宽排序安全性。

CAGE段给CPU隔离2–26K及Monitor1301行。既有独立CAGE报告显示1301是新增Monitor代码，约26k RMM/约2k SHELTER是不同CPU隔离选项，仍依赖已有Monitor等可信组件；不能把这些数字写成全系统TCB。综述自己也承认仅LoC无法合理比较安全高低。

## 6. GPU 攻击的实际研究启发

架构/逻辑攻击部分关注新分配页、跨上下文寄存器和共享内存残留。清零必须覆盖真正会交给新主体的状态，并在旧访问停止后进行；“用户BO已清零”不等于上下文、固件内部状态、缓存和页表生命周期都安全。具体应清什么取决于目标设备状态模型。

微架构部分区分CPU–iGPU共享LLC/互连、同GPU资源竞争和跨GPU/NVLink。MIG的末级TLB例子提示：即使缓存和DRAM路径分区，翻译结构仍需单独检查。对GPUVM隔离的正确论证是非法访问不能产生架构可见结果，不能把它扩大成所有共享结构无可观察差异。

限制性能计数器和高精度timer有价值，但综述引用的WebGPU工作通过共享变量与专用线程构建计时器；因此“禁用某个计数器”不是消除全部计时能力。合法任务的完成延迟、队列反压和IRQ频率也可能提供观察面，项目要明确允许泄漏。

物理/故障部分表明CPU侧管理权限可以影响GPU电压、频率、PMIC或reset。用户给定假设已经保护关键MMIO，后续仍可核对哪些电源/复位操作由可信层代理、参数范围和顺序是否合法；不能只限制GPU寄存器而遗漏仍能改变设备状态的其他控制器。

综述将随机负载、噪声和masking并列讨论，但添加随机GPU工作并不天然具有密码学掩码的独立性证明。分区、常时间、隐藏调度或噪声方法都需给出可保护的泄漏模型及开销；它们可作为扩展，不宜未经验证纳入本项目主贡献。

## 7. CPU TEE 攻击如何影响 GPU 服务

附录A覆盖SGX页表/缓存/分支/瞬态执行、ABI和接口、故障注入；TrustZone实现错误、缓存和DVFS；SEV加密完整性、ASID/TLB、CacheWarp以及中断驱动攻击。其核心价值是把CPU侧可信服务看作GPU保护链的一部分，不能假设“驱动放进TEE后无需再审查”。

接口攻击尤其贴近ProxyRealm：可信代码可能复制共享字段、调整引用、发布完成或恢复执行。字段格式正确仍需核对原始Client权限、当前对象代际和合法状态。私有快照阻止校验后共享数据被更改，却不替代对象引用、权限和reset交错的一致性。

WeSee说明伪造事件原因可诱导可信handler读写不该触及的状态；Heckler说明非timer事件的handler可改变控制/数据流；SEV-Step则主要支持单步观测与组合侧信道。三者作用不同，不能笼统写成“所有中断都绕过内存保护”。

既有WeSee独立报告明确其不适用于论文所分析的TDX与CCA，Heckler也单独讨论CCA过滤及未见同类handler。本综述引用x86攻击不能构成Arm GPU存在同类漏洞的证据。可迁移的是来源、事件原因、接收目标及handler副作用必须符合授权，而不是照搬x86中断号或异常机制。

附录建议禁用handler或监控注入，属于原则性方向。GPU正常服务依赖合法完成/错误中断，实际设计更需要可信路由与状态验证；单纯禁用全部中断既不能解释服务进展，也不能保护被其他途径调用的业务逻辑。

## 9. 当前代码的限定交叉检查

本轮完整读 `opencca/tf-rmm/runtime/core/xshm_irq.c`，定向读 `xshm_endpoint.c` 的305–440行以及Proxy驱动545–615行。记录全文文件哈希是输入定位，不表示把这些大文件全部审计，也没有新增硬件或故障测试。

IRQ代码拒绝Host使用保留LR或伪造占用可信INTID，并由可信注入路径保留Active状态再置Pending。endpoint分支核对调用端是否属于channel；NOTIFY递增对端pending，ACK限制序号范围，ACK_ARM仅更改认证接收端事件并要求队列重查。该分支的持久pending与唤醒hint分离，不把一次IRQ视为唯一数据记录。

Proxy快照发布函数根据已signal的native fence检查error，仅无error时用release写cookie；unwatch取消回调或等待回调结束后释放fence引用和slot，避免旧回调写入复用槽。本轮只确认该局部代码行为；完整chain成功条件、全部reset/cancel交错及GPU数据可见性还需既有全链证据和定向验证。

这些观察支持继续使用现有机制，而不是另造身份token：RMM身份、GPUVM、认证队列、私有plan/snapshot、原生fence、cookie/epoch和IRQ127应共同表达一条任务生命周期。epoch失效仅阻止旧逻辑凭据再被接受，不能当作GPU已停止DMA的证据。

## 10. 建议的论文设计与验证组织

第一部分“Arm GPU直通/共享实现与性能”描述CPU/设备控制分工、可信服务路径和可复用计划。分别测创建/首触、注册/建图、首次执行、温态提交、完成回传及撤销；说明工作量、频率、并发、对象池和版本，不将综述中CAGE对StrongBox的1.96–13.16%跨平台复制为项目收益。

第二部分“GPU任务隔离”把内存和通信统一为：认证接收→私有快照与授权→真实提交→可信终态→数据同步及输出可见→发布成功/错误→静止后回收。这里是项目规范建议；当前代码已有若干机制，不能把该建议包装成全部已实现或已发现缺陷。

建议安全不变量包括：Client身份与GPUVM/对象始终一致；计划命中不绕过生命周期检查；任意通知都不能越权改变他人任务；成功仅由对应真实终态产生；重复/乱序通知不重复执行；错误/reset不落成成功；撤销后旧引用和翻译不能访问新归属页；重分配前有设备静止与必要清理证据。

评估应同时覆盖恶意共享描述符、旧cookie/epoch、跨Client handle、未完成fence、重复/丢失/乱序通知、cancel/reset与回收交错。合法进展、公平性、通知时序泄漏与功能隔离分开报告；Host拒绝调度的无限延迟不能归为设计已提供的无条件可用性。

## 11. 独立评价与后续文献

优点是将CPU TEE接口/中断、GPU残留、资源竞争和设备管理放入统一威胁分析，避免只保护显存数据。局限是系统分类与实例有概括冲突，文献覆盖未延续至Portal等主线，部分产品假设、单位及术语需要回到原始证据；不存在对全部GPU TEE的一套实测排名或已证实攻击矩阵。

后续优先沿中断研究追踪SEV-Step的原文和工具，区分单步观察与伪造完成；沿共享观察面追踪TLB-pilot、TunneLs、Leaky Buddies等，原文未读前只列候选。新的模型保护候选MirageNet、TEE-X则比较完整Realm/分割与GPU可信边界，取得全文不计为精读完成。

未完成项包括出版方最终全文对照、所有194项原文及产品最新补丁覆盖、表中符号逐像素确认、所有攻击的真实GPU可迁移性、完整项目安全审计和硬件验证。保留这些边界不影响本篇已完成的39页全文与独立分析。
