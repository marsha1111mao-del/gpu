## 2. 研究问题

传统 GPU 利用常争取直接破坏页表。PhantomMap 的观察是：分配真实页和建立映射之间存在多个中间结构，若攻击者能破坏保存页地址或页来源的元数据，而最终映射入口没有验证实际页，就可能让正常驱动帮助建立指向非预期页的映射。

分配与映射解耦本身并不构成漏洞。攻击链还需要可破坏的中间元数据、能触发的映射路径以及不足的最终页验证。把论文概括为“GPU 只要采用异步映射就不安全”会丢失这些前提。

## 3. 威胁模型与边界

攻击者是普通 Android 应用，但已具有某种有限内核堆破坏原语，例如 UAF、越界或 double free。论文研究如何把较弱原语放大为任意物理读写，再用于权限提升和内核代码修改；不是无需初始缺陷的远程攻击。

目标是原生 Mali kbase 的 JM 和 CSF 驱动路径。论文没有证明 Linux Panthor 或本项目 ProxyRealm 存在同一问题。CPU W^X、CFI 等主要限制 CPU 访问或控制流，并不能自动约束设备通过有效映射进行的写入；这也不等于所有阶段的 MTE 都无效，阻止初始内存破坏与阻止利用后的 DMA 是两个问题。

## 4. 攻击机制

可以将关键过程理解为：有限堆破坏 → 改写页地址或关联结构 → 触发正常映射操作 → 驱动安装攻击者指定的实际页 → 借 CPU/GPU 可达路径读写目标物理内存。安全问题不只在最后一条 PTE，也在决定这条 PTE 指向何处的页来源信息。

论文归纳六类关键结构，并分析不同分配来源到 CPU/GPU 映射入口的链条。相同末端映射函数可能消费不同来源的页，因此仅检查一个普通分配接口不足以覆盖导入、别名、池化或其他间接路径。

## 5. 静态分析器

分析器从映射 sink 出发，沿调用图向上追踪物理页来源和关键结构，再关联分配起点与来源类别。作者报告得到 16 个候选，经人工确认排除 1 个，最终保留 15 条链，其中 12 条具有读写能力，3 条为只读。

这个结果说明自动化分析能够发现多个中间元数据入口，不构成“所有映射链已穷尽”的证明。调用图、间接调用、驱动版本和人工分类都会影响覆盖率。`PageAnalyzer.cc` 的静态阅读也不能替代对完整工具的构建、运行和误报漏报评估。

## 6. CVE 与端到端验证的口径

论文分析 13 个 CVE，不能写成 13 个 CVE 均已完成独立端到端利用。15 条链的主要验证使用 CVE-2022-20409、CVE-2023-48409；另有 CVE-2025-21836、CVE-2022-38181 等代表性案例，其余部分根据原语能力判断适用性。

某些受限漏洞仍不能直接使用，例如论文讨论的 CVE-2023-20938、CVE-2022-20421 需要额外 cross-cache pivot。这反映了方法的前提，并不支持“任意轻微内核漏洞均能稳定升级为任意物理写”的说法。

## 7. 成功率与性能

作者报告 CVE-2023-48409 在 20 次试验中的成功率由 45% 提升到 90%；CVE-2022-20409 在普通条件下超过 95%，在 stress-ng 繁忙条件下相应对照约为 20% 与 50%。这些是具体漏洞、设备与条件下的结果，不能合成为通用成功率。

缓解措施评估使用 Pixel 6 / Mali G78 / JM 和 Pixel 7 / Mali G710 / CSF，21 个 Rodinia 应用，每项 30 次，报告均值和标准差。Table V 的几何平均开销分别为 0.56% 和 0.34%。单项有明显差异，例如 Pixel 7 的 BFS 为 1.91%，不能把几何均值当作所有任务的开销上界。

作者在 Rodinia 后执行 Android LTP，报告补丁前后结果一致。这支持所测配置下的回归结论；它不是所有驱动功能、并发状态、设备版本或恶意调度条件的完整正确性证明。论文分数也不能用于推断本项目 glmark 分数。

## 8. 缓解机制及补丁观察

论文在物理页元数据中加入 GPU 页类别标识：分配给 GPU 时设置，返回普通 buddy 分配器时清除，并在关键映射入口验证。其目标是阻止被破坏的页地址指向不属于 GPU 页集合的内存。

所读 CSF 补丁包含 protected allocation、用户页 pin/unpin、DMA-BUF 导入/解除、CPU mmap、alias 以及部分 fault 路径的标记或检查。这说明实现试图覆盖不同页来源，而不是只保护一个常规分配路径。部分检查对 `pfn_valid` 有条件分支，用户页 pin 路径也修改了原有地址数组填充逻辑；未结合完整版本和配套 pixel.patch 执行验证，不能据片段断言所有路径均正确。

页在 GPU 内部池中与返回 buddy 后的状态不同。标签清理必须与真实生命周期一致，也要考虑导入页别名、共享引用和并发映射。过去曾被验证为 GPU 页，不代表今后仍可授权使用。

## 9. 为什么仅启用 IOMMU 不够，以及适用条件

论文测试手机未启用相应外部 SMMU 保护。作者指出：若同一个已被破坏的驱动仍能设置 IOMMU 映射，增加一层由它控制的映射机制未必能阻止攻击。

这与本项目的假设不同。本项目把最终授权和真实页表控制放在独立可信 ProxyRealm，依据 RMM 认证身份检查 HPA；不能以论文这段讨论否定该架构。正确问题是：不可信 Client 的地址、页数组和句柄，是否都经过可信状态解析，再进入受保护的最终映射。

## 10. 与本项目的直接关系

`TYPE_GPU` / `PageGpu` 表达页类别，不表达 Client A 或 B 的归属、读写权限、对象代次或撤销状态。因此可以借鉴其“检查实际页”的方法，但不能把它直接作为跨 Client 隔离方案。

建议可信授权记录至少关联 RMM 认证的 Client 身份、对象身份及代次、实际 HPA 范围、访问权限、设备上下文以及有效生命周期。软件 IPA→HPA 翻译应使用可信且被固定的页归属状态；不要将 Client 提交的“物理页列表”视为授权凭据。

建立直接 HPA Stage-1 映射后，硬件持续执行限制，但已经失效的授权不会自动从 PTE 中消失。撤销需要同时关闭新提交、处理在途访问、移除映射并完成相关 TLB/设备同步，之后才允许页和身份被复用。具体同步步骤应依据所用 GPU/SMMU 协议实现，而不是把一句“清页表”视为完成证明。

## 11. 建议验证场景

| 场景 | 需要验证的不变量 |
| --- | --- |
| A 提交 B 的对象、IPA 或旧句柄 | 最终 HPA 授权必须绑定原始 Client，不能只检查数值范围 |
| 合法页数组在检查后被改写 | 安装映射消费可信快照或受锁定的元数据 |
| 导入、alias、分段对象、部分解除 | 所有实际页及权限均经过同一授权边界 |
| 撤销与提交并发、旧页重新分配 | 在途引用、失效同步与回收顺序一致；旧代次不能恢复访问 |
| 任务出错、reset、Client 退出 | 错误路径同样完成撤销，不能留下可达旧映射 |
| 旧完成通知晚到 | 不得让旧任务事件释放新代次对象或错误完成新 fence |

最后一项是由映射生命周期进一步推导出的项目测试方向，不是 PhantomMap 已证明的中断攻击。完成通知与资源回收的关联需要结合 Devlore、受保护中断和本项目实际协议另行分析。

## 12. 研究定位

这篇论文不是完整 GPU TEE，而是验证 GPU 内存管理信任边界的攻击与缓解研究。它对本项目的价值在于补充 PORTAL 的服务隔离、ACAI 的身份与映射归属原则：授权必须落实到实际物理页，且在所有映射入口和回收路径保持一致。
