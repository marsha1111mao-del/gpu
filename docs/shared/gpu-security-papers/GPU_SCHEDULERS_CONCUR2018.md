## 2. 问题与模型范围

GPU 上通常有比硬件驻留资源更多的工作组。若已运行组自旋等待尚未获调度的组，程序可能永远无法结束。互斥锁、跨组 barrier、生产者消费者通信需要不同强度的进展保证，仅有原子指令并不足够。

作者不逆向具体调度硬件，而以时序逻辑描述允许的执行路径，并据此说明同步算法能否免于调度饥饿。这里全文的 thread 实际指不同 workgroup，不是同一工作组中的 lane，也不是 VM、Client 或 vCPU。

预设为固定工作组数、组内确定计算、所有组从开始到结束一直 enabled、程序在公平调度下应能终止，以及 sequential consistency。自旋仍是 enabled。动态任务生成、休眠唤醒、弱内存和任意恶意无限循环均不在这套证明的直接范围。

## 3. 核心定义：公平性限制执行路径

程序建模为带工作组标号的 LTS；一条执行记录状态和哪个组执行了步骤。公平性是对无限路径的约束，不是源码里增加一把锁，也不是一次 GPU 测试的通过结果。

弱公平性为：对每个 t，如果从某点起一直 enabled，则该组此后总会再次执行。时序写作 `∀t: ◇□ en(t) ⇒ □◇ ex(t)`。作者引入 TFC，即线程公平条件，把前件改为 `◇□(en(t) ∧ TFC(t))`。

TFC 越弱，必须受到公平调度的组越多，公平保证越强。TFC=false 不要求公平；TFC=true 得到弱公平。公式只要求最终执行，没有给等待时间上界或每时间片最低份额。

| 模型 | TFC 的含义 | 保证边界 |
| --- | --- | --- |
| Unfair | 恒假 | 无跨组公平承诺 |
| OBE | t 在过去至少执行过一次 | 对已观察到执行的组保证后续进展 |
| HSA | 不存在仍 enabled 的更低 ID 组 | 优先保证最低未结束组的进展 |
| HSA+OBE | 上述两条件的析取 | 同时覆盖两类进展义务 |
| LOBE | 过去存在执行过的 t′，且 t′≥t | 观察到高 ID 组后，其低 ID 前缀也获得进展保证 |
| Weak fairness | 恒真 | 所有一直 enabled 的组都最终执行 |

OBE 的“曾执行”是历史谓词，不应误读成只在当前物理驻留期间有效。HSA 条件是作者对文字规范的 best-effort 形式化，不是已经得到厂商认证的等价规范。

## 4. 模型之间的关系与同步例子

HSA 与 OBE 不可比较。HSA 可支持低 ID 生产者、高 ID 消费者的单向依赖；OBE 可以支持已发现组之间的双向交互，但不能保证从未执行过的生产者及时开始。

论文用有限互斥示例说明 OBE 能排除“持锁组不再调度，其他组永久自旋”的路径。不能据此证明任意无限竞争程序的无饥饿性；临界区是否结束、锁是否可被不断重抢、程序是否满足既定终止前提都需要独立考虑。

一般全局 barrier 需要所有参与组到达，即使 LOBE 也不自动保证任意高 ID 组会启动。先发现参与集合，可以把同步范围缩到满足进展条件的组；这依赖具体发现协议和对应调度模型。

HSA+OBE 不是把两类独立应用简单放在一起：一个程序内部可能同时包含单向依赖和互斥，必须在同一次执行中满足组合条件。LOBE 严格强于 HSA+OBE，但仍弱于所有组的弱公平性。

## 5. LOBE 发现协议的具体增量

原 OBE 发现协议用互斥保护 polling 和 closing 阶段：polling 时记录实际到达组，分配新的紧凑 ID；关闭后未发现组退出。barrier 只等待发现的组。

LOBE 版本利用“高 ID 已执行意味着低 ID 前缀也会进展”：计数改为 `count=max(count,tid+1)`，取消动态 id_map。即使 poll 已关闭，`tid<count` 的晚到低 ID 组也可进入。若只有 HSA+OBE，未曾执行的中间 ID 仍可能饥饿，该优化不成立。

保留原生 ID 可能有利于数据局部性，这是作者的动机和假设。论文没有测量该修改的吞吐、缓存命中或加速比，不能把它写成已经验证的性能提升，更不能把工作组 ID 替换成 Client ID 后直接应用到 VM 队列。

## 6. 威胁模型、可信依赖与安全证据

这是程序语义论文，没有恶意 Host、Realm 身份、设备固件证明或多租户保密威胁模型。调度器必须满足选定 TFC；程序必须满足模型前提及同步正确性；论文据此分析哪些无限等待路径可被排除。

它既不保证任务授权，也不阻止泄密、越界访问和伪造完成。调度公平性证明不了某个完成通知属于当前 job；真实 IRQ、可信完成和实际数据可见性也不证明所有等待者最终得到 CPU 调度。

论文示例和附录提供形式化论证及反例路径，不是已经对真实调度器 RTL、现代 Mali、Panthor 或项目 Proxy 的实现证明。没有单独宣称可直接复用的完整机器检查证明链。

## 9. 与当前项目的关系：四层进展分别论证

接受可信 ProxyRealm 控制 SMMU、RMM 认证 Client、映射时软件授权合成受保护 Stage-1、可信固件与安全回收的架构假设。已有 GPUVM、认证队列、私有快照、native fence、cookie/epoch、persistent IRQ127 继续作为基础。

| 层级 | 本项目需要表达的性质 | 本篇不能替代的依据 |
| --- | --- | --- |
| Client/vCPU | 获准运行的接收端最终能执行 | Host/Realm 调度及明确的可用性假设 |
| Proxy 队列 | 合法 Client 的就绪任务不会被持续插队 | admission、配额、公平策略及依赖处理 |
| GPU 工作组 | 受支持程序的跨组同步可取得进展 | 实际执行模型、内核前提与设备约定 |
| 完成处理 | 已发生的真实完成最终被 worker 处理 | 唤醒、锁序、worker 调度、错误与 reset 路径 |

Proxy 的 round-robin 只能约束它真正控制的选择点。若 GPU 内核不终止、依赖任务被长期阻塞，或共享锁持有者无法运行，仅轮转 Client 队列不足以证明服务整体进展。

IRQ127 的 persistent pending/ACK/ARM 解决通知状态连续性；还需说明 worker 和目标 vCPU 在什么假设下最终运行。这是活性条件，不是据此认定当前机制存在丢中断。

## 10. 可迁移的研究设计与评价

建议将隔离规格区分安全性和有条件活性：任何时刻都不跨 Client 授权或伪造成功；在明确的调度和设备前提下，已就绪/已完成任务最终得到处理。公平性应写明作用对象、触发条件和适用层级。

超时是取消、失败或 reset 的策略入口，不能直接把超时任务写成成功完成。取消确认、DMA 停止、页表失效、安全清理与页面复用仍各有条件；调度公平不能缩短这些证明链。

后续可分析低优先级持锁、队列持续涌入、依赖反转、接收端停调度、旧 epoch 完成迟到等执行。对等待时间上界应额外给出预算、抢占、最长不可抢占段和恢复假设；弱公平本身不产生实时保证。

公平性也不替代内存顺序。GPU 写结果、DMA/缓存可见、可信 fence/完成记录发布、通知和 Client 读取之间的顺序仍需独立依据；本篇 SC 模型不能证明所有 CPU/GPU/SMMU 一致性域已经连通。

独立评价：该文最适合用于“共享 GPU 实现与调度”和“任务隔离的活性边界”之间的连接，帮助避免把队列轮转、硬件进展和业务完成混成一个性质。它提供清晰模型和反例方法，没有提供可直接移植的 CCA 保护机制。
