## 2. 安全目标：条件可用性而非无条件送达

通常 TEE 把加密流量交给不可信 OS 转发；加密可保护内容，却无法强迫 OS 发包、收包或调度 TEE。论文定义 CNA：只要 REE 能经这个接口处理数据，TEE 也应能处理数据。其目的是防止恶意 OS 保留自己的连接，同时选择性阻断可信管理/监控服务。

攻击者控制 NW 内核、驱动数据、时钟、电源和 NIC 禁用操作；硬件与 SW 可信，安全启动及固定信任根成立。攻击者可关闭设备或把双方网络都破坏，网络基础设施被控、物理攻击与侧信道排除；明确不覆盖依赖及时数据包的安全关键系统。

因此 CNA 不是每个合法包最终到达、每个流具有最低带宽、服务截止期、抗流量洪泛或恢复已丢数据。它也不自动提供包内容认证、端点身份、抗重放或命令授权，这些仍由上层协议承担。不能把可信 UDP 目的端口当成身份凭证。

## 3. 分割驱动与可信控制位置

原驱动的大部分逻辑仍在 NW，包括 CLK、PWR、PHY 和 NIC IRQ handling。SW 中增加 T-MMIO、T-TX、T-RX、T-Queue、T-Timer；PoC 将示例服务 T-Service 也直接链接进 TF-A。复杂网络协议栈不在当前实现范围。

NIC 的控制寄存器只允许 SW 访问，NW 的 MMIO 操作改经 SMC。物理 TX/RX 描述符环放入 SW，避免 NW 在检查后替换 DMA 指针、修改所有权或重新指定根地址。NW 仍保留其软件所需的环视图，由可信模块同步。

这与项目可信 ProxyRealm 持有 SMMU、页表根和关键 MMIO 的职责有直接类比：不可信一侧可管理非关键功能，但任何能够选择性绕过可信路径的配置都必须受约束。将某项配置留在 NW 的理由是其故障只能按威胁模型影响双方，而非“硬件功能无需检查”。

## 4. TX：专用环、私有描述符与 DMA 发布

从多个硬件 TX 环中分配一个给 SW，NW 使用其余环。T-TX 处理 NW 提供的描述符时，先复制到 SW scratch/shadow memory，再检查实际数据地址和长度，最后设置 ready 位交设备使用。私有描述符避免检查后地址被 NW 替换，payload 本身仍可以留在 NW。

T-MMIO 必须限制环根、启停、结构、帧长和硬件解释方式，且识别 reset 后恢复索引。仅保护描述符页而允许 NW 重设环、单独关闭 SW 环或改变解析方式，并不能推出 CNA。作者通过提取原驱动配置值设置过滤规则，规则是否穷尽硬件行为仍依赖具体设备语义。

这项 snapshot 只固定已检查描述符，不保证 NW payload 内容不可修改；当前设计并不需要把 NW 的普通发包视为可信秘密任务。对本项目，如果任务安全还依赖命令/参数内容，则需继续使用现有私有提交快照、对象引用与权限检查，不能只复制一个外层指针。

## 5. RX、可信队列与拥塞的连带条件

所有 RX 先 DMA 到 SW buffers。NW 处理 RX IRQ 时必须经 T-RX 才能获得自己的包；T-RX 解析 Ethernet/IP/UDP 目的端口，把可信服务流量放入1MiB T-Queue，其他流量经检查后复制到 NW。对于 SW 包，NW 看到的缓冲区置零，因而当成无效包丢弃。

若 T-Queue 满，作者也丢弃 NW 包。否则攻击者能把 SW 队列淹满、让合法 SW 包丢失，却维持 NW 接收，这会破坏其条件目标。这个策略使双方接收连带受阻，不证明合法 SW 流在洪泛下仍获服务，也不提供不同可信服务间公平性。

若 NW 不处理 RX IRQ 或不调用 SMC，双方都不能通过此 RX 路径处理新包，仍符合 CNA 的条件定义。因而“定义得到满足”和“可信服务实际收到数据”必须分开陈述。它对项目最有用的是提醒研究者明确恶意 Host 可以令哪些主体一起停顿，不能从 pending 状态直接推出最终投递。

## 6. 为什么它没有实现可信 NIC 中断转发

论文主动保留 NIC IRQ 的原路由。SW TX 描述符清除触发 IRQ 的标志，改由安全定时器轮询；RX 仍由 NW IRQ 路径触发 SMC，服务在下一可信 tick 处理 T-Queue。这样减少可信中断分发逻辑，但不构成 IRQ 来源和目标的跨域认证机制。

T-Timer 不能被 NW 修改或屏蔽，用来获得周期性的可信执行。其计算可用性假设是 CNA 的前提；若服务仍只能由恶意 Host 调度，受保护队列本身不能强迫服务运行。定时轮询的开销与 NW jitter、吞吐和延迟折中分别衡量。

本项目已用 RMM 持久 pending/ack/armed 与 IRQ127 传递通知，IRQ只提示检查队列。无需为引用本篇而改成轮询，也不能据本篇认定可信 IRQ 已证明。可以进一步写出条件：在什么可信调度/服务预算下，合法完成记录最终被目标处理；Host完全拒绝调度时哪些保证仍成立。

## 7. 实验条件、吞吐与延迟

作者使用 Nitrogen8M、NXP `i.MX8M` ARMv8-A、2GB RAM、1Gbps Freescale NIC / Atheros AR8035 PHY、`i.MX` TF-A2.2、Linux5.10.63。轻载 FritzBox7390 路由器连接同子网静态IPv4的开发板和 ThinkPad T14s，后者为 i7-10610U、32GB、Intel I219-V。

发送器生成 MTU 大小 UDP 流量压满链路，接收器按10秒窗口计吞吐，每实验20轮平均。作者称标准差不显著，但未给逐轮原始值和置信区间；不能由此断言不存在尾延迟或所有场景稳定。延迟实验是一个 UDP 包往返的 RTT，不是单向时延。

| NW修改后吞吐 | 956.32Mbit/s | 949.05Mbit/s |

并发TX时，NW20.95、SW935.46、总956.51Mbit/s；并发RX时，NW476.72、SW480.39、总957.11Mbit/s。TX刻意优先SW，NW仅约21Mbit/s，不能描述为双向公平共享。RX约半分的解释是路由器可能轮转，不能把外部流量分配当成本机机制的带宽保证。

动态tick在20–170Hz间调整，作者实测170Hz足以压满其链路；这是该网络和MTU下的配置，不是GPU安全通知的适用频率或通用延迟界。所有数字均为作者结果，本轮未复现，不套用于项目glmark、ML或多Client性能。

## 8. TCB 与部署证据

作者用cloc1.82统计核心模块992 LoC，相对12.5kLoC TF-A约7.93%；NW NIC驱动约4.3kLoC。T-Service被排除，因为是示例/基准程序；实际服务、完整网络协议、依赖和平台固件仍会增加TCB。992不是整套可信软件总量，也没有足以独立比较不同论文的统一裁剪口径。

正文称在NW启动前分配NIC；固定后续仓库README及 `service.c` 却明确在Linux驱动初始化期间经SMC调用 `prot_nic`，以免修改同样配置NIC的U-Boot，且注释写明这不适合生产安全设置。必须补齐从可信启动到配置接管的连续保护，不能拿最终运行时隔离替代这一边界。

README还说明TF-A位于外部DRAM、物理攻击不在范围。只要当前威胁模型如此，不据此否定逻辑隔离；也不把烧录指南、默认测试登录或可构建描述当作安全启动/生产部署已经验证。

## 9. 固定核心代码的静态核查

全文阅读 `checks.c/.h`、`state.c/.h`、`nic_common.c/.h`、`nic_mmio.c`、TX同步/ACK/通用helper、RX同步/ACK/通用头、`selector.c`、`service.c`、`timer.c`、descriptor/data ring头及 `packet.c/.h`，共20份文本。没有读完NW驱动、TF-A依赖、完整中断集成或基准应用，因此不作全调用链或形式验证复现的声明。

TX实现确实先复制descriptor、暂不转交ready，检查shadow中的地址/长度，再做cache/barrier和所有权发布；`copy_desc`将状态最后写入。SW专用TX queue2对NW请求拒绝，RX来源检查绑定预设SW buffer。可把这些作为论文具体机制的代码证据，不等同于证明所有错误路径。

`is_nw_ram_region`检查RAM时使用区间相交条件，而非整个请求区间包含于RAM；另有独立SW保护区相交排除及整数溢出检查。防溢出、排除SW和完整合法RAM范围是不同条件，当前表达式不足以证明传入范围全合法。本轮没有执行边界输入、构造利用或审计所有调用/平台映射，因此记录为局部静态问题，而非已复现跨域攻击。

`nic_write32`已保护环根、若干寄存器和值、ECR后SW环初始化与索引重置，并禁止QoS寄存器写；但仍保留“验证选择性启停SW ring2”的TODO，其他未命中case的合法MMIO写默认透传。不能只因存在若干过滤分支就认定选择性控制面已穷尽，也不能只据TODO断定某个未核对硬件寄存器一定能破坏CNA。

`selector_run`在可信队列满时优先返回“已消费”，促使NW缓冲置零，符合连带丢弃设计。分类器只检查固定长度、IPv4和固定偏移的目的端口6666；没有完整处理IP options、fragment、协议字段与包身份。它是固定测试流的PoC，不是完整TCP/IP解析或远程管理授权协议。

`service.c`以全局spinlock串行化SMC，`timer.c`先禁安全timer、调用 `pta_tick`，再按返回频率重设。此次未读完 `app/app.c` 或可信timer在TF-A的注册链，故不认定已经核实任意恶意重入、多核时序和所有频率合法性。代码中“便于形式验证”的注释不构成完成证明或验证工具结果。

## 10. 对多 Client GPU 项目的增量

项目继续接受RMM认证原始Client、可信ProxyRealm控制SMMU、映射时核验对象/实际HPA/权限/生命周期、软件IPA→HPA合成受保护直达合法HPA的GPU Stage-1，其他设备保留Stage-2的假设。本文的NIC/TrustZone硬件条件不替代项目目标假设，不以实验板限制否定设计。

可把通信目标分成可审查的性质：记录内容不可伪造；只能投递到授权Client；迟到或旧epoch不能复用；有调度机会时可发现pending；更强的共享预算或有限等待是否另有保证。CNA提供条件可用性的例子，却没有证明GPU任务进展、故障隔离、结果正确性或每Client带宽。

继续复用认证队列、私有快照、GPUVM、native fence、cookie/epoch和持久IRQ127。可信完成记录可以合并唤醒，但不能漏掉待处理状态；IRQ本身不证明job成功，真实fence也不单独证明旧DMA静止和页可复用。reset必须协调真实设备状态、私有索引、在途任务终态及新配置，不仅清软件计数。

与BarriCCAde合读时，两篇分别揭示接口语义与相对可用性的边界：通过授权的请求仍可能用恶意参数伤害可信服务；不可伪造的通知仍可能被调度、拥塞或复位妨碍。建议把已有保护机制的前提和状态转换写成连续规范，而不是再造一套身份/token协议。

后续可验证正常Client受另一Client通知洪泛影响、满队列时错误隔离、ACK/ARM与新完成并发、Host暂时拒绝调度后恢复、复位时旧索引与旧完成，以及描述符整体范围校验。公平性/延迟保证若未纳入研究目标应明确列出；本轮未实现或执行这些测试。
