## 2. 为什么与项目相关

LEAP 希望让移动应用的敏感代码、模型和推理不依赖可信 Android 内核，同时尽量复用 Linux 驱动与现有应用。它不是 CCA 系统，而是 TrustZone 辅助的 Normal World 沙箱：可信固件管理 CPU Stage-2 隔离，应用在独立 Linux 环境中运行，并直接访问被分配的外设。

它适合对照项目的“直通与共享”部分：直接设备访问能降低代理开销，但需要处理设备切换、驱动初始化、GUI 占用以及所有权转移。它也提供一个明确的研究边界：多个沙箱并行，不代表多个沙箱同时使用 GPU。

## 3. 安全目标、假设和可信基

论文允许 Rich OS（ROS）被控制，其他沙箱可能窥探受保护代码或数据；目标是保护敏感执行及资产。其明确假设沙箱内外设驱动良性且无漏洞，排除物理攻击、DoS 和缓存侧信道。

LEAP_ATF 在 EL3 负责隔离和资源检查，LEAP_SW 在可信 OS 中负责密钥及镜像验证；LEAP_SOS 是沙箱内裁剪 Linux，LEAP_ROS 是不可信 ROS 内的准备与通信模块。跨沙箱隔离依赖可信固件，应用自身的机密性和执行完整性仍依赖其沙箱内核、驱动和运行时。固件新增代码量不能代表完整应用可信基。

## 4. 启动和身份边界

应用被拆成 ROS 中的 pAPP 和沙箱中的 sc-pAPP。后者与沙箱镜像加密、签名，验证材料和密钥存于可信环境。ROS 提供候选内存和镜像；可信固件先隔离待验证内存，再验证、解密和启动，避免仅验证一份随后仍可被 ROS 改写的镜像。

这个顺序值得借鉴：不可信端负责准备，可信端负责判断实际资源和最终启动。对本项目，Client 声称的身份、对象和地址只是请求输入；Proxy 应依据 RMM 认证身份及可信授权状态决定是否执行。

## 5. CPU 与内存隔离

每个沙箱默认独占一个物理 CPU 核和一段内存。EL3 管理各执行环境的独立 Stage-2 表，从 ROS 的表中移除沙箱内存。作者称其为使用虚拟化实施隔离而不虚拟化资源：没有普通 hypervisor 调度虚拟 CPU，但确实使用 Stage-2 机制。

共享通信区按沙箱分配，其他沙箱不可映射。页表存于 ROS 和沙箱都无法访问的保留内存；论文使用内存 2MB、MMIO 4KB 粒度，八核原型预留 16MB 页表空间。内存加入沙箱时要检查地址、大小、连续性、上限及与其他区域的重叠，并使旧翻译失效。

作者的 cache direct attack 防护主要依赖撤销地址翻译和清理相关 TLB，不能扩写为消除所有缓存侧信道。论文自身将缓存侧信道排除在模型之外。

## 6. GPU 和其他外设如何切换

普通外设切换过程是：ROS 判断设备空闲并卸载驱动，EL3 撤销其他执行环境的 MMIO 映射并授予目标沙箱，沙箱校验并加载驱动。回收执行相反过程。论文要求驱动可独立模块化、设备能够有空闲期，并承认不支持所有外设。

GPU 因 GUI 持续使用而难以卸载，LEAP 改为在 ROS 暂停 GPU，保持驱动存在，再由沙箱使用设备；ROS 的 MMIO 访问仍被 Stage-2 阻断。暂停是正常运行协调手段，Stage-2 才是阻止恶意 ROS 直接访问被撤销 MMIO 的边界。绕过正常暂停直接访问会导致 fault，而不应被解释为重新获得权限。

代价是 GPU 被沙箱使用期间 ROS GUI 冻结。作者明确承认同一外设不能由多个沙箱同时访问；较长推理可退回 CPU。论文讨论的短暂冻结建立在移动模型任务较轻的条件上，不能作为任意长 GPU kernel 的可用性保证。

## 7. MMIO、DMA 与中断应分别理解

CPU Stage-2 封锁 MMIO，只限制 CPU 对设备控制面的访问，不能单独证明设备 DMA 的隔离。论文 §5 另声明使用 SMMU 防止 DMA 绕过主存访问控制；但正文没有给出足以复核所有 GPU 页表、SMMU 配置、root 切换和失效步骤的完整协议。本次也没有对应实现可补齐这个证据范围。

沙箱之间和 ROS 的通信使用 IPI 与共享内存，IPI 编号表示请求类型。原文报告通信延迟，但没有详细展开可用于本项目的原始 Client 身份认证、任务代次、伪完成过滤、重放检测或 reset 后旧事件处理。不能从“有 IPI 通信”推导出完整可信完成协议，也不能据缺少叙述直接认定实现存在可利用漏洞。

实现移除了沙箱启动时的 GIC 初始化，并调整系统时钟初始化以避免多 OS 冲突。这是可运行性设计；其本身不能替代防止恶意环境改写共享中断控制状态的安全论证。

## 8. 弹性资源和应用适配

内存通过 CMA 提供连续区域，按需增长或归还；CPU 通过 hotplug 转移。优化版本让待转移 CPU 在 EL3 等待并重建上下文，避免完整物理断电再上电。作者设置 CPU 利用率高于 99% 持续 2 秒时扩容，剩余核低于 40% 持续 5 秒时收回。这是原型策略，并非所有工作负载的最佳策略。

App Adapter 基于 Soot 做 Java 字节码调用图和数据流分析，开发者提供敏感 API 入口，工具抽取模型和相关代码、生成通信库、重新打包。它不通用于任意 Android 服务或 C/C++ 程序。论文限制部分明确说明仍有入口配置等人工工作，不能按摘要的便利性表述称其完全自动适配所有应用。

## 9. 原型和对照的范围

Hikey960：四 Cortex-A53 加四 Cortex-A73、4GB 内存、Mali-G71；ROS 为 Android 9 / Linux 4.14，可信 OS 为 OP-TEE 3.4.0，沙箱 Linux 3.13。总新增代码 4,689 行：ATF 539、SW 651、ROS 1,327、SOS 972、DevOps 1,200。总和是新增实现规模，不包含 Linux、OP-TEE、GPU 驱动及应用运行时。

对照包括 KVM/ARM 和作者复现的 SANCTUARY，后者使用与 LEAP 相同的沙箱 OS，并通常启用 L2；部分实验另比较禁用 L2 的版本。KVM 原型没有为相关外设实现可比的直通支持，SANCTUARY 原型也没有可用的 GPU 可信驱动。因此 GPU 加速相对这些 CPU 对照的收益，不是三种 GPU 安全映射方案的独立开销比较。

## 12. 对本项目的设计建议

第一，直通与共享应分别给出安全语义。LEAP 是 CPU 沙箱并行、GPU 时间独占；本项目若由 Proxy 同时承载多个 Client，需要另证上下文、映射和完成状态的归属，不能引用 LEAP 的整设备独占结论替代。

第二，资源准备与资源授权分离。可以让不可信 Host 或 Client 准备输入与候选区域，但可信端应校验实际页、所有权、权限及生命周期，并保护最终 PTE、root、MMIO。用户设定的可信 Proxy 软件合成 HPA Stage-1 映射可沿此原则分析，不必复制 LEAP 的全部 CPU 沙箱方案。

第三，GPU 切换或 Client 退出时，要区分停止新任务、在途任务结束、旧映射失效、事件排空和内存回收。LEAP 的 GUI 暂停经验有工程参考价值，但暂停驱动、失去 MMIO 和 GPU 已无在途访问是不同状态。

第四，把中断看作“需要检查可信任务状态”的通知。Client 会话、queue/job 身份、generation、原生 fence 终态及错误/reset 状态应在可信侧关联。具体协议需结合 Devlore 与当前 RMM/Proxy 实现，而不是给每个 IPI 加一个编号就宣称完成认证。

## 13. 可验证的研究问题

可以设计从整设备独占到可信 Proxy 共享的对照，分别测量设备切换、长任务对其他 Client 的影响、按任务持有映射的成本和通知延迟；同时测试恶意 Client 提交其他 Client 对象、退出时保留在途任务、重放旧通知等。性能与隔离正确性分别记录，避免只凭吞吐提升判断隔离有效。
