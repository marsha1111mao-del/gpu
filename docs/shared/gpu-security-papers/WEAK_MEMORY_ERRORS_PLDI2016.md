## 2. 问题：原生运行很少出错不代表同步正确

GPU 并发程序可能依赖未被内存模型保证的访问顺序。在特定调度和缓存状态下，错误结果出现概率极低，正常跑应用难以暴露。本文构造测试环境，主动扰动访问与执行布局，放大弱内存相关错误，再用经验式 fence 插入帮助定位缺失顺序。

作者以 MP、LB、SB 三种微测试调参，将观察到的有效压力策略用于真实应用。它回答“如何提高找到反例的概率”，不回答“没有反例时如何证明所有执行安全”。这一区别对项目完成记录与通知优化尤其重要。

论文讨论 CUDA 7、PTX 4.2 时代的模型状态。2016 年“缺乏一致的正式 CUDA 模型”等背景表述不能照搬为对当前 CUDA/PTX 的事实判断，旧 GPU 的经验也不能直接指定 Mali 或 CPU/DMA 的屏障。

## 3. 测试环境与源码要求

环境加入访问独立 scratchpad 的压力线程块，调节访问位置、读写序列、覆盖区域和压力线程比例；还随机化应用线程到逻辑工作的对应关系。压力数据与应用数据分开，目标是改变时序/缓存行为而非直接破坏应用内存。

这里的随机化保留原 thread block 和 warp 成员关系，以维持当时的 warp lockstep 等语义前提；不能概括为适用于现代 independent thread scheduling 的任意线程重排。

应用必须适配以插入压力块、重映射线程 ID，并提供功能性 postcondition。所谓 black-box 是无需预先掌握每个应用的通信 idiom，不是完全不改代码、不看源码或自动生成正确性规范。

依赖 occupancy 的全局 barrier 应用被排除，因为增加线程块可能导致死锁。作者还先修复 ct-octree 和 tpo-tm 的未初始化/OOB 等无关错误；不能将所有观察到的失败不加区分地归为弱内存反例。

## 4. 七张旧 GPU 上的压力策略搜索

测试硬件为 GTX 980、Quadro K5200、GTX Titan、Tesla K20、GTX 770、Tesla C2075、Tesla C2050，覆盖 Maxwell、Kepler、Fermi 三代。它们不是 Arm/CCA 平台。

位置/距离阶段每项 256 个选择、各 1000 次、三种微测试，约 196.6M 次/芯片。后续再搜索短读写指令模式及扩展区域；整套调参耗时约 1,731–4,215 分钟，不是一个低成本的快速回归。

经验上的关键 patch 为 Kepler 32 words、Fermi/Maxwell 64 words；被测设备的最佳扩展为两个区域。980 的 MP 还需要探索更远距离。作者并不知道精确物理地址，因此 patch 现象不是对真实 cache line 或 coherence granule 的证明。

策略选择兼顾 MP、LB、SB 的联合表现，而非为每种微测试单独取最佳策略。不同 GPU 最优读写模式不同，说明经验环境有设备依赖；不能只选一个模式就宣称覆盖所有弱顺序。

## 5. 应用实验：55/70 的含义

十项应用来自七个基线：cbe-ht、cbe-dot、ct-octree、tpo-tm、sdk-red、cub-scan、ls-bh，再加后三者的去 fence 版本。七芯片乘十应用构成 70 个组合，包含人为制造的缺 fence 情况。

每组合比较无压力、简单压力、随机压力、定制缓存压力，分别开关线程随机化，共八种环境；每种环境运行一小时，约 160–10,907 轮，单轮 timeout 为 30 秒。压力线程块约占 15%–50%，其循环时间约为应用 kernel 的十倍。

| 作者结果 | 正确解读 |
| --- | --- |
| 原生发现错误 3/70 | 所选应用在默认执行下很少显错，不代表其余 67 项正确 |
| 定制压力发现错误 55/70 | 测试环境放大反例；不是发现 55 个独立新 CVE |
| 其中 43/55 被称为 effective | 按论文阈值，错误出现概率超过 5% |
| 简单方法最好为 13/70、其中 6 项 effective | 是本文所选环境/应用下的比较，不是所有现有测试工具的完整排名 |

未出现错误的一小时测试仅排除这次实际探索的执行；不能用作安全关键路径移除屏障、授权检查或完成状态检查的充分依据。

## 6. 经验式 fence 插入与算法文字疑点

作者先在每次内存访问后插入 fence，再通过二分与逐项删除缩小集合；迭代轮数倍增，最终进行一小时稳定性测试，整体设 24 小时 timeout。所得集合依赖删除顺序、测试预算和非确定性，不是已证明的全局最小正确集合。

Algorithm 1 的二分阶段存在值得保留的印刷/表述不一致：正文描述检查 A+(F∖F1)，即删除第一半 fence 后运行；伪码第 16 行却写 CheckApplication(A,F1,I)，成功后再令 F←F∖F1，第二半也有同类差别。在未获得匹配源码前不能默默改成某一种并称为原实现。

经验式检查会产生错误信心。770 上 cbe-dot 找到的 fence 位置与正确释放边界存在差异；sdk-red-nf 在部分设备上即使已观察错误，最终仍可能给出零 fence。论文明确讨论基于测试的限制，没有提供完备证明。

## 7. fence 成本：低中位值不能代替正确基线

运行时间用 CUDA events 记录，取 100 次通过功能 postcondition 的运行；不通过的运行被丢弃、不计入这 100 次。无 fence 程序本就可能错误，因此它可用于讨论机制成本，但不应成为安全方案“同等正确”的性能基线。

能耗只在支持查询的四张设备上用 NVML 平均功率乘时间估计，作者明确承认精度限制。图中省略十个运行时间与三个能耗异常值，不能只看图上靠近对角线的点。

| 作者比较 | 结果 |
| --- | --- |
| 每访问后插 fence 对无 fence | 运行时间中位开销 +174%，能耗 +171% |
| 经验式 fence 对无 fence | 两项中位开销均低于 3%，不等于所有应用低于 3% |
| 极端保守开销 | C2075/cbe-ht 运行时间 +35,120% |
| 极端经验式开销 | 770/cbe-ht 运行时间 +7,052% |

这些均为作者旧平台实验，不是本项目测量。昂贵屏障可能值得优化，但优化必须保留所需顺序与正确性；经验测试不能将必需屏障“证成可删”。

## 9. 对项目内存与中断通信主线的具体作用

应分开论证访问授权、GPU 计算完成、缓存维护/数据可见、可信记录发布及通知投递。合法 GPUVM/SMMU 映射不自动保证这些操作有序；CPU release/acquire 也不自动提供异构 GPU/DMA 所需的缓存与互连可见性。

项目已有 RMM 认证队列、私有快照、真实 GPUVM、native fence、cookie/epoch 和 persistent IRQ127。适合进一步明确的顺序链是：真实设备完成 → 所需结果同步/可见性 → 可信完成记录发布 → 通知目标 Client → Client 按当前身份、cookie/epoch 和状态读取结果。

每条边应标明由设备规范、Linux 同步语义、缓存同步或既有锁/屏障中的哪一项提供，而不是额外堆叠没有依据的 fence。GPU 指令级 memory fence 与 Linux dma_fence 是不同概念：前者约束访问顺序，后者表达异步工作完成；不能因名称相同而互相替代。

后续若做验证，可从协议状态与 litmus 风格的小反例入手，再安排设备故障、延迟通知、并发撤销等实验；本轮只提出验证义务，没有运行这些实验。安全边界仍采用可信 ProxyRealm 控制 SMMU、RMM 原始 Client 认证、建图授权合成合法 HPA Stage-1 的项目假设。
