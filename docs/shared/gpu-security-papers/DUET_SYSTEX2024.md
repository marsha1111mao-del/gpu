## 2. 为什么启动证明不足以信任 GPU 服务

CVM 可以隔离不可信基础设施，但服务所有者通常仍有 root/管理权限。启动时证明了某个初始镜像，不代表运营方之后不会安装调试工具、替换服务、读取用户进程或修改 GPU 软件栈。duet 研究的正是“服务所有者管理能力”与“服务用户数据机密性”的关系。

参与方包括服务所有者、服务用户、基础设施提供者。SGX 中的小控制器负责创建和管理 SEV-SNP/TDX CVM，CVM 提供完整 OS、应用兼容性和机密 GPU 的使用可能性；用户先信任控制器，再审查它记录的 CVM 操作。将小控制面与功能丰富的服务运行面组合，是本篇与 ProxyRealm 最相关的结构。

论文明确假定基础设施不会篡改 CVM 的 rootfs 挂载，启动证明覆盖固件，不能独自证明根文件系统。Azure HCL/MAA 还被纳入信任；侧信道排除，平台需正确更新。不能把结果描述成在完全恶意磁盘、云控制面、所有固件与服务包条件下都成立。

## 3. 控制器独占管理入口

控制器在 enclave 内为每个 CVM 生成 SSH 密钥，向云平台只提交公钥，私钥不交给服务所有者。特权接口要求所有者签名，普通用户可取得 quote 和 CVM 状态。所有后续管理操作通过控制器执行并记录，避免所有者绕过可信审计入口。

| 论文接口 | 作用及约束 |
| --- | --- |
| `/quote` | 返回控制器 SGX 证明，所有者和用户均可访问 |
| `/start_cvm` | 创建 CVM、SSH 密钥、取得初始证明，所有者调用 |
| `/run_cvm_commands` | 顺序执行并记录命令和输出，只允许更新模式 |
| `/mark_cvm` | 切换更新/服务模式，论文要求更新前终止原服务进程 |
| `/get_cvm_state` | 返回模式、初始证明、命令与输出，供用户审查 |
| `/stop_cvm` | 停止并删除 CVM 资源，可保留审计信息 |

“独占 SSH 私钥”只是入口控制的一部分。若控制台、cloud-init、云代理、其他 SSH 密钥、服务漏洞、持久化启动任务或被委托凭据仍可修改服务，就不能推出所有管理变化都在日志中。迁移到 GPU 时还包括设备固件、驱动模块、页表根、SMMU 与关键 MMIO 的管理路径。

## 4. 证明链、状态审查与密钥交付

控制器可以先在新 CVM 安装证明工具，再取得并验证 CVM 报告；这些安装命令也须被记录。论文提出 HOST_DATA 可包含 SSH 公钥，控制器保存初始报告，并向所有者返回实例标识。用户验证控制器 quote，再取 CVM 的初始报告、日志和模式，审查后才把私有数据或密钥交给服务。

两个有效的硬件报告不自动形成同一实例的安全组合。需要把控制器测量值、被管理 CVM、SSH 服务端身份、服务会话、策略版本和证明新鲜度连接起来。HOST_DATA 中出现一个主机提供的公钥字段，也不独自证明正在通信的端点持有相应私钥，或该字段已绑定预期服务配置。

命令日志体现受中介的管理历史，不是对全部运行内存、应用数据流或 GPU job 结果的直接测量。用户能读源码、签名包和命令，不等于已经证明服务非干扰；签名证明来源和完整性，不能证明包无恶意。镜像 `latest` 也不能替代可复现的确切镜像度量。

论文建议将日志对称加密后放在外部存储，以降低 enclave 内存占用，但没有给出完整防回滚、分叉、一致追加和多控制器一致性协议。日志本身可能含命令参数、输出或秘密，公开审计与输出脱敏也需要策略。

## 5. 服务模式切换为什么是生命周期边界

初始状态为 `in-update`，允许安装与维护；完成后进入 `in-service`，禁用命令接口。若服务已接触用户秘密，重新进入更新模式前，论文要求杀死所有者启动的长运行进程，以阻止随后直接 dump 进程内存。

进程终止不能推出秘密已从磁盘、swap、缓冲区、共享对象、缓存或设备显存清除。还需阻止新请求、等待或取消在途任务、处理后台服务及派生进程、撤销凭据与旧映射，并决定哪些状态可以安全保留。公开服务代码可被审查，是其信任条件；它不能替代这些状态转换的执行保证。

对本项目，更适合将这条思路放进已有会话和 epoch：服务配置改变时关闭旧授权入口，排空或终结旧 job/fence，撤销旧 GPUVM/页授权，再开放新 epoch。不能仅改变布尔模式后继续接受旧 cookie、旧对象或迟到中断。

## 6. 固定 artifact 的定向静态核对

已读文件包括 `README.md`、`AdminEnclave/admin.py`、`AdminEnclave/azure_client.py`、`AdminEnclave/cvm.py`、`AdminEnclave/utils/crypto.py`、控制器 requirements、`AdminEnclaveClient/duet_admin_client.py`、Gramine manifest/build 模板以及 SNP/TDX 安装脚本。代码是可行性原型，下面只陈述这些文件中的静态事实，不声称已复现攻击或完成全依赖审计。

`admin.py` 在 `run_commands` 检查 `in-update`，特权参数经 RSA-PSS 签名，返回结果也签名。但 `mark_cvm` 在切回更新模式时只保留“清除机密数据和密钥”的 TODO，然后直接更新模式；没有实现论文要求的进程清理。Flask 以 `threaded=True` 运行，已读状态转换与命令执行路径没有按 CVM 的锁或原子排空协议，不能用一次模式检查证明并发切换安全。

`cvm.py` 的 `get_current_state` 返回实例标识及命令输出/输出摘要，未包含论文所述当前模式和结构化初始 CVM 证明。SSH 命令读取 stdout 并写入日志，但没有在这条路径核对退出状态，不能把“记录了输出”直接当成命令成功或状态转换已完成。日志输出还通过普通 logger 发出，涉及敏感数据时需单独审查可见性。

客户端确实向 MAA 验证 SGX quote，并检查 quote 中的公钥摘要；但预期 MRENCLAVE 比较被注释，属性、MRSIGNER、产品和安全版本检查留有 TODO。控制器验证失败只打印 warning，随后仍装入收到的公钥继续工作。这允许 direct 调试模式演示，不能视作生产条件下失败即拒绝的证明策略。

`_encrypt_data_for_controller` 直接返回原参数，后面的加密代码不可达；默认客户端 URL 是 HTTP，服务端启动代码未配置 TLS。特权签名覆盖 params，已读代码没有请求 nonce、时效、单调序号或明确操作名的签名绑定；响应也没有绑定新的客户端挑战。签名完整性因而不能单独证明防重放、新鲜性或端到端机密性，外部 TLS 部署亦未在本轮核验。

`cvm.py` 使用 Paramiko `AutoAddPolicy` 接受未知 SSH 服务端密钥。公开 SNP/TDX 脚本安装并运行证明样例，将 token 的前两段 base64 解码后输出；在已读控制器/脚本中，没有看到完整的结构化 CVM token 签名、预期测量值和 SSH 端点绑定验证流程。不能将打印 JWT 声明当成控制器已完成验证；没有审计下载的 Azure 样例内部行为。

Gramine 模板使用加密挂载保存控制器签名私钥，但服务所有者公钥列入 `sgx.allowed_files`，控制器启动时从该路径读取。该配置需要另核验最终 manifest 的路径匹配和信任初始化：允许读文件本身不提供其内容认证，不能仅因输入文件位于 enclave 可见目录就信任授权根。未生成最终 manifest，也不据模板推断已利用成功。

控制器 `CVMs`、命令日志和模式保存在进程内存；已读代码仅对控制器签名私钥有 sealed 存储，没有恢复 CVM 管理状态及防回滚的完整协议。Python 依赖未固定版本，镜像/构建模板含 `latest`，证明样例从分支压缩包下载。这些都应与论文设计保证分开列出。

## 7. 作者实验与可推广范围

作者实现约1K行 Python 控制器和约300行客户端，用 Gramine 在 Azure SGX DC2sv3 上运行，创建 AMD SEV-SNP DC2adsv5 或 Intel TDX DC2edsv5 CVM，使用 Ubuntu22.04 机密计算镜像。当前客户端充当所有者测试创建、命令、模式、读取状态和销毁等接口。

论文没有延迟/吞吐量表格、GPU 工作负载实验、任务隔离攻击实验或多租户 GPU 测量。代码行数不是完整 TCB；依赖还包括 Python、Gramine、密码库、云 SDK、CVM OS、证明组件与设备固件。讨论中的便宜、易扩展和多服务支持不能改写成测量结论。

SGX sealing/unsealing 可帮助存储密钥，但不自动解决跨机器密钥分发、多控制器日志一致性和授权撤销；相关规模扩展是未来工作。论文中“可利用 confidential GPU”是服务部署动机，不代表它实现或验证了 GPU TEE。

## 8. 对 ProxyRealm 研究路线的具体启示

继续接受 RMM 认证原始 Client、可信 ProxyRealm 控制 SMMU、建图时核验对象/实际 HPA/权限/生命周期并合成受保护的直达 HPA GPU Stage-1，其他设备使用硬件 Stage-2 的假设。duet 不构成否定该模型的证据，也不要求因测试硬件限制更换方案。

PORTAL/CAGE/ACAI 侧重设备纳入保护域的条件，duet 补充服务运行后的管理权限：固件/驱动更新、映射策略改变、reset 和密钥重新交付如何影响用户仍信任的服务实例。可在既有身份、GPUVM、认证队列和 cookie/epoch 上记录配置度量与允许的管理转换，无须新增一套每任务 token 或重复身份机制。

中断方面，本篇没有证明物理事件真实性、Client 路由完整性、ACK/重放防护或 job 完成归属。仍应保持“真实 native fence 完成 → 精确 cookie/epoch 发布 → RMM 持久 IRQ127 通知 → Client 检查队列”的区分；管理模式证明不能代替任务完成证明。

可进一步验证：服务状态读取后立即发生管理切换、旧证明/响应重放、更新与在途 job 竞争、reset 后旧 cookie 到达、控制器重启后状态恢复、失败证明仍继续使用服务，以及安装命令失败却被视为配置成功。本轮只建立研究条件，没有执行上述测试。
