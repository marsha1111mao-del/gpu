## 2. 问题与可信边界

TrustZone可保护可信应用，但可信OS通常只有少量简单驱动。把Linux驱动及依赖移入可信世界会扩大TCB；交给普通世界代理I/O又使操作受恶意OS控制。Driverlets利用成熟Linux驱动与设备交互的记录，生成可信世界可独立重放的紧凑驱动。

作者信任开发者、记录环境、gold driver、生成工具链、TEE和SoC硬件及固件，部署后的普通世界OS可以恶意。gold driver是已能正确驱动设备的参考驱动，不代表经过形式化认证。录制环境或签名发布链被攻陷不在其运行时隔离保证内。

设备实例须独占分配给TEE，其行为可用响应请求的有限状态机描述，状态转换不依赖实际I/O数据，且没有难以控制的自主操作。作者为简化重放主动关闭IRQ合并、并发请求和运行时电源管理；不是保留任意Linux并发行为后仍自动得到等价驱动。

这与当前ProxyRealm服务多Client的前提不同。记录/重放的正确性不能直接推出跨Client隔离、恶意GPU固件防护、设备共享公平性或每个输出的真实性。物理平台提供的安全归属按论文目标假设接受，不因其RPi测试载体而否定设计。

## 3. 从交互事件到模板

系统分为可信录制阶段和可信运行时。开发者在具备完整驱动的环境执行覆盖目标功能的record campaign；工具捕获MMIO、共享内存、IRQ及环境请求，分析数据和控制依赖，形成interaction template；部署时小型replayer根据请求选择模板、检查条件并执行。

输入事件包括寄存器/共享内存读、IRQ、DMA分配响应、随机数和时间戳；输出事件包括写入设备或共享区域的值。不是所有读都决定设备状态：作者识别会因果影响后续输出的读，以及IRQ和环境响应等state-changing input，避免将忙等循环的每次观察硬编码成固定次数。

工具用选择性符号执行探索输入条件，在输出或事件序列发生分叉时剪枝；动态污点分析追踪算术/位运算的数据依赖；识别轮询和延迟循环并提升为meta-event。它从执行过的代码和请求归纳可复用模板，不是穷举实际设备的完整物理状态机。

模板保存允许的请求范围、输入约束、参数化输出、设备交互顺序和必要等待。DMA分配次数与描述符拓扑由模板固定，具体地址可以按新环境参数化；地址可重定位不等于已检查实际物理页的Client所有权、授权和生命周期。

论文的条件性论证是：若gold driver的可观察交互包含足够的状态变化信息，重放相同的state-changing sequence就沿相同设备FSM路径。如果设备发生gold driver也未观察到的静默失败，前提就不足；该论证不是任意恶意设备或任意输出的完整正确性证明。

## 4. 重放、中断与异常

模板由开发者签名并保持不可修改，作为静态头文件/C函数链接到OP-TEE。运行时期望恰有一个模板匹配请求；没有覆盖的参数或路径应报错，而不是由普通世界临时补充任意MMIO操作。

replayer单线程执行，顺序调度原驱动普通上下文和IRQ上下文；少量手工代码识别中断来源，`wait_for_irq`按照模板恢复后续上下文。它缩小了动态调度状态，但代价是关闭原驱动IRQ合并、并发和部分性能机制。

模板只有在约束、交互和及时IRQ等条件满足后才返回成功。发生分歧则软复位并重试，持续失败后中止并输出诊断。论文称之为transactional，应理解为模板执行的检查边界；它不保证已经发出的外部存储写可回滚、操作恰好一次，也没有给出任意DMA在复位后已静默的通用证明。

作者在每个模板前和分歧后复位到干净的初始化设备状态。迁移到共享GPU时，必须重新分析复位影响域、在途工作、取消和旧DMA；全局复位可能破坏其他Client，不能直接把reset/retry作为局部错误恢复。

模板验证、边界检查和只接收可信应用输入是论文给出的安全设计。代码少有利于审计，但不能用1k行规模代替其参数检查、签名验证、IRQ来源验证和故障恢复的实现证据。真实IRQ也只说明某个硬件事件发生，不能单凭该事件判定某个Client的job成功。

## 5. 原型与三类设备

录制器约2kSLoC，基于S2E/QEMU动态二进制翻译，模拟部分库函数并复用LoopDetector；运行时约1kSLoC，使用不缓存的MMIO访问、连续内存分配器和OP-TEE随机数。时间戳服务经RPC到普通世界，因此“关键I/O路径不跨世界”不应扩大为所有环境调用均完全封闭在TEE内。

实验为Raspberry Pi 3B+，四核Cortex-A53 1.4GHz、1GB RAM，Linux4.14、OP-TEE3.9。平台缺少TZASC，作者修改Arm Trusted Firmware分配设备，可信RAM约3MB；设备保护依赖其平台设置。按其独占设备假设评价，不把该原型称为原生CCA多Realm设备共享。

| 设备 | 交互模板与实际范围 |
| --- | --- |
| MMC | 对1、8、32、128、256个block各录读/写，共10模板，覆盖约31M块范围；固定DMA通道和描述符布局，并保留最后3个word手工传输的硬件处理 |
| USB storage | 同样10模板，覆盖约15M块，保留一个控制器通道并关闭SoF；不是完整USB热插拔、全部设备class或共享调度实现 |
| CSI camera / VCHIQ | 通过VC4多媒体加速器的VCHIQ/MMAL协议录制OneShot、ShortBurst、LongBurst，对应1/10/100帧及720p/1080p/1440p；每模板约75–680事件，大量交互发生在共享内存 |

摄像头路径包含共享slot元数据、消息队列、页面列表和doorbell；doorbell触发后还需解析消息并检查图像大小等约束。它使用VC4多媒体固件服务，不等于已支持通用GPU shader、图形API或恶意多Client GPU隔离。原驱动多个线程的交互被线性化重放。

## 6. 安全与正确性验证的证据强度

作者做模板静态一致性检查、块读写内容比对、JPEG格式检查和设备故障实验；MMC与USB覆盖超过31M/15M块，摄像头重复10k次。块地址范围广不代表枚举了所有数据、时序、故障和并发组合；JPEG可解析也不证明捕获的是正确现实场景。

可移除介质故障触发复位、重试和最终中止，支持其有限设备错误处理的可行性，没有构成多Client恶意IRQ、共享页竞态或GPU reset后旧任务复用的实验。gold driver已有的功能或安全错误仍可能进入模板。

可信签名保护模板来源，受约束重放减少运行时不可信OS可控制的接口；设备和固件可信、录制环境可信、独占分配等前提仍须列入TCB和安全论证。不能将“模板来自正确记录”与“每个运行时设备行为都可靠”合并成一个结论。

## 7. 性能和开发成本

作者报告每个driverlet开发约1–3天，对比其估计移植/重写需月级；campaign约20行，底层通用工具开发仍花费数周。这是作者工程经验，并非统一开发者能力下的普遍生产率测量。

| 论文测量 | 数值及对照条件 |
| --- | --- |
| SQLite–MMC | 平均434 IOPS、超过100 queries/s；native平均快1.8倍，读为主约1.4倍、写为主约2倍；native-sync比driverlet慢约1.5倍 |
| SQLite–USB | 平均369 IOPS、超过90 queries/s；相对native约1.5倍开销，写为主约2倍；native-sync比native慢1.7倍、比driverlet慢1.2倍 |
| Camera | 单帧模式比native增加约11%延迟，100帧burst达到约2.7倍延迟；逐个等待IRQ而原驱动合并处理，是作者给出的主要原因 |
| 单次MMC/USB交互 | 作者报告平均延迟降低约12%/13%，USB 256-block写低约40%；避免Linux调度成本，不代表端到端数据库同样提速 |
| driverlet可执行文件 | MMC约6KB、USB约26KB、VCHIQ约19KB；不包括整个可信OS、固件、签名工具链和设备TCB |

数据库native、native-sync的同步语义不同，不能只选更慢baseline掩盖相对native的损失。微基准优于native与宏基准变慢并不矛盾：初始化、分块、串行执行和IRQ等待会改变端到端成本。

正文单帧请求在720p到1440p的时延约2.1–3.6秒，摘要另报告2.1FPS；它们的条件和指标不同，不能将2.1FPS当成2.1秒的倒数或补造未给出的分辨率数据。Figure7提取文字中的坐标单位µs与caption的milliseconds不一致，本报告不用未经图像核对的坐标给出精确读数。

端到端示例约50行可信应用，把摄像头图像写入SD；作者报告约3.7秒/帧，存储约154ms。它是可信感知案例，不是当前项目glmark或GPU计算结果。本轮没有新增性能测量，也不从上述设备性能推断GPU收益。

## 9. 与相关工作及当前项目的联系

LDR保留编译后的可信twin driver并跨世界调用依赖；Driverlets通过离线记录和模板减少运行时驱动行为；GPUReplay也重放设备交互，但模板参数化和使用范围需按各自论文比较。已有GPUReplay解读不重复计数；本篇不是把所有轻量驱动技术归为同一种方案。

当前 `PLAN_REGISTER/PLAN_EXEC`缓存的是已授权执行计划，不是录制后重放GPU任务或MMIO轨迹。可迁移的经验是明确计划输入范围、前置/后置条件、受保护的不可变内容、IRQ等待边界和失败状态；缓存不能跳过对象、实际页、权限或生命周期授权。

继续以RMM认证原始Client、可信ProxyRealm控制SMMU、建图时检查对象/HPA/权限/生命周期、软件IPA→HPA合成受保护GPU Stage-1为目标模型，其他设备保留硬件Stage-2。Driverlets没有证明这些条件，也没有理由用其独占TrustZone实现替代当前CCA设计。

复用已有GPUVM、认证队列、私有快照、native fence、cookie/epoch和持久IRQ127：物理IRQ只启动可信状态检查；真实fence终态确定对应工作是否结束；cookie/epoch确定完成归属和新鲜度；持久pending及ACK协议负责可靠通知。每层都需要自己的条件，不能把“等到IRQ”合并为“可信成功”。

若把计划执行写成可审查状态机，应特别记录：计划注册后对象变化如何失效；任务取消/reset后迟到IRQ如何被拒绝；重试是否允许重复外部副作用；复位影响哪些Client；最后一次DMA与页回收如何同步。现有epoch和对象引用可承担这些职责，不另设通用身份token框架。

## 10. 评价与后续研究

该工作的价值是把“可信环境需要多大驱动栈”转化为“特定设备功能实际需要哪些被约束交互”。它也给出清晰代价：设备独占、覆盖有限、串行化和复位，使审计容易，但削弱通用共享和性能。当前项目适合吸收边界表达和不可变计划，而非直接采用逐模板复位的执行模型。

后续研究优先检验现有共享协议的状态转换、异常与重连，而不是另起重放框架。直接CCA/GPU候选GR-T正式版、XpuTEE、AccShield及原库未完成项仍需取得全文；Cinch补充恶意外设输入隔离。这些论文的完成状态分别登记，不把候选代码或元数据当精读完成。
