## 2. 问题与威胁模型

问题是单体内核中的恶意或被利用驱动可能攻陷整个内核。攻击入口包括恶意闭源模块、用户态利用驱动漏洞，以及恶意外设触发驱动缺陷；另允许 Hypervisor 完全恶意。其余主内核、TF-A 与 RMM 可信，物理攻击及侧信道排除。

这与 CAGE/PORTAL 的保护目标不同：后者主要研究如何把设备执行纳入机密计算域，本篇首先保护内核免受驱动攻击。它提到 GPU 与反作弊闭源模块作为动机，却没有完成真实 GPU 直通、GPU 多 Client 共享或 GPU job 完成链评估。

作者提出 R1 数据结构机密性、R2 数据结构完整性、R3 函数调用完整性、R4 同步安全和 R5 小规模 TCB 增量。R4 明确只约束同步输入和参数，不包含基于 race condition 的接口漏洞；不能写成已经提供任意并发驱动隔离。

## 3. CCA 域划分与可信职责

主内核运行在受 RMM 保护的 Kernel-VM，每个被隔离驱动放进自己的 Driver-VM。KVM 仍承担创建和管理，但不信任它维护机密性/完整性；RMM 中加入 BarriCCAde 的同步模块 Sync-M、过滤模块 Filter-M 及上下文切换逻辑。主内核与 KVM 另有加载辅助修改。

“驱动不修改”不是“整个平台不修改”：Linux 模块加载、RMM、KVM 和配置工具都发生变化。Driver-VM 避免装入另一份完整内核，但仍需要栈、同步区、页表与运行状态；结论中的“无额外内存开销”缺少完整测量，不能字面扩展为零增量内存。

把 KVM 排除出保密性/完整性 TCB，需要 CCA 正确绑定创建请求、初始内容、资源归属和跨域调用。其可调度/拒绝执行的能力不会随之消失。论文借用的 CCA 形式化成果也不等于新增模块、eBPF 策略、所有固件依赖或实际 SoC 全部经过同一证明。

## 4. 从 ELF 和 DWARF 建立同步配置

工具读取闭源模块 ELF 的未定义符号，识别依赖哪些内核函数与全局对象；从带调试信息的 `vmlinux` 提取 DWARF 类型，生成 sync config。基本参数通过保存的寄存器复制，指针目标复制到 Driver-VM 可见的 sync region，并重写指针。

嵌套结构按 DWARF 展开、递归复制成员与指针；函数返回时对需要写回的对象反向同步。全局数据结构也通过类似规则处理。规则被编码为 C 结构，经共享内存装入 RMM，由可信同步模块执行。

类型布局不能单独决定所有接口语义：数组长度、`void *`、别名、环状指针、所有权、引用寿命、回调、并发和条件化输出仍需处理。作者承认一般指针语义不可判定，当前工具无法推导的配置需人工补足，复杂数据结构和 opaque 参数还是后续重点。“任何闭源驱动均可运行”属于研究目标，当前证据是简单 dummy driver。

迁移到本项目时，不能仅把一个地址落在已授权区域当成该调用合法；还需验证对象类型、操作、长度、权限和生命周期。项目已有对象归属、私有快照与执行计划，适合承载这些语义，无须照搬通用深复制框架。

## 5. 允许调用不等于允许任意参数

Filter-M 在每次同步前运行内核提供的 eBPF 程序，输入包括资源地址、函数参数或拟写入值，以及对应同步规则。通过后再执行 Sync-M；没有配置的访问拒绝。接口策略不仅限定资源集合，也限定如何使用这些资源。

论文列三种规则来源：通用 presets，例如不允许 DMA/MMIO 映射内核代码；从内核可能触发 panic 的条件反推参数约束；厂商给定使用约定，再由第三方审查。后两项大量内容是待完善方法，不是已经自动生成所有安全策略的证明。

形式化验证 eBPF VM 的执行正确性，不证明用户策略覆盖所有危险调用，也不证明 helper、同步编码、共享输入解析和资源修改都正确。若过滤参数与执行时参数可被修改、指向另一个对象，正确执行的过滤器仍可能检查错误事实；需要可信快照或原子化的检查/使用关系。

本项目可借鉴的是对每条 Proxy 操作写出“哪些 Client 可在什么状态对哪个对象做什么”，特别包括 reset、取消、导出、页表根切换、故障处理和完成发布。不能只验证函数编号属于白名单，也不能因有 eBPF 就认定访问语义安全。

## 6. 加载、异常与往返控制流

主内核重定位模块后，把 ELF 放进与 Hypervisor 共享的内存，向 RMM 提供位置及摘要；不可信 KVM 创建 Driver-VM，RMM 根据主内核提供的摘要核验驱动内容。摘要的来源必须是受保护主内核，所校验字节还应与最终执行字节一致；论文没有给完整的恶意并发加载协议。

原内核中仍保留模块映像，但其物理页被标记为 `GPT_GPI_NO_ACCESS`。内核调用模块，包括初始化，触发异常交给 RMM；Driver-VM 中不映射内核资源，反方向访问再次触发异常。RMM 根据资源、参数和规则过滤、同步并切换到目标上下文；返回和 callback 继续反向处理。

该设计需要正确识别故障来源、访问种类、指令效果、调用返回栈和当前实例。论文称没有同步配置时拒绝并继续到下一指令，但没有完整定义各种读写/函数调用的拒绝返回语义、错误传播或重试规则。不能把“跳过访问”直接等同于驱动状态机安全恢复。

GPT 的 PAS 归属、Realm Stage-2 的实例隔离及异常路由是不同机制。论文使用无访问标记触发中介，不意味着仅凭同处 Realm PAS 就能隔离 Driver-VM 和 Kernel-VM。实际设备 DMA、MMIO、GIC 和恶意设备访问仍需独立约束，本篇没有给真实 GPU 的完整配置和任务生命周期。

## 9. 与本项目、PORTAL/CAGE/ACAI 的比较

PORTAL 的可信服务 Realm 管理和本项目 ProxyRealm 将设备服务放进受保护域；BarriCCAde 进一步提醒：可信服务内部的复杂驱动本身也可能是攻击面。它选择在 RMM 做细粒度中介，本项目则可优先把已有高层对象/计划接口的授权收紧，避免为了隔离所有内核 API 而显著增加 RMM 复杂度。

若未来把 Panthor 驱动视为不可信，则威胁模型已经变化：必须另有可信组件持有页表根、SMMU/MMIO 与回收权限，驱动请求都要经过约束。单独把 Panthor 移到另一个 Realm 并不会限制它已持有的设备控制能力；这是可选研究扩展，不是当前可信 ProxyRealm 假设自相矛盾。

继续接受 RMM 认证原始 Client、ProxyRealm 统一控制 SMMU、建图时核验对象/实际 HPA/权限/生命周期并合成直达合法 HPA 的 GPU Stage-1，其他设备保留硬件 Stage-2 的假设。不用 RK3588 模拟限制否定目标设计，不重复添加身份 token 框架。

BarriCCAde 没有研究多 Client IRQ 的来源、路由、ACK、重放或 job 绑定；不能据其函数调用完整性认定中断链已解决。项目仍复用 GPUVM、认证队列、私有快照、native fence、cookie/epoch 与持久 IRQ127，分别论证真实完成、结果发布、通知投递及旧页回收。

后续可验证：合法接口配恶意参数、配置生成遗漏、嵌套对象别名/长度、过滤后共享输入变化、callback 归属、拒绝后错误终态，以及撤销/reset 时的迟到请求。优先验证现有语义边界，再决定是否需要驱动内部隔离；本轮仅提出条件，未实施测试。
