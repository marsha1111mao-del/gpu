## 2. 研究问题及项目定位

H100 机密计算通过认证加密在 CPU CVM 与 GPU 之间传输数据。大模型权重、KV cache、训练状态超出显存时，频繁换入换出让 CPU 加解密成为 GPU 等待的关键路径。PipeLLM 通过预测传输和预加密，把加密、复制、PCIe 与 GPU 计算重叠。

这是机密计算性能论文，主要信任现有 CVM 和 GPU TEE 的保护；不是新的 Arm CCA GPU 隔离系统。它与项目第一部分的流水线优化密切相关，也能帮助第二部分说明“提前准备”不能提前产生授权、完成或资源复用。

## 3. 威胁模型与可信边界

允许 Host OS 和 hypervisor 恶意，依赖 CVM 私有内存及 CC-enabled GPU 保持秘密与完整性；guest 内核、CUDA/驱动、PipeLLM runtime、密码库及 GPU 固件属于所依赖可信栈。排除 DoS 与侧信道，作者另外承认 NOP 会引入新的可观察信息。

应用的规则换页行为是性能预测来源，预测错误须由验证和回退处理。guest 内的 MPK/PKU 用于检测应用对预处理数据的访问，不等价于在同一地址空间防御能够任意执行指令的恶意程序。本项目面对互不信任 Client 的隔离，仍应依赖 RMM、私有 Proxy 状态和 GPUVM 等可信边界。

## 4. 为什么内存加密仍需要独立传输协议

CVM 内存加密与 GPU CC 加密使用不同机制。HtoD 时 CPU 在私有内存读取明文，用 AES-GCM 加密到共享 DMA 区，GPU copy engine 验证并解密；DtoH 则相反。共享区对 Host 可见，只有已认证的密文适合经过这里。

论文描述的 H100 路径在两侧同步初始 IV，此后随传输递增；IV 序列在实现中有编码，论文用整数表达。不能将这个具体驱动路径概括为所有 GPU 或未来 CC 接口都使用同一种 IV 管理方式。AES-GCM 是认证加密模式，安全不只是“数据看起来是密文”。

## 5. Predictor：预测什么以及依赖什么

模型换出通常重复层序；KV cache 换页可呈 FIFO/LIFO。Predictor 依据历史批次、尚未换回的对象、当前 IV，以及已知模型结构和大小，预测地址、长度与未来 IV。重点是大块、不常被 CPU 改写的换页，较小普通输入输出不走预加密，但仍消耗传输 IV。

这种预测不适用于任意数据相关程序。即使地址和长度相同，内容可能已改；即使内容相同，当前会话或 IV 也可能不同。因此命中缓存索引只是候选匹配，不能单独证明结果有效。对项目可复用执行计划同样应区分结构匹配、对象有效和当前执行授权。

## 6. Validator：内容版本和访问可见性

论文为预加密数据记录源地址范围，并撤销对应明文页写权限。若应用修改，触发 fault，使旧密文失效或回退；真正传输时检查地址、长度及对应 IV。作者预期模型权重和换出的 KV cache 很少被 CPU 改写，因而 fault 成本低。

建立“源内容仍是预处理版本”的条件，需要保护、预加密和最终使用之间没有未检测写入，也需覆盖别名、释放重分配与其他写入路径。正文没有形式化证明这些所有交错；本次公开代码的实际保护范围见后文，不能只凭有一个 address/size 标签就认定实现全部验证。

## 7. 错误预测：重排与 NOP 的安全条件

预测 IV 已落后于当前值时，旧候选密文丢弃并重建。预测顺序错误但仍可利用时，在同一独立换页批次内重排；若目标 IV 比当前值大，则发送 1-byte NOP 推进对端状态。不能回退计数器或直接重新使用已消费的传输密文。

重排依赖批次内操作没有必须维持的语义次序，批次边界由同步操作划定；不能推广为任意 CUDA stream 或任意 GPU 命令可重排。项目的通知合并和批处理也应保持发布、缓存同步、原生提交和完成之间的必要顺序。

## 8. 推测结果必须先留在私有区

§6 明确指出，若预加密直接输出到共享区，未提交的候选密文会对攻击者可见。PipeLLM 因而将其留在 CVM 私有内存，验证后才复制到共享 DMA 缓冲。固定共享缓冲、流水化复制与 PCIe 用于摊销额外复制开销。

这个约束在讨论未来 IV、错误预测与密码状态时尤其重要：不能把“最终未被 GPU 使用”当作“攻击者从未观察到”。本轮未独立证明全部 AES-GCM 状态和候选丢弃路径，但已确认这是论文明确的安全设计要求。

对 ProxyRealm，可迁移的原则是候选执行计划、对象引用和任务状态在可信私有状态中校验，再对外发布；Client 可改写的共享描述符不能在校验后继续作为执行真值。当前基线已有请求私有快照，应重点核对其引用和撤销边界。

## 9. 异步解密与“返回不等于可读”

对预测不会被 CPU 立即使用的换出数据，论文允许 copy API 提前返回，后台解密；目标明文尚未就绪时撤销读写权限。若应用提前访问，fault 路径同步解密再继续，防止使用占位旧内容。

安全终态应在认证与数据准备完成后产生。DMA 完成、解密 update 结束、认证标签通过、明文可见以及应用同步返回是不同事件。项目中 IRQ、真实 fence、缓存可见性和对象可回收同样需要各自的判据。

## 10. 平台、工作负载和基线

正文 §7 使用双 Intel Xeon Platinum 8462Y+、4.10GHz，KVM VM 分配 16 vCPU 和 250GB RAM，独占直通 H100-SXM / 80GB，PCIe 5.0。v1 将评估环境写为 KVM VM，不能据此独立证明测试同时启用了真实 TDX/SNP 私有内存；GPU CC 的测量与完整 CVM 部署证据应分开。

FlexGen 使用 OPT-66B 与 4-bit OPT-175B，1000 次合成请求，输入/输出长度 32/128 或 256/32；PEFT + DeepSpeed/LoRA 使用 OPT-30B/13B、Ultrachat 一轮约 6K 序列；vLLM 使用 Alpaca/ShareGPT、30 分钟请求轨迹及 2/4/6 并行采样。

对照是 CC-disabled 原生系统、现有 NVIDIA CC 和 PipeLLM。模型 offload 实验将 KV cache 留在 GPU，KV swap 实验将权重留在 GPU，避免混合解释瓶颈。模型 offload 使用多个 CPU worker，vLLM KV swap 使用一个加密和一个解密线程；CPU 资源成本不能省略。

## 12. 公开原型结构和部署限制

仓库 README 明确是 prototype；构建前要修改硬编码路径和参数，先 profile IV。生成替代 `libcrypto.so.3`，通过 preload/hook 介入 OpenSSL 和 CUDA。CUDA 程序可能要重新以 shared cudart 编译；PyTorch 路径要求替换对应 CUDA 静态库后源码重编译，conda 也涉及库替换。

因此应用模型与框架逻辑不用改，不等于所有现成二进制无需重编译或库环境适配。README 提到的 `profile.sh` 在本次完整根树中未见，实际有 `profile_iv.sh`；不能原样宣称具备一键完整复现实验脚本。仓库含静态库二进制，本轮仅记录结构，没有下载运行或替换本机库。

## 14. 安全目标的边界

NOP 会暴露正在换页和预测失败频率，作者承认其可能泄漏访问模式，安全后果仍待研究。因此“保持 NVIDIA CC 安全”应限定在论文的机密性/完整性与侧信道排除模型，不能解释为观察面完全不增加。

它使用单 GPU 独占直通，不提供恶意多 Client 的 GPUVM 隔离、资源撤销或中断路由协议。其 AEAD 传输防重放也不等同于应用 job 语义防重放：合法传输仍需绑定对应对象版本和当前任务。

## 15. 对本项目的设计与验证建议

将推测性准备与可信提交分开：缓存执行计划或预取数据必须绑定会话、对象版本、范围和权限；提交前重新确认仍有效，验证失败进入正确回退，不能发布候选成功。这个原则与 PhantomMap 的实际页和生命周期检查相互补充。

将任务终态与数据可见性分开：完成必须同时满足所需原生 fence、错误状态及真实缓存维护；若有额外认证/转换，还需成功后再让结果可读。不要把 API 早返回或 IRQ 抵达当作输出已安全就绪。

若评估异步/批处理优化，覆盖小任务、乱序依赖、输入被改写、对象复用、reset 与取消，以及多个 Client 竞争；分别测量吞吐、尾延迟、额外 CPU 与私有缓存占用。当前集成 GPU 架构无需凭此论文增加 PCIe 加密；应把它用于提炼优化不变量，硬件差异仅影响实验选项。
