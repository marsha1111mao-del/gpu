## 2. 为什么值得接在 ACAI 与 PORTAL 后面读

ACAI 强调设备、Realm 和映射的身份与归属一致，PORTAL 强调可信设备服务。sIOPMP 进一步讨论：授权规则大量增加、设备身份切换、频繁 map/unmap 时，如何兼顾权限检查、资源有限和原子撤销。

用户设定的 ProxyRealm 合成 HPA Stage-1 映射已经覆盖建立时授权；本论文最有价值的补充是权限更新过程中不能出现新旧身份或新旧区域的混合状态。它不要求本项目复制 IOPMP，也不能据此否定软件合成映射的设计假设。

## 3. 威胁模型与 TCB

论文信任 SoC 内 CPU 核、sIOPMP 等硬件与轻量 secure monitor，不信任 REE OS 和外部设备；恶意设备可发任意 DMA 读写。CPU 内存隔离及安全中断依赖已有 TEE 机制。排除 DRAM 物理攻击、内存窥探/拼接以及 SoC 内侧信道。

因此该方案保护的是被隔离主存不被未授权 DMA 访问，不是证明恶意加速器会正确计算、返回诚实结果或保护设备内部秘密。可信计算任务若把明文交给设备，仍需另行确立该设备及固件的可信性。

## 4. IOPMP 的权限对象

请求带有 source ID（SID）；SID 关联 memory domain（MD），MD 包含若干带读写权限和优先级的连续物理区域。匹配多个区域时，低编号项优先，可用高优先级禁止项限制较宽的授权范围。不同通道或特权模式要有可区分的源身份。

SID 不是普通软件可自填的 Client 字符串。论文机制依赖总线和可信配置正确标记来源；不能只依据报文中声明的身份做授权。对本项目，同一个物理 GPU 的流标识也不自动区分其全部 Client，必须由可信 Proxy 和 GPU 上下文管理承担相应职责。

## 5. MT checker：扩大规则数量但保留优先级

第一项优化把检查拆成多级流水线，以增加延迟换取吞吐；第二项用树形仲裁组合匹配结果，保留优先级语义并缩短逻辑深度。不同流水级间保存中间结果，最终检查通过才授权内存事务。

关键安全细节：总线被阻止时，检查流水线里可能仍有请求。论文增加 monitor，使总线和 checker 的 block 状态一致。这个说明比“加锁修改表”更具体，但正文没有给出可移植到任意设备的全局在途事务排空证明。

## 6. Mountable IOPMP：有限热集合与可换入冷状态

硬件无法无限增加表项。扩展表保存于受保护主存；对冷设备第一次请求触发 SID-missing 中断，由 monitor 将设备 ID、MD 和区域换入硬件。原型为冷设备使用最后一个 MD，切换时清除旧项并检查请求 ID 与当前 eSID 匹配。

所谓支持无限设备，是设备命名与后备状态不受固定寄存器数量直接限制，仍受实际内存、硬件活跃集合和切换开销约束。尤其不能写成无限设备同时以原生速度访问：同一冷槽反复换入会严重降低吞吐。

## 7. CAM remapping：改变热设备集合

DeviceID2SID 使用 CAM，将范围较大的实际设备 ID 映射到有限热 SID；未命中则走 eSID 冷路径。原型 CAM 为 63 项，查找不增加额外周期；可显式指定热集合，也可由 monitor 根据 clock / 近似 LRU 策略调整。

“零额外查找周期”不是冷热切换、配置写入和安全撤销零开销。正文讨论处有“64 hot devices”的概括，而细节将最后位置留给冷路径、CAM 为 63 项；本记录保留具体结构，不把概括误作可无限并行的性能承诺。

## 8. 拒绝事务与原子更新

违规事务可采用 packet masking：屏蔽写 strobe，并对不合法读返回值清零；或者引向 dummy 节点返回 bus error。两种方式都记录地址、SID、权限类型并通知 monitor。掩码路径还需关联响应，不能仅阻止请求侧写入就声称读保护完成。

§5.3 区分两种不一致。**Entry inconsistency**：逐项修改时可能让旧、新区域同时可访问。**Device inconsistency**：冷槽 eSID 与区域未同时切换，可能让新设备访问上一设备的区域。解决方法是在修改前按 SID 阻断，完成全部相关配置后恢复，并照顾 checker 中的请求。

对 GPU 共享，软件锁可以串行化 CPU 更新，但并不自动停止 GPU 已取走的命令、缓存翻译和 DMA。需要明确停止新提交、在途任务终止条件、旧翻译失效完成、事件处理和对象可复用时刻。这是应用本论文原则的推论，不是它已经给出的 Mali 协议。

## 9. 所有权与 capability 接口

启动时 monitor 持有资源 capability；派生只能缩小区域或权限，转移改变所有者，复制也受权限约束。创建 TEE 时转移设备和内存资源，随后 Device_map 由可信侧依据 capability 验证。资源管理器维护 ownership chain，TEE manager 管理 capability 与硬件的关系。

该层可表达“同时拥有设备与内存资源才可建立对应映射”。对本项目可以落为 RMM 身份、会话、对象、HPA 范围、权限及生命周期的一致检查，未必需要新增一套 capability API。论文描述中没有足够材料证明任意深派生链的全部撤销语义，不宜自行补写为完整形式化 capability 系统。

## 10. 实现和评估必须分开读

硬件原型在 Chipyard，含 Rocket / BOOM、IceNet、NVDLA 和 dummy DMA；Verilator 用于微测，FireSim 用于应用。软件修改 Penglai monitor，正常域和 TEE 使用 Linux 5.15。

由于缺少可用 RISC-V IOMMU，对照还包含 Intel Xeon Gold 5317 的 IOMMU、AMD EPYC 7T83 的 SEV-SNP/SWIO，以及 x86 上按硬件微测成本加入额外开销的软件 sIOPMP 模型。它们不能当作同一芯片上所有机制的直接硬件对照。

## 12. 翻译缓存与授权撤销的区别

混合方案的核心是：IOMMU 可继续保留陈旧翻译，但 sIOPMP 在实际物理地址处立即拒绝旧访问，因而安全不依赖 IOTLB 立即失效。翻译与最终授权由两个独立机制执行。

本项目若最终只有 GPU Stage-1 持续执行访问边界，旧 Stage-1 翻译的失效就是安全相关步骤。不能直接借用“可延迟 IOTLB”结论而省略失效；只有另有可信、独立、检查实际 PA 的拒绝机制或明确隔离的复用协议时，才可能重新论证。这里讨论的是用户架构假设内的职责与顺序，不要求硬件具备论文同款单元。

还应注意，区域检查阻止“已撤销地址”的旧访问，不等于自动识别同一 PA 被重新授权后的旧请求。物理页从 A 转给 B、随后同一设备又获授权时，仍需讨论旧事务排空、身份变化、内容清理和复用时点。本文未展示适用于任意 GPU 异步任务的代次协议。

## 13. 与中断可信性的关系

本文使用违规中断、SID-missing 中断并依赖已有安全中断控制；中断是 monitor 的工作触发器。它没有构造 Client 任务成功完成的真实性协议，也没有证明恶意 Host 下的及时交付。不能用其“secure interrupt”引用替代 GPU 完成记录、接收目标和防重放的独立设计。

项目应分别论证：事件发往哪个经认证端点；队列记录属于哪个会话/任务；真实 fence 是否已经进入正确终态；旧事件能否命中新 epoch；通知被合并、重放或延迟时是否影响安全及活性。
