## 2. 核心问题：初始化结束不意味着初始化者的影响结束

一些GPU TEE把小型shim纳入TCB，复杂驱动留在不可信OS；安全任务运行时锁住MMIO、保护内存、接管中断。它们把初始化视为发生在秘密计算之前的非敏感操作。

MOLE指出，初始化会决定持续运行的MCU固件及其映射。若Host在此前装入恶意固件，之后关闭Host对MMIO的写权限，也不会使已运行的MCU自动变得可信。

这是一种跨阶段的信任问题。它并不证明页表隔离无效，而是说明被授权设备内部还包含能访问数据、调度任务和报告完成的程序主体。外部授权无法区分同一设备标识下的恶意内部固件。

## 3. 威胁模型与攻击前提

论文假设高权限攻击者控制shim之外的GPU驱动，尤其能控制firmware management、固件加载和初始化映射。这与其研究的Host/驱动不可信GPU TEE目标相对应；不是无权限普通Client自动具备的能力。

目标主要为带CSF/MCU的现代Mali。实验探索于RK3588板并在Pixel8/TensorG3核实部分结论。论文选择StrongBox式保护作为实际攻击对象，说明当时无法在商用硬件直接运行CAGE的CCA；对CAGE/MyTEE还采用源码分析和作者确认作为设计适用性依据。

因此不能称其在原版CAGE硬件上完成了相同攻击，也不能把MyTEE的framebuffer原型解释成已具备完整CSF计算TEE。作者引用和比较表的分类要结合各原论文真实范围阅读。

## 4. MCU是计算与通知路径中的持续主体

作者逆向表明MCU采用Armv7-M指令集，负责接收CPU任务、分发至compute unit和通知CPU。其内存访问由定制GPU MMU以及MCU MPU约束；MCU有独立地址空间，任务使用其他地址空间。

Host与MCU有共享内存和双向事件通路。MCU能参与任务提交和完成处理，因此不只是一个“只读固件文件”，更不是完全透明的硬连线。

论文对MCU调度事件的观察是针对所测固件版本，不能据相同Mali产品名推导所有版本都使用相同事件编号、内存布局或权限。对于项目，需要固定实际固件与驱动版本再界定信任边界。

## 5. 为什么既有外部保护没有挡住攻击

| 外部防护 | 正常保护对象 | MOLE的绕过前提 |
| --- | --- | --- |
| CPU Stage-2/GPC | 不可信CPU软件不能访问秘密或控制页 | 恶意代码已在设备MCU内运行 |
| TZASC/设备GPC/SMMU | 未授权设备不能访问受保护页面 | MCU与合法GPU compute unit使用同一设备侧身份/授权边界 |
| 任务运行期MMIO保护 | Host不能临时换root、插入任务 | 恶意固件及可写映射已在初始化阶段建立 |
| MCU MPU | 限制固件执行/数据范围 | 策略自身由攻击者可替换的固件配置 |
| 数据传输加密 | 不可信Host不能读取密文 | 真实GPU计算仍需使用明文，内部恶意MCU处于明文端 |

正确理解是：固件进入了设备被授权的一侧。MCU也不天然拥有任意全系统物理访问；攻击还依赖映射控制、设备可达页和已有访问授权，不能把“MCU存在”直接写为所有内存隔离都可绕过。

项目已假设固件加载可信、实际PTE/root/MMIO受到保护，这排除了MOLE最直接的恶意初始化前提。后续应核验该假设在首次启动、恢复、更新、reset和错误重载时都成立，而不是重复提出一套与现有前提相同的保护。

## 6. 攻击效果与机密性/完整性的区别

数据泄漏路径利用MCU在秘密计算期间读取获准的明文，再输出到攻击者可读区域；结果篡改路径利用完成处理阶段覆盖输出，使可信CPU读到符合格式但语义被修改的结果。

后者与本项目的完成研究尤其相关：即使物理IRQ的来源确为GPU，若产生事件或维护完成状态的固件不可信，IRQ真实性也不能推出结果真实性。因此必须把GPU/固件可信根与物理GIC事件认证、Proxy的job归属检查分开论证。

同时，可信固件也不意味着可以信任工作负载可写的同步计数。需要核对谁能写计数、固件如何解释、错误状态如何传播；MOLE只证明了其恶意固件路径，不能自动判定项目同步页已可利用。

## 7. 实现和实验范围

论文报告约940行Rust firmware parser和约1400行kernel module，用于修改与装载测试固件。它是攻击研究原型，不能把这两项LoC写作GPU TEE完整可信基。

实际实验使用目标设备上的保护配置、MCU行为分析和应用数据比对。部分被研究TEE的完整配置在新设备上采用适配/模拟，而非所有原始系统和所有产品都逐一部署。GPU MCU在多个设备中广泛存在，说明攻击面值得关注，但设备清单不等于每项设备均被端到端攻击验证。

论文对NVIDIA RISC-V、AMD MES只提出可研究的推广方向，明确尚未绕过这些固件验证机制；不能将其写为已攻破H100或所有离散GPU机密计算。

## 9. 作者提出的缓解与各自边界

**可信固件管理：** 将加载/初始化/重载放进可信域，阻断Host对固件及相关控制对象的修改。对完整可信驱动VM路线更自然，但必须保证真正使用的固件和配置由可信路径建立。

**签名验证：** 使用可信公钥验证厂商固件，并保护校验到装载/运行之间的数据及映射，防止TOCTOU。仅显示GIT_SHA或对Host提供的内容算hash不能认证来源。签名的版本策略和撤销还需定义；合法但被撤销的旧版本不能因签名正确便永久接受。

**MCU内部分域：** 可信/非可信执行模式及内存隔离是可能架构，需要重新证明共享调度状态与安全边界。作者将其作为方案讨论，未提供完整实现或评估，不应列作已完成修复。

对于项目，优先按已定完整可信Proxy路线落实前两项，不必为了与论文对齐新增硬件分域；也不把某块板缺少某机制当作目标设计不成立的理由。

## 10. 固件与任务生命周期联合考虑

建议把固件状态作为可信设备epoch的一部分：可用固件/配置经核验后，才允许建立新job；reset或恢复期间禁止新启动，旧job以明确错误终止；恢复后递增epoch，旧完成和旧控制对象不能匹配新job。

需要区分固件代码完整性与运行中可变状态。MCU队列、共享接口、GPU页表、job记录、错误状态和cache都可能包含跨Client信息；不能仅清理固件文件就声称没有残留。允许Host保留的调度/电源建议也应受可信接口约束。

这不是要求每个job都重新证明/重载全部固件。可以在一段经验证的设备epoch内摊销证明和初始化成本，前提是没有未授权修改或越过可信状态的恢复路径。

已取得作者PDF和项目入口；本轮尚未取得并核验与论文匹配的完整parser/kernel module固定源码版本，没有运行恶意固件、作者PoC或板端实验。文中的攻击能力和数字来自原文及上述具体证据，不能表述为本轮独立复现。

## 12. 与其他论文和项目的关系

MOLE补充StrongBox/CAGE等小shim路线未闭合的持续设备主体；其对完整可信VM“不适用”仅限本文攻击前提，不是对完整VM无漏洞的证明。PORTAL/ACAI和本项目仍应明确固件信任，但不因此需要推翻已选可信驱动服务。

Devlore/TEEtime解决事件在CPU侧的来源和路由；MOLE提醒事件生成者本身也必须在信任链。CAEC解决通信端点；PhantomMap提醒实际映射页和生命周期不能只看逻辑对象。项目可沿这几种边界建立端到端job授权、可信完成及安全回收论证。

验证应覆盖未认证固件、校验后修改、旧版本重载、reset中提交、旧epoch通知、固件重启后句柄复用和受害Client恢复。本篇未改运行代码，无新增性能测量；无硬件run-id、无新增硬件PASS。
