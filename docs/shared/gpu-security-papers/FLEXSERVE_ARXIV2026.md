## 2. 问题：内存隔离与资源利用之间的矛盾

大型模型、KV cache 与普通移动应用竞争内存。固定保留大块 TrustZone 安全内存会挤压普通应用；每次重新分配连续大块又增加碎片整理和首次响应延迟。让安全环境独立缓存，却不给普通 OS 可回收接口，也容易造成双方无法根据整体内存压力调节资源。

FlexServe 的主张是分离管理权与访问权：普通 OS 可请求分配或回收，但不因此能读取受保护内容；可信环境决定哪些安全页可返还，并先完成必要保护步骤。它把安全回收作为性能设计的一部分，而不是只研究如何建立保护。

## 3. 与本项目的关系及类型

这是 TrustZone / NPU / 端侧 LLM 系统，实际设备不是 GPU，隔离域不是 CCA Realm。其 NPU 采用 normal 与 protected 模式时分切换，不能同时归两个不互信主体直接访问。论文提出可推广到其他 xPU，不等于已经实现或评估 Arm GPU 多 Client 共享。

对本项目最直接的迁移是共享池和授权状态管理：Host 或 Client 可以表达资源压力、提出释放请求，但只有可信 Proxy/RMM 可以使实际页恢复为可访问状态。无需为模仿 TrustZone 路线改变用户设定的软件 HPA 翻译及硬件 Stage-1 执行模型。

## 4. 威胁模型、可信基和客户端边界

攻击者可以控制 normal-world 应用，并在启动后利用漏洞控制内核；初始内核代码由 secure boot 保证良性。信任 secure-world OS、FlexServe TA 及 EL2/EL3 Flex-Monitor，排除物理攻击、侧信道与 DoS。

普通世界客户端的输入输出不因调用 TEE 而变得对恶意内核保密，作者明确承认这点。安全世界 TA 作为客户端时，输入输出才在相应可信边界内。模型权重保护与普通客户端自身的机密性应分别评价。

该模型没有完整覆盖任意恶意受保护推理应用或多个相互不信任安全租户。共享一个“Flex-Mem 集合”与逐 Client 授权粒度不同，不能直接替代本项目对象归属检查。

## 5. Flex-Mem 的建立与 DMA 保护

Flex-Mem 物理上仍属于 TrustZone normal memory，通过 EL2 CPU Stage-2 从不可信 OS 的地址空间撤销访问，再由 secure world 映射使用。这避免必须依赖少量连续安全区域。

Monitor 同时从其他设备的 SMMU 映射移除这些页，并封锁 SMMU MMIO，使配置更新陷入可信层，追踪或验证 active roots。这与本项目保护真实页表、root 和 MMIO 的假设一致：限制 CPU 地址空间与限制 DMA 必须同时成立。

正文对 root 更新有描述，但没有完整展开页表存储写保护、所有别名、在途 DMA、TLB/IOTLB 同步和失败回滚。它声称 SMMU 不可被内核修改或绕过；在没有完整源码协议核验时，应把这作为设计要求，不能用一句“拦截 root 寄存器”替代全部实现证据。

## 6. 回收：已选择返还与已安全可访问是不同状态

`rsmem_reclaim(size)` 允许普通 OS 请求数量，可信框架选择实际页。权重页通常清零即可重载；KV cache 要先加密写回，再清零。Monitor 最后恢复 CPU Stage-2 映射并归还普通 OS。

异步版本先返回已选择页，使 OS 可以安排后续复用，但暂不恢复实际访问。若普通应用提前访问，Stage-2 fault 阻塞，直到加密、写回、清零和重映射完成。这说明“分配器认为可安排复用”和“硬件已允许读取”可以分离，前提是故障路径与生命周期严格闭合。

对本项目，可以有已撤销、正在排空、待清理、可回收等状态；不能把 Client release、ACK 或 RPC 返回直接解释为页面已安全返还。任何 DMA 别名也必须受同一回收屏障约束，CPU fault 不能阻止仍保留映射的设备访问。

## 7. Flex-NPU 的驱动沙箱和切换

普通模式下 OS 使用 NPU；保护模式撤销 OS 对 NPU MMIO 的访问，切换到独立 Stage-2 沙箱运行复用的驱动。驱动代码与数据在沙箱可见，在普通 OS 不可见。NPU SMMU 只映射 Flex-Mem，限制把秘密直接拷贝到不受保护页的机会；其他设备不能访问这些页。

切回普通模式时，恢复相应 MMIO/驱动可见性，并把 NPU 页表恢复为只可访问普通内存。该方案具有整个保护域的粗粒度隔离，不是本项目按对象、权限和 Client 的最小授权模型。

作者以“NPU task launching 是无状态操作”论证普通模式遗留驱动状态不影响安全任务。此结论依赖所用驱动、提交接口和硬件，不能推广为 GPU queue、固件、doorbell、GPUVM 或任务管理都无状态。本次原文没有给出足以核验 GPU 式异步队列、固件重载、恶意 IRQ 和 reset 残留的完整流程。

## 8. On-demand protection 与恢复可信执行

空闲一段时间后可关闭 Stage-2，降低普通应用的虚拟化开销。EL3 在安全内存中保存 EL2 monitor 代码、数据和页表的摘要；恢复时重新启用保护并验证摘要。EL2 不含模型秘密，因此此处主要维护完整性。

摘要只能在可信恢复顺序成立时发挥作用：验证前不能执行已被改写的 EL2 代码或依赖其不可信页表开放秘密；验证与进入保护态之间也不能再次被修改。论文的高层流程没有细化所有恢复原子性及多核同步，本次不将它判为已证明的实现漏洞，也不将其作为可以无条件照搬的优化。

本项目存在受保护池、长期映射或在途 GPU job 时，不能仅因“暂时没有新请求”解除保护。需要证明所有仍受保护对象已安全转移或回收；这是比一个空闲 timeout 更强的条件。

## 9. LLM 流水线与缓存

流水线按层重叠分配、密文加载、解密和计算，保留同一层内依赖。缓存策略使用模型调用率、频率、历史 prompt 长度，优先保留早期权重与选定 KV cache；常见 agent workflow 还可以预取后续模型。

回收优先级与缓存价值分开：先返还清理成本低的权重页，再处理必须写回的 KV cache；随后异步重排剩余缓存。后台预先加密 KV cache 可降低紧急回收成本。这是“先快速满足压力，再改善缓存布局”的性能策略，不能放松实际访问授权和清理顺序。

论文讨论通过 inline crypto 在存储 DMA 路径解密，但评估板不支持，正常评估没有实现这一优化；消融中的 NoDec 是模拟潜在收益，不能算已部署硬件测量。

## 11. 实现及可信规模

NanoPC-T6 / RK3588 NPU，16GB 内存，Linux 6.1.57、OP-TEE 4.5.0；SSD 带宽约 2.65GB/s。Monitor 约 4.5K LoC，TA 推理框架约 8.3K LoC，支持 Llama3/Qwen3。两项是新增组件规模，不能代替 OP-TEE、驱动、固件及库的总 TCB。

作者绕过不可插入优化的闭源模型 runtime，使用社区逆向 NPU INT8 GEMM，并增加分块和 CPU/NPU 流水化。原型还因 IOMMU 地址空间约束切换页表覆盖较大模型。硬件限制是实验实现条件，不用于否定其目标设计；对应切换一致性仍需要可验证证据。

原文没有明确提供可固定版本的完整 FlexServe artifact；本次做了相关仓库检索，没有运行或审计匹配实现。引用的开源矩阵乘项目不能自动当作完整系统源码。

## 13. 97.2% 普通应用性能的条件

摘要把该结果概括为维持普通应用性能。§7.5 的端到端实验明确说安全推理与普通 benchmark **不同时运行**，两者交替且可用内存不足以让双方都无条件保留全部缓存。实验比较的是跨工作阶段的回收/缓存政策，不能写成活跃并发推理下普通应用仍有 97.2% 吞吐。

背景 stress-ng 在主要配置中占用内存，却刻意不增加 CPU 或内存带宽竞争；模型真实并发、热状态和带宽压力可改变结果。没有用论文结果证明本项目多 Client 的性能或公平性。

## 14. 相对 TZ-LLM、ASGARD 和项目的增量

TZ-LLM 通过流水线缓解连续内存与加载成本，FlexServe 引入页粒度撤销和协同回收，进一步利用普通 OS 的内存压力信息。ASGARD 把完整 NPU 栈放到受保护 VM，FlexServe 复用 secure-world 软件和受保护驱动片段。两者信任与切换边界不同，本论文未给出与它们完全同环境的直接性能复现。

本项目采用可信完整驱动 Proxy，不需要为了缩小某篇论文的 TCB 口径拆分驱动；可以吸收资源管理与内容访问分离、基于真实终态的异步回收及按生命周期缓存合法映射。每个缓存项仍需检查 Client 实例、对象 generation、HPA、权限和当前授权。

## 15. 需要继续验证的设计问题

| 场景 | 项目需要的事实 |
| --- | --- |
| OS/Client 请求回收正被 GPU 使用的页 | 不可信请求不能越过在途引用、停止访问和失效屏障 |
| 回收页被新 Client 立即申请 | 新 owner 只能在清理完成后获得实际访问；旧映射不再可达 |
| 保护关闭与新任务同时发生 | monitor、页表、对象授权和设备 epoch 转移具有可信顺序 |
| 普通模式污染驱动/固件状态 | 不能以启动 API 被称为无状态而跳过状态重建与校验 |
| 合并、伪造或旧完成通知 | 只根据可信 job/fence 终态推进资源生命周期 |
| 后台 KV 写回被替换或重放 | 需要明确密文完整性、版本及会话绑定，而非仅声明加密 |

这些是由论文机制和未展开协议推导的研究问题，不是本轮已复现的 FlexServe 漏洞。其主要贡献对项目的意义是：内存隔离并非只在 map 时检查，资源回收与性能优化也必须保留同一授权生命周期。
