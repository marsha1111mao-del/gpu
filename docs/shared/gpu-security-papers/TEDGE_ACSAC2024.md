## 2. 研究问题与贡献

CPU TEE 保护软件，并不自动保护 FPGA 配置。恶意平台可替换 bitstream、在配置中加入泄露通道，或在证明后重新配置设备。仅证明 CPU 应用、仅保密 bitstream 的传统 IP 保护，均不足以建立远程用户对异构执行的信任。

T-Edge 利用 ARM 与 FPGA 位于同一 SoC 的布局，将片内连线放入物理信任边界；由 TrustZone 保护 CPU↔FPGA MMIO 和配置入口，再用启动测量、设备证明与挑战响应使用户决定是否信任当前应用。其增量主要是异构配置纳入信任建立、开发者部署灵活性及制造/预置/运行参与方的责任拆分。

论文选择单租户边缘设备，主动避免恶意共同租户的共享问题。它提供与可信 Proxy 相近的“控制入口收归可信侧”思路，但没有提供 GPU 多 Client 并发上下文、页归属或可信中断路由方案。

## 3. 参与方、威胁模型与可信基

| 参与方 | 论文信任或攻击能力 | 对本项目的对应关系 |
| --- | --- | --- |
| Manufacturer M | 硬件、TrustZone、根信任正确，但可能好奇应用使用情况 | 平台硬件信任假设，不能代替 RMM 的 Client 认证 |
| Provisioning P | 正确发布设备公钥映射、审核并签署 FSBL；可能好奇使用情况 | 根密钥和启动策略供应方 |
| Platform owner O | 控制板卡与外部物理环境、可加载任意软件；不能探测片内状态或连线 | 恶意 Host 类对手，但不具备片内物理攻击能力 |
| Developer D | 用户选择的合法应用应无漏洞、不泄露用户数据；其他恶意应用可试图窃取设备根密钥 | 应用可信假设与保护基础设施密钥的目标分开 |
| User U | 从可信渠道取得设备公钥，核验预期测量后才交付数据 | 远程策略核验者，不等于已认证的本地 Client |

可信基包含 Boot ROM、正确硬件/片内隔离、受信 FSBL、TrustZone 运行保护及被用户接受的 secure OS、应用和 FPGA 配置。论文没有给出完整系统 TCB 的 LoC。不能将少量补丁或 FSBL 当作全部 TCB；“允许第三方程序启动”也不意味着恶意程序可以获得用户数据。

作者称 TrustZone 漏洞应被修补，这是模型前提，不是对现有实现已经完备的证明。片外 DDR 未加密与 cold boot 在 §7.2 明确讨论；单芯片并不自动保护外置 DRAM、软件数据流或任何形式的侧信道。单租户减少共同租户攻击面，不能据此推导零时序泄漏。

## 4. 架构与控制流程

启动链为 Boot ROM→FSBL→ATF、OP-TEE、U-Boot/Linux 等组件及 FPGA 配置。传统签名验证只强制用于 FSBL；其后组件先测量，再由远程用户按测量策略决定是否接受。该选择允许第三方部署，不要求 OEM 为每一应用重新签署整镜像。

FPGA 资源映射为 secure-world-only，阻止 Normal world 直接 MMIO。运行时重新配置必须由可信应用控制；若不使用或不能保护重新配置入口，则在 bitstream 中关闭该能力，并要求完整 reset 后重新证明。控制面和配置稳定性是论文安全结论的必要前提。

论文把片内 CPU↔FPGA 通路放在不被物理探测的假设内，从而不为该通路加密。这一安排不包含一般离散 GPU、PCIe 或片外共享内存的保护证明；也没有完整展开 FPGA master、实际 PA、所有 DMA 路径和其他处理器的逐域授权状态机。

## 5. 远程证明协议逐步分析

制造/预置阶段固定设备序列号 i 与设备根密钥，P 发布 i→设备公钥，并配置 FSBL 验证根。概念设计在 FSBL 取得设备私钥，仅允许启动阶段使用，签名后清除工作副本并关闭后续根密钥读取。

FSBL 测量自身 F 与后续程序 P，生成本次应用临时密钥对 ks，使用设备根密钥签署报告 (i, Hash(F), Hash(P), ks_pub)，再把签名报告和 ks_priv 交给 secure OS。设备根私钥与应用会话私钥承担不同角色，不能混为一个长期共享密钥。

运行时用户生成临时公钥 kc_pub 作为新挑战；应用用 ks_priv 签署“启动报告+kc_pub”。用户检查挑战一致、ks 签名、设备签名，再检查 Hash(F)/Hash(P) 是否满足自己的策略。签名有效只证明来源和绑定，测量策略通过才代表用户接受该程序。

随后双方利用 ks 与 kc 的 Diffie-Hellman 共享秘密建立通道。挑战新鲜度必须来自用户；本地恶意 Host 给出的 nonce 不能自行证明远程用户当前会话。论文未详细规定报文编码、KDF 域分隔、AEAD 序列号、错误处理或多并发会话协议，不能将这些细节写成已验证实现。

该协议向用户证明设备/程序，并绑定用户发出的临时公钥；没有以独立用户证书证明任意挑战发送者具有设备访问权。因此不能用它替代本项目的 RMM 原始 Client 认证及对象权限检查。

## 6. 安全论证及其边界

§5 用根密钥仅 FSBL 可访问、签名不可伪造、临时密钥隔离及挑战响应解释设备/程序认证和重放阻断。它依赖合法上下文不泄露 ks_priv、不同启动会话正确产生并隔离临时状态、测量后程序/配置不被未授权替换。

摘要、引言和结论称使用 ProVerif 自动验证。然而完整公开稿未呈现可审查的 applied-pi 模型、查询、事件对应、输出结果或附录；本轮取得的完整公开仓库树也未见模型文件。因此登记为“作者声称使用 ProVerif”，不声称本轮重现验证或证明具体多会话性质。

隐私目标针对 M/P 不必在线参与应用会话：U 可离线取得设备公钥，P 不知道运行哪个应用。这不是对用户或 Host 隐藏设备序列号的匿名证明，也没有分析网络流量、配置更新或查询关联造成的额外元数据泄漏。

重新配置属于可信应用行为的前提非常关键：若应用可以在测量之后加载新硬件设计，用户接受的 Hash(P) 必须覆盖相应加载策略。初始测量不会自然证明将来每个设备配置的内容、当前代次和有效期。

## 7. 原型与作者实验

平台为 Xilinx ZCU106 ARM/FPGA MPSoC，使用修改后的 FSBL 和 OP-TEE；工作负载是 Vitis HLS 综合的 2D convolution filter，源自 Xilinx 教程。作者要求生产部署关闭 JTAG、开启 secure boot、将未用处理器置于 non-secure，启动上下文也必须初始化。

| 指标 | 无 attestation | 有 attestation | 正确解读 |
| --- | --- | --- | --- |
| 启动耗时 | 2125.80 ms | 2167.45 ms | +41.65 ms，约 +1.96%，是作者的两镜像比较 |
| 卷积吞吐 | 28.80 MB/s | 28.97 MB/s | 作者认为差异处于误差范围，不能宣称安全设计带来约 0.59% 加速 |

论文明确排除将秘密数据重路由到 TrustZone 的成本，理由是基础 TEE 本就需要。因此“无运行吞吐影响”只覆盖其测量口径，不是网络传输、通道密码学、数据搬运与证明在内的端到端零成本。

表格没有展开样本量、方差或置信区间；仅一项卷积应用，没有多租户、GPU job、IRQ、reset、DMA drain、冷启动攻击或并发恢复测试。恶意双通道 bitstream 的说明是设计攻击场景与摘要检查解释，不能添加未报告的攻击实验结果。

FSBL 补丁的 measure_partitions 只读取 `PartitionHeader[5]` 指向的内容；key_derivation 使用设备 AES 源和 eFuse IV 处理测量，再 SHA3 派生材料，取其中 32 字节附到 OP-TEE 映像尾部。它不是概念协议中显式呈现的“完整启动报告+每次新生成的 ks+设备签名”实现。未核对实际 BOOT.BIN 分区布局，不能认定第 5 项覆盖整个应用、FPGA 和固件。

OP-TEE 补丁从映像尾部取该材料为 Ed25519 种子；attestation_sign 对 nonce、bitstream 分别 SHA256，再签署二者摘要的组合。Host 示例只产生本地 64-bit nonce、上传 bitstream、输出签名字节；未呈现用户侧预期测量策略、设备证书验证、DH 或完整安全数据通道。

加载 PTA 使用全局 _session(len, off, mem)，UPDATE 将输入复制到可信分配区，FIN 先签名该缓冲区，再调用 PM_FPGA_LOAD。私有副本有助于避免直接签署随后可被 Host 修改的缓冲区；但所读补丁没有逐会话配置代次、Client 身份、并发锁、显式释放/回收状态机或把加载成功状态纳入签名的字段。

“签署准备加载的内容”与“确认设备已完成该配置且当前仍保持它”有不同语义。调用返回值确实传播加载错误，不能直接断言失败会被上层当成功；然而仅凭上述签名格式也不能证明配置完成、旧任务已停止或当前运行代次。这里记录协议证据边界，不宣称新发现已利用漏洞。

补丁含 FSBL DEBUG_DETAILED 的派生材料/密钥打印，以及 OP-TEE DMSG/DHEXDUMP 私钥打印。附加配方设置 CFG_TEE_CORE_LOG_LEVEL=3，不能未经宏展开和实际镜像核对就声称 debug 私钥已经在生产日志泄露；应记录为生产构建需排除的敏感诊断代码及未核验条件。

设备树 no-map 是 OS 内存保留描述，不能单独视为恶意 OS 下的硬件保护。工程脚本仍链接 raw 卷积程序/模块，完整静态路径没有证明论文 secure-world-only 配置在所有运行镜像生效。本轮未下载预制 SD 镜像、未核对全部 FSBL/ATF/PMU/XMPU/XPPU，也未执行 README 的任何部署命令。

## 9. 与 CCA GPU 主线比较

| 工作 | 本文可确认的侧重点 | 不应互相替代的性质 |
| --- | --- | --- |
| T-Edge | 单租户 TrustZone 设备配置、测量与证明、片内通道假设 | 不提供恶意多 Client GPU 任务隔离 |
| PORTAL | 可信服务 Realm 管理设备访问 | 合法服务实例仍需设备/配置与生命周期绑定 |
| ACAI | Realm 身份、设备与映射归属一致性 | 设备启动证明不代替每页/每请求授权 |
| CAGE/PhantomMap | GPU 可信执行、实际物理页与映射生命周期 | 初始内容摘要不代替当前页和在途访问的有效性 |

本项目假设保持不变：RMM 认证原始 Client，可信 ProxyRealm 控制 SMMU，在建图时校验对象、实际页、权限和生命周期，软件 IPA→HPA 合成受保护的 GPU Stage-1；其他设备使用硬件 Stage-2。T-Edge 不构成否定该模型的硬件证据。

## 10. 对现有设计的增量建议

第一，将服务证明与设备配置的运行代次明确关联：被接受的 Proxy 镜像、固件、设备配置/路由策略、设备归属和当前 epoch 各是什么，谁有权改变。可以扩展已有 epoch 与配置记录；无需另建重复身份或认证队列。

第二，将可信设备更新定义为事务：准备并验证私有配置快照→停止接纳受影响任务→按设备保证确认旧执行/访问停止→加载并确认状态→发布新配置代次→恢复授权。签名、SMC 返回、真实 fence、DMA quiescence 分别负责不同条件。

第三，限定密钥与特权服务的职责：根/证明密钥不应对一般工作负载暴露；给可信签名接口的内容须由可信状态构造，并注明“启动测量”“已接受请求”“已生效配置”或“终态结果”的实际语义，避免把任意缓冲区签名提升为运行证明。

第四，多 Client 下复用现有 GPUVM、认证队列、私有快照、native fence、cookie/epoch、persistent IRQ127，将 job 的配置代次纳入既有归属检查。旧配置的完成、ACK、reset 回调不得授权新配置对象，且不把 epoch 更新当作硬件已经停止访问。

后续可验证项包括：证明后重配置、加载错误、配置更新中 Client 退出、旧完成迟到、配置回滚、重启后旧会话重放，以及生产日志/证明材料的一致性。本轮只列设计与验证建议，未新增测试或安全 PASS。
