## 2. 研究问题：隔离内存之后仍可能完全得不到服务

传统 TEE 可以保护 enclave 的私有数据和控制流，但通常把何时调度、何时中断以及共享 I/O 的服务次序交给外部软件。恶意软件即使读不到别人的内存，也可能一直占有 CPU、制造大量短睡眠、阻塞 I/O 或触发导致全机复位的异常，使另一个 enclave 永远无法完成任务。

Aion 针对开放系统：多个互不信任的参与方能够加载应用，其中可能有恶意 enclave。关键难点是同等优先级的参与方需要公平分享时间资源，而不是简单以高优先级可信任务压过所有不可信任务。

论文增量是把安全抢占、有限不可中断区间、受保护调度器与可信 I/O 服务组合起来，为已准入的有限数量应用提供有条件的进展和激活延迟保证。这与证明某个中断或某条 GPU 完成消息是真实的不同。

## 3. 威胁模型与按性质划分的可信基

攻击者控制 TCB 外的系统软件、普通程序、其他 enclave 及目标应用不依赖的驱动，可以进行任意软件执行、非法访问及原子性违规。硬件隔离与异常机制按设计执行；目标 enclave 自身及其依赖服务需要正确实现接口。

作者将可信基按性质区分：基础机密性与完整性依赖硬件和应用及其必要依赖；可用性额外信任小型 scheduler enclave 和目标使用的设备驱动。调度器能够拒绝服务，但基础平台不因此授予它读取其他 enclave 私有数据的权力。不能直接把这个结论迁移为当前拥有设备映射和管理权的 ProxyRealm 也只影响可用性。

可用性还要求平台原本可调度：必须限制获保证的任务数量并在部署时确认资源容量；依赖的外设服务必须能在规定时间内完成。TCB 代码的正确性验证在论文范围外，全文没有提供 scheduler 的形式化正确性证明。

任意触发物理外部 IRQ 的硬件攻击者明确不在范围内。作者讨论屏蔽外部 IRQ 的可能性，同时指出漏掉 timer tick 会损害可信时间。因此不能把结论写成抵抗一切硬件中断风暴或 Host 任意停机。

## 4. 核心硬件机制

异常引擎负责安全保存 enclave 上下文、清除交给 handler 的状态，并将中断与安全违规统一交给受保护调度器。违规处理必须先阻断或回滚被禁止指令的效果，不能先让未授权内存或控制寄存器写入生效再通知软件。

中断向量表由小型 driver enclave 保护，scheduler 取得 timer 的独占访问权。平台还限制普通软件修改全局中断使能、CPUOFF 和相关振荡器控制位，防止恶意应用关闭调度所需的时间源或直接让 CPU 停止。

clix 提供有上限的原子执行区间，长度受平台上限限制，不能通过嵌套或连续延期构成无限屏蔽。进入 enclave 的短暂硬件原子期用于建立安全保存区及入口状态，避免在初始化尚未完成时被中断并破坏恢复语义。

Sancus scheduler 固定使用 enclave ID 1，因此必须首先加载；部分限制在初始 enclave 初始化后才启用。启动顺序与保护生效点属于安全条件，不能只讨论稳定运行阶段的中断路由。

长耗时硬件密码操作采用放弃后重启：中断到达时清除密码核心内部状态，用状态标志通知操作未完成，由软件决定重试。这里的安全性依赖操作没有提交外部副作用；不能移植成重复 GPU submit、doorbell、DMA 或任意 MMIO 写入。

## 5. 软件调度与可信 I/O

作者在 RIOT 上将 scheduler 和软件 timer 数据结构放入 enclave，以受保护定时器实施抢占、睡眠唤醒及周期任务调度。原型 scheduler 自身不可抢占，因此每个入口的最坏执行时间是激活延迟的一部分；“可信”不能替代该时间上界。

攻击者可用最长 clix 接续一个最慢 scheduler 入口，延迟已经到达的 timer IRQ。原型在离开 scheduler 前检查 pending interrupt，避免先恢复恶意任务再处理已经过期的事件。这个顺序控制是论文给出有限延迟的重要原因。

I/O 案例以可信 enclave 封装读传感器和串口输出。短同步入口在一个 clix 内完成；异步输出先写入按调用者区分的缓冲，再由独立 I/O 任务公平处理。Sancus get_caller_id 提供真实调用者身份，避免由不可信参数自行声明 buffer 所有者。

案例静态使用固定 enclave ID；运行时申请受保证 I/O buffer、确认服务承诺以及向部署方报告准入结果，是 §6 讨论的扩展 API，不能当作已实现的完整动态多租户资源管理。

## 6. 实验条件与定量结果

原型基于修改的 Sancus 2.0、MSP430、RIOT 2019.10，使用周期精确 Verilator 模拟。论文采用 8 MHz CPU，并按受限任务/定时器数量测量执行周期；这里的数字不是 Arm CPU、GPU job 或当前项目的性能结果。

| 项目 | 作者测量或分析 | 解释边界 |
| --- | --- | --- |
| 创建任务 | 688–860 cycles | 受当前任务数及入口路径影响 |
| 退出任务 | 512–736 cycles | 不包含 GPU 或外设 DMA 回收 |
| 睡眠请求 | 1124–1320 cycles | 最坏情况涉及最长允许 timer 列表 |
| yield | 424–628 cycles | CPU 调度入口，不是 GPU 上下文切换 |
| 读取时间 | 212 cycles | 受原型时钟与保护路径约束 |
| 第一个获保证任务激活 | 最佳 2035；最坏 5920+clix cycles | 只针对同时到期任务中第一个被调度者 |

取 clix=1000 时，最坏第一任务激活为 6920 cycles。论文推导攻击者以入口原子期、最长 clix、最慢 sleep 入口接续形成延迟，随后 scheduler 处理 timer 与调度；不能把 6920 泛化为任意被害任务或端到端 I/O 的统一上界。

对最多 N 个获保证任务，各自至少执行 M 个 CPU cycles，论文给出周期预算 `T=(5920+M)+(1845+M)*(N-1)`。在 N=15、M=1000、其余 14 个均为恶意任务且排在受害者之前的配置下，最后任务的最坏激活延迟为 46,750 cycles。

按作者 8 MHz 换算，6920 与 46,750 cycles 分别约为 0.865 ms 和 5.844 ms；仅用于理解该模拟配置。测得周期加有限容量和路径分析不等于对整个系统实现完成形式化 WCET 证明。

## 7. 限制与尚未解决的问题

CPU 周期进展不自动意味着某个长硬件操作进展。作者明确指出密码操作若无法在一个 clix 内完成，可能不断被放弃重启而饥饿；可恢复引擎或新的调度语义留待未来研究。这个限制正好说明，给 GPU 服务线程 CPU 配额并不能保证 GPU job 完成。

侧信道不是 Aion 本身已经封闭的性质。论文引用 Nemesis，并将 CSF 2020 的硬件中断延迟填充防御集成列为未来工作。可信路由和有界延迟不能因此被描述成隐藏所有中断时序。

案例假设共享外设的访问逻辑可被正确封装；复杂校准、较长异步操作及动态资源请求仅讨论可扩展性。没有实现 GPU command queue、DMA、地址空间切换或多 Client GPU reset 故障隔离。

代码支持论文主线：调度队列和线程状态使用 SM_DATA；CPU 入口用硬件 caller ID 区分受保护调用；恢复普通线程前清除 CPUOFF/SCG1，避免借 scheduler 的更高控制权限恢复攻击者提交的危险状态；pending timer 在恢复前处理。

周期 enclave 的 sm_entry_periodic_sm.s 中，验证调用者为 scheduler ID 1 的检查被注释，旁注明开发期间禁用、以后启用；scheduler 返回 stub 也保留重新使能 IRQ 时机的 TODO。它们是固定版本中的未完成约束，论文架构保证不能仅凭现成 stub 就认定全部落实。本轮未构造绕过或执行攻击。

scheduler 周期参考/运行时间保留忽略 32-bit overflow 的注释，timer 内部也注明可能忽略刚发生的溢出。可导出的 sched_shut_down 入口执行 CPUOFF，本轮没有证明所有最终配置中的入口授权或保护限制；只能列为安全构建与 API 暴露面需要继续核验，不能据此直接断言已复现拒绝服务漏洞。

案例的“传感器读数”实际为受保护 timer 的时间值；输出缓存为 4 个单字节槽，无效或超范围 caller 合并至槽 0。UART 输出含等待 TX 空闲的循环，因此时间保证仍依赖外设响应上界。该演示不能替代任意多租户 GPU 对象与队列授权实现。

## 9. 与 PORTAL、CCA 及本项目的关系

PORTAL 为可信服务 Realm 管理设备提供框架，ACAI 强调身份与地址归属，PhantomMap 提醒检查真实页和生命周期。Aion 则补充另一维度：即使空间隔离成立，时间资源和中断服务仍可能被恶意参与方垄断。它不是替代现有内存方案的论文。

保持本项目假设：RMM 认证原始 Client；可信 ProxyRealm 控制 SMMU；建图时检查对象、实际物理页、权限及生命周期，软件 IPA→HPA 后形成受保护 GPU Stage-1；其他设备继续硬件 Stage-2。Aion 不以当前实验硬件是否实现这些能力来否定该研究模型。

已有认证队列、GPUVM、私有快照、native fence、cookie/epoch 与 persistent IRQ127 提供任务与通知基础。值得补充的是它们在攻击负载下的服务预算和恢复边界，而不是重新发明一组通知字段。

| 研究性质 | 与现有机制的结合 | 仍需独立条件 |
| --- | --- | --- |
| 完成真实性 | 可信 completion 绑定原 Client/job/epoch，并依据真实 fence/状态 | 收到 IRQ 或 CPU 得到调度不证明任务完成 |
| CPU 服务公平 | 每 Client 请求、完成处理和错误处理纳入可信预算 | Proxy 实际能得到 CPU，关键段时间有界 |
| GPU 进展 | 与任务准入、GPU 调度和超时策略组合 | GPU 可抢占、job 有限或可信复位/隔离等明确假设 |
| 安全回收 | epoch 失效、停止新提交、实际终止后再释放 GPUVM/页 | timeout、通知 ACK 和 CPU 配额均不证明 DMA 静止 |
| 时序机密性 | 定义 IRQ 与调度可泄露信息 | 有界公平不等于秘密无关的事件轨迹 |

## 10. 建议加入的设计与可验证主张

第一，把“可用性”写成分层服务承诺：请求被可信侧接纳、获得提交机会、设备执行、完成记录发布以及资源释放分别是什么保证。若 Host 可无限停调 Realm，则需要明确排除全局拒绝服务，或另外提出可信调度前提；不能用队列认证消除该依赖。

第二，复用 RMM 认证的 Client 身份做配额与准入，限制每 Client 的在途 job、待处理 completion 和异常处理工作量。认证身份只能决定记账归属，实际预算还应覆盖共享 worker、重试、扫描、错误路径和取消操作，避免把恶意成本转嫁到别人的时间片。

第三，对 Proxy 关键段建立上界：尤其是 IRQ 排空、完成队列扫描、取消、映射撤销和 reset 协调。锁、全局队列或不可抢占调用若无限增长，单纯 round-robin 选择 Client 不能推出有界等待；应将当前实现的实际路径纳入分析。

第四，区分 Client 故障与共享设备故障。某个任务超时可使其 Client 请求失效，但设备级 reset 可能影响全部 Client；需要沿已有 epoch/fence 状态机明确受影响集合、唯一终态和安全回收条件。不能声称隔离了超时任务就自然隔离所有 reset 后果。

第五，在后续验证中分别检查软件请求风暴、完成通知风暴、反复取消、短周期重试以及一个不进展的设备任务。指标应同时包含其他 Client 的服务份额、尾延迟、处理预算和恢复正确性；本轮仅提出验证问题，没有执行测试或给出通过结论。

## 11. 独立评价

Aion 对本项目的价值是为“共享”增加可精确定义的时间隔离条件。它说明可信中断不仅涉及来源、目标与合法副作用，还涉及谁能阻止中断处理、处理路径能耗费多少时间、已经准入的参与方能否持续获得服务。

适合在论文第二部分作为可信中断与任务隔离的支撑文献，并把可用性限制写清。第一部分的直通和共享性能优化可据此解释批处理、IRQ 排空和线程交接优化对服务上界的影响，但没有本项目实测，不能从作者 CPU 周期推断 glmark 或当前 GPU 吞吐。

后续引用链包括 Provably Secure Isolation for Interruptible Enclaved Execution on Small Microprocessors（CSF 2020）。该文需独立取得全文和分析，不能因为 Aion 引用了它就算完成。
