## 2. 问题与信任边界

模型提供者希望在用户边缘设备执行完整私有模型，既防止 Normal World 提取或修改模型，也希望知道部署和执行符合服务协议。论文将模型隐私、模型真实性及使用条件审计放在同一目标框架，但实现成熟度不同。

三方为模型提供者、设备 Client、提供可验证 Realm 镜像的 trusted verifier。模型提供者不信任设备 Normal World OS/hypervisor，信任 Root monitor、RMM 和选定的 Realm 镜像及其内部软件。把 Linux/TFLite 放进 Realm 会保护其私有内存，也把相应运行时和依赖纳入模型处理的可信基。

侧信道排除；论文还假设 Host 不干扰 Realm 创建和调度。CCA 的内存保护不自动保证进展、服务时间、配额执行或抗恶意调度。论文中的 Client 是边缘设备一方，不能直接等同于本项目经 RMM 认证的多个 Client Realm 身份。

相对将深层、浅层、中间层或非线性留在 TrustZone 的分割方案，GuaranTEE 选择完整模型驻留 Realm。这样减少模型分割导致的暴露，但不消除正常 API 的黑盒提取，也不自动认证传感器输入、共享文件、设备完成事件或模型更新来源。

## 3. 提议部署流程与已实现流程

设计流程为：可信镜像提供与启动测量；Realm 与提供者建立 TLS；提供平台和 Realm 证明；验证通过后释放模型；Realm 推理并与 Normal World 交换数据；根据协议更新、限制使用或终止。远程证明意图验证所选隔离环境和代码，不能仅凭“使用 CCA”推导每一步协议已经落实。

TLS 还需明确对端认证、会话密钥、挑战新鲜性及证明证据与当前信道的绑定。可信初始测量不等于某次模型推理的收据，也不自动绑定原始 Client、模型版本、输入快照、提交任务、输出和真实完成。本轮未见实现这些完整属性的协议代码。

实际 FVP 原型将 MobileNet/TFLite 在普通 VM 与 Realm 内分别运行，通过 9p 共享目录交换图片、信号文件和输出。作者明确未实现远程证明，因为所用 FVP 缺少 HES；所以标题里的 attestable 是框架目标，不能报告为已验证的在线证明系统。

没有 GPU 直通、GPU 安全执行或多 Client 共享的实现结果。ACAI 等安全外设访问被列为补充方向；配套 CMake 的通用 GPU delegate 选项也不证明本原型跑了可信 GPU。给定启动命令启用的是 XNNPACK。

## 4. 共享 I/O 与信号通信

论文明确承认 Normal World 中输入和输出未受保护，攻击者可篡改或投毒输入，或滥用模型；把模型装入 Realm 不构成完整 ML pipeline 的机密性与真实性。模型输出若必须只给授权接收方，还需相应的可信或经认证加密的发布路径。

官方 `NW_signalling.sh` 先删除旧 BMP，写 processed 状态；每张输入等待状态后拷入共享目录，再分两次写入 query 状态和文件名，轮询间隔为 5 秒。Realm 的 `VM_signalling` 读取同一文件并在 query 时接受文件名，完成后截断写回 processed；文件中没有请求认证、Client 身份或事务序号。

两次写入不是一个原子记录发布：若读者在中间观察，可能看到尚无完整文件名的 query。共享图片与文件名也没有构成可信私有快照。这里是静态可见的协议边界，未执行并发测试，不声称已经复现漏洞；它本来是单服务原型控制通道，不能直接用于恶意多 VM 通信。

`label_image.cc` 从信号取得文件名，读取 BMP、准备张量、调用 TFLite Invoke、提取 top-N 并记录输出，然后更新 processed。文件状态用于驱动循环，不是可信硬件完成证据；返回值、预测日志和“请求已处理”也不能自动证明输出属于哪次认证请求。

服务脚本把标准输出和错误重定向到共享目录 output.txt。原型这样方便取实验结果，但不能支持对恶意 Host 的结果完整性或隐私主张。异常、重复/丢失消息、恶意路径、输入解析器与模型运行时的完整安全审计不在本轮有限阅读范围内。

## 5. 供应、撤销与生命周期

构建脚本将公开测试模型放入 Realm 文件系统，又把相应文件系统复制进 Host overlay。这适合公开 MobileNet 实验，却没有演示“私有模型仅在证明成功后供应”的生产路径；不能以该 artifact 中公开模型的预置方式证明秘密已经泄露，也不能据此宣称秘密供应已完成。

模型提供者若按次数或时间收费，需要受保护计数、可信时间语义、断连/重启/回滚策略，以及新会话是否继承旧额度的规则。普通磁盘计数或 Host 时钟不能独立建立这些性质。论文讨论这些需求，未实现完整防回滚配额协议。

发起 Realm 终止请求不等于证明所有执行、外设访问和残留秘密均已撤销。未来接 GPU 后还需区分停止提交、任务终态、设备静止、撤销完成和页安全复用；不能把 CPU Realm 退出当作 DMA 结束，或把测量镜像当作当前服务状态。

配套 README 指导拉取未固定的 TensorFlow master，限制长期可重复构建；这与本轮固定读取 artifact 提交是两件事。没有下载运行 4.57MB 的 realm_inference 二进制、执行构建、启动 FVP、安装依赖或进行攻击。

## 6. 评估环境与指标口径

作者使用 Arm `AEMFVP-A-RME-2023.12.22`，控制机为 Lenovo ThinkCentre M75t Gen2、Ryzen 7 PRO 3700、8 核、16GB RAM、Ubuntu 22.04.4。FVP 是 instruction-accurate，而非 cycle-accurate；模拟器墙钟时间不等于真实 Arm 运行时间。

模型 MobileNet_v1_1.0_224，约 16MB；40 张图片、每张 5 轮。普通 VM 与 Realm 的创建脚本均为 1 vCPU、300MB、GICv3、禁 SVE 和 9p 共享，关键启动参数区别为 --realm。没有把不同 VM 配置下的结果伪装成同条件。

每次推理普通 VM 222.2M instructions（SD46.5M），Realm361.6M（SD4.4M）；倍率约1.6274，增加139.4M、约62.74%。正文写1.62，摘要/结论取1.7，应保留取整和指标差异，不能写成真实硬件“延迟增加1.7倍”。

模拟墙钟普通 VM34.25秒、Realm27.28秒，看似 Realm 更快也不能用于证明真实处理器更快。两类指标的方向不同，正说明不能把模拟器耗时当实际性能；作者主比较使用扣除背景活动后的指令统计。

98MB 镜像（55MB文件系统+43MB内核）、300MB RAM 时，Realm 启动18880.6M instructions（SD1655.3M），普通709.8M（SD6.7M），约26.6倍；终止970M（SD98.9M）对105.1M（SD0.2M），约9.23倍。对应模拟创建约6分21秒/1分31秒、终止1分01秒/8秒，不能跨指标混算。

139MB 镜像（96MB文件系统+43MB内核）时，RAM 同时增至400MB，Realm 启动27190M instructions、普通725M，约37.5倍。由于镜像和 RAM 一起变化，不能把差异完全归因于镜像体积，更不能据此给出每 MB 的固定安全成本。

论文将额外指令与更多上下文切换、中断等联系，但没有给出本项目 GPU/IRQ 路径的逐项因果消融、尾延迟或公平性实验。benchmark.h 的 HLT/寄存器标记用于 FVP trace，不是远程执行认证或安全通信。

## 7. 对本项目的直接启发

继续采用 RMM 认证原始 Client、可信 ProxyRealm 统一控制 SMMU，建图时检查对象归属、实际 HPA、权限与生命周期，软件 IPA→HPA 合成受保护 GPU Stage-1；其他设备保留硬件 Stage-2。硬件模拟的限制不作为否定设计前提的理由；本文也不提供替代该设计的 GPU 授权方案。

GuaranTEE 最有价值的联系是将“可信环境确实启动”与“可信请求确实完成”分开。模型/服务镜像证明是前者，任务隔离需再把 RMM Client 身份、认证请求、输入快照、实际 GPU 提交、native fence 终态及输出发布连续关联；现有 GPUVM、认证队列、私有快照、cookie/epoch 和 persistent IRQ127 是基础，不另造重复 token 框架。

中断应触发对可信终态的检查，不能仅因收到通知就承认 query 完成；通知重复、伪造、乱序或旧 epoch 到达，不应改变另一 Client 的成功状态或触发提前回收。共享通知的机密性也应单独定义：公开唤醒时刻/次数与泄露结果内容是不同的允许观察。

可把项目第二部分规范写成连续状态链：认证接收→私有快照及授权→真实设备提交→可信终态→输出可见→成功/错误发布→静止后回收。取消、超时、断连、reset 在各阶段定义合法转移；模型、映射和通知通道的身份/epoch 不得被分别检查后失去关联。这是由论文原型边界导出的验证任务，不声称当前代码已有对应缺陷。

远程证明如后续加入，应证明并绑定当前服务策略、镜像与会话，再明确哪些运行事件有受保护记录；不把一次启动证明升级为持续设备状态证明。模型使用次数限制、输入来源认证和 GPU 结果验证可作为各自独立扩展，避免与“直通/共享实现”和“内存/中断隔离”主线混为同一安全承诺。
