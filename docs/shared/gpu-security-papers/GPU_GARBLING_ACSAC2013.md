## 2. 问题：保护双方输入，而非建立设备隔离

论文以遗传疾病筛查举例：患者不希望泄漏DNA，服务方不希望泄漏专有标记，双方需要计算共同函数并只获得约定输出。Yao garbled circuits把函数编译为布尔电路，通过编码线值、加密gate table和oblivious transfer（OT）隐藏双方输入和中间值。

已有系统利用GPU计算加密原语，或为cut-and-choose生成许多相同结构电路。本文关注HbC及1BM下只需一份或两份电路时，如何把一张电路内部的不同gate充分映射到GPU，而不是让每条线程只负责大量复制电路中的同一个gate。

因此，“GPU上运行安全计算”在这里表示GPU执行密码协议，不表示GPU硬件、驱动和Host对本地秘密均不可信。论文没有构建Realm、受保护GPUVM、可信页表、MMIO授权、设备证明或可信中断服务。

## 3. 三种攻击模型及保证范围

| 模型 | 对对手的约束与可获得的保证 |
| --- | --- |
| Honest-but-curious（HbC） | 双方按协议执行，但可分析自己看到的完整transcript；安全要求不额外学到输出以外的输入信息 |
| Malicious | 对手可任意偏离协议；论文介绍cut-and-choose作为背景，并与相应系统比较，没有把本文全部实现宣称为该强模型 |
| One-bit-leaked malicious（1BM） | 容许恶意偏离，并放宽为每次执行可泄漏私有输入的任意一位谓词；不能当成零额外泄漏的恶意安全 |

HbC需要一方生成、一方求值；1BM让双方分别生成并求值对方电路，再用恶意安全的专用协议验证输出是否一致。完整恶意模型的cut-and-choose需要约k份电路，抽查部分、求值剩余部分，再结合输入一致性等相应条件。

“每次允许一位”也不等于整个长期会话永远至多泄漏一位；重复执行可能积累不同谓词。本项目若运行类似协议，任务隔离与epoch防重放本身不会消除协议主动容许的泄漏，应用还需明确调用次数、输入复用和输出策略。这是本报告对组合使用的分析，不是论文做过的多Client实验。

双方本地计算端被恶意OS读取全部标签或种子，不是其HbC保证可自动覆盖的攻击。密码协议证明、TEE本地隔离和设备执行正确性需要分开判断；本文没有对GPU侧信道、固件篡改、错误DMA或中断注入做安全实验。

## 4. 基础协议和计算流程

生成方为每根wire选择0/1两套随机标签及置换位，将每个二输入gate的四种输入组合编码为四行密文。本文用含gate标识及两个输入标签的SHA1哈希产生掩码，再与输出标签及置换位异或；不是直接把应用明文交给求值方。

求值方取得生成方输入对应标签，并通过OT取得自己的输入对应标签且不能同时获得另一标签。置换位使其直接选中一行、解出下一根wire的标签；按拓扑顺序最终求得输出。本文继承Yao、OT extension等已有工作，正文没有逐项给出OT全部实现或新的完整安全证明。

Free-XOR让每根wire的两个标签满足同一个全局差值R，XOR gate无需常规加密表，求值只异或输入标签。但传统构造中，XOR输出标签由前面输入决定，继而影响后续gate，生成阶段也被迫遵守层间依赖。

普通gate在输入和输出标签确定后可以并行生成；问题正是如何在保留廉价XOR求值的同时，去除标签生成的这种依赖。不能因为生成阶段可并行，就声称整个函数的求值也不再有数据依赖。

## 5. 关键增量：用偏移换取整电路并行生成

作者为包括XOR输出在内的所有wire预先“虚拟分配”标签：根据本电路独立seed s和wire标识i，通过伪随机函数取得 `k0_i = F_s(i)`，再以全局R得到 `k1_i = k0_i XOR R`。不是把所有完整密钥先写到GPU内存，而是在相关gate需要时重算，降低存储与搬运。

对XOR gate，设输入a、b，输出c，生成额外偏移 `V_c = k0_a XOR k0_b XOR k0_c`，置换位也生成相应 `P_c`。求值时用 `k_a XOR k_b XOR V_c`及对应置换位操作，得到预先分配的输出标签。各gate的偏移可独立计算，因此不必先串行遍历XOR链。

代价是每个XOR gate额外通信一个标签量级及置换位信息，并多做少量XOR；传统Free-XOR不需传这些额外gate数据。本文明确不采用garbled row reduction（GRR）：它虽可把普通table由四行降至三行，却重新引入标签依赖，并在求值missing row时产生不同路径。

这项设计在HbC/1BM下选择增加通信来降低生成成本，而完整恶意协议传输许多电路，交换关系可能改变。正文把将本文技术用于cut-and-choose列为可组合方向并要求更多实验，不能只因并行化有效就推定所有安全模型都同样受益。

具体协议仍依赖标签伪随机性、全局R保密及所采用哈希/加密构造的安全条件。论文引用基础Yao和Free-XOR论证，没有给出本文标签偏移变体的完整独立形式化证明或GPU实现到协议的精化证明。本报告解释其代数操作，不把解释本身当作新安全证明，也不把2013年的SHA1实现选择当作现代部署建议。

## 6. GPU/CPU 架构与流水化

生成阶段每条GPU线程处理一个不同gate，将XOR与普通truth-table gate分到不同kernel，避免warp中混合执行不同gate类型。CUDA warp为32线程，线程块取适当倍数；这是论文所用NVIDIA架构的调度条件，不是Arm Mali上已经测得的最佳参数。

求值必须按层执行，每层XOR和普通gate分别启动kernel；若层很窄，层尾会有大量lane空闲，不能提前执行仍有依赖的下一层。作者也指出求值数据布局缺乏良好memory coalescing，增加全局内存读写成本。

API支持把若干连续层作为分块传输/求值，并异步搬入后续分块；但基准对比中的部分路径关闭了分块开销，而且与PCF编译器的流水集成尚未完成。架构描述支持分块，不等于所有公布结果都验证了任意大电路的完整流水执行。

CPU版本用OpenMP并行求值，同一层按线程均分gate；没有额外平衡XOR与普通gate比例。CPU不需PCIe搬运，MIMD调度不受同样warp分歧限制。论文据此建议GPU负责生成/部分验证，CPU负责求值，并把两端流水组合列入后续方向。

哈希代码由John the Ripper的SHA1实现手工优化：每条消息只需一个block，利用固定前缀预计算省去80轮中的6或14轮，同时控制寄存器占用。作者尝试BLAKE256但吞吐不如该SHA1路径，尚未验证fixed-key AES优化；这些是实现选择和未完成比较，不是哈希函数安全性的排名。

表格正文把Xeon拼为“Xenon”，本报告按型号说明，不据此改写原实验硬件。即使EC2机器有多GPU，文中结果只使用一块；未测多卡扩展，不把设备数量误当实际并行度。

作者自身结果平均100轮，Kreuter等对照平均50轮。Frederiksen/Nielsen代码在两套GPU环境重跑，但双方电路文件格式不通，使用相似而非完全相同的AES电路；通过复制独立AES电路模拟cut-and-choose工作量，不等于本文实现了完整恶意协议。

Kreuter等比较可用相同PCF电路，但没有在相同单机重跑完整对照系统，而是引用其论文数据；无法装入GPU的大电路被排除。每core归一化可以帮助观察扩展趋势，CUDA core与CPU core的资源、调度和指令能力仍不同，不能据此认定为严格等成本公平比较。

EC2 Xen开销未直接测量；正文引用其他Xen基准的0–30%范围，不是本实验已校正的虚拟化损失。数据通信及其网络延迟被明确排除出本轮性能评价，因此未覆盖OT、全部传输和双方协议的一体化端到端时延。

| 结果 | 应如何解释 |

| 对先前GPU系统约2.3倍 | 摘要及不同硬件比较口径；正文另有约3倍表述，不能不区分平台、协议和电路就给出同机精确倍率 |
| GPU求值 | 只与Kreuter的CPU结果大致可比，略逊Frederiksen/Nielsen；不能把生成吞吐优势套到求值 |
| 本文CPU求值 | 比本文GPU路径更适合部分单电路，并优于Kreuter引用对照，但仍逊Frederiksen/Nielsen特定GPU路径 |

作者解释cut-and-choose虽多做工作，却有k份同结构电路可并行，天然拓宽层、整齐排列内存并减少warp分歧。安全模型加强可能增大总成本，同时改变并行度和瓶颈，不能只依据“安全步骤更多”推断某个kernel效率一定更低。

正文未提供图1–4全部原始数值、置信区间、功耗和单位成本测量，本报告不从文字抽取曲线估读每个点。更便宜或更节能的GPU描述未经过同条件能耗/成本实验支撑；作者承认缺少统一标准电路、文件格式和完整可比实现。

## 10. 与 Piranha、Slalom 及 CCA/GPU 主线的关系

与原库Piranha等GPU安全计算框架相比，本文是较早的两方garbling并行化研究；不能以年代或生成速度跨协议比较。Slalom、SOTER、TEE切分等工作把某些计算外包给不可信加速器，其校验、隐私和TCB条件不同；本文也没有提供任意GPU任务的通用结果认证。

PORTAL、CAGE、ACAI和当前项目关心恶意Host下的设备资源保护。本项目继续接受RMM认证原始Client、可信ProxyRealm统一控制SMMU、建图时校验对象/实际HPA/权限/生命周期、软件IPA→HPA合成受保护GPU Stage-1，其他设备保留硬件Stage-2；本文不替代这些基础条件，也不因使用旧NVIDIA平台而限制目标Arm设计。

如果两个Client在各自受保护Realm内运行两方协议，本项目保护各方本地标签、seed和设备访问；密码协议限制双方互相学习的信息。两类机制可以组合，但仍需确认双方本地执行环境、会话和输入策略，不能因为gate table被加密就让恶意Host读取生成方的全部两套标签或R。

真实GPU fence和cookie/epoch能够帮助确认“属于这次任务的执行已经结束”，不等于密码协议验证通过、双方输出一致或结果具有应用语义正确性。继续复用GPUVM、认证队列、私有快照、native fence和持久IRQ127；不要给每个garbled gate另造一套身份token或IRQ机制。

## 11. 可迁移的研究方法和项目建议

第一，按依赖图区分可提前计算的内容与必须等待真实前驱完成的内容。本文放开生成依赖，没有放开求值依赖；当前执行计划缓存、前缀fence观察等优化也应明确依赖已满足的证明条件，不能只凭提交顺序、IRQ到达或预计耗时发布完成。

第二，按阶段测量端到端成本：Client提交、Proxy校验、建图/缓存命中、GPU执行、输出可见、完成记录和通知确认。本文的生成峰值与端到端协议分离，提醒本项目不要用减少RPC/IRQ次数或单kernel吞吐替代完整glmark/ML任务的正确性和性能证据。

第三，保持安全模型一致再比较。HbC与1BM、完整恶意模型、可信Host与恶意Host的结果应明确标注；当前性能优化不以削弱Client授权、对象生命周期或真实完成语义换取吞吐。局部并行重排还需保留取消/reset、迟到事件及资源回收条件。

这些是分析所得的设计与评价建议，未实现新协议、未跑攻击，也没有新增GPU测试。本文没有解决多Client虚拟IRQ的路由、pending/ACK竞争、通知可用性或中断时间隐私；不把它列入“可信中断已解决”的文献证据。
