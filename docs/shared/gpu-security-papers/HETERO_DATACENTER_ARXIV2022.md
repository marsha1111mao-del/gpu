## 2. 问题与项目关联

异构数据中心同时有 CPU TEE、支持 TEE 的加速器和完全不支持 TEE 的传统设备。把每台设备独立保护仍不够：不可信管理平面可以重复分配资源、修改设备配置、改变连接、插入恶意节点，或通过网络/总线访问其他租户。

作者提出混合结构：TEE 节点使用自己的 SM、证明和安全通道；非 TEE 节点放在可信 Security Controller（SC）后，由 SC 代理证明、归属检查和通信保护。多个 SC 分别管理本地设备，跨 SC 通过认证加密连接，避免中央控制器掌握全数据中心状态。

与项目最接近的是可信代理统一掌握设备分配和访问，而非把任意 Host 配置当授权。区别在于本文跨机架、考虑物理攻击，并且非 TEE 节点整节点独占；项目重点是同 GPU 的多 Client 共享和任务级隔离，不能直接照搬独占节点模型。

## 3. 威胁模型与明确排除项

攻击者控制 OS、Hypervisor、云管理平面、网络设备和共租户；可插拔恶意节点、操作固件和配置、探测总线和操纵网络。租户之间互不信任，但同一 job 内的 CPU enclave、驱动和 DSA 代码都被信任。

可信基包括 CPU/DSA 硬件、设备固件和 SM、SC 的软硬件、密钥保存及安全启动。还依赖厂商身份、最新撤销策略和可验证证明。不能将新增约几百行保护逻辑当完整 TCB，也不能把“SC 代理非 TEE”理解成完全不依赖设备固件可信。

侧信道、DoS、硬件木马和 Iago 攻击被明确排除。因而密码通道之外的错误返回、任务语义和进展问题没有被本篇完全覆盖；不能把其隔离声明推广成恶意调度及任何中断注入都无害。

物理攻击保护依赖额外边界：CPU/TEE 设备依赖自身内存保护，传统节点和 SC 的明文部分依赖防篡改容器。正文在某处将容器对象写作 SC/TEE 节点，其他段落明确用来包围非 TEE 节点；不能省略明文设备及链路必须在受保护边界内这一条件。

## 4. 设计空间与选择

论文比较全中央 SC、CPU TEE 配传统设备、半中央混合、全设备 TEE 及混合五种方式。全设备 TEE 可以分散检查，但要求所有设备具备保护；全中央 SC 容易成为拓扑及密码带宽瓶颈。

最终选择混合：TEE 节点自治，不经过 SC；非 TEE 节点由本地 SC 管理。SC 只需记录本地设备的 job 归属，通过同一 job 密钥与其他 SC/TEE 节点连接，不必同步全部 ERT。

这是改变管理责任和通信边界的设计，不是证明取消所有全局协调。资源授权、证明策略、密钥发放和 job 终止仍须一致；正文没有完整给出跨 SC 故障、分区、部分撤销和重新部署时的全局事务协议。

## 5. 资源单位、静态内存与独占限制

TEE 节点可被本地 SM 分为 fungible device units（FDU），不同 FDU 属于不同 job。用户 manifest 声明设备类型、核数、内存及所执行代码，验证证明后发放秘密。

正文 §4 明确：非 TEE 节点不允许多租户；至少使用一个 CPU TEE；内存分配在 enclave 建立时决定，用户提供静态最大需求。前文对节点共享的泛述应受这个具体设计约束限定。

因此 ERT 能保证传统设备没有同时归属于两个 job，但不证明传统 GPU 内部多个恶意 Client 同时执行时的空间隔离。若项目一个 Proxy 服务多个互不信任 Client，必须继续依赖每 Client 的真实 GPUVM、对象授权和执行/完成状态，而非只检查“设备在这个 Proxy 名下”。

## 6. SC 的 ERT、缓冲区与通信

SC 复位传统节点，识别受信拓扑中的本地设备，为它们安排不重叠明文 staging buffer。Enclave Routing Table（ERT）记录节点与 job 及密钥的关系，分配前检查未被占用，结束时删除。

TEE 与传统节点通信经过 SC 的认证加密；SC 内同 job 传统节点之间主要做访问检查、不加密。跨 SC 的传统节点通过 SC 间安全通道连接；ERT 是本地授权依据，而密码通道保护边界外数据。

同一 SC 内还讨论 zero-copy：可信 SC 检查双方属于同一 job，建立共享关系后不再逐次介入。此时保护取决于建立后的映射不可被未授权改变，以及撤销前实际访问保持有效归属；不能由“初始检查通过”直接推出任意重分配仍安全。

所谓本地设备 ID 不可伪造也依赖受保护拓扑/入口，不能把软件报出的 PCIe ID、stream ID 当成任意平台通用身份根。项目更直接的依据是 RMM 认证原始 Client 和受保护设备配置，不需要照抄网络节点身份形式。

## 7. 节点生命周期与安全回收

启动路径为 manifest → 管理平面选择资源 → SC/SM 检查归属与配置 → 用户验证证明 → 建立密钥和通道 → 部署执行。管理平面可以提出请求，但最终授权由可信实体承担。

结束由主 CPU FDU 发送 job 终止命令；SC 识别所属 job，复位涉及节点，清理内部状态并移除 ERT，随后通知管理平面可再分配。TEE FDU 也由 SM 清理残留并撤销分配。

原文描述了顺序和目标，没有完整枚举所有在途 DMA、缓存、旧网络包、异步 reset、丢失通知或部分设备失败。安全回收还需说明复位/清理成功的可信确认，以及何时禁止旧密钥和旧映射继续生效。

同 job 的全局通信密钥跨多个节点使用，使失效范围与租户内信任关系有关。项目若 Client 互不信任，应保留各 Client 独立会话和任务归属，不因共用一个 Proxy 或物理 GPU 就放进同一信任组。

## 8. 配置证明与密钥发放

附录用 property-based attestation 表达 debug 关闭、核隔离、cache/memory 属性等。可信 SM 在启动和配置过程中将预定值 extend 到 PCR，用户依据白名单判断设备是否符合要求；多个 FDU 继承设备级属性并附加自身配置。

证明样例包含 DeviceID、公钥、厂商、固件、PCR/PolicyQuote、BAR、streamID、核和内存配额。manifest 还包含代码哈希及签名。关键思想是检查实际配置和分配，而非只识别某种芯片型号。

challenge 用于防止重放旧证明；用户先与每 FDU 建立单独密钥，再下发 job 内共享通信密钥。正文有时将密钥描述为 pair-specific，附录则明确有 job-wide 共享密钥；两种层次须分别说明，不能仅凭 job-key 的认证就证明具体发送者。

PCR 值证明受测量的代码记录过配置，不会自动阻止后续重配置。完整保证仍依赖所有关键配置修改受 SM/SC 约束，并在变更时撤销或更新原有授权。白名单、撤销列表、固件版本策略和 key release 也必须有可信来源。

nonce 分配、方向/发送者区分、消息序号、重放窗口及 job 重新部署代次没有全部展开。这里是协议材料未充分细化，不能仅凭省略宣称存在已证实重放漏洞。

## 9. TEE 节点的 DMA 与 MMIO 保护

DMA 可在显式传输 API 处由 enclave 内薄驱动加密并复制到非 enclave 共享区；避免要求应用自行处理每一项密码操作。透明接口不意味着底层驱动和数据路径没有修改。

MMIO 访问较难截获，论文提出将相应映射标为不可访问，利用 fault handler 对 load/store 做加密、复制和远程处理。该方法的实际异常来源、指令解码、重试/恰好一次及副作用顺序均需要可信处理。

仅保护总线内容不足以证明 MMIO 命令合法：发往哪个设备、哪个上下文、允许修改哪些寄存器、命令是否重复及所引用对象是否仍存活，属于授权协议。对项目，已有可信 Proxy 的集中 MMIO 控制和私有快照比套用通用 page-fault 转发更直接。

## 10. 加速器与 SSD 原型的边界

作者为 DaVinci 风格 AI 加速器增加 ACUcore、ACUmem、FDU mapping table（FMT）、MPE 和安全 deallocator。前者约束核间通信，后者约束主存访问；结束时按跟踪的 tensor 区域清零。对 SSD，则在 Host Interface 与 controller 间增加访问检查和密码处理，支持不同 namespace/FDU。

原型以高层功能模型、RTL 合成延迟和周期级模拟组合评估；AI 模型使用 800 MHz 核、DRAMSim3 DDR4-3200 等，SSD 使用 SimpleSSD/Gem5。HSM 经 I2C 接入模拟平台用于证明。这不是实体 Ascend 片上已部署全部隔离逻辑的证明。

AI 部分增量约 200 行 SystemVerilog、650 行 Python/shell，原高层模型约 15 KLoC；SSD 约 259 行 C++、150 行 RTL、150 行 cocotb/Python，原模型约 55 KLoC。SC 软件原型单线程，约 400 行 wrapper 加 libsodium/runtime，使用 AES-NI 和 AVX2。增量 LoC 不包含全部可信依赖。

GPU 案例复用 Graviton 的设计思想，以 RTX3080 的 mmiotrace/nsys 收集访问行为并估算额外加密成本；没有在商品 GPU 上实现 Graviton 的全部可信硬件。FPGA 部分使用 ShEF/DNNWeaver 及本地 SVD。不同案例的真实执行、trace、模拟与估算应分别标明。

## 12. 中断安全：加密只能回答其中一部分问题

§6 讨论恶意软件中断可能诱使 enclave 发起 DMA，认为数据离开 enclave 时已被认证加密，因此不泄漏。该论证主要回答“明文是否经由错误请求流出边界”，有意义但覆盖范围有限。

它没有证明中断来自真实设备、属于当前 job、表示成功而非错误，或对应数据已经可读。认证加密还必须绑定正确目的端、消息类型与当前实例；对旧合法密文的重放，也需要独立 freshness 条件。

中断触发了一个加密传输，并不等于触发条件本身获准；更不能据此修改可信完成状态、跳过依赖或提前释放内存。本文没有多 VM IRQ 路由、pending/ACK/ARM、native fence 与每任务 cookie/epoch 的完整协议或专门中断攻击实测。

因此它恰好说明本项目为什么可以把中断通信隔离作为独立研究贡献：保护消息内容和保护控制状态转换是相关但不同的目标。这里没有声称本论文已存在可利用完整性攻击，而是指出其明示安全论证没有闭合项目要求的任务语义。

## 13. 公开实现和复现限制

完整 v1 没有指向匹配全系统实现的 artifact 仓库。它引用 DRAMSim3、SimpleSSD、Gem5、ShEF 等公共基础，但这些不等于作者新增 SC/ERT/ACU 代码。本轮三个精确题名/文件名 GitHub repository 搜索均无结果；这个有界搜索不证明源码一定未公开。

没有固定可审计的本论文实现提交，因此无法核对实际 ERT 原子更新、密钥/nonce 分配、真实设备 reset 确认和所有撤销路径。未运行模拟器、模型、硬件或攻击，也没有通过基础项目代码来冒充原型复现。

作者网页链接和正式 DOI 证明存在后续论文，不能将相同作者、相似架构或演讲稿当作正式版所有细节相同的依据。后续仍应取得 ACSAC2024 的实际正文并做版本增量分析。

## 14. 对当前 ProxyRealm 设计的建议

项目既定假设保持：RMM 认证原始 Client，可信 ProxyRealm 控制 SMMU，授权时检查实际页归属/权限/生命周期并软件 IPA→HPA 合成受保护 Stage-1；关键页表、根与 MMIO 受平台保护。本文不以实验板能力否定这些假设。

第一，将“节点/job 归属”收敛为项目已有 Client/session、对象和 GPUVM 归属，不能只验证请求来自 Proxy 通道。对于共享设备，授权必须能回溯到原始 Client，计划引用与完成也受相同边界约束。

第二，把设备配置纳入可验证执行契约：固件版本、可修改 MMIO、地址空间根、设备授权代次与恢复策略应由可信实体控制。远程启动测量说明起点，运行期约束保证它没有被未授权改写。

第三，复用现有 native fence、cookie/epoch、私有快照和 persistent IRQ127，明确定义真实终态、结果可见、完成发布、目标唤醒、Client 接受的顺序。加密不是必须新增的万能步骤；同平台受保护共享页可由既有身份/访问机制实现所需属性。

第四，验证结束与重新分配：停止新提交、确定在途任务、撤销并完成失效、清理敏感状态、使旧通知/完成失效、最后重新授权。已存在的 safe reclaim 应补充覆盖说明及负例，而非重新声称项目尚无回收机制。

这些是从论文抽取的验证义务，本轮未重审项目所有路径，不据此认定当前代码缺少对应检查或已出现漏洞。下一步最值得补强的研究论证是多 Client 下任务和通知的实例关联，而非仅增加另一层笼统“内存保护”。
