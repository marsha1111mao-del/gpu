# GPU 项目性能实验总览：条件、结果与结论

Notion文档：https://app.notion.com/p/41b659a3b8cc81c786dbf6ac4ebebf27 。Notion版本另附完整对照表、完整请求表、历史Native报告、资源敏感性CSV和最新glmark摘要。

整理日期：2026-11-18；实测结果截至2026-11-17。本次汇总已有实验，没有新增跑分，也没有修改运行代码。

## 1. 可以得出的主要结论

1. **当前冻结共享版本的完整720p成绩约为1170分。** 第二阶段验收为1170，最近一次复测为1169，差−1分/−0.0855%。单轮差异不足以认定稳定退化，也不能把工具代码清理解释为性能优化。
2. **已测图形配置中，共享方案的综合分数高于本地Realm直通原型和virgl配置。** 但它们的运行模式、API、表面格式和后端资源有差异；不能推广成所有GPU虚拟化实现的排名，也不能把分差当作某个检查的成本。
3. **计算性能取决于工作负载。** 在扩展实验中，直通占有设备期间的共同GLES算子延迟通常最低；共享通常优于virgl。真实ResNet50则是Venus最快；MobileNetV2是共享略快。没有一个方案在所有指标上占优。
4. **活动期间快，不一定完整请求快。** 将初始化、校验、排队和交接算入后，直通的多用户请求成本明显增加；一些短请求中virgl反而更快。
5. **最明确的新增优化收益来自等待重叠与完成通知批处理。** S3同预算对照约+1.49%；S8同镜像开关对照约+5.02%。两者控制组不同，不能直接相加。
6. **下一步值得优化的热点是首次上下文准备与大结果读回。** 批次增大并非总有收益；直通B16下部分每输出延迟反而增加。

**独立批次、批内迭代和用户数分别计数。** 三次独立重启批次可以报告均值及批次范围；一个批次内100次推理不等于100次独立实验。下文未注明的完整图形配置均为一轮；不据此给出统计显著性或长期稳定性结论。

## 11. 失败、未执行与解释边界

- 初轮Venus模型失败，后续补齐同版本渲染服务和标准UDMABUF路径后才通过正式模型资格。不能写成“一开始全部成功”，也不能依据最初失败认定硬件不支持。
- 早期三/四Client1080p及四Client空权重ResNet曾失败；修复和独立复验后的通过结果单列。失败、超时或退出不完整的局部分数不进入有效均值。
- 双Client glmark曾出现可选WAIT_HINT错误并回退原路径；完整任务可完成不等于所有通信分支都无错误。
- 共享正式模型的多用户扩展按用户选择未继续；真实训练、功耗、能效、隔离后的单个检查开销均没有本报告可支持的测量结论。
- glmark分数不是FPS之和，多个用户分数不相加当作总吞吐；串口开始/结束交叠不是GPU硬件并行率。
- 论文Custom的GPU数字属于其OP-TEE/Linux6.14环境，不计入本项目成绩。论文机制可以启发实验，不能替代本项目对照数据。

## 12. 面向项目的结论

**现有图形性能基线可继续使用1170，最近复测记录1169。** 正式三方实验的1158是另一套匹配条件，应保留其原值。最新清理只涉及控制机工具代码，没有部署新的生产GPU实现，不能将1169解释为清理收益或损失。

**方案选型必须按负载和计时窗口。** 共享的图形综合分数较好；直通在占有GPU期间的许多共同算子更低延迟，但完整请求要承担准备和排队。Venus在真实ResNet50与部分短请求有明显优势。当前数据不支持“共享所有负载都优于virtio”或“直通一定接近Host原生”。

**优化顺序应由热点和完整对照驱动。** 先拆首次EGL/context准备与大读回内部，再评估上下文/内存复用、结果返回和通知路径；保留B16变慢、总分变高但复杂场景退化等反例。候选是否保留，以同条件完整负载、正确性、健康和恢复为准，而不是源码行数、调用数或局部计时。
